# ADR-0007. Один контракт операций: REST + OpenAPI 3.1, из него и MCP, и клиент UI

> Статус: принято
> Дата: 2026-09-11
> Контекст-документы: [02. Архитектура системы](../02-architecture.md), [14. MCP-контракт для агентов](../14-mcp-contract.md), [15. Studio: фронтенд](../15-studio-frontend.md), [20. Репозиторий, сборка, тесты, CI](../20-repo-and-tooling.md)

## Контекст

Одни и те же операции («запустить прогон», «пропатчить спеку», «прочитать трейс») нужны двум
потребителям: агенту Claude через MCP-тулы и Studio через HTTP. Потребители разные физически:
MCP-сервер и агент живут вне нашего TS-монорепо, самоописание контракта им нужно по URL, а не
через импорт типов.

Решающие факты, проверенные по установленным пакетам:

| Факт | Источник |
|---|---|
| `@voltagent/server-hono@2.0.14` внутри построен на `@hono/zod-openapi`: в `dist/index.d.ts` вендорные символы `__vendor_zod_openapi_v3_OpenAPIHono \| createRoute \| z \| extendZodWithOpenApi`, конфиг `configureApp?: (app: OpenAPIHonoType) => void \| Promise<void>` | node_modules |
| Сервер уже отдаёт OpenAPI-документ и Swagger UI (`getEnhancedOpenApiDoc`, `enableSwaggerUI`), deps `openapi3-ts ^4.5.0`, `@hono/swagger-ui ^0.5.1` | node_modules |
| `zod@4.6.2` даёт встроенный `z.toJSONSchema(schema, { target, io })` — проверено запуском; сторонний `zod-to-json-schema@3.25.2` не нужен | запуск |
| MCP-тулу нужен JSON Schema в `inputSchema`/`outputSchema`; `@modelcontextprotocol/sdk@1.30.0` принимает и zod raw shape, и готовую JSON Schema | `.d.ts` |
| `app.doc()` отдаёт OpenAPI 3.0, `app.doc31()` — 3.1; JSON-Schema-совместимость с MCP даёт только 3.1 | node_modules |

Выбор транспорта здесь — это не выбор «с нуля», а выбор «лечь на уже существующий контракт
control plane или поставить рядом второй».

## Решение

Источником правды объявляется пакет `@wf/contracts`: только zod-схемы домена и выведенные типы,
без рантайм-зависимостей на Hono, Next и VoltAgent. Из одной и той же схемы порождаются три
артефакта — HTTP-роут, MCP-тул и типизированный клиент UI. Второй реализации операции не
существует нигде: MCP-тул и HTTP-хендлер вызывают один и тот же use-case (паттерн Adapter поверх
одного порта, зависимость обеих сторон от схемы — Dependency Inversion).

```
@wf/contracts (zod 4.6.2)
  ├─ createRoute(...) -> OpenAPIHono -> GET /openapi.json (3.1, app.doc31)
  ├─ z.toJSONSchema(S, { target: "draft-2020-12", io: "input" }) -> MCP inputSchema/outputSchema
  └─ openapi-typescript 7.13.0 (CI) -> packages/api-types/schema.d.ts -> openapi-fetch createClient<paths>()
```

Конкретика:

| Элемент | Выбор | Версия |
|---|---|---|
| Описание роутов | `@hono/zod-openapi` (своя прямая зависимость, не вендорная копия) | 1.6.3 |
| Схемы | zod | 4.6.2 |
| Документ | OpenAPI 3.1 через `app.doc31()` | — |
| Генератор типов клиента | openapi-typescript (в CI, результат коммитится) | 7.13.0 |
| Клиент Studio | openapi-fetch | 0.17.0 |
| MCP SDK | `@modelcontextprotocol/sdk` | 1.30.0 |

Правила, вытекающие из решения:

1. `operationId` == имя MCP-тула == стабильный идентификатор операции. Переименование внутри
   мажора запрещено (см. также [ADR-0008](0008-mcp-tool-naming-and-phasing.md) о форме имени).
2. Префикс пути `/v1/...`. Аддитивность внутри мажора: можно добавить опциональное поле запроса
   и новое поле ответа; нельзя сделать поле обязательным, сузить enum, сменить тип, удалить поле.
3. Для входных схем всегда `io: "input"` — иначе поле с `.default()` попадает в `required` и агент
   обязан его слать.
4. На корне схемы MCP-тула не ставим `.meta({ id })`: zod выносит такую схему в `$defs` и ссылается
   `$ref`, а часть MCP-клиентов плохо переваривает `$ref` в `inputSchema`.
5. Граница применимости: Next Server Actions допустимы только для UI-состояния, не входящего в
   MCP-контракт (layout канвы, переименование вкладки). Всё, что обязан уметь агент, — только
   типизированный HTTP.
6. Единый формат ошибки `ApiError` из `@wf/contracts`: HTTP отдаёт его телом, MCP-адаптер кладёт
   его же в `structuredContent` при `isError: true`. Транслятор `DomainError -> ApiError` — один
   модуль `map-error.ts`, используемый и `app.onError`, и MCP-адаптером.

## Альтернативы

| Альтернатива | Почему отвергнута | При каких условиях вернёмся |
|---|---|---|
| tRPC v11 (`@trpc/server@11.18.0`, MIT) | Это TypeScript-типы по проводу, а не машиночитаемая схема. MCP-агенту нужен JSON Schema; из tRPC он достаётся только сторонними `trpc-to-openapi`/`trpc-openapi`, исторически отстающими от мажоров — ровно тот велосипед, который запрещён. Пришлось бы поставить tRPC вторым транспортом рядом с уже существующим Hono+OpenAPI внутри VoltAgent | Если UI станет единственным потребителем операций и MCP-контракт будет закрыт |
| Next.js Server Actions как основной способ | Непубличный RPC с внутренним протоколом (action id): нет схемы, нет версионирования, недоступны MCP-агенту, плохо стримят прогресс, тяжело тестируются вне Next | Не вернёмся как к основному; остаются для UI-состояния |
| `hono-openapi@1.3.2` вместо `@hono/zod-openapi` | Поддерживает любой Standard Schema, но спека живёт отдельно от хендлера, типизация ответа слабее, и VoltAgent внутри использует не его | Если понадобится не-Zod валидатор (valibot/arktype/effect) |
| GraphQL | Не рассматривался как источник MCP-схем: контракт операций у нас командный (`flow_patch`, `run_start`), а не граф выборок; вторая схема-язык в CI не окупается | Нет условий в рамках текущей области |
| Писать MCP-схемы руками отдельно от HTTP | Два источника правды расходятся молча; агент получает контракт, которого нет на сервере | Никогда |

## Последствия

Положительные:
- Добавление операции — одно место: схема в `@wf/contracts`. HTTP, MCP и типы клиента едут следом.
- Дрейф контракта ловится автоматически: `schema.d.ts` и `openapi.json` в репозитории, расхождение — красный билд.
- Агент и человек нарываются на одну и ту же валидацию и один и тот же формат ошибки, значит
  `candidates[].patch` из ошибки применим и кнопкой в Studio, и вызовом тула.
- `deprecated: true` в `createRoute` попадает в OpenAPI и в описание MCP-тула, агент перестаёт выбирать операцию.

Отрицательные:
- Вендорный слой `server-hono` помечен `__vendor_zod_openapi_v3_*` и импортирует типы `ZodObject/ZodTypeAny/ZodEffects` из zod v3, тогда как у нас zod 4.6.2. Риск несхождения типов при монтировании роутов.
- Нужен шаг кодогена в CI (openapi-typescript), это лишняя ступень в пайплайне.
- `z.number().int()` дорисовывает `maximum: 9007199254740991` — шум в промте тула, требуется постпроцессор JSON Schema.
- Swagger UI в проде по умолчанию выключен, публикация `/openapi.json` наружу требует отдельного вызова `getEnhancedOpenApiDoc`/`app.doc31`.

Обязаны делать:
1. `@wf/contracts` не импортирует ничего из `hono`, `next`, `@voltagent/*` — запрет правилом no-restricted-imports.
2. Свои роуты держать в отдельном `new OpenAPIHono()` из явной зависимости `@hono/zod-openapi@1.6.3` и монтировать через `app.route("/v1", api)` в `configureApp`, а не строить их на вендорном инстансе.
3. Постпроцессор JSON Schema для MCP: снять шумные `maximum`, инлайнить `$defs`, выставить `io: "input"`.
4. Каждый `createRoute` объявляет `422 contract_violation` и остальные ответы схемой `ApiError`, иначе `openapi-fetch` отдаст нетипизированную ошибку.
5. Коммитить `openapi.json` и `packages/api-types/schema.d.ts` в репозиторий.

## Проверка

| Что проверяем | Как |
|---|---|
| Нет второй реализации операции | Тест равенства множеств: `operationId` всех роутов == имена зарегистрированных MCP-тулов |
| Нет ломающих изменений внутри `/v1` | Diff-гейт по коммитнутому `openapi.json` в CI; падение на сужении enum, смене типа, удалении поля, новом required |
| Нет дрейфа MCP-контракта | Снапшот-тест: для каждого `operationId` фиксируется `z.toJSONSchema(input, { io: "input" })`; любой дрейф виден в diff |
| Нет дрейфа клиента | Регенерация `schema.d.ts` в CI и `git diff --exit-code` |
| Изоляция пакета схем | Правило линтера no-restricted-imports в `@wf/contracts` |
| Совместимость zod 4 с вендорным слоем | Мини-проект `server-hono` + zod 4.6.2 + наши роуты, прогон `tsc --noEmit` в CI. До зелёного прогона решение считается непроверенным в этой точке |
| Kill-критерий | Появилась операция, которую нельзя выразить в OpenAPI 3.1 без потери информации, нужной MCP-тулу, — решение пересматривается, а не обходится руками |

## Пересмотр

Пересматриваем при любом из событий: VoltAgent уходит с Hono или ломает `configureApp`;
`@hono/zod-openapi` перестаёт поддерживать zod 4; появляется второй крупный потребитель операций,
которому OpenAPI непригоден; проверка совместимости zod 4 с вендорным слоем даёт неустранимый
конфликт типов.
