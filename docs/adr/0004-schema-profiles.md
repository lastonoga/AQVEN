# ADR-0004. Профиль схемы — свойство пары (IR-схема × провайдер)

> Статус: принято
> Дата: 2026-09-11
> Контекст-документы: [04. Формат IR и схема спеки](../04-ir-schema.md), [05. Система типов и реестр типов](../05-type-system.md), [07. Компилятор](../07-compiler.md), [11. Провайдеры, каталог моделей и маршрутизация](../11-providers.md), [13. Evals, датасеты и гейты выпуска](../13-evals-and-gates.md)

## Контекст

Спека исходит из того, что одна strict-схема описывает выход узла для любого провайдера. Проверка
официальной документации (OpenAI `structured-outputs.md`, 135 953 байта; Anthropic
`structured-outputs.md`, 110 492 байта; обе скачаны 2026-09-11) показывает обратное: требования
провайдеров взаимно противоречивы.

| Требование | OpenAI strict | Anthropic strict |
|---|---|---|
| Опциональные поля | запрещены, все ключи в `required` | разрешены, но лимит **24** на запрос |
| `["T","null"]` | штатный приём эмуляции опциональности | считается union-типом, лимит **16** на запрос, «exponential compilation cost» |
| `oneOf` | не поддержан | не назван в поддержанных |
| `anyOf` | поддержан, но **не в корне** схемы | поддержан |
| `allOf` | не поддержан | поддержан (кроме связки с `$ref`) |
| Рекурсия `"$ref":"#"` | поддержана | **не поддержана** |
| `minimum`/`maximum`/`minLength`/`maxLength` | поддержаны (кроме fine-tuned моделей) | **не поддержаны** |
| `minItems`/`maxItems` | поддержаны | только `minItems` со значением 0 или 1 |
| `format: uri` | нет в списке | есть |
| Порядок ключей в выводе | строго порядок схемы | сначала `required`, затем optional |

Приём, который делает схему валидной для OpenAI (все поля required + `["T","null"]`), напрямую
расходует оба дефицитных лимита Anthropic. Обратный приём (оставить `optional`) даёт у OpenAI
ошибку 400. Общей схемы не существует.

Лимиты OpenAI на схему: 5000 свойств, 10 уровней вложенности, 120 000 символов на все имена
свойств, имена определений, enum- и const-значения вместе, 1000 enum-значений на схему, 15 000
символов на один строковый enum при более чем 250 значениях. У Anthropic сверх явных лимитов есть
недокументированный предел размера скомпилированной грамматики — ошибка
«Schema is too complex for compilation.».

Zod 4.6.2 из коробки даёт вывод, невалидный для OpenAI strict. Проверено запуском
(`scratchpad/probe/zodtest.mjs`), ломается следующее:

1. `z.discriminatedUnion("kind", [...])` выводит **`oneOf`**, а не `anyOf`. OpenAI `oneOf` не
   принимает; документация OpenAI называет этот паттерн Zod прямым примером невалидной схемы.
2. `.optional()` просто убирает ключ из `required`, `null` в тип не добавляется. Для strict нужно
   ровно обратное: ключ в `required` и `type: ["string","null"]`.
3. `.meta({ id })` переносит схему в `$defs`, корень становится `{"$ref":"#/$defs/Node"}`.
4. `z.date()`, `z.bigint()`, `z.custom()` при `unrepresentable: "any"` дают `{}` — схему без
   `type`, которую strict отклоняет; при дефолтном `"throw"` компиляция падает.
5. `target: "openapi-3.0"` выдаёт `{"nullable": true}` вместо union-типа — OpenAI понимает
   union-тип и не понимает `nullable`.

Совпадает с ожиданием только `additionalProperties: false`: `z.toJSONSchema` ставит его сам при
`io: "output"` и не ставит при `io: "input"`.

Каталог §8 строка 37 (R-37) требует проверки совместимости схемы с профилем провайдера и
трансформаций вида optional → nullable. Строка 35 (R-35) требует линта порядка полей: поле
обоснования обязано стоять перед полем решения, а OpenAI документирует, что «outputs will be
produced in the same order as the ordering of keys in the schema».

## Решение

Схема для модели компилируется под **профиль** — пару (IR-схема × провайдер). Профиль не является
свойством IR: в IR лежит одно нейтральное описание типа, а wire-схема получается компиляцией под
конкретную цель. Минимальный набор профилей: `openai-strict`, `anthropic-strict`, `permissive`
(self-hosted vLLM/SGLang и модели без constrained decoding).

Между `z.toJSONSchema` и провайдером обязателен собственный слой пост-обработки. Сырой вывод Zod
в запрос не уходит никогда. Слой реализуется как Strategy: один интерфейс профиля, реализация на
провайдера, выбор через Registry по идентификатору профиля из каталога моделей.

```ts
interface SchemaProfile {
  readonly id: ProfileId;
  compile(ir: IrTypeRef): CompiledSchema;
  budget(schema: JsonSchema): BudgetReport;
}

interface CompiledSchema {
  wire: JsonSchema;
  postChecks: ZodTypeAny;
  descriptionCarried: ReadonlyArray<StrippedConstraint>;
}
```

Фиксированные параметры входа: `z.toJSONSchema(schema, { target: "draft-2020-12", io: "output",
unrepresentable: "throw", cycles: "throw", reused: "inline", override })`. `io: "output"` обязателен —
именно он ставит `additionalProperties: false` и включает поля с `.default()` в `required`, то есть
запрещает модели опустить поле.

Правила пост-обработки, обязательные для strict-профилей:

| Что пришло от Zod | Во что переписывается | Почему |
|---|---|---|
| `oneOf` | `anyOf` | OpenAI `oneOf` не поддерживает |
| ключ вне `required` | ключ в `required` + `type: [T, "null"]` | OpenAI требует полный `required` |
| union в корне | `{ type:"object", properties:{ result: <union> }, required:["result"], additionalProperties:false }` | корень обязан быть объектом |
| корневой `$ref` из `.meta({id})` | инлайн корня | предсказуемая форма запроса |
| `minimum`, `maximum`, `multipleOf`, `minLength`, `maxLength`, `maxItems` в `anthropic-strict` | вырезается из `wire`, дописывается в `description`, проверяется Zod на приёме | Anthropic эти keyword'ы отвергает с 400 |
| `{}` без `type` | ошибка компиляции | strict отклоняет схему без типа |

Стиль схем IR по умолчанию, общий для всех профилей: все поля `required`, опциональность через
`null`, `additionalProperties: false`, рекурсия запрещена, числовых и строковых ограничений в
wire-схеме нет, порядок полей сохраняется в порядке IR и никогда не сортируется. Это пересечение
трёх провайдеров, и оно же снимает расхождение в порядке ключей: при полном `required` у Anthropic
нет группы optional, которую он переносит в хвост, и порядок совпадает с OpenAI.

Границы применимости: решение касается только схем, уезжающих в вызов модели. Схемы IR-документов,
конфигов и внешних JSON Schema от MCP-клиентов профилями не компилируются и проверяются ajv
(Ajv2020, `strict: false`, `allErrors: true`) на границах.

Компилятор обязан считать бюджет схемы (число enum-значений, суммарные символы одного enum,
суммарные 120 000 символов, глубина, число свойств, для Anthropic — число optional и union-типов)
и падать с внятной ошибкой ДО запроса к провайдеру, а не ловить 400.

## Альтернативы

| Альтернатива | Почему отвергнута | При каких условиях вернёмся |
|---|---|---|
| Одна универсальная strict-схема на всех провайдеров (как в спеке) | Физически невозможна: все-required + nullable расходует лимиты Anthropic (24 optional, 16 union), а optional даёт 400 у OpenAI | Если провайдеры сойдутся на общем подмножестве JSON Schema и опубликуют его |
| Сырой `z.toJSONSchema` без пост-обработки | Проверено запуском: `oneOf`, потерянный `null` у optional, корневой `$ref`, `{}` на unrepresentable | Если Zod добавит официальный `target: "openai-strict"` и он пройдёт наши golden-тесты |
| Профиль как поле IR-схемы | Привязывает документ к провайдеру: смена модели требует правки IR и ломает переносимость и экспорт | Никогда для IR; допустимо как override на узле для отладки |
| `target: "openapi-3.0"` как общий знаменатель | Даёт `nullable: true` вместо union-типа и теряет `$schema`; OpenAI `nullable` не понимает | Только как стартовый профиль для Gemini, если подтвердится, что новый `response_format` наследует OpenAPI-подмножество |
| BAML как компилятор схем | Второй источник истины по схемам рядом с IR, нативный бинарь, DSL и кодогенератор; см. ADR по BAML-референсу | Если выйдет отдельный WASM/JS-пакет только с SAP-парсером |
| Валидация ajv на горячем пути вместо Zod | Дублирует Zod, из которого и так выводятся типы TS; enum-сравнение у ajv чувствительно к регистру, а Anthropic регистр enum не гарантирует | Нет |

## Последствия

Положительные:
- Каждая целевая модель получает схему, валидную по её собственным правилам; несовместимость ловится
  на компиляции, а не в проде (R-37 закрыт механически).
- Ограничения, вырезанные из wire-схемы, не исчезают: они переезжают в `description` и в Zod-проверку
  на приёме, то есть смысл сохраняется даже там, где грамматика его не выражает.
- Полный `required` + `null` делает порядок полей одинаковым у OpenAI и Anthropic, что и требуется
  для «обоснование перед решением» (R-35).

Отрицательные:
- Одна IR-схема даёт N wire-схем; их надо хранить, версионировать и покрывать тестами.
- Часть ограничений перестаёт быть гарантией грамматики и становится post-hoc проверкой, то есть
  появляется ветка ремонта там, где раньше предполагалась гарантия.
- Anthropic кеширует скомпилированную грамматику до 24 часов; смена профиля или схемы — это холодный
  старт и дополнительная латентность первого запроса (у OpenAI то же самое явно задокументировано).

Обязаны делать:
1. Смена профиля модели у узла — это перекомпиляция всех его схем и прогон eval-гейта; профиль
   входит в ключ кеша компиляции и в провенанс прогона.
2. Идентификатор профиля хранится в каталоге моделей рядом с моделью, а не в IR-документе.
3. Компилятор считает бюджет схемы и отказывает до сетевого вызова.
4. Значения enum обязаны быть уникальны без учёта регистра, валидатор сравнивает
   case-insensitive и нормализует к каноническому значению: Anthropic документирует, что регистр
   enum-значений не гарантируется и расхождение приходит без ошибки и без особого `stop_reason`.
5. `z.date()`, `z.bigint()`, `z.custom()` в IR запрещены; даты — `z.iso.datetime()`.
6. В запрос уходит и грамматика, и текстовое описание схемы в промпте: грамматика держит форму,
   промпт — смысл.

## Проверка

- Golden-тесты: на каждую IR-схему из реестра типов снапшот wire-схемы по каждому профилю. Диф
  снапшота без записи в ADR или в документ профиля — красный CI.
- Self-check компилятора: скомпилированная wire-схема прогоняется ajv (Ajv2020) против примеров из
  `.meta({ examples })`. Примеры, не проходящие собственную схему, валят сборку.
- Инвариант-тесты strict-профиля на произвольной схеме (fast-check): в выводе нет `oneOf`, нет
  ключей вне `required`, на каждом объекте стоит `additionalProperties: false`, корень — `object`,
  нет `$ref` на корень, нет пустых схем без `type`.
- Бюджетный лint компиляции: превышение любого из лимитов (5000 свойств, 10 уровней, 120 000
  символов, 1000 enum-значений, 15 000 символов на enum, 24 optional и 16 union-типов для Anthropic)
  — ошибка компиляции с указанием узла и поля.
- Kill-критерий: если для профиля доля узлов, у которых ограничение пришлось вырезать в
  `description`, превышает половину полей схемы, профиль считается непригодным для этой схемы и
  узел маршрутизируется на другой профиль.

## Пересмотр

Пересматриваем, если: провайдер меняет правила strict-режима (например, OpenAI разрешает `oneOf`
или корневой union, Anthropic снимает лимиты 24/16 или добавляет рекурсию); Zod выпускает
официальный провайдерский target и он проходит инвариант-тесты; появляется четвёртая целевая
платформа, чьи ограничения не ложатся на существующие три профиля; эмпирический замер лимитов
Gemini показывает, что `permissive` для него недостаточен.
