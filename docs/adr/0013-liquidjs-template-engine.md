# ADR-0013. liquidjs как движок шаблонов промтов

> Статус: принято
> Дата: 2026-09-11
> Контекст-документы: [08. Промты](../08-prompts.md), [07. Компилятор](../07-compiler.md), [06. Реестры](../06-registries.md), [05. Система типов](../05-type-system.md), [11. Провайдеры](../11-providers.md); спека §7.6

## Контекст

Промт у нас — не строка, а компилируемый артефакт: правила R-T1..R-T12 требуют доказательств **до** запуска модели.
R-T1 (плейсхолдер → объявленный слот совместимого типа), R-T2 (каждый слот использован либо помечен `unused`),
R-T3 (условия только по bool/optional/enum), R-T4 (полнота `switch` по enum), R-T5 (`for` только по массивам со
scope-трекингом переменной цикла), R-T6 (`{{ output_format }}` ровно один раз), R-T7/R-T8/R-T12 (анализ статических
текстовых узлов), R-T9 (верхняя оценка размера отрисовки ≤ окно профиля). Спека §7.6 прямо ограничивает язык:
«Произвольных выражений и функций в шаблоне нет — только разрешённые фильтры».

Отсюда требования к движку, все обязательные одновременно:
типизированный AST с различимыми узлами и позициями; отсутствие произвольного кода в выражениях; возможность
зарегистрировать собственный блочный тег (роли сообщений); живой релизный цикл.

Пять кандидатов реально распарсены одним и тем же шаблоном (`probe/ast-probe.cjs`, `probe/ast-probe2.cjs`, запуск
2026-09-11). Результаты замеров и выводы — `research/templating.md`.

## Решение

Движок шаблонов промтов — **liquidjs 10.29.0 (MIT, публикация 2026-08-11, 1.89 МБ unpacked)**. Собственный парсер
не пишем: оценка была ~1.5–2.5 тыс. строк (лексер, теги, выражения, позиции, рендер, стриминг) плюс вечное
сопровождение. Наш код — **визитор ~400–600 строк** (паттерн Visitor) поверх чужого AST и таблица правил.

Конкретика применения:

| Аспект | Что делаем |
|---|---|
| Инстанс | `new Liquid({ strictVariables: true, strictFilters: true, ownPropertyOnly: true, jsTruthy: false })` — все четыре флага проверены запуском (`UndefinedVariableError` с `line:col`, `ParseError: undefined filter`) |
| R-T1 / R-T2 | встроенный статический анализ: `globalFullVariablesSync()` даёт ровно множество **внешних** путей (`request.with_kids`, без локальных `h.name`), `parseAndAnalyzeSync()` — `variables/globals/locals` c `Variable.location {row, col, file}` |
| R-T3 | `IfTag.branches[i].value.initial.postfix` — условие в виде RPN-массива токенов (`PropertyAccessToken`, `QuotedToken`, `OperatorToken`, `NumberToken`); правило = линейная проверка списка по белому списку операторов, без своего парсера выражений |
| R-T4 | встроенный `CaseTag`: `branches[].values[].content` сверяем с полным множеством значений enum из реестра, дополнительно требуем `elseTemplates.length === 0` |
| R-T5 | `ForTag.token.args` (`h in hotels`) + `ForTag.templates` → scope-стек визитора |
| R-T6/R-T7/R-T8/R-T12 | обход узлов `Output` по всем ветвям и сканирование **только** узлов `HTML` (`token.input.slice(token.begin, token.end)`) |
| R-T9 | рекурсивный `maxTokens(node, typeEnv)`: `IfTag`/`CaseTag` → `max` ветвей (не сумма), `ForTag` → `maxItems × maxTokens(тело)`, `IncludeTag` → рекурсия во фрагмент версии; счёт — `gpt-tokenizer` (`gpt-tokenizer/encoding/o200k_base`) × `token_ratio` профиля |
| Роли сообщений | кастомный блочный тег `{% message system\|user\|assistant %}` через `registerTag` + `parser.parseStream(...).on('tag:endmessage')` (проверено запуском); рендер каждого `MessageTag` отдельно → `PromptContent { type: 'chat', messages }` VoltAgent |
| Фильтры | из 88 встроенных оставляем белый список ~8–10: лишние снимаем `liquid.unregisterFilter(name)` на старте **и** дополнительно проверяем `Output.value.filters[].name` в визиторе (двойная защита) |
| Теги | разрешены `if/elsif/else`, `case/when`, `for`, `include`, `comment`, `#`, наш `message`. Запрещены `assign`, `capture`, `increment`, `decrement`, `cycle`, `tablerow`, `layout`, `block`, `render`, `echo`, `raw`, `unless` и инлайн-режим `{% liquid %}` |
| Фрагменты | анализ partials включён по умолчанию и ходит в файловую систему → подставляем собственный `LiquidOptions.fs`-loader, который резолвит `fragment@version` из реестра; сквозной анализ шаблон+фрагменты одним вызовом |

**`{% switch %}` из спеки §7.6 не реализуется.** Такой конструкции нет ни в одном движке, а в Liquid ровно эта
семантика уже есть как встроенный `{% case %}/{% when %}` с типизированным AST (`value: Value`,
`branches: { values, templates }[]`, `elseTemplates`). Писать свой тег ради чужого имени — значит терять готовый
разбор веток. Спека §7.6 в этой части переписывается: синтаксис — `{% case subject %}{% when 'value' %}…{% endcase %}`,
`{% else %}` внутри `case` запрещён правилом R-T4 (иначе неполнота enum маскируется).

Границы применимости: движок обслуживает **только** шаблоны промтов и фрагментов. Кодогенерация экспорта — шаблонные
строки + prettier, сериализация данных — canonicalize/YAML. Liquid туда не проникает.

## Альтернативы

| Альтернатива | Почему отвергнута | При каких условиях вернёмся |
|---|---|---|
| **eta 4.6.0** (MIT, 0.21 МБ) | Дерева нет: `eta.parse()` → плоский список `{t:'e'\|'i'\|'r', val:'<сырой JS>'}`. Статический анализ невозможен без парсинга JS, а произвольный JS прямо противоречит §7.6 | Не вернёмся: противоречие в основании языка |
| **nunjucks 3.2.4** (BSD-2) | Нормальный AST (`Root/Output/If/For/LookupVal/Filter`), но `time.modified = 2023-04-13` — три года без релизов; плюс богатый язык выражений (`{{ a if b else c }}`, вызовы), который пришлось бы урезать чёрным списком узлов | Возобновление релизов + готовность вести чёрный список узлов выражений |
| **handlebars 4.7.9** (MIT, 2.81 МБ) | AST лучший по качеству (`loc` строка:колонка у каждого узла), но синтаксис `{{#if}}/{{#each}}` вместо `{% %}` из спеки, любая новая конструкция — «хелпер», неотличимый в AST от вызова функции; тащит компилятор | Если откажемся от Liquid-синтаксиса в спеке и примем «всё есть хелпер» |
| **@huggingface/jinja 0.5.10** (MIT, свежайший 2026-09-04) | Чистейший AST, но **нельзя зарегистрировать кастомный тег** (в `dist/index.d.ts` только `Environment, Interpreter, tokenize, parse`), а `{% include %}` не понимает вовсе. `{% message %}` невыразим | Возьмём как reference-парсер, если понадобится читать chat-template моделей HF |
| **Собственный мини-парсер** | ~1.5–2.5 тыс. строк + сопровождение; liquidjs даёт то же самое плюс встроенный анализ, позиции и 88 фильтров при живом релизном цикле | Если liquidjs умрёт и не найдётся замены с кастомными тегами |

## Последствия

**Положительные**

- R-T1 и R-T2 закрываются встроенным анализом, а не нашим кодом: `globalFullVariablesSync()` — это ровно множество
  внешних путей, сравнение в обе стороны с объявленными слотами даёт оба правила.
- Диагностика с `row/col` из коробки (`Variable.location`) — не считаем offset→line:col сами.
- R-T4 получает готовую структуру веток `case/when`; полнота enum проверяется сравнением множеств.
- `{% message %}` отдаёт `PromptContent { type: 'chat' }` VoltAgent напрямую, вместе с `metadata.name/version` —
  связь трейса с версией шаблона бесплатна.
- Статичность поддерева `MessageTag` (нет ни одного `Output`/`IfTag`/`ForTag`/`CaseTag`) — это и есть формальный
  критерий точки кэширования; AST даёт его без эвристик.

**Отрицательные**

- 88 встроенных фильтров и десяток лишних тегов надо гасить руками; апгрейд движка может добавить новые.
- `liquid.parser` помечен `@deprecated` — в кастомных тегах берём `parser` из аргумента конструктора.
- Ветка `IfTag` — `{ value, templates }`, а не `{ cond, ... }`: старые статьи и любой сгенерированный код по памяти
  будут неверны.
- `Output.value.initial.postfix` — итератор; перед анализом копировать через `[...]`.
- Анализ partials по умолчанию лезет в файловую систему — без своего loader-а компилятор станет зависеть от диска.
- Спека §7.6 расходится с реализацией в части `{% switch %}` и требует правки.

**Обязаны делать**

1. Реестр типов обязан задавать `maxLength` у каждой строки и `maxItems` у каждого массива — без этого R-T9
   недоказуем. Это правило реестра, а не шаблонов; фиксируется в [06. Реестры](../06-registries.md).
2. `MessageTag` допустим только на верхнем уровне шаблона: внутри `{% if %}`/`{% for %}` число сообщений начинает
   зависеть от данных и рушатся кэш-префиксы.
3. Белый список фильтров и тегов хранится как данные (один модуль), а не разбросан по коду; визитор и
   `unregisterFilter` читают один и тот же список.
4. Системные слоты (`run.date`, `locale`, `tz`) запрещены в сообщениях, помеченных `cache`: у OpenAI кэш
   автоматический по префиксу, единственный рычаг — стабильность префикса.
5. Оценка R-T9 калибруется по факту: `usage.inputTokens` из трейса сравнивается с offline-оценкой, `token_ratio`
   профиля подстраивается (по умолчанию 1.15 латиница, 1.3 кириллица/CJK).

## Проверка

- Тест-снапшот AST на эталонном шаблоне: набор узлов и их порядок (`HTML/Output/IfTag/ForTag/CaseTag/IncludeTag/MessageTag`)
  фиксируется; апгрейд liquidjs, меняющий форму AST, валит тест, а не продакшн.
- Тест равенства множеств: зарегистрированные теги и фильтры инстанса **точно равны** белому списку. Появился новый
  фильтр после апгрейда — красный тест.
- Тест на каждое правило R-T1..R-T12: минимум один шаблон-нарушитель, ожидаемый код правила и непустой `candidates`.
- Мутанты классов `non-exhaustive-branch`, `invented-enum-value`, `prompt-raw-interpolation` из
  [ADR-0014](0014-ir-mutation-testing.md) обязаны быть пойманы шаблонными правилами.
- Kill-критерий: если для какого-то R-Tx нельзя указать механику обхода на AST liquidjs (узел, поле, сравнение) —
  правило неисполнимо, и это дефект либо правила, либо выбора движка; обсуждается до релиза, не после.

## Пересмотр

Пересматриваем при любом из событий: liquidjs без релизов более 12 месяцев или ломающая смена API статического
анализа (`analyzeSync`/`globalFullVariablesSync`) или `Tag`/`registerTag`; появление требования к выражениям, которых
в Liquid нет (арифметика, вызовы) — тогда решение принимается заново вместе с §7.6, а не обходится кастомными тегами;
изменение формата сообщений у провайдеров настолько, что `{% message %}` перестаёт его выражать.
