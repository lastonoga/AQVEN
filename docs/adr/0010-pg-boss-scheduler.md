# ADR-0010. pg-boss как планировщик и единственная очередь

> Статус: **заменено [ADR-0025](0025-python-engine.md)** (2026-09-16)
> Дата: 2026-09-11
>
> Заменено целиком: pg-boss уходит, очереди с лимитом конкурентности и расписания даёт DBOS 2.31.1 — библиотека в
> процессе движка, системная БД на SQLite локально и на PostgreSQL 18 в проде (ADR-0025 §4). Механика pg-boss
> уходит вместе с ним: постановка через `fromDrizzle`, политики по `singletonKey`, сверяющий cron, миграции схемы
> pg-boss. Остаются верными: перечень сценариев — таймаут human-задачи, синхронизация каталога по расписанию,
> batch-прогоны eval, shadow/canary с лимитом параллелизма — они переходят на очереди и расписания DBOS; ключи
> идемпотентности у узлов с внешними эффектами, потому что прерванный падением шаг выполняется заново целиком.
> Запуском на DBOS проверены только восстановление, fork и история шагов; ожидание человека с дедлайном и
> параллельные ветки не проверены (открытые вопросы 1–2 ADR-0025).
> Контекст-документы: [17. Задачи и планирование](../17-jobs-and-scheduling.md), [10. Рантайм](../10-runtime.md), [16. Модель данных](../16-data-model.md), [19. Безопасность и политики](../19-security-and-policies.md)

## Контекст

Четыре сценария требуют отложенного и повторяющегося исполнения, и ни один не закрывается рантаймом:

| Сценарий | Что именно нужно |
|---|---|
| Таймаут human-задачи | VoltAgent приостанавливает воркфлоу через `suspend(reason)` и возобновляет **только явным вызовом**; таймера у него нет (`@voltagent/core/docs/workflows/suspend-resume.md`). Дедлайн — наш |
| Синхронизация каталога моделей | расписание (OpenRouter, models.dev), с отработкой пропущенных срабатываний после простоя |
| Batch-прогоны eval | сотни задач пачкой + финальная сводка, зависящая от них (`@voltagent/evals@2.0.5`) |
| Shadow/canary прогоны | фоновый трафик с приоритетом ниже продового и лимитом параллелизма на тенанта |

Ограничения: PostgreSQL 18 уже в стеке и там же живёт `@voltagent/postgres@2.1.3`; заводить Redis ради очереди — новая инфраструктура, новый бэкап, новый режим отказа. При этом движок durable execution у нас **уже есть** — воркфлоу VoltAgent с `suspend/resume` и чекпоинтами после каждого шага. Второй такой движок означал бы две модели исполнения, два формата трасс и две семантики ретраев. Нужен не движок, а таймер + планировщик + надёжный enqueue.

Числа по кандидатам (`npm view`, 2026-09-11): pg-boss 12.31.0 MIT (node >= 22.12.0), graphile-worker 0.18.0 MIT, BullMQ 6.3.4 MIT, Inngest 4.20.0 Apache-2.0, Trigger.dev 4.5.16 MIT (SDK), Temporal TS SDK 1.23.0 MIT. Все живые, у всех релизы за последние две недели — выбор не по свежести, а по топологии.

## Решение

Берём **pg-boss 12** (пин `12.x`, MIT) как единственную очередь и единственный планировщик. Никакой второй очереди, никакого `setTimeout` для доменных задержек, никакого своего поллера.

Ключевой механизм — **транзакционная постановка задачи вместе с бизнес-транзакцией**. `SendOptions.db` принимает адаптер `fromDrizzle(tx, sql)` (сигнатура из `pg-boss/dist/adapters/drizzle.d.ts`: `fromDrizzle(tx: DrizzleTransactionLike, sql: DrizzleSqlTagLike): IDatabase`; есть также `fromKysely`, `fromKnex`, `fromPrisma`, `fromPglite`, `fromBunSql`). Очередь лежит в том же Postgres, значит «записать бизнес-факт и поставить задачу» — одна атомарная транзакция. Это готовый transactional outbox без своей таблицы и без релея; именно это и есть главный довод против Redis-очередей.

Конкретика применения:

- **Очереди объявляются явно** (`createQueue(name, options)`, иначе `send` падает) в одном реестре очередей с полным набором опций. Дефолт `retryLimit = 2` нас не устраивает — задаём явно на каждой очереди.
- **Политики очереди** (`standard | short | singleton | stately | exclusive | key_strict_fifo`) применяются **в разрезе `singletonKey`**, а не всей очереди. Это наш механизм «ровно один живой таймер на задачу».
- **Таймер human-задачи**: `sendAfter('human.deadline', payload, { singletonKey: '<executionId>:<stepId>', db: fromDrizzle(tx, sql) }, deadlineAt)` в той же транзакции, что и вставка в `human_tasks`. Очередь: `policy: 'stately'`, `retryLimit: 5`, `retryBackoff: true`, `retryDelayMax: 300`, `expireInSeconds: 120`, `deadLetter: 'human.deadline.dlq'`. Продление дедлайна — `upsert(name, data, { singletonKey, startAfter })`, без гонки delete+insert.
- **Страховочный сверяющий cron**: `schedule('human.reconcile', '*/5 * * * *', {}, { tz: 'UTC', missed: 'once' })`. Находит `status='pending' AND deadline_at < now() - interval '1 minute'` и переставляет таймер с тем же `singletonKey` (дубликат отсекается политикой). Сверка идёт и в обратную сторону: `WorkflowRegistry.getSuspendedWorkflows()` даёт список приостановленных, исполнения без строки в `human_tasks` — «повисшие навсегда», это алерт.
- **Расписания**: второй аргумент `schedule()` — cron-выражение **или** RFC 5545 RRULE. `missed: 'once'` для синка каталога (одна задача за самое свежее пропущенное срабатывание), `key` позволяет держать несколько расписаний на одной очереди (`catalog.sync` с ключами `openrouter` и `models_dev`).
- **Топология — один образ, роль по env**: `ROLE=api` поднимает VoltAgent + server-hono + pg-boss только как producer (`schedule: false`, без `work()`); `ROLE=worker` — реестр + компилятор без HTTP + `work()` на всех очередях. Оба процесса строят реестр воркфлоу из одного источника (определения в БД + компилятор IR→VoltAgent), поэтому «зарегистрировано в обоих» получается само. На v1 это один процесс с обеими ролями, разделение — переключателем.
- **Границы применимости**: pg-boss — транспорт и таймер, не движок исполнения. В хендлере нет бизнес-логики шага: он claim'ит, зовёт домен/`resumeSuspendedWorkflow` и возвращает результат. Решение о том, что делать по таймауту (`fail | default_value | escalate | continue_without`), принимает шаг воркфлоу, воркер только передаёт политику в `resumeData`.
- **Идемпотентность**: очередь даёт at-least-once. Честная формулировка — exactly-once доставки не существует, есть at-least-once + idempotent receiver = effectively-once эффект. Тулы с `effects: true` оборачиваются декоратором `IdempotentTool` поверх журнала `tool_effects` с ключом `sha256(JCS(tenant_id, workflow_id, execution_id, node_id, iteration, tool_input))` и claim'ом через `INSERT ... ON CONFLICT DO NOTHING RETURNING`. Чистые тулы не журналируются.
- **Миграции схемы pg-boss**: в проде `migrate: false`, `createSchema: false`; DDL — через CLI/`getMigrationPlans(schema, version)` отдельным шагом деплоя, рантайм-роль прав на DDL не имеет. `detectSchemaDrift()` — в health-чек.

## Альтернативы

| Альтернатива | Почему отвергнута | При каких условиях вернёмся |
|---|---|---|
| graphile-worker 0.18.0 (MIT, Postgres) | Тот же класс решения, но скромнее: нет dead-letter из коробки, нет `sendThrottled`/`sendDebounced`, дедуп только `jobKey` + `jobKeyMode`. Всё это пришлось бы писать руками | **Запасной вариант.** Если pg-boss окажется тяжёл для нашей БД (`slow_query`, `index_bloat`, `xmin_horizon` на штатной нагрузке) |
| BullMQ 6.3.4 (MIT, Redis) | Лишний Redis сверх нашей инфраструктуры. Решающее: бизнес-запись в Postgres и enqueue в Redis атомарными не сделать — пришлось бы писать таблицу outbox и релей. Зрелые UI (Bull Board) этого не перевешивают | Если Postgres-бэкенд BullMQ 6 (`peerDependencies.pg >= 8.0.0`) окажется production-ready — сравнение придётся переоткрыть. Сейчас его зрелость не проверена |
| Inngest 4.20.0 | Внешний сервис и публичный webhook-эндпоинт в критическом пути; это ещё и второй движок durable execution | Если продукт уйдёт от самостоятельного хостинга целиком |
| Trigger.dev 4.5.16 | Self-host — стек Postgres + Redis + ClickHouse; vendor lock; второй durable-движок | Нет обозримых условий |
| Temporal TS SDK 1.23.0 | Отдельный кластер плюс своя БД. Концептуально дублирует VoltAgent: две модели исполнения, два формата трасс, две семантики ретраев | Если решим **заменить** VoltAgent как движок исполнения (распределённые саги, компенсации, шаги вне процесса), а не дополнить его. Тогда Temporal приходит вместо VoltAgent, не рядом |
| Свой планировщик на `setTimeout`/`setInterval` | Не переживает рестарт процесса — ровно то свойство, ради которого планировщик и заводится | Никогда |
| `pg-transactional-outbox@0.6.5` | Pre-1.0, ~8 месяцев без релизов; `SendOptions.db` + `fromDrizzle` закрывают сценарий без зависимости | Если понадобится outbox на CDC/логической репликации |

## Последствия

**Положительные.**
- Ноль новой инфраструктуры: задачи, трассы, чекпоинты и бизнес-данные в одной БД, одном бэкапе, одном мониторинге.
- «Записали факт — поставили задачу» атомарно. Нет состояния «human-задача есть, таймера нет» и наоборот.
- SQL-наблюдаемость поверх задач: `findJobs`, `getQueues`, `getQueueStats`, `getWipData` — страница задач в нашей Studio строится без отдельной системы.
- Встроенный DAG задач (`flow(jobs[])`, `dependsOn`, `getDependencies/getDependents`) закрывает eval-батч «N прогонов + сведение отчёта» без своего оркестратора.

**Отрицательные.**
- Схема и нагрузка pg-boss живут в нашей БД; миграции pg-boss становятся частью нашего релизного процесса.
- `useListenNotify` держит отдельное соединение и **не работает через PgBouncer в transaction pooling** — деградирует на поллинг с `warning`.
- At-least-once вынуждает журналировать эффекты: `tool_effects` — обязательная таблица, а не опция.

**Обязаны делать.**
1. Все очереди объявлять в одном реестре с явными `retryLimit`, `retryBackoff`, `expireInSeconds`, `heartbeatSeconds`, `deadLetter`. Ретраи — на очереди, не на туле, чтобы не было двух конкурирующих механизмов.
2. **Проверять `null`** от `send`/`sendAfter`/`sendThrottled`: `null` означает «отброшено политикой или дедупом». Без проверки дедуп работает молча, а код думает, что поставил задачу.
3. Пробрасывать `job.signal` (AbortSignal) во все fetch- и LLM-вызовы: иначе остановка воркера и истечение `expireInSeconds` ничего не отменяют.
4. Подписываться на `boss.on('error')` (иначе EventEmitter роняет процесс) и `boss.on('warning')`. В алерты обязательно: `clock_skew`, `invalid_schedule`, `queue_backlog`. Бэклог мерить `readyCount` (= `queuedCount - deferredCount`), а не `queuedCount`.
5. Гонку «человек ответил ровно на дедлайне» закрывать в БД: `UPDATE human_tasks SET ... WHERE status='pending' RETURNING *` — и в воркере таймера, и в API ответа человека. Выигрывает один, `resumeSuspendedWorkflow` зовёт только победитель.
6. `resumeSchema` шага обязана допускать вариант таймаута (дискриминированный union `{kind:'human'} | {kind:'timeout', policy, deadlineAt}`) — иначе резюм по таймауту упадёт на валидации. Это требование к компилятору IR.
7. `resumeSuspendedWorkflow` вернул `null` (воркфлоу не найден/не зарегистрирован) — это ошибка job'а: ретрай с backoff, затем dead-letter. Не успех.
8. На `SIGTERM`: `suspendAllActiveWorkflows(reason)`, затем `boss.stop()`. При старте воркера: реестр → `boss.start()` → объявление расписаний (идемпотентно по `(name, key)`) → немедленный прогон `human.reconcile`, не дожидаясь cron.
9. Не использовать `priority`/`orderByCreatedOn` из `JobFetchOptions` — помечены `@deprecated` с 12.30.0 и игнорируются. Приоритет — на job'е.
10. Батч-обработчики объявлять с `perJobResults: true` и возвращать `JobResult[]`: job, не упомянутый в результате, считается failed.

## Проверка

| Что проверяем | Как |
|---|---|
| Таймер срабатывает ровно один раз | Интеграционный тест на `backend: 'pglite'` (встроенный WASM-Postgres) с `__test__enableSpies: true` + `getSpy(name)`: suspend → сдвиг времени → ровно один `resumeSuspendedWorkflow` |
| Гонка человек/таймер | Параллельно ответ человека и срабатывание таймера → ровно один resume, вторая сторона получает 0 строк из `UPDATE ... WHERE status='pending'` |
| Переживание рестарта | Поставить `sendAfter`, убить процесс, поднять заново → задача исполняется |
| Атомарность enqueue | Тест: откат бизнес-транзакции → задачи в очереди нет |
| Идемпотентность эффектов | Повторная выдача job'а с тем же `idempotency_key` → внешний вызов ровно один, ответ берётся из `tool_effects` |
| Изоляция зависимости | Правило `no-restricted-imports`: `pg-boss` импортируется только в `@aqven/jobs`; запрет `setTimeout`/`setInterval` для доменных задержек |
| Дрейф схемы | Health-чек CI: `detectSchemaDrift()` возвращает пустой отчёт |
| **Kill-критерий** | Если при штатной нагрузке метрика `human_deadline_missed_total` за сутки > 0 (то есть основной путь теряет таймеры и их стабильно подбирает reconciler) — механизм отложенных job'ов признаётся несостоятельным, и reconciler повышается из страховки в основной путь |

## Пересмотр

- p95 задержки взятия job'а > 5 с при штатной нагрузке, либо устойчивые `slow_query`/`index_bloat`/`xmin_horizon` от pg-boss → переход на graphile-worker 0.18.
- Появление второго самостоятельного движка исполнения (шаги вне процесса, распределённые саги, компенсирующие транзакции) → Temporal вместо VoltAgent, а не рядом с ним.
- Postgres-бэкенд BullMQ 6 подтверждает production-готовность → переоткрыть сравнение.
- Нагрузочный прогон eval-батчей показывает, что pg-boss с `partition: true` мешает нашим горячим запросам → вынести очередь в отдельную БД (не в отдельную технологию) и потерять транзакционный enqueue осознанно.
