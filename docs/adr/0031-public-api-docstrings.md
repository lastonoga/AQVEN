# ADR-0031. Docstring на публичном API `aqven` и `aqven-llm` — исключение для документации

> Статус: принято
> Дата: 2026-09-18
> Зависит от: [ADR-0026](0026-yaml-spec-and-code-refs.md) §8 (`E_DOCSTRING`)
> Меняет: [CLAUDE.md](../../CLAUDE.md) «Жёсткие правила» — уточняет цитату ADR-0026 §8 и добавляет исключение
> Источники: [docs/superpowers/specs/2026-09-18-docs-site-design.md](../superpowers/specs/2026-09-18-docs-site-design.md) §3, §7, §9 — codegen-мост для справочника Python API сайта документации

## Контекст

Сайт документации AQVEN строит справочник Python API (`Project`, `RunOptions`, `create_local_app`,
`create_mcp_server` и аналоги `aqven-llm`) генерацией из кода, как и остальные справочные страницы сайта
(CLI — из `--help`, HTTP API — из OpenAPI, конфигурация — из JSON Schema Pydantic-моделей). Стандартный способ
получить такой справочник для Python-библиотеки — прочитать docstring и сигнатуру публичного объекта; griffe
2.0.0 (MIT), тот же экстрактор, на котором работает mkdocstrings, делает это без исполнения кода и без mkdocs:
`griffe dump <package> -s <path>` отдаёт JSON.

Действующая формулировка CLAUDE.md «Жёсткие правила» — «Никаких комментариев в коде... Docstring считается
комментарием (ADR-0026 §8)» — цитирует ADR-0026 §8 шире, чем сам ADR устанавливает. Там `E_DOCSTRING` запрещает
docstring только у функций шагов и `Signature` builder-а **проекта на aqven** (DECISIONS.md «Описание
воркфлоу»): такой docstring выглядит инструкцией модели, но движок его не читает и молча игнорирует. Про код
самого движка (`packages/aqven`, `packages/aqven-llm`) ADR-0026 §8 ничего не говорит. Прямого конфликта с
генерацией API-документации нет, но нынешняя формулировка CLAUDE.md читается как запрет на весь код репозитория
и увела бы агента от единственного стандартного инструмента получить справочник Python API без ручного
дублирования описаний, которое дрейфует от кода.

## Решение

| Решение | Что берём | Версия | Лицензия | Почему |
|---|---|---|---|---|
| Извлечение API из docstring | griffe | 2.0.0 | MIT | стандартный экстрактор для Python API-референса (движок mkdocstrings); `griffe dump` отдаёт JSON без mkdocs |

Docstring разрешён **только** на публичной поверхности пакетов `aqven` и `aqven-llm` — на объектах, которые
проект-хозяин импортирует из корня пакета (DECISIONS.md «Библиотека и проект»: `Project`, `RunOptions`,
`create_local_app`, `create_mcp_server`, тестовые хелперы, и аналогичный публичный слой `aqven-llm`). На этой
поверхности docstring обязателен там, где он служит источником API-референса, и пишется как документация —
что делает объект, что принимает, что возвращает — а не как комментарий к реализации.

Везде, где исключение не применяется — реализация движка, шаги проекта на aqven, `Signature` builder-а, Lumen
и любые другие примеры, — правило CLAUDE.md действует без изменений: docstring и комментарии запрещены.

`E_DOCSTRING` не расширяется на публичный API движка: это проверка `aqven check` над кодом **проекта**, на
пакеты `aqven`/`aqven-llm` она не запускается.

## Альтернативы

| Альтернатива | Почему отвергнута |
|---|---|
| Docstring запрещён везде, API-референс — только из данных без прозы (сигнатуры pyright, описания полей Pydantic) | Работает для конфигурации и CLI — так уже сделано на сайте, — но для «что делает функция и почему» нет источника без докстринга: пришлось бы дублировать описание в отдельном месте, которое дрейфует от кода |
| Разрешить docstring везде в движке | Противоречит явному решению заказчика «никаких комментариев» и расширяет исключение за пределы того, что реально нужно генератору документации |
| Свой формат описания API рядом с кодом, не docstring | Изобретение велосипеда: griffe — живая поддерживаемая библиотека именно для этого случая |

## Последствия

**Положительные.** Справочник Python API генерируется из кода и не дрейфует от реализации; не нужен отдельный
формат описания функций. Формулировка CLAUDE.md перестаёт цитировать ADR-0026 §8 шире, чем он есть на самом деле.

**Отрицательные.** Граница «публичная поверхность против остального кода» проверяется человеком на ревью, а
не линтером: `ruff` в этом проекте не запускает правила `D` (pydocstyle) и не отличит docstring на публичном API
от docstring там, где ему быть не положено. Случайный docstring на внутренней функции движка не поймается
автоматически.

**Обязательства.** Docstring на публичной поверхности `aqven`/`aqven-llm` пишется и поддерживается как источник
API-референса сайта — стилистически как документация, а не объяснение реализации.

## Проверка

- `griffe dump aqven -s packages/aqven/src` отдаёт JSON с docstring и сигнатурами публичных объектов пакета.
- `aqven check` над проектом Lumen продолжает падать с `E_DOCSTRING` на docstring у step-функции или `Signature`
  builder-а — поведение не меняется.

## Пересмотр

- Если griffe перестаёт поддерживаться или меняется стандартный инструмент Python API-документации —
  пересмотреть выбор экстрактора; исключение для публичного API остаётся.
- Если появляется линтер, отличающий публичную поверхность пакета от остального кода, — включить его вместо
  ручной проверки на ревью.
