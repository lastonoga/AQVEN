# ADR-0005. Три исхода вызова модели и запрет ремонта обрезанного ответа

> Статус: **частично изменено [ADR-0029](0029-trust-and-quality-python.md)** (2026-09-16)
> Дата: 2026-09-11

## Контекст

Спека трактует результат вызова модели как бинарный: распарсилось или нет, а «нет» лечится
толерантным парсером и ретраем (каталог §8, строка 30). Документация обоих managed-провайдеров
описывает не два состояния, а три, и два из них внешне выглядят одинаково — как невалидный JSON.

| Исход | OpenAI | Anthropic |
|---|---|---|
| Отказ модели | поле `refusal` в ответе; «a refusal does not necessarily follow the schema you have supplied in `response_format`» | `stop_reason: "refusal"`, HTTP 200, токены тарифицируются, схема может не соблюдаться |
| Обрыв по лимиту | `finish_reason: "length"`, ответ — невалидный JSON | `stop_reason: "max_tokens"`, «Retry with a higher max_tokens value.» |
| Нормальный ответ | схема соблюдена грамматикой | схема соблюдена грамматикой |

Ключевой факт, обнаруженный экспериментом (`scratchpad/probe/repairtest.mjs`, `jsonrepair@3.15.0`,
ISC): на обрезанном JSON jsonrepair **не бросает исключение**, а молча достраивает недостающее.

```
вход:  {"id":"x","items":[{"a":1},{"a":
выход: {"id":"x","items":[{"a":1},{"a":null}]}
```

Синтаксические дефекты он чинит корректно (`{"id": "x", "n": 1, kind: 'a', "trail": [1,2,],}` →
`{"id": "x", "n": 1, "kind": "a", "trail": [1,2]}`). Но отличить «модель налажала с синтаксисом» от
«ответ оборван по max_tokens» он не может: во втором случае он возвращает правдоподобный объект с
дырами из `null`. Такой объект проходит Zod там, где поле объявлено nullable, попадает в
`workflowState`, в провенанс и в датасет evals — и дальше воспроизводится как «настоящий» результат.
Это самая опасная найденная ловушка во всём конвейере структурированного вывода.

Требования каталога §8: строка 33 (R-33) — детектор отказа, маршрут «ретрай → фолбэк-профиль →
эскалация», молчаливый дефолт запрещён, уровень L2; строка 34 (R-34) — оценка размера выхода по
типу, запас `max_tokens`, детект обрыва, уровень L1/L2. Обе требуют, чтобы отказ и обрыв были
различимыми состояниями, а не общим «невалидным JSON».

## Решение

Исполнитель узла возвращает сумму из трёх вариантов, а не `Result<T, Error>`. Ветвление по исходу
происходит ДО любого парсинга — на основании `finish_reason`/`stop_reason` и поля `refusal`.

```ts
type CallOutcome<T> =
  | { kind: "ok"; value: T; issues: WorkflowIssue[] }
  | { kind: "refusal"; reason: string; usage: Usage }
  | { kind: "truncated"; maxTokens: number; usage: Usage };
```

Конвейер разбора, порядок шагов фиксирован:

| Шаг | Что делает | Применяется при исходе |
|---|---|---|
| 1 | constrained decoding на стороне провайдера (профиль из ADR-0004) | все |
| 2 | гейт исхода: `refusal` / `truncated` / `ok` | все |
| 3 | извлечение блока: снять markdown-ограждение, взять первый сбалансированный `{...}` | только `ok` |
| 4 | `JSON.parse` — быстрый путь, при успехе шаг 5 пропускается | только `ok` |
| 5 | `jsonrepair`, ровно одна попытка, без участия модели | только `ok` |
| 6 | `zod.safeParse` — типы, точечная коэрсия, межполевые проверки → `WorkflowIssue[]` | только `ok` |
| 7 | LLM-ремонт по `Issue[]` с `severity: "assert"`, лимит попыток из IR узла | только `ok` |

Маршруты для двух других исходов, ремонт в них запрещён:

- `truncated` → повтор с увеличенным `max_tokens` (одна ступень увеличения, предел из IR узла) →
  если лимит модели исчерпан, фолбэк-профиль с большим окном → иначе эскалация. Шаги 3-7 не
  выполняются вообще; сырой текст сохраняется в провенанс как артефакт, но никогда не парсится.
- `refusal` → типизированная ошибка политики, поднимается наверх как есть. Ретрай того же промпта
  без изменения входа запрещён; допустимы фолбэк-профиль и эскалация человеку. Молчаливый дефолт,
  пустой объект и «best-effort» результат запрещены.

Частично распарсенный объект (стриминг) существует только в канале UI и не может быть записан в
`workflowState` как результат узла.

`max_tokens` узла не берётся из глобального дефолта: он назначается из оценки размера выхода по
IR-типу узла с явным запасом, и эта оценка — часть компиляции узла, а не константа рантайма.

## Альтернативы

| Альтернатива | Почему отвергнута | При каких условиях вернёмся |
|---|---|---|
| Два исхода: валидно / невалидно (как в спеке, §8 строка 30) | Схлопывает отказ и обрыв в одну ветку, а лечения у них противоположные: отказу нужен другой вход или эскалация, обрыву — больший лимит. Ремонт отказа впустую жжёт бюджет, ремонт обрыва фальсифицирует данные | Никогда: различие приходит от провайдеров и никуда не денется |
| `jsonrepair` до проверки `finish_reason` | Проверено запуском: на обрезанном JSON молча подставляет `null` и закрывает скобки, ложный объект неотличим от настоящего | Только если jsonrepair начнёт сигнализировать «вход был неполным» отдельным флагом |
| Чинить обрезанный ответ и помечать результат как «частичный» | Метка не спасает: значение уже попало в провенанс, в кассету и в датасет evals, а `null` в nullable-поле проходит Zod. Порча воспроизводится при реплее | Нет |
| Продолжение генерации с места обрыва (continuation) | Склейка двух ответов даёт JSON, который не был порождён одной грамматикой; constrained decoding по второй половине не гарантирует согласованность с первой | Если провайдер даст штатный механизм продолжения внутри той же грамматики |
| BAML / Schema-Aligned Parsing как парсер | Это язык и кодогенератор, второй источник истины рядом с IR, нативный бинарь; практическую часть покрывают jsonrepair + коэрсия Zod. Обрыв SAP тоже не отличает от синтаксического мусора | Если выйдет отдельный WASM/JS-пакет только с SAP-парсером без DSL |
| Молчаливый дефолт при отказе (пустой объект, значение по умолчанию) | Прямо запрещено каталогом §8 строка 33; превращает отказ безопасности в тихую потерю данных | Нет |
| `partial-json` для частичных объектов | Релизов нет с мая 2024; и сам сценарий ограничен UI. На горячем пути частичный объект запрещён | Нет; для UI берём стриминг частичных объектов из `ai@6`, который уже в дереве |

## Последствия

Положительные:
- Ложноположительный «успех» на обрыве исключён конструктивно: шаги парсинга физически недостижимы
  для исхода `truncated`.
- Отказ становится наблюдаемым событием со своей метрикой и своим маршрутом, а не шумом в счётчике
  ошибок парсинга (R-33).
- Ремонтный бюджет тратится только там, где он может сойтись, — на синтаксических и семантических
  дефектах полного ответа.

Отрицательные:
- Исполнитель узла обязан знать провайдерские поля завершения; нормализация `finish_reason`/
  `stop_reason`/`refusal` в общий исход — наш код на порту модели.
- Три исхода расходятся по всему стеку: типы результата узла, провенанс, метрики, UI, экспорт.
- Обрыв теперь стоит дороже: вместо дешёвой «починки» — повторный вызов с большим лимитом.

Обязаны делать:
1. Порт модели нормализует ответ провайдера в `CallOutcome` до разбора; адаптер на провайдера
   (Adapter), общий код разбора — один.
2. `jsonrepair` импортируется ровно в одном модуле разбора и вызывается только на ветке `ok`;
   одна попытка, без LLM.
3. Исход вызова пишется в провенанс каждого узла как отдельное поле, попадает в трассу Langfuse и
   в запись кассеты; при реплее исход воспроизводится, а не пересчитывается.
4. Политики `on_refusal` и предел увеличения `max_tokens` — поля IR узла, а не константы кода.
5. Цикл ремонта питается `WorkflowIssue[]`; повторение того же набора issue два раза подряд
   прерывает цикл досрочно, не дожигая бюджет.
6. Частичные объекты не покидают канал UI.

## Проверка

- Фикстура обрыва в тестах: ответ `{"id":"x","items":[{"a":1},{"a":` со `stop_reason: "max_tokens"`.
  Тест требует исхода `truncated`, отсутствия вызова jsonrepair (шпион) и отсутствия записи в
  `workflowState`. Тот же фикстур в варианте «повреждённый синтаксис, `stop_reason: "end_turn"`»
  обязан дать `ok` после ремонта.
- Фикстура отказа: `stop_reason: "refusal"` и HTTP 200 — тест требует типизированной ошибки политики
  и ненулевого учёта токенов в бюджете узла.
- Правило Biome `no-restricted-imports`: `jsonrepair` разрешён только в модуле разбора ответа.
- Инвариант провенанса в CI: ни одна запись результата узла не имеет исхода `truncated` или
  `refusal`; такие записи — баг конвейера, а не данные.
- Метрики-гейт: доли `truncated` и `refusal` по узлу за окно. Рост `truncated` означает, что оценка
  размера выхода по типу занижена (R-34), и ловится до того, как превратится в падение качества.
- Kill-критерий: если после увеличения `max_tokens` до предела модели узел продолжает давать
  `truncated`, узел признаётся несовместимым с профилем и маршрутизируется на модель с большим
  окном либо разбивается на несколько узлов; тихое продолжение работы запрещено.

## Пересмотр

Пересматриваем, если: провайдер даёт штатное продолжение генерации внутри той же грамматики;
`jsonrepair` начинает явно сигнализировать о неполном входе (тогда шаг 5 может подниматься выше
шага 2 для части случаев); появляется провайдер, у которого отказ и обрыв неразличимы по полям
ответа (тогда нужен собственный детектор и отдельная запись в этом ADR); доля узлов на моделях без
`finish_reason`-семантики превышает четверть каталога.
