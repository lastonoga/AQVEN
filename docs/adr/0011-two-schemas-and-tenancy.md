# ADR-0011. Две схемы в одной базе и мультитенантность с первого дня

> Статус: принято
> Дата: 2026-09-11
> Контекст-документы: [16. Модель данных](../16-data-model.md), [10. Рантайм](../10-runtime.md), [17. Задачи и планирование](../17-jobs-and-scheduling.md), [19. Безопасность и политики](../19-security-and-policies.md), [06. Реестры](../06-registries.md), [ADR-0010](0010-pg-boss-scheduler.md)

## Контекст

**Чужой DDL в нашей базе.** `@voltagent/postgres@2.1.3` создаёт свои таблицы **в рантайме** через `CREATE TABLE IF NOT EXISTS` (проверено по `dist/index.js`): `${prefix}_users`, `${prefix}_conversations`, `${prefix}_messages`, `${prefix}_workflow_states`, `${prefix}_steps` и векторная таблица; префиксы по умолчанию `voltagent_memory` и `voltagent_vector`. Опции адаптера: `connection`, `tablePrefix`, `schema?: string`, `maxConnections` (10), `searchPath`. В `dist/index.js` найден ровно один `CREATE SCHEMA IF NOT EXISTS` — схему адаптер создать умеет. Одновременно у нас версионированные миграции drizzle-kit 0.31.10: при `generate`/`push` он видит чужие рантайм-таблицы как «лишние» и предлагает их снести. Два владельца схемы в одной БД — это конфликт, который надо развести явно, а не дисциплиной.

**Противоречие со спекой по тенантности.** Спека называет мультитенантный SaaS не-целью v1. Но `tenant_id` нужен во всех вариантах модели данных, кроме database-per-tenant, а добавление колонки постфактум — самая дорогая миграция из возможных: переделка PK/FK и всех составных индексов, включая партиционированную горячую таблицу, плюс бэкфилл на живых данных и ревизия каждого запроса. Противоречие разрешается разделением двух разных вещей, которые спека склеила в одно слово «мультитенантность».

**Прочие вводные.** PostgreSQL 18 принёс встроенный `uuidv7()` (time-ordered UUID) и `uuid_extract_timestamp()`. Образ — `pgvector/pgvector:0.8.6-pg18` (опубликован 2026-08-13). `run_nodes` — самая горячая таблица: запись на каждый шаг каждого узла, включая итерации циклов и элементы foreach. Встроенное векторное хранилище VoltAgent — колонка `vector BYTEA`, полный `SELECT` и `cosineSimilarity` **в JS-процессе** (`dist/index.js`, `async search(queryVector, options)`), никакого ANN.

## Решение

### 1. Две схемы в одной базе

`app` — наши таблицы, единственный владелец — drizzle-kit (forward-only, expand/contract, без down). `voltagent` — рантайм-DDL адаптера. Разведение: `schema: 'voltagent'` в опциях `@voltagent/postgres` и `schemaFilter: ['app']` в `drizzle.config.ts`. Схему `voltagent` создаём миграцией заранее и выдаём рантайм-роли только `USAGE` — это предпочтительнее, чем давать роли `CREATE` на базе.

Связь между схемами — `execution_id text` (это `${prefix}_workflow_states.id`, тип TEXT) **без настоящего FK через границу схемы**: иначе наши миграции сцепятся с рантайм-DDL чужого пакета. Ссылочная целостность логическая. Чекпоинты suspend/resume живут в `voltagent.*_workflow_states` (`workflow_state`, `suspension`), наша таблица `app.checkpoints` — про другое (снимки для time-travel/replay); дублировать не надо, надо связывать по `execution_id`.

### 2. Мультитенантность: разрешение противоречия со спекой

Разделяем два уровня и фиксируем их по отдельности:

| Уровень | Решение v1 |
|---|---|
| **Модель данных** | мультитенантная: `tenant_id uuid not null` во всех таблицах `app` + RLS с `FORCE`, включённая сразу |
| **Продуктовая поверхность** | одно-тенантная: нет регистрации, нет тарификации, нет биллинга, нет переключателя тенантов в UI. Одна строка в `tenants`, значение берётся из конфига |

Стоимость обоих путей честно:

| | Поставить сразу (выбрано) | Отложить до v2 |
|---|---|---|
| Разработка на v1 | колонка + политика на таблицу + хелпер `withTenant` + правило «`tenant_id` первым в составном индексе» | 0 |
| Рантайм | один дополнительный предикат в плане; при `tenant_id` в ведущей колонке индекса накладные расходы близки к нулю | 0 |
| Миграция потом | не нужна | переделка PK/FK/индексов всех таблиц, включая партиционированную `run_nodes`, бэкфилл на живых данных, ревизия всех запросов и всех политик |
| Риск утечки | БД гарантирует изоляцию | цена одной забытой `WHERE tenant_id` — утечка между клиентами |

Решающий довод **именно для нашего продукта**: часть запросов будет формироваться LLM-инструментами, то есть вероятность «забыли `WHERE tenant_id`» выше обычной. RLS здесь — страховка от целого класса инцидентов, а не архитектура сама по себе.

Механика: `pgPolicy` на таблице (Drizzle 0.45 умеет `pgPolicy`/`pgRole`), плюс custom-миграция `ALTER TABLE app.<t> ENABLE ROW LEVEL SECURITY; ALTER TABLE app.<t> FORCE ROW LEVEL SECURITY;`. `FORCE` обязателен: без него владелец таблицы обходит собственные политики, и всё выглядит работающим до первого инцидента. Контекст тенанта ставится **только** `SELECT set_config('app.tenant_id', $1, true)` внутри транзакции (`true` = `SET LOCAL`) — сессионный `SET` протекает в чужой запрос при transaction pooling. Единственная точка входа прикладного кода в БД — хелпер `withTenant(tenantId, fn)`. Фоновые джобы, миграции и аналитика ходят под отдельной ролью с `BYPASSRLS` и помечены явно.

### 3. Ключи, партиционирование, блобы, векторы

- **PK — `uuid DEFAULT uuidv7()`** (PostgreSQL 18, встроено). v7 даёт локальность вставки в B-tree (нет random-IO как у v4) и корреляцию со временем, без которой BRIN бесполезен. Время — `timestamptz` в UTC, деньги — `numeric(18,8)`, контентная адресация — `bytea` (32 байта sha256), не hex-текст.
- **`run_nodes` партиционируется** `PARTITION BY RANGE (started_at)` помесячно, `PRIMARY KEY (started_at, id)` (ключ партиционирования обязан входить в PK), `USING brin (started_at) WITH (pages_per_range = 32, autosummarize = on)` плюс btree `(run_id, node_id, iteration, attempt)`. Партиции создаются заранее джобом на 3 месяца вперёд. Партиции берутся **не ради скорости** (BRIN+btree тянет до ~50–100 млн строк), а ради дешёвого удаления `DROP PARTITION` вместо `DELETE`+VACUUM и ради поштучной работы autovacuum. Вводим сразу: ретрофит партиционирования живой таблицы дороже.
- **Правило трёх зон для блобов.** Основание — механика TOAST: порог выноса ~2 КБ на кортеж, страница 8 КБ, и главное — **TOAST не поддерживает частичное чтение jsonb**: любое обращение к полю (`->>`, `@>`) де-TOAST'ит и распаковывает значение целиком, а каждая версия строки пишется в WAL целиком.

| Размер значения | Куда | Почему |
|---|---|---|
| < 8 КБ | `jsonb` в строке | влезает в страницу, индексируется GIN, транзакционно |
| 8 КБ – 1 МБ | `app.blobs` (сателлит, `SET COMPRESSION lz4`, `UNIQUE (project_id, sha256)`), в горячей таблице только `{blob_id}` | TOAST справляется, но не должен мешать сканам горячей таблицы |
| > 1 МБ | объектное хранилище по sha256, в БД метаданные + ключ | де-TOAST целиком дорог, WAL-амплификация |

Порог — конфиг `BLOB_INLINE_MAX_BYTES` (дефолт 1 МБ), а не константа в коде. Выбор зоны знает единственное место — `BlobStore` (Strategy): один интерфейс `put(bytes, meta) -> blobId` / `get(blobId)`, две реализации. На v1 S3-бэкенд не включаем (MinIO как дефолтный образ не берём — он не публикуется с 2025-10). Дедуп по sha256 не украшение: в матрице моделей один отрисованный промт уходит в N моделей и хранится один раз. Postgres Large Objects (`lo_*`) — мёртвая ветка: вне MVCC-логики таблиц, требуют явного `lo_unlink`, не реплицируются логической репликацией.
- **Векторный поиск — наш**, pgvector 0.8.6, только HNSW (`m=16, ef_construction=64`, на запросе `hnsw.ef_search = 40..100`), таблица `app.embeddings`. Для фильтрованных ANN-запросов — `hnsw.iterative_scan` (есть с 0.8.0) плюс партиционирование по `tenant_id`/`project_id`: обычный HNSW сначала берёт top-k по вектору и только потом фильтрует, то есть на `WHERE project_id = $1 ORDER BY embedding <=> $2 LIMIT 10` можно получить меньше 10 строк. **Встроенное векторное хранилище VoltAgent не берём** для нашего поиска: BYTEA + полный скан + косинус в JS годится на память агента (сотни-тысячи векторов) и разваливается на сотнях тысяч; ANN там нет вообще. Для памяти агента оставляем его как есть.

## Альтернативы

| Альтернатива | Почему отвергнута | При каких условиях вернёмся к ней |
|---|---|---|
| Одна схема на всех (наши таблицы вперемешку с VoltAgent) | drizzle-kit видит рантайм-таблицы адаптера как лишние и генерирует `DROP` | Если VoltAgent начнёт поставлять версионированные миграции вместо рантайм-DDL |
| Отдельная БД под VoltAgent | Теряем «одна транзакция, один бэкап»: бизнес-запись, enqueue pg-boss и чекпоинт перестают быть атомарными; появляется распределённая согласованность там, где её не было | Если нагрузка памяти/трасс VoltAgent начнёт мешать нашим горячим запросам |
| `tenant_id` без RLS (изоляция только кодом) | Цена одной забытой `WHERE` — утечка между клиентами; часть запросов генерируется LLM-инструментами | Никогда |
| schema-per-tenant | Миграции × N схем при forward-only drizzle-kit (частичные отказы — постоянная боль); каталог пухнет, autovacuum страдает. И главное: `@voltagent/postgres` принимает `schema` **строкой**, а не функцией от тенанта — VoltAgent-часть всё равно осталась бы общей, изоляция вышла бы дырявой | Никогда в этом виде; физическую изоляцию даём отдельной БД |
| database-per-tenant | Пул соединений на тенанта не масштабируется; сквозная аналитика только через ETL | Точечно, по требованию крупного клиента: из `tenant_id`-модели переезд — дамп по фильтру, из schema-per-tenant был бы невозможен дёшево |
| Отложить `tenant_id` до v2, как в спеке | Самая дорогая миграция из возможных: PK/FK/индексы/партиции + бэкфилл на живых данных | Нет условий: стоимость только растёт со временем |
| `uuid` v4 как PK | random-IO в B-tree, нет корреляции со временем — BRIN на `run_nodes` становится бесполезен | Только на PostgreSQL < 18, и тогда `pg_uuidv7` или генерация v7 в приложении |
| Встроенный vector store VoltAgent для нашего поиска | BYTEA + полный `SELECT` + `cosineSimilarity` в JS, без ANN | Для памяти агента используем как есть; для поиска по компонентам/журналу/датасетам — нет |
| Выделенный ANN (Qdrant и аналоги) | Вторая операционная сущность и второй источник правды; наш объём оценочно ~100k векторов (10k компонентов × 10 чанков), нужен join с фильтрами и транзакционность «вектор и его источник в одной транзакции» | > 5 млн векторов **или** p95 поиска > 150 мс при корректно настроенном HNSW |
| Postgres Large Objects для больших payload | Вне MVCC-логики таблиц, утечка без `lo_unlink`, не реплицируются логической репликацией | Никогда |

## Последствия

**Положительные.**
- Одна БД — одна транзакция, один бэкап, один мониторинг. Бизнес-запись, постановка задачи (ADR-0010) и чекпоинт коммитятся вместе.
- RLS снимает целый класс инцидентов и делает безопасными LLM-генерируемые запросы на чтение.
- Путь в SaaS открыт без миграции модели данных: меняется продуктовая поверхность, а не схема.
- `uuidv7` + BRIN + партиции дают дешёвую запись и дешёвое удаление на самой горячей таблице.

**Отрицательные.**
- Каждый прикладной запрос обязан идти внутри транзакции с `set_config('app.tenant_id', …, true)`. Это дисциплина, которую нельзя забыть в одном месте.
- Часть рантайма остаётся одно-тенантной по своей природе: `WorkflowRegistry.getInstance()` — глобальный синглтон на `globalThis`. Это осознанный долг, он ограничивает не данные, а процесс.
- RLS-политика — дополнительный предикат в каждом плане; при неудачном индексе это заметно.
- Часть DDL (партиции, `FORCE RLS`, `SET COMPRESSION lz4`, `REVOKE`, `CREATE EXTENSION`, гранты) Drizzle не выражает — живёт в custom-миграциях и требует ручного ревью.

**Обязаны делать.**
1. `tenant_id uuid not null` во всех таблицах `app`; `ENABLE` + **`FORCE`** `ROW LEVEL SECURITY` в custom-миграции для каждой.
2. Контекст тенанта — только `set_config(..., true)` внутри транзакции. Сессионный `SET` запрещён. Единственная точка входа — `withTenant(tenantId, fn)`.
3. Везде, где есть политика по `tenant_id`, этот столбец — **первый в составном индексе**.
4. Фон, миграции и аналитика — под ролью с `BYPASSRLS`, явно помеченной в коде.
5. Ни одного FK через границу `app` ↔ `voltagent`. Связь — `execution_id text`.
6. `drizzle.config.ts` обязан нести `schemaFilter: ['app']`, адаптер VoltAgent — `schema: 'voltagent'`.
7. Запись в `run_nodes` — очередь в памяти и flush пачкой 50–200 строк по таймеру 100–250 мс из хука `onStepEnd`, не `INSERT` на шаг. Потеря хвоста при падении допустима: источник правды о статусе исполнения — `voltagent.*_workflow_states`, `run_nodes` — наблюдаемость.
8. Партиции создаются заранее джобом на 3 месяца вперёд; отсутствие партиции = отказ записи, значит джоб мониторится.
9. Миграции forward-only, expand/contract, без down; отдельный шаг деплоя, не из N реплик одновременно.
10. Неизменяемые таблицы (`spec_versions`, `cassettes`, `journal`) защищаются `REVOKE UPDATE, DELETE` для рантайм-роли, а не только дисциплиной.

## Проверка

| Что проверяем | Как |
|---|---|
| RLS реально изолирует | Тест под ролью `app_user` **на отдельном соединении**: с чужим `app.tenant_id` — 0 строк на `SELECT`, отказ на `INSERT`. Под владельцем политики тест пройдёт даже при забытом `FORCE`, поэтому отдельная роль обязательна |
| `FORCE` не потерян | Негативный тест: снятие `FORCE ROW LEVEL SECURITY` ломает тест изоляции |
| Схемы не разъехались | CI: поднять приложение (адаптер создаст свои таблицы), затем `drizzle-kit generate` — сгенерированный SQL не должен содержать ни одного `DROP TABLE`. Это детектор того, что `schemaFilter`/`schema` разошлись |
| Миграции применяются на чистой БД | testcontainers 12.1.0, образ `pgvector/pgvector:0.8.6-pg18`, миграции один раз на прогон, затем `container.snapshot()` и `restoreSnapshot()` перед каждым файлом — работает с DDL и несколькими соединениями, в отличие от отката транзакции |
| Контекст не течёт мимо фасада | Правило линтера: прямое обращение к драйверу/`db.*` мимо `withTenant` запрещено вне `@wf/db` |
| План запроса не деградирует | `EXPLAIN` на горячих запросах (`runs`, `run_nodes`, `embeddings`): seq scan при наличии подходящего индекса — провал сборки |
| **Kill-критерий** | Если политика, выраженная через подзапрос `project_id IN (SELECT id FROM app.projects WHERE tenant_id = …)`, даёт seq scan на горячих таблицах — денормализуем `tenant_id` в эти таблицы и ставим первым в составной индекс. Проверяется измерением, не обсуждением |

## Пересмотр

- `@voltagent/postgres` переходит на версионированные миграции вместо рантайм-DDL → схему `voltagent` можно вести drizzle-kit, две схемы остаются, но конфликт владельцев исчезает.
- Клиент требует физической изоляции → отдельная БД под тенанта (дамп по фильтру). Модель данных не меняется — ради этого она и такая.
- Объём векторов > 5 млн или p95 поиска > 150 мс при корректном HNSW → выделенный ANN.
- `run_nodes` переваливает за ~50–100 млн строк на партицию, либо появляется полноценная retention-политика с `DETACH CONCURRENTLY` → `pg_partman` вместо самодельного джоба.
- Продуктовая поверхность становится SaaS (регистрация, биллинг, тарификация) → отдельный ADR на продуктовый слой; **модель данных при этом не меняется**, в чём и был смысл настоящего решения.
