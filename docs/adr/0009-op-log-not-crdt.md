# ADR-0009. Server-authoritative op-log вместо CRDT для совместного редактирования спеки

> Статус: принято
> Дата: 2026-09-11
> Контекст-документы: [14. MCP-контракт для агентов](../14-mcp-contract.md), [15. Studio: фронтенд](../15-studio-frontend.md), [16. Модель данных](../16-data-model.md), [ADR-0007](0007-single-operation-contract.md)

## Контекст

Одну спеку воркфлоу одновременно правят двое: агент Claude через MCP-тулы и человек в Studio.
Задача внешне похожа на совместное редактирование текста, но отличается по четырём пунктам:

1. Агент пишет **не символы, а операции** (`add_node`, `bind`, `set`). У него нет курсора и
   посимвольного ввода, ему не нужно видеть чужие буквы в реальном времени.
2. Спека — **типизированный граф с инвариантами**: типы портов, DAG без циклов, обязательные
   биндинги, полнота enum в ветвлениях.
3. Спека **компилируется** и порождает версии и прогоны. Для `version_propose(evidence)` и `run_diff`
   нужна **линейная история ревизий** — то есть серверный op-log нужен в любом случае.
4. Одновременных редакторов единицы, а не сотни. Конфликтов мало.

Кандидаты-библиотеки проверены и живы: `yjs@13.6.32` (MIT, 2026-08-04), `y-websocket@3.1.0` (MIT,
2026-08-06), `loro-crdt@1.16.1` (MIT, 2026-09-10). Риска «заброшено» нет ни у одного — отказ от них
основан не на состоянии пакетов, а на свойствах задачи.

Ключевой факт: **CRDT гарантирует сходимость, но не гарантирует валидность**. Конкретный пример на
нашем графе. Агент удаляет узел `parse_pdf`. Человек в ту же секунду связывает вход
`extract_line_items.input.text` с выходом `parse_pdf.output.text`. Обе операции корректны
по отдельности, коммутируют и сливаются без конфликта: реплики сходятся к состоянию, где
существует биндинг на несуществующий узел. Структурно документ цел, семантически мёртв —
компилятор упадёт, а в истории уже лежит «успешная» ревизия. Второй пример из того же класса: два
параллельно добавленных ребра `A→B` и `B→A`, каждое поодиночке цикла не создаёт, вместе нарушают
инвариант DAG. У CRDT нет точки, где инвариант можно проверить и **отклонить** изменение: отклонять
слияние он не умеет по своей природе.

## Решение

Редактирование спеки — **server-authoritative**: оптимистическая блокировка по ревизии,
транзакционная валидация инвариантов, линейный op-log. CRDT для структуры графа не берём.

Единица записи — один тул `flow_patch` с массивом операций (он же закрывает консолидацию
поверхности из [ADR-0008](0008-mcp-tool-naming-and-phasing.md)):

```ts
const PatchInput = z.object({
  spec_id: z.string(),
  base_rev: z.number().int(),
  ops: z.array(Op).min(1).max(50),
  idempotency_key: z.string().optional(),
  dry_run: z.boolean().default(false)
});
```

`base_rev` — оптимистическая блокировка, `ops` применяются атомарно всё-или-ничего,
`idempotency_key` защищает от ретраев MCP-клиента, `dry_run` показывает результат без записи.

Серверная транзакция:

| Шаг | Действие |
|---|---|
| 1 | `BEGIN; SELECT rev FROM specs WHERE id = $1 FOR UPDATE;` |
| 2 | `rev !== base_rev` → ответ-конфликт (не голый 409): конверт с `conflict { your_base_rev, current_rev, ops_since, rebase: "auto" \| "manual", rebased_ops? }` |
| 3 | Применить `ops` → прогнать валидатор инвариантов (типы портов, DAG, биндинги) |
| 4 | Валидатор упал → `ROLLBACK`, вернуть `problems[]` + `candidates[]` каноничного конверта |
| 5 | `INSERT INTO spec_ops (spec_id, rev, actor, ops, ts)`; `rev := rev + 1`; `COMMIT` |
| 6 | Ответ несёт новый `version { rev, etag }` |

Большинство конфликтов ребейзится автоматически: операции затрагивают разные узлы и пути. Ручное
разрешение нужно только при пересечении путей.

Один и тот же механизм версии у обоих входов, а не два разных: у MCP это `base_rev` в аргументах,
у REST — `GET /v1/specs/:id` с `ETag: W/"<rev>-<hash>"` и `PATCH` с `If-Match`, расхождение —
`412 Precondition Failed`. Доменный код ошибки один: `conflict` из `ApiError`
([ADR-0007](0007-single-operation-contract.md)).

Живые обновления UI: op-log → broadcast по SSE → Studio применяет операции инкрементально;
`@tanstack/react-query@5.102.8` держит кэш, инвалидация по `rev`. Никакого CRDT-синка — только
«сервер сказал, что `rev` стал 43, вот дельта».

Мягкая блокировка снимает большую часть конфликтов организационно, а не алгоритмически:
`flow_lock({ spec_id, ttl_s: 300 })` — advisory-lock, Studio показывает «Claude редактирует»,
человек может перехватить принудительно. Блокировка мягкая: истечение TTL не ломает запись,
она лишь предупреждает.

**Где CRDT всё-таки уместен позже** — точечно и только там, где нет доменных инвариантов:
свободный текст промта внутри одного узла (совместная правка формулировки) и позиции узлов на
канве (last-write-wins по полю, конфликт невозможен по определению). Структура графа — никогда.

## Альтернативы

| Альтернатива | Почему отвергнута | При каких условиях вернёмся к ней |
|---|---|---|
| Yjs (`yjs@13.6.32` + `y-websocket@3.1.0`, MIT) на структуру графа | Сходимость без валидности: удаление узла + привязка к его порту сливаются в «целое, но битое» состояние. Поверх CRDT всё равно пришлось бы строить серверную валидацию и линеаризацию истории — то же самое плюс лишний слой и лишний бандл | Для свободного текста промта внутри узла и позиций на канве |
| Loro (`loro-crdt@1.16.1`, MIT) | То же возражение по сути; выбор между CRDT-движками не меняет ответа на вопрос об инвариантах | Аналогично Yjs, если понадобится богаче текстовая модель |
| Operational Transformation (свой OT-слой) | Требует собственной функции трансформации операций с доказательством корректности — прямой велосипед на ровном месте при единицах редакторов | Нет условий в обозримой области |
| Пессимистическая блокировка документа на всё время правки | Агент держит спеку минутами; человек оказывается заблокирован и начинает обходить механизм. Оставлена как мягкая advisory-версия | Если конфликты окажутся частыми и автоматический ребейз не справится |
| Last-write-wins по всему документу | Тихо теряет чужие изменения; для спеки, из которой компилируются прогоны, недопустимо | Только для полей без инвариантов (позиция узла на канве) |
| «Сначала сходимся, потом чиним валидатором» (CRDT + фоновая починка) | Починка означает автоматическое изменение чужой работы без её автора; невозможно объяснить в `run_diff` и в `version_propose(evidence)` | Никогда |

## Последствия

Положительные:
- Невалидная ревизия физически не может попасть в историю: валидатор внутри той же транзакции.
- История линейна — `run_diff`, `version_propose(evidence)` и lineage форков получают порядок бесплатно.
- Один механизм версии на два входа (MCP `base_rev`, REST `If-Match`) — одна реализация, одна точка отказа.
- Конфликт — не тупик: ответ несёт `ops_since` и, где возможно, готовые `rebased_ops`, агент повторяет вызов без похода за контекстом.
- Нет CRDT-рантайма в бандле Studio и нет второго канала синхронизации.

Отрицательные:
- Офлайн-правка невозможна: без связи с сервером записать нельзя.
- Конфликты разруливает агент/человек явно, а не библиотека молча.
- `SELECT ... FOR UPDATE` на горячих спеках сериализует записи; при взрывном росте параллельных агентов это станет узким местом.
- Автоматический ребейз требует формальной таблицы коммутативности операций — её ещё нет.

Обязаны делать:
1. Таблица `spec_ops` в схеме `app`: `tenant_id`, `spec_id`, `rev`, `actor`, `ops jsonb`, `ts`,
   PK `uuidv7()`, уникальность `(spec_id, rev)`, RLS по `tenant_id`.
2. Уникальный индекс по `(spec_id, idempotency_key)` — повтор того же ключа возвращает прежний
   результат, а не применяет операции дважды.
3. Валидатор инвариантов вызывается **внутри** транзакции и только там; ни один путь записи не
   обходит его (в том числе импорт и миграция спеки).
4. Формальная таблица коммутативности пар операций для автоматического ребейза — проектируется
   вместе с компилятором ([07. Компилятор](../07-compiler.md)); до её появления `rebase: "manual"`
   по умолчанию для пересекающихся путей.
5. Решить и зафиксировать: `dry_run` остаётся флагом `flow_patch` или выносится в отдельный
   `flow_validate` — пока не решено, реализуется как флаг.
6. Ответ на конфликт всегда в каноничном конверте с `problems`/`candidates`, а не голый HTTP-код.

## Проверка

| Что проверяем | Как |
|---|---|
| Оптимистическая блокировка работает | Интеграционный тест: два `flow_patch` с одинаковым `base_rev` → первый `rev+1`, второй отвечает конфликтом с `current_rev` и непустым `ops_since` |
| Атомарность | Патч из 50 операций, где падает 37-я → `rev` не изменился, в `spec_ops` нет строки, документ побитово равен исходному |
| Инвариант не обходится | Property-тест (`fast-check`): случайные последовательности `ops` из генератора; постусловие — любая записанная ревизия компилируется. Падение генератора = дыра в валидаторе |
| Пример из контекста | Регрессионный тест: удаление `parse_pdf` и привязка к `parse_pdf.output.text` в двух параллельных патчах → ровно один применён, второй получает `problems[{ code: "MISSING_BINDING" }]` и кандидата на исправление |
| Идемпотентность | Повтор `flow_patch` с тем же `idempotency_key` → тот же `rev`, одна строка в `spec_ops` |
| Единство версии | Контрактный тест: `etag` из REST-ответа и `version.rev` из MCP-ответа указывают на одну ревизию; `PATCH` с устаревшим `If-Match` → 412 с тем же телом `ApiError(code=conflict)`, что у MCP |
| Мягкость advisory-lock | Тест: истёкший `flow_lock` не блокирует запись; активный — не блокирует, а помечает |
| Kill-критерий | Доля конфликтов, требующих ручного разрешения, устойчиво выше 10% от записей за неделю — решение (в части ребейза, не в части server-authoritative) пересматривается |

## Пересмотр

Пересматриваем при любом из событий: появляется требование офлайн-редактирования спеки;
число одновременных редакторов одного документа вырастает с единиц до десятков;
`SELECT ... FOR UPDATE` становится измеримым узким местом по латентности записи;
структура графа перестаёт иметь инварианты, проверяемые синхронно (что означало бы другой продукт).
Отдельно и независимо пересматривается вопрос о CRDT для текста промта внутри узла — это не отмена
настоящего ADR, а его точечное дополнение.
