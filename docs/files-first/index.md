# База как индекс

> Решает: файлы — источник истины определений; база держит производный индекс для запросов и остаётся источником истины для событий.

## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Что такое индекс | производная проекция файлов, отдельная схема `idx`, ни одной FK из `app.*` | снести и пересобрать обязано быть штатной операцией, а не аварией |
| Кто пишет в `idx` | только индексатор; валидатор и компилятор читают **файлы**, не индекс | устаревший индекс физически не может пропустить недопустимую запись |
| Что отвечает индекс | «где», «сколько», «что затронуто» | «что именно написано» отвечает файл: индекс не цитируется как содержимое |
| Миграции `idx` | нет; смена версии индексатора = полная пересборка | схема индекса меняется чаще всего, а данных, которых нет в файлах, там нет |
| Где живёт | та же Postgres, схема `idx`, `tenant_id` первым столбцом каждого индекса (RLS, §16) | гейты и анализ влияния считаются на сервере; локальный режим — та же DDL на PGlite 0.5.8 |
| Модель рёбер | одна таблица `idx.refs` для всех связей | использование типа, включение фрагмента, профиль модели, обратные ссылки компонента — один и тот же вопрос «кто на кого ссылается» |
| Атомарность пересборки | одна транзакция `DELETE`+`COPY` на проект | MVCC даёт подмену бесплатно, поколения-двойники не нужны |
| Watcher | `@parcel/watcher@2.6.0` основной, `chokidar@5.0.0` запасной, за интерфейсом `FileWatcher` | только у parcel есть `getEventsSince` — это единственный механизм для «процесс был выключен» |
| Датасеты | метаданные файлом, строки в базе; исключение — замороженные golden-наборы ≤500 строк | строки порождаются прогонами и растут во время прогона, диффу не поддаются |

## 1. Что индексируем

| Запрос продукта | Что нужно в индексе | Как считается |
|---|---|---|
| `type_usages(typeId)` — где используется тип (R14) | `idx.refs` по `dst_kind='type'` | один скан обратного индекса |
| `type_usages(typeId, value)` — где используется значение enum | `dst_value` в том же ребре, `usage_kind ∈ {switch_branch, template_case, template_text, dataset_row, judge_rubric}` | скан с равенством по `dst_value` |
| `type_impact` — что сломает изменение | множество затронутых файлов из `idx.refs` → компилятор перекомпилирует **только их** | индекс даёт множество, вердикт PASS/WARN/BLOCK даёт компилятор по файлам |
| Глобальный поиск | `idx.search`: `tsvector` + триграммы по текстам промтов, описаниям, именам, статическому тексту шаблонов | `gin` по обоим |
| Список воркфлоу / реестров | `idx.objects` с `summary` (число узлов, статус, версия, входной тип) | скан по `(project, kind)` без чтения файлов |
| Какие промты используют фрагмент | `dst_kind='fragment'`, транзитивность через `depth > 1` | заменяет `app.prompt_fragment_uses` (§16 2.5) |
| Какие узлы используют профиль модели | `dst_kind='model_profile'`, `ref_path` = путь до узла | смена профиля → список узлов на перекомпиляцию |
| Обратные ссылки компонента | `dst_kind='component'`, `usage_kind='component_call'` | «где вызывается», «можно ли удалить» |
| Битые ссылки | `idx.refs LEFT JOIN idx.objects` без пары | фоновый отчёт, не блокирует запись |

Всё это — вопросы вида «покажи множество», которые по 500 файлам решаются полным обходом за секунды, а по индексу — за миллисекунды. Ни один из них не отвечает на вопрос «что написано в файле».

## 2. Схема индекса

```sql
CREATE SCHEMA idx;

CREATE TABLE idx.state (
  tenant_id uuid NOT NULL, project_id uuid PRIMARY KEY,
  generation bigint NOT NULL DEFAULT 1, head_commit text,
  builder_version text NOT NULL, built_at timestamptz NOT NULL DEFAULT now(),
  status text NOT NULL CHECK (status IN ('ready','building','degraded'))
);

CREATE TABLE idx.files (
  tenant_id uuid NOT NULL, project_id uuid NOT NULL, path text NOT NULL,
  content_hash bytea NOT NULL CHECK (octet_length(content_hash) = 32),
  size_bytes integer NOT NULL, mtime_ns bigint NOT NULL, kind text NOT NULL,
  parse_status text NOT NULL CHECK (parse_status IN ('ok','invalid','unreadable')),
  parse_error jsonb, indexed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, project_id, path)
);

CREATE TABLE idx.objects (
  tenant_id uuid NOT NULL, project_id uuid NOT NULL,
  kind text NOT NULL CHECK (kind IN ('workflow','component','type','model_profile',
    'agent','tool','prompt','fragment','dataset')),
  key text NOT NULL, path text NOT NULL, content_hash bytea NOT NULL,
  status text NOT NULL, summary jsonb NOT NULL DEFAULT '{}',
  PRIMARY KEY (tenant_id, project_id, kind, key)
);
CREATE INDEX objects_path_idx ON idx.objects (tenant_id, project_id, path);
CREATE INDEX objects_summary_gin ON idx.objects USING gin (summary jsonb_path_ops);

CREATE TABLE idx.refs (
  tenant_id uuid NOT NULL, project_id uuid NOT NULL,
  src_kind text NOT NULL, src_key text NOT NULL, src_path text NOT NULL,
  dst_kind text NOT NULL, dst_key text NOT NULL, dst_value text,
  usage_kind text NOT NULL, ref_path text NOT NULL,
  line integer, depth integer NOT NULL DEFAULT 1
);
CREATE UNIQUE INDEX refs_uidx ON idx.refs
  (tenant_id, project_id, src_kind, src_key, ref_path, dst_kind, dst_key, coalesce(dst_value,''));
CREATE INDEX refs_reverse_idx ON idx.refs
  (tenant_id, project_id, dst_kind, dst_key, dst_value, usage_kind);
CREATE INDEX refs_src_path_idx ON idx.refs (tenant_id, project_id, src_path);

CREATE TABLE idx.search (
  tenant_id uuid NOT NULL, project_id uuid NOT NULL,
  kind text NOT NULL, key text NOT NULL, path text NOT NULL,
  ref_path text NOT NULL, snippet text NOT NULL,
  tsv tsvector GENERATED ALWAYS AS (to_tsvector('simple', snippet)) STORED,
  PRIMARY KEY (tenant_id, project_id, kind, key, ref_path)
);
CREATE INDEX search_tsv_idx  ON idx.search USING gin (tsv);
CREATE INDEX search_trgm_idx ON idx.search USING gin (snippet gin_trgm_ops);
```

**Свойство выводимости, зафиксированное явно.** `DROP SCHEMA idx CASCADE` с последующей пересборкой обязан давать побайтово ту же картину при том же дереве файлов и той же `builder_version`. Следствия, которые из этого обязаны выполняться: `idx.*` не бэкапится, не реплицируется логически, не участвует в миграциях данных, `app.*` не ссылается на `idx.*` внешними ключами, и ни одна колонка `idx.*` не содержит ничего, что нельзя вывести из файлов (`generation`, `built_at`, `builder_version` — служебные, они про сам индекс). Тест конформанса: пересобрать индекс дважды и сравнить дамп с сортировкой — расхождение это баг индексатора.

Таблицы `app.prompt_fragment_uses` и `app.context_needs` (§16 2.5, 2.6) переезжают в `idx.refs` и `idx.objects.summary` — это были ровно те же обратные индексы, только заполняемые на публикации версии.

## 3. Поддержание актуальности

| Путь изменения | Как узнаём | Режим | Латентность |
|---|---|---|---|
| Наша операция (MCP, агент) | сами знаем `path` и хеш после записи через валидатор | точечный upsert в той же транзакции, что и ответ операции | 0, эхо-событие watcher'а гасится совпадением хеша |
| Правка в редакторе, Claude Code | событие watcher'а, debounce 80 мс | инкрементальный разбор изменённых файлов | ~50-150 мс |
| `git pull`, `checkout`, `rebase` | изменились `.git/HEAD` / `.git/index` | **не** N событий, а один reconcile по `git diff --name-status <old>..<new>`; если дельта > 25% файлов — полная пересборка | 0.3-3 с |
| Процесс был выключен | `getEventsSince(snapshot)` на старте | инкрементально по вернувшейся дельте | доли секунды |
| Снапшот протух, watcher умер, дельта неприменима | несовпадение `head_commit` или ошибка подписки | полная пересборка, `status='building'` | см. §4 |
| Сменилась `builder_version` | сравнение при старте | полная пересборка | см. §4 |

**Выбор библиотеки.** `@parcel/watcher@2.6.0` — нативный (FSEvents / inotify / ReadDirectoryChangesW), рекурсивная подписка из коробки, и единственный с `writeSnapshot`/`getEventsSince`: без этого «пока нас не было, человек сделал pull» закрывается только полной пересборкой. `chokidar@5.0.0` (Node ≥ 20.19, `readdirp@5`, globs и `fsevents` выкинуты ещё в 4.x) — чистый JS поверх `fs.watch` с режимом polling: запасной путь для сетевых ФС, WSL и контейнеров со сломанным inotify. Оба за одним интерфейсом `FileWatcher` (Strategy), выбор — конфигом, не `if` по платформе. Голый `fs.watch` не берём: рекурсия на Linux не поддерживается, а дедупликация событий пришлось бы писать самим.

**Инкрементальный шаг** на один файл: прочитать, посчитать sha256, сравнить с `idx.files.content_hash` (совпал — выход), разобрать, `upsert` в `idx.objects`, `DELETE FROM idx.refs WHERE src_path = $path`, `COPY` новых рёбер, обновить `idx.files`. Удалённый файл — каскад по `src_path`; входящие на него рёбра остаются висячими намеренно: из них строится отчёт о битых ссылках. Файл не разобрался — `parse_status='invalid'`, старые объекты и рёбра **не** удаляются: наполовину сохранённый YAML не должен обнулять карту использований.

## 4. Стоимость

Проект 50 воркфлоу + 300 промтов — это порядка 500-700 файлов и 3-6 МБ текста. На файл: чтение из page cache ~0.05 мс, YAML-разбор (`yaml@2.9.1`) 0.3-1 мс на 8 КБ, Zod-валидация IR 0.2-0.5 мс, разбор Liquid для промтов 0.5-1 мс, извлечение рёбер ~0.1 мс. Итого **1.5-3 с в один поток**, 0.6-1 с на четырёх воркерах; вставка 20-50 тыс. рёбер через `COPY` — ещё 0.3-0.5 с. Инкрементальный шаг на один файл — 5-15 мс.

Проблемой это станет, когда полная пересборка перевалит за 10 с: ~3000-5000 файлов, либо крупные строки датасетов, залитые в файлы вопреки §6. Лечение на этом рубеже известно заранее и не требует переделки схемы — кеш разбора по `content_hash`: пересборка вырождается в «stat + хеш» (sha256 ~500 МБ/с, 100 МБ дерева — 0.2-0.3 с) и разбор только реально изменившихся файлов.

## 5. Расхождение индекса и файлов

Расхождение — норма, а не авария: между записью файла и событием watcher'а всегда есть окно. Ловим по `idx.files.content_hash`, дешёвый предфильтр — `(size_bytes, mtime_ns)`.

| Класс операции | Правило |
|---|---|
| Чтение множества (список, поиск, «где используется») | отвечаем по индексу сразу, ответ помечен `generation` и `indexed_at`; хеши не сверяем — это было бы чтением всех файлов |
| Чтение содержимого | индекс не используется вовсе: читаем файл |
| Действие (компиляция, патч, запуск, применение патчей влияния) | перед действием сверяем хеши затронутых файлов; расхождение — синхронная переиндексация этих файлов и одна повторная попытка; повтор не сошёлся — отказ `INDEX_STALE` с путями |
| Анализ влияния и гейт | принудительный reconcile всего проекта до отчёта: отчёт ведёт к BLOCK, он обязан быть по текущим файлам |
| Индекс недоступен или `status='degraded'` | операции чтения множеств деградируют до обхода файлов (медленно, но верно), запись и запуск не блокируются |

**Человек видит**: в Studio — счётчик «индексируется: N файлов» и пометка «по индексу поколения N» на списках; на действии с расхождением — не ошибку, а прозрачную паузу на переиндексацию; отказ `INDEX_STALE` показывается с путём файла и кнопкой «переиндексировать». Формулировка «индекс говорит одно, файл другое» не может привести к неверному результату ни в одном сценарии, потому что индекс нигде не является ответом на вопрос «что написано».

## 6. Что остаётся в базе источником истины

| Сущность | Почему не файл |
|---|---|
| `runs`, `run_nodes`, `checkpoints`, `run_lineage` | миллионы строк в сутки, партиционирование по времени, запись идёт из рантайма параллельно |
| Трассы и метрики (Langfuse, [ADR-0012](../adr/0012-langfuse-as-store.md)) | внешнее хранилище событий, диффу не подлежат |
| `cassettes`, `cassette_entries` | привязаны к хешам схем и записей, объём растёт от прогонов, не от правок |
| `scores`, `judge_calibrations`, разметка | порождаются прогонами и людьми асинхронно, версионируются собственной осью |
| `human_tasks`, `tool_effects`, `journal`, `access_log` | журнал событий и аудит: append-only, правка руками недопустима по определению |
| `blobs`, `embeddings` | бинарь и векторы; переиндексация эмбеддингов — не правка определения |
| Раскладка канваса | LWW-канал, своя ось `layout_rev`, вне определения ([31](../31-canvas-editing.md)) |

**Датасеты — раздельно.** Метаданные (`name`, `schemaRef`, описания сплитов, политика происхождения, `storage`) — файлом: они часть контракта гейта, их правят руками и обязаны диффаться. Строки — в `app.dataset_items`: их порождают прогоны (`source_run_id`), их тысячи-миллионы, на них ссылается `experiment_items` внешним ключом, они содержат пользовательские данные с политикой хранения и часто дописываются **во время** прогона. Файл, который растёт от исполнения, — не артефакт ревью.

Исключение одно и оно ограничено конструкцией: `storage: rows_in_file` для golden-наборов — не больше 500 строк и 1 МБ, рядом с метаданными в `.jsonl`. Такие наборы определяют ожидаемое поведение, и их дифф в PR — главная ценность. Валидатор отклоняет превышение лимита с предложением перевести набор в `rows_in_db`. Для замороженной под гейт версии в метаданные пишется `frozen: sha256-…` по канонизированному содержимому строк — гейт становится воспроизводимым, а подмена строк в базе видна как расхождение хеша. Экспортный бандл ([18](../18-export-and-conformance.md)) материализует строки в обоих случаях.

## Крайние случаи

| Ситуация | Поведение системы | Что видит человек |
|---|---|---|
| YAML не разбирается | `parse_status='invalid'`, прежние объекты и рёбра сохранены, файл исключён из компиляции | файл красный в дереве, текст ошибки с позицией; остальной проект работает |
| Два файла объявляют один `key` | оба в `idx.objects` нельзя — побеждает лексикографически первый путь, второй помечается `duplicate_key`, компиляция проекта блокируется | ошибка с обоими путями, предложение переименовать |
| Файл удалён, на него есть ссылки | объект и исходящие рёбра удалены, входящие висят | отчёт «битые ссылки»: кто ссылался и откуда |
| Ветка переключена во время запроса | запрос дочитывается по старому поколению, следующий — по новому | список мигает один раз, пометка поколения меняется |
| `ENOSPC` на inotify, лимит watcher'ов | переход на `chokidar` в polling-режиме, `status='degraded'` | предупреждение «слежение за файлами деградировало, индекс обновляется раз в N с» |
| Регистронезависимая ФС: `Order.yaml` и `order.yaml` | коллизия ключей ловится на индексации как `duplicate_key`, а не на деплое в Linux | ошибка локально, до пуша |
| Симлинк наружу проекта, огромный файл (> 5 МБ) | не индексируется, `parse_status='unreadable'` | файл в списке пропущенных с причиной |
| Индекс пуст, БД поднялась чистой | первый запрос запускает полную пересборку, `status='building'` | прогресс-бар, списки доступны по завершении |

## Открытые вопросы

1. **Один индекс на ветку или на рабочую копию.** git worktree даёт два дерева одного проекта одновременно; ключ `project_id` этого не различает. Кандидат — `workspace_id` = хеш абсолютного пути рабочей копии.
2. **Кто владеет watcher'ом**, когда одновременно запущены сервер, Studio и Claude Code. Кандидат — advisory-lock в Postgres на `project_id`, остальные читают.
3. **Ранжирование глобального поиска**: `ts_rank` против триграммной похожести против гибрида с эмбеддингами (`app.embeddings` уже есть) — решать после первого замера на реальном проекте.
4. **Порог полной пересборки** (25% дельты) взят из здравого смысла, не из замера; проверить на реальном `git pull` с сотней изменённых файлов.
