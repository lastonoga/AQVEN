# Внешние правки: человек, git, Claude Code

> Решает: файл проекта меняется мимо системы — как это заметить, пережить и не потерять инварианты.

## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Как внешняя правка попадает в систему | не запись файла в БД, а `flow_patch` от актора `fs:<hash>` / `git:<sha>` с `base_rev` = ревизия последней синхронизации файла | одна точка записи, один валидатор, один op-log; ровно протокол [research/git-bidirectional.md §«git — ещё один актор»](../research/git-bidirectional.md) |
| Обнаружение | нативный fs-watcher + дебаунс 250 мс + сверка `content_hash`; git-операции ловятся по `.git/HEAD`, `ORIG_HEAD`, `index` и дают **один** батч, а не N событий | `git pull` трогает сотни файлов за миллисекунды; пофайловая реакция даст шторм патчей |
| Защита от петли | writer кладёт ожидаемый `content_hash` в outbox; событие с совпавшим хешем — no-op | анти-луп Windmill `[WM]`, без него push→pull→push |
| Канвас при внешней правке | молчаливое применение с атрибуцией `fs`/`git` (штриховая обводка, как у агента); плашка — только при пересечении с несохранённым жестом; блокировки нет никогда | блокировка канваса на чужой коммит — прямой путь к потере работы человека |
| Битый файл | карантин файла, не проекта: в индексе остаётся `last_good`, файл помечен `quarantined`, соседи работают | «проект не грузится из-за одной запятой» — неприемлемо для инженерного инструмента |
| Прогон из битого/карантинного файла | запрещён из рабочей копии, **разрешён из опубликованного релиза** — релиз иммутабелен и лежит в БД | файл сломан, продакшн жив |
| Валидация на старте | дешёвый скан (stat + hash) обязательно, парс и компиляция — лениво по обращению плюс фоновый прогрев | полная компиляция 2 000 файлов на каждый старт — секунды простоя ради данных, которые почти никто не спросит |
| Правка во время прогона | прогон пинится на `spec_version_id`, снятый в момент старта; файл дальше меняется свободно | Airflow `dag_run.created_dag_version_id`, Argo `status.storedWorkflowSpec`, Flyte «continues unhindered» ([research/git-orchestrators.md](../research/git-orchestrators.md)) |
| Повторный запуск и replay | по умолчанию **исходная** версия прогона; «на текущей» — явное действие | урок Airflow: `clear` из UI берёт latest, из API — исходную, и это источник путаницы |
| Правка во время правки | импорт проходит тот же ребейз `pendingIntents`, что и поток агента ([31 §Одновременность](../31-canvas-editing.md)) | внешняя правка для клиента неотличима от правки агента, отдельного кода не пишем |
| Маркеры конфликта в файле | отдельный класс `MERGE_CONFLICT_MARKERS`, не «битый YAML»: экран разрешения по путям IR, результат пишется через `flow_patch` | Appsmith #14498: пользователь чинит граф текстовым редактором — этого не повторяем |
| merge-драйвер git | поставляем, но как UX; корректность держит валидатор после merge | драйвер живёт в `.git/config`, на сервере GitHub/GitLab не работает ([research/git-merge-structured.md §1](../research/git-merge-structured.md)) |

## 1. Обнаружение и путь импорта

Конвейер один на все источники внешней правки:

```
fs event -> debounce 250ms -> read + hash -> hash == expected? -> drop
                                          -> parse + canonize -> semantic diff vs serverDoc
                                          -> ops[] -> flow_patch(actor, base_rev) -> validator -> rev++
                                          -> SSE delta -> canvas
```

| Источник | Триггер | Латентность до канваса | Гранула патча |
|---|---|---|---|
| Редактор (save) | событие файла | 250–400 мс | один файл = один патч |
| `git pull` / `checkout` / `rebase` | `.git/HEAD` или `ORIG_HEAD` изменились | 300–800 мс на сотню файлов | один батч, `actor: git:<sha>`, `exclusive: true` |
| Claude Code через Write/Edit | событие файла, плюс хук `PostToolUse` даёт результат агенту синхронно | 250–400 мс | один файл = один патч |
| Правка вне watcher (ssh, `docker cp`) | не ловится; подхватится ленивой сверкой хеша при первом обращении | до первого обращения | то же |

Три правила, без которых конвейер разваливается:
1. **`base_rev` файла хранится**: `spec_fs_sync(spec_id, path, last_synced_rev, last_content_hash, mtime, size)`. Без него импорт не отличает «файл уехал вперёд» от «БД уехала вперёд».
2. **Атомарность чтения.** Пишут все через `rename()` временного файла; читаем целиком и только после тишины 200 мс — частично записанный файл не диагноз.
3. **Раскладка не импортируется как спека.** `*.layout.json` идёт своим LWW-каналом (`flow_layout_set`), `rev` не двигает, в `content_hash` не входит ([31 §Два канала](../31-canvas-editing.md)).

Канвас реагирует по состоянию клиента, а не по источнику события:

| Состояние клиента | Что делает канвас |
|---|---|
| Нет `pendingIntents`, диффы не пересекаются | молчаливое применение, штриховая обводка, бейдж `git`/`file` |
| Есть `pendingIntents`, пути не пересекаются | авто-ребейз, ничего не спрашиваем |
| Пересечение путей | плашка «в git — X, у вас — Y», три исхода: принять чужое / оставить своё / разобрать по путям |
| Батч > 200 операций либо > 10 ревизий | полный `flow_get`, плашка «проект обновлён из git (47 файлов)», ссылка на семантический дифф |
| Импорт отклонён валидатором | канвас не меняется вовсе, плашка «файл `X` не принят», список `problems[]` |

## 2. Невалидный файл: карантин вместо падения

Четыре уровня поломки, и обращаются они по-разному:

| Уровень | Пример | Что с файлом | Что с проектом |
|---|---|---|---|
| L0 нечитаемый | нет прав, обрыв диска | `unreadable`, показываем ошибку ОС | ничего |
| L1 синтаксис | сломанный YAML, маркеры merge | `quarantined`, в индексе живёт `last_good` | ничего, кроме этого воркфлоу |
| L2 схема | лишнее поле, `type` не из реестра | `quarantined`, плюс точная позиция (строка/колонка из парсера с якорями) | ничего |
| L3 семантика | цикл вне `loop`, `TYPE_MISMATCH`, неполный `switch` | `invalid`, IR разобран и виден на канвасе **в красном**, запуск запрещён | потребители компонента → `degraded` |

**Что значит «проект частично сломан».** Индекс держит две колонки на спеку: `current` (что в файле) и
`last_good` (последняя скомпилированная версия). Запуск, экспорт и `component_expand` берут `last_good`
только с явного согласия («запустить последнюю рабочую версию»); по умолчанию отказ с `problems[]`.
Всё остальное в проекте — поиск, анализ влияния, компиляция соседей, прогоны других воркфлоу,
опубликованные релизы — работает без оговорок, потому что зависит от индекса, а не от разбора файла.

Каскад — один шаг с ослаблением: битый **компонент** делает потребителей `degraded` (запуск на
закреплённой версии из `component_lock` плюс предупреждение), битый **воркфлоу** не заражает никого.
В шапке проекта счётчик `2 файла в карантине` с путями и первой проблемой каждого.

## 3. Валидация на загрузке: два уровня, ни одного полного прохода

| Что | Когда | Стоимость на 2 000 файлов | Что даёт |
|---|---|---|---|
| Скан: `stat` + хеш содержимого, сверка с `.aqven/cache/index.json` | старт, обязательно | 120–200 мс | список изменившихся файлов, карта путей, глобальный поиск живой |
| Парс + схема (L1–L2) | лениво при первом обращении; фон прогревает очередь | 3–6 мс на файл | позиции ошибок, автодополнение |
| Компиляция (L3) | лениво; при старте — только для открытых в Studio | 20–40 мс на воркфлоу | запуск, экспорт, анализ влияния |
| Полный проход всего проекта | `aqven check`, pre-commit, CI, публикация релиза | 15–40 с | гарантия «весь проект валиден» |

Кеш индекса — производная: потерян или устарел по версии схемы — пересобираем, те же 200 мс.
Порядок прогрева: открытые вкладки → их зависимости → общая библиотека → остальное.

## 4. Правка во время прогона: прогон пинится, файл свободен

Механизм — «вкопанный спек» Argo плюс FK Airflow, у нас обе детали уже есть в модели данных:

1. Старт прогона компилирует текущую рабочую копию и материализует `spec_versions` с
   `origin: 'working_copy'`, `content_hash`, `release_hash`. Одинаковый хеш переиспользует строку.
2. `runs.spec_version_id` — NOT NULL FK. Дальше прогон читает **только** БД; файл ему не нужен.
3. Внешняя правка файла в это время идёт обычным импортом и не касается прогона. В ленте прогона
   появляется пометка «определение изменилось на `rev 52`, прогон идёт на `rev 49`».
4. `run_replay_node`, `run_resume` и повтор берут `spec_version_id` прогона. Запуск на текущей версии —
   отдельный, явный, называется «запустить заново на текущей», и это новый прогон, не продолжение.
5. Ретенция `working_copy`-версий: TTL 30 дней после завершения прогона, но не раньше, чем истечёт
   ретенция самого прогона; версии, на которые ссылается релиз или датасет, не удаляются никогда.

Половинчатого прогона, как у Airflow с неверсионированным бандлом, быть не может: версия снимается
один раз на прогон, а не на задачу. Недетерминизма Temporal тоже нет — мы не реплеим код, мы храним IR.

## 5. Правка во время правки: жест переживает `git pull`

Сценарий «мышь зажата, приехал коммит» разбирается штатной машинкой из [31](../31-canvas-editing.md),
новой семантики не добавляем:

| Что делает человек | Что привёз импорт | Исход |
|---|---|---|
| Тащит узел (канал раскладки) | правку полей того же узла | обе применяются: разные оси версий, пересечения нет |
| Тащит узел | удаление этого узла | позиция отброшена, узел — призрак, тост «вернуть» (создаст узел заново новым патчем) |
| Печатает в инспекторе, не закоммитил | правку того же поля | поле помечено `conflicted`, показаны оба значения, черновик человека не стирается |
| Тянет ребро, диалог открыт | смену `schemaId` источника | отказ `TYPE_MISMATCH` при коммите жеста + `candidates[]` |
| Выделил 12 узлов, жмёт «в компонент» | любую правку внутри выделения | эксклюзивная операция проигрывает, UI предлагает повтор на новой `rev` |

Правило: пока кнопка мыши нажата, применение отложено — `serverDoc` обновлён, проекция нет; импорт
никогда не стирает несохранённый ввод молча, максимум помечает его конфликтующим.

## 6. Комплект для Claude Code

Агент правит файлы напрямую — это целевой сценарий, а не обход. Инварианты держим четырьмя вещами:

| Средство | Что даёт | Где живёт |
|---|---|---|
| JSON Schema 2020-12, генерируется из IR ([04 §2](../04-ir-schema.md)) | `$schema` в шапке файла: агент и редактор ловят L1–L2 **до** записи | `.aqven/schema/*.json`, версия схемы в имени |
| `aqven check [пути] --format json` | полная проверка L1–L3 тем же компилятором, что и сервер; `problems[]` в том же формате, что в MCP; exit-код | пакет `@aqven/cli` |
| `aqven fmt` / `aqven fmt --check` | канонический YAML (round-trip, kill-критерий 13) — убивает классы конфликтов «порядок ключей» и «стиль» | там же |
| Хук `PostToolUse` на `Write`/`Edit` по маске `**/*.flow.yaml` | агент получает `problems[]` сразу после своей записи, в том же ходу, без опроса | `.claude/settings.json` проекта |
| Хук `pre-commit` (`aqven check --staged` + `aqven fmt --check` + детектор маркеров) | битое не уезжает в ветку | `.githooks/`, ставится `aqven init` |
| Секция в `CLAUDE.md` проекта, генерируемая `aqven init` | правила словами: править файлы можно; после правки — `aqven check`; `*.layout.json`, `.aqven/cache/`, `dist/` не трогать; `uses:`-пины руками не редактировать — `aqven pin`; на конфликт путей звать человека | корень проекта |

MCP остаётся первоклассным, а не запасным: `flow_patch` проверяет **до** записи и даёт кандидатов
исправления, `aqven check` — после. Агенту, который умеет только файлы, хватает файлов; агенту, которому
нужны кандидаты и анализ влияния, — MCP. Ядро компилятора одно, расхождение диагностик исключено
конформанс-тестом «`aqven check` и `flow_compile` на одном входе дают идентичный `problems[]`».

## 7. Маркеры merge-конфликта в файле

Парсер ловит `<<<<<<<` / `=======` / `>>>>>>>` **до** YAML-разбора и даёт отдельный код
`MERGE_CONFLICT_MARKERS` — это не «битый файл», а известная ситуация с известным разрешением:
файл в карантин, обе стороны разбираются как отдельные документы, человеку показывается
семантический дифф по путям IR (не по строкам), исход на путь — «наше / их / вручную»;
выбранное пишется одним `flow_patch`, файл перезаписывается каноническим `aqven fmt`.
Разобрать не удалось (маркеры внутри блочного скаляра, вложенный конфликт) — честно говорим
«разрешите в редакторе», ссылка на `git checkout --ours/--theirs`, в БД ничего не меняется.
Поставляем `.gitattributes` с `merge=aqven` и драйвером поверх `aqven merge` — сокращает частоту
ручных разрешений, но на инварианты не влияет: проверяет их валидатор после merge, не драйвер.

## Крайние случаи

| Ситуация | Поведение системы | Что видит человек |
|---|---|---|
| `git checkout` другой ветки, 300 файлов | один батч-импорт, `exclusive`, ELK один раз | «проект обновлён из git» + ссылка на дифф |
| Файл удалён внешне | спека помечена `missing`, из индекса не стирается, прогоны и релизы живы | «файл удалён, восстановить или удалить спеку» |
| Два файла с одним `spec_id` | оба в карантин, ни один не побеждает | «дубль `spec_id`, разведите» |
| Правка во время прогона | прогон доигрывает на `spec_version_id` старта | «идёт на `rev 49`, в файле `rev 52`» |
| Внешняя правка `*.layout.json` | LWW-канал, `rev` и хеши не трогает | узлы переехали, история пуста |
| Агент записал файл через Write, минуя MCP | `PostToolUse` вернул `problems[]`, импорт прошёл обычным путём | правка агента со штриховой обводкой |
| Watcher умер (лимит inotify, сетевой FS) | переход на поллинг хешей раз в 5 с, баннер деградации | «обновления с задержкой» |
| Маркеры конфликта закоммичены и запушены | CI-джоба `verify` падает на `aqven check` | красный PR, не красный прод |
| Битый файл на prod-проекте | `flow_patch` там запрещён вовсе; прогоны идут из релизов | prod не замечает |

## Открытые вопросы

1. Гранула файла (один YAML на воркфлоу против каталога «файл на узел») меняет частоту merge-конфликтов
   на порядок — решается в срезе раскладки файлов, здесь принято «как решат там».
2. Порог батча (200 операций / 10 ревизий) взят из [31](../31-canvas-editing.md) и не измерялся на git-импорте.
3. Переключение ветки с незакоммиченными правками в Studio: предлагать стеш или блокировать.
