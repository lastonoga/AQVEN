# Модель записи и конкурентность на файлах

> Решает: как два редактора — человек и агент — пишут в один каталог проекта без потери правок, без текстового merge и без полуприменённых изменений.

## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Владелец рабочей копии | каталог проекта пользователя; сервер — локальный процесс внутри него, зеркала нет | инженер грепает, диффает и правит те же файлы; копия на сервере вернула бы БД-как-истину через заднюю дверь |
| Замена `base_rev` | CAS по `file_hash` (sha256 байт файла), `expects[]` на каждый затрагиваемый путь | версия больше не глобальный счётчик; истина — содержимое файла |
| Конфликт | CAS отбивает запись, ребейз идёт по IR-операциям, не по тексту | текстовый merge ломает инварианты — прямой запрет заказчика |
| Транзакция N файлов | staging-каталог + журнал намерения + `rename(2)` + `fsync` каталогов | ФС не даёт транзакций; roll-forward после краха даёт ту же гарантию «всё или ничего» |
| Единственный писатель | межпроцессный `.aqven/lock` (O_EXCL + pid + ttl) | два сервера на одном каталоге — реальный сценарий (Studio + Claude Code) |
| Валидация | in-memory на дереве проекта, до сериализации; на диск попадает только прошедшее | «файловое хранение не означает пишем что попало» |
| Частичная валидность | два класса диагностик: `blocking` не пишется, `advisory` пишется и метит воркфлоу нерабочим | промт правят итеративно, он обязан иметь право быть временно неполным |
| Промт | явный коммит; черновик — в `.aqven/drafts/`, вне дерева определений и вне git | решение заказчика; черновик переживает перезагрузку вкладки, но не притворяется определением |
| Правки агента | пишутся сразу, коалесинг только внутри одного `flow_patch` | буфер на сервере сломал бы главное: агент читает файл и обязан видеть свою правку |

## 1. Кто владеет рабочей копией

| Вариант | За | Против | Вердикт |
|---|---|---|---|
| Каталог проекта пользователя, сервер работает в нём | грепается, диффается, Claude Code правит напрямую; нет синхронизации двух истин | нужен межпроцессный lock и watcher; общий доступ команды — через git, не через сервер | **основной режим `local`** |
| Рабочее дерево на сервере (модель Appsmith) | один писатель, простая конкурентность, готов к multi-tenant | пользовательский каталог становится вторичным — ровно то, от чего уходим; синк = второй источник правды | режим `hosted`, вторым приоритетом |

Одна абстракция на оба: порт `ProjectStore` (`read(path) → {bytes, file_hash}`, `commit(txn)`, `watch()`),
реализации `LocalFsStore` и `ServerWorkspaceStore`. Выше порта — компилятор, MCP-слой, Studio: они
не знают, где лежат байты. Сетевого протокола между ними нет: `hosted` — тот же код с другим корнем.

## 2. CAS вместо `base_rev`

Три хеша, которые нельзя путать:

| Хеш | От чего | Зачем |
|---|---|---|
| `file_hash` | sha256 **байт файла на диске** | оптимистическая блокировка записи; сравнивается с тем, что перезаписываем |
| `spec_hash` | канонический IR без `ui`/`meta` ([04](../04-ir-schema.md) §4.4) | идентичность версии, релиз, сравнение «та же ли это спека» |
| `tree_hash` | sha256 отсортированного списка `path → file_hash` | «состояние проекта целиком»: SSE-курсор, кэш индекса, ответ `flow_get` |

Протокол записи:

```json
{
  "op": "flow_patch",
  "expects": [
    { "path": "workflows/intake/flow.yaml", "file_hash": "sha256-a91f…" },
    { "path": "prompts/intake/classify.md", "file_hash": null }
  ],
  "ops": [ … ],
  "idempotency_key": "01JB…"
}
```

`file_hash: null` — «файла не должно существовать» (создание). Сервер под `.aqven/lock` пересчитывает
хеши всех путей из `expects[]` непосредственно перед staging; расхождение — отказ до единого изменения.

| Код | Условие | Что дальше |
|---|---|---|
| `STALE_FILE` | хеш на диске ≠ `expects[].file_hash` | конверт `conflict { path, your_hash, current_hash, ops_since[], rebase: 'auto' \| 'manual', rebased_ops[] }` — прежний блок [14](../14-mcp-contract.md) §9.2, сменился только ключ |
| `FILE_VANISHED` | ожидали хеш, файла нет | ребейз невозможен: путь удалён внешне, вопрос человеку |
| `FILE_EXISTS` | ожидали `null`, файл есть | коллизия имён; `candidates[]` с вариантами имени |
| `LOCK_BUSY` | `.aqven/lock` держит другой процесс | ретрай с backoff, после 3 попыток — read-only плашка |
| `TREE_DIRTY` | `tree_hash` разъехался после последнего `flow_get` | клиент перечитывает проект, `pendingIntents` переигрываются |

**Ребейз остаётся семантическим.** CAS защищает от потери байтов, но два актора, правящие разные узлы
одного `flow.yaml`, байтово конфликтуют всегда. Поэтому на `STALE_FILE` сервер перечитывает файл,
переигрывает `ops` на новом IR и авто-принимает, если множества путей операций не пересекаются
и все читаемые `id` живы. Иначе `rebase: 'manual'`. Текстовый трёхсторонний merge не применяется нигде.

Дробность CAS = дробность файла. Чем мельче файлы ([layout.md](layout.md)), тем реже ложный
`STALE_FILE`; это аргумент раскладки, а не модели записи.

## 3. Транзакция на несколько файлов

Переименование узла меняет `flow.yaml`, два промта и ссылку в компоненте. Три из четырёх на диске —
битое состояние. Механизм — журнал намерения плюс атомарная публикация:

| Фаза | Действие | Гарантия |
|---|---|---|
| 1. lock | захват `.aqven/lock` (O_EXCL, содержит pid + ttl 30 с + heartbeat) | единственный писатель в каталоге |
| 2. check | пересчёт `expects[]` | никто не обогнал |
| 3. stage | полные новые версии всех файлов в `.aqven/txn/<ulid>/`, `fsync` каждого, `fsync` каталога txn | байты на диске раньше, чем решение «коммитим» |
| 4. intent | запись `intent.json { targets[], renames[], created_at }`, `fsync`, затем `fsync` каталога | **точка невозврата**: есть intent — транзакция обязана завершиться |
| 5. publish | `rename(2)` каждого staged-файла на целевой путь, затем `fsync` каждого каталога-родителя | каждый файл заменяется атомарно |
| 6. clear | `unlink` intent, снос `.aqven/txn/<ulid>`, релиз lock | след убран |

Восстановление при старте: каталог `.aqven/txn/*` с `intent.json` → **roll-forward** (повторить renames;
они идемпотентны, staged-файлы полные). Без `intent.json` → **roll-back** (снос каталога). Оба случая
дают тост «восстановлена незавершённая правка», а не молчаливое расхождение.

Чего механизм не даёт: мгновенной атомарности **для внешнего читателя**. Между renames есть окно в
единицы миллисекунд, где `grep` увидит половину. Внутренние читатели идут через `ProjectStore` и держат
read-lock, поэтому не видят его; git-коммит делается после фазы 6. Считаем окно приемлемым: цена
альтернативы (свой оверлей поверх ФС) убивает главное свойство — «это просто файлы».

Платформенное: на Windows `rename` поверх существующего — `ReplaceFileW`, `fsync` каталога недоступен,
порядок гарантируется только флагом write-through на файлах. Порт `ProjectStore` прячет разницу.

## 4. Валидация до записи

```
parse(diff) → apply ops к in-memory дереву → validate(IR) → canonicalize → serialize
   → CAS check → stage → intent → rename → reindex (БД) → SSE
```

Валидатор стоит **до сериализации** и работает на всём дереве проекта, а не на одном файле: цикл вне
`loop`, несовместимость типов портов, неполный `switch`, висячая ссылка на промт — межфайловые инварианты,
их не проверить, глядя на один документ. `dry_run` — тот же конвейер до фазы CAS.

| Класс | Примеры | Поведение |
|---|---|---|
| `blocking` | цикл вне loop, тип порта, неполный switch, ссылка на несуществующий узел/промт, дубль имени | запись отклонена целиком, `problems[]` + `candidates[]`, диск не тронут |
| `advisory` | неразрешённая переменная в шаблоне, пустой промт, несвязанный слот, TODO-узел | записывается; воркфлоу получает статус `not_runnable`, запуск и сборка релиза отказывают |

Граница ровно одна: **ломает ли невалидность чужие файлы**. Локальная неполнота внутри своего файла —
`advisory` (иначе итеративная правка промта невозможна). Нарушенная ссылочная целостность или инвариант
графа — `blocking`. Диагностики живут в индексе, не в файле: файл остаётся чистым и диффабельным.

## 5. Явный коммит промта

Текст сохраняется командой (`Cmd+S` / кнопка), не по blur и не по таймеру.

| Аспект | Решение |
|---|---|
| Где черновик | `.aqven/drafts/<путь>.draft` + `.meta.json { base_file_hash, updated_at, actor }`; каталог в `.gitignore`, вне дерева определений |
| Почему файл, а не только память вкладки | переживает перезагрузку и падение; виден агенту как «этот промт кто-то правит»; но не притворяется определением и не попадает в индекс как версия |
| Запись черновика | debounce 1 с, LWW, без компилятора; `advisory`-диагностики считаются на лету и показываются |
| Уход со страницы | ничего не теряется и ничего не блокирует: `beforeunload` не вешаем, при возврате плашка «черновик от 14:02, база — на диске» с кнопками «продолжить» / «отбросить» |
| Сохранение | `expects: [{path, file_hash: base_file_hash}]` → обычный конвейер §4 → `.draft` удаляется в фазе 6 той же транзакции |
| Агент переписал тот же файл | черновик не трогается; при Save — `STALE_FILE` и трёхпанельный дифф (черновик / база черновика / диск) с выбором «моё» / «диск» / «открыть в редакторе». Автослияния текста нет |
| Агент через MCP | черновиков не имеет: любая его правка — сразу коммит |

## 6. Очередь правок агента

Пишем сразу. Коалесинг ровно один: `flow_patch(ops[1..50])` — одна транзакция §3, один набор renames,
одно событие. Тридцать правок агента — это 2-4 вызова `flow_patch`, а не 30 транзакций.

Почему без серверного буфера: агент в Claude Code читает файлы напрямую (`cat`, `grep`). Отложенная
запись означает, что он не видит собственной правки — рушится главное свойство файловой модели.
Стоимость известна: `fsync` на транзакцию — единицы миллисекунд, порядок десятков транзакций в ход.

Канвас не меняет поведение из [31](../31-canvas-editing.md): режимы `live` / `batched` (по умолчанию) /
`paused` — это **визуальная** буферизация, сервер применил всё немедленно. Бейдж «показано на
`tree_hash` X · на диске Y» висит всё время отставания. ELK пересчитывается один раз на батч.

Watcher обязан отличать свои записи от чужих: пути транзакции попадают в `selfWrites` с ожидаемым
`file_hash`, событие с совпадающим хешом гасится. Иначе — петля «записал → увидел → переиндексировал →
разослал». Это тот же приём, что префикс коммитов синка у Windmill ([ADR-0016](../adr/0016-git-as-release-boundary.md)).

## Крайние случаи

| Ситуация | Поведение системы | Что видит человек |
|---|---|---|
| Второй процесс сервера на том же каталоге | `.aqven/lock` не взят → read-only режим, чтение и индекс работают | плашка «каталог занят Studio (pid 4821)», кнопка «перехватить» после ttl |
| Крах между renames | при старте roll-forward по `intent.json` | тост «правка «переименование node.classify» дописана» |
| `ENOSPC` / `EACCES` на фазе 3-4 | откат, ни один целевой файл не изменён | ошибка записи с путём и причиной, черновики целы |
| Человек и агент правят разные узлы одного файла | второй получает `STALE_FILE`, авто-ребейз, прозрачный retry | ничего, кроме чужой правки на канвасе |
| Человек и агент правят один путь | `rebase: 'manual'` | два значения на выбор |
| Внешний редактор сохранил файл (свой atomic rename) | watcher видит новый `file_hash`, индекс обновлён, открытый черновик помечен устаревшим | бейдж «изменён вне Studio», подробности — [external-edits.md](external-edits.md) |
| `git checkout` другой ветки под работающим сервером | массовое событие watcher → полный reindex, черновики сохраняются | «проект перечитан: 14 файлов» |
| Промт временно без переменной | записан, `advisory`, воркфлоу `not_runnable` | жёлтый бейдж на узле, кнопка «Запустить» заблокирована с причиной |
| Переименование узла (4 файла) прерывается валидатором на 4-м | не записано ничего | `problems[]` с указанием на конфликтующую ссылку |

## Открытые вопросы

1. Гранулярность CAS зависит от [layout.md](layout.md): один `flow.yaml` на воркфлоу даёт ложные `STALE_FILE` при параллельной правке разных узлов — терпим ли, или узлы отдельными файлами.
2. Нужен ли `.aqven/lock` per-project или per-root в режиме `hosted` с несколькими тенантами в одном дереве.
3. TTL и уборка `.aqven/drafts`: чистить по возрасту, по факту совпадения с диском, или не чистить.
4. Группировать ли `fsync` при агентском шторме (> 20 транзакций в секунду) ценой окна потери в 1-2 правки.
5. Коммит в git — на каждую транзакцию или только на релиз ([ADR-0016](../adr/0016-git-as-release-boundary.md) говорит второе); от этого зависит, где живёт история «кто сделал» — см. [history.md](history.md).
