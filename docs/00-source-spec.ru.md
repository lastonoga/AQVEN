# Платформа для надёжных AI-воркфлоу — архитектурный план v0.5

> Статус: черновик для обсуждения и передачи в разработку, в том числе Claude Code.
> Язык: русский; идентификаторы — английские.

## 0. Коротко

- **Что строим.** Платформу, в которой Claude или любой MCP-агент собирает, запускает, отлаживает и в цикле чинит многошаговые LLM-воркфлоу: 15+ шагов, параллелизм, дивергенция, конвергенция, циклы. Человек видит всё визуально, настраивает модели и агентов, пишет evals.
- **Главная идея.** Агент не пишет код оркестрации — он редактирует типизированную спеку через операции. Спека — программа на языке с жёсткими рамками: маленькое ядро примитивов, а судьи, циклы, панели и агенты — не встроенные сущности, а компоненты, которые видно, правится и расширяется (§6.0). Промты агент пишет свободно, но как типизированные шаблоны: текст его, а данные, формат и динамику контролирует платформа (§7.6).
  - Компилятор не пропускает типовые ошибки.
  - Рантайм гарантирует формат вывода, провенанс и бюджеты.
  - Гейты не выпускают непроверенное.
- **Ядро доверия — это и есть продукт.** Своими руками строятся IR, реестры, компилятор, интерпретатор и контракт для агентов. Провайдеры, constrained decoding, durable execution, трассы, evals и канвас — готовые кирпичи.
- **Выбран вариант C — своё ядро исполнения.** Гарантии живут в исполнителе. В чужом оркестраторе они превращаются в обёртки, а отладчик не видит твоих семантик (§4).
- **Каталог §8** — 87 типовых проблем; у каждой есть механизм и уровень гарантии.
- **Сквозной сценарий (§1.1).** Бриф → архитектура → контекст → воркфлоу → промты → судьи и циклы → визуальный ревью → датасеты → тест узла → тест воркфлоу → улучшение → выпуск.
- **Контекст первичен (§6.7).** Сначала — какой контекст нужен каждому решению, откуда он берётся и от чего зависит; промты пишутся потом.
- **Провайдеры (§7.7).** OpenRouter, Together AI и прямые API с синхронизацией каталога моделей, цен и проверенных возможностей; матрица моделей на узел (§12.2).
- **Агенты (§7.3).** Агент — набор настроек: модель, параметры, тулы, память, лимиты. Любое поле переопределяется на конкретном вызове; итоговая конфигурация видна с происхождением каждого поля.
- **Экспорт для воссоздания 1:1 (§15.1).** Бандл с нормативной семантикой ядра и конформанс-набором: любой LLM воссоздаёт воркфлоу в любом фреймворке, а записанные прогоны доказывают совпадение узел в узел. Для VoltAgent — готовый codegen.
- **Бэкенд на VoltAgent (§20).** Исполнение, агенты, память, MCP, сервер и трассировка — на VoltAgent. Наш слой — проекты и БД, компилятор, сборщик цепочек из IR, исполнители узлов с гарантиями, MCP для агентов, Studio.
- **Первый шаг** — спайк ядра на одном реальном 15-шаговом воркфлоу; kill-критерии в §18.

## 1. Цель и требования

**Цель.** Собирать сложные LLM-воркфлоу быстро и стабильно так, чтобы типовые ошибки агента и моделей были невозможны или гарантированно пойманы до прода.

| ID | Требование |
|---|---|
| R1 | Подключение к Claude и любому MCP-агенту; агент сам собирает, запускает, отлаживает и чинит воркфлоу |
| R2 | Визуальный граф — просмотр и правка; отладка прогона по узлам |
| R3 | Настройка моделей: провайдеры, параметры, фолбэки, лимиты, стоимость |
| R4 | Настройка агентов: тулы, память, саб-агенты, границы автономии |
| R5 | Пайплайны 15+ шагов: параллелизм, дивергенция, конвергенция, циклы, подворкфлоу |
| R6 | Агент не может сломать промты, схемы вывода и привязку контекста |
| R7 | Отладка: данные по узлам, отрисованный промт, происхождение каждого куска контекста, переигрывание |
| R8 | Типовые проблемы закрыты архитектурно (каталог §8) |
| R9 | Evals пишут и человек, и агент; цикл «тест → правка → проверка» |
| R10 | Переиспользование: воркфлоу как тул (MCP/HTTP), подворкфлоу по версии |
| R11 | Прод: устойчивость к сбоям, ретраи, ожидание людей, версии и откат |
| R12 | Агностичность: нет привязки к агенту, модели или провайдеру; рантайм заменяем за контрактом |
| R13 | Промты собираются программно из выходов шагов и данных БД/API, а не пишутся руками |
| R14 | Изменение enum предсказуемо распространяется по всей системе |
| R15 | Контекст первичен: для каждой задачи и решения описано, какой контекст нужен, откуда он берётся (статика, данные, база знаний, генерация, человек) и от чего зависит |
| R16 | Библиотека архитектур через MCP и свободная композиция своих |
| R17 | Судьи: правила, модели, панели из нескольких моделей, агрегация, разногласия |
| R18 | Циклы: генерация → проверка → доработка до закрытия задачи и другие паттерны |
| R19 | Датасеты генерирует Claude; тест отдельной задачи и всего воркфлоу с поэтапными результатами |
| R20 | Провайдеры OpenRouter, Together AI и другие: каталог моделей и цен, полноценная интеграция |
| R21 | Экспорт всего проекта для воссоздания воркфлоу 1:1 в любом фреймворке силами LLM; готовый экспорт в VoltAgent; конструктор production-воркфлоу без lock-in |
| R22 | Переопределение настроек агента (модель, параметры, тулы, память, лимиты) на каждом вызове |
| R23 | Бэкенд на VoltAgent: не писать рантайм с нуля; продукт — БД, настройки проекта и умная сборка воркфлоу VoltAgent для AI-агентов |
| R24 | Встроенные агенты внутри продукта — основа для продажи сервиса |

**Не цели v1:**
- 1000 интеграций уровня n8n;
- no-code для нетехнических пользователей;
- мультитенантный SaaS — архитектура ему не мешает, но в v1 его нет.

### 1.1. Сквозной сценарий

Идеальный путь от задачи до прода. Каждый этап даёт артефакт и имеет проверку; Claude проходит этапы через MCP, ты видишь всё в Studio.

| № | Этап | Что происходит | Артефакт | Проверка |
|---|---|---|---|---|
| 0 | Бриф | Ты ставишь Claude задачу: цель, спецификации, на что обратить внимание, разрешённые модели и провайдеры, бюджет, требования к качеству | `Brief` | Полнота: пробелы, меняющие структуру, превращаются в вопросы к тебе |
| 1 | Архитектура | Claude получает через MCP подходящие паттерны или собирает свою композицию | Решение с обоснованием в журнале | Совместимость с брифом: модели, бюджет, латентность |
| 2 | Потребности в контексте | Для каждой задачи и решения — какая информация нужна, чтобы решить правильно | `ContextNeed[]` | У каждого решения есть потребности (R-C1) |
| 3 | Источники контекста | Откуда берётся каждая потребность: статика, данные, база знаний, генерация, человек; зависимости между ними | Граф контекста | R-C2…R-C8 |
| 4 | Композиция воркфлоу | Шаги, ветки, параллелизм, дивергенция и конвергенция с привязкой контекста к решениям | IR | Правила §8 уровня L1 |
| 5 | Промты | Шаблоны LLM-узлов поверх слотов, представлений и фрагментов | Шаблоны | R-T1…R-T12 |
| 6 | Судьи и циклы | Правила и модели судей, панели из нескольких моделей, циклы «генерация → проверка → доработка» | Конфигурации панелей и циклов | R-J, R-L |
| 7 | Визуальный ревью | Ты смотришь граф управления, граф контекста, карту сборки промтов и статический отчёт по стоимости и лимитам | Аппрув дизайна (по желанию) | — |
| 8 | Датасеты | Claude генерирует датасеты на узлы и воркфлоу с целями покрытия; ты проверяешь выборку разметки | Датасеты со сплитами | Отчёт покрытия |
| 9 | Тест узла | Узел в изоляции на своём датасете; варианты шаблона и матрица моделей по провайдерам | Эксперимент узла | Скореры узла |
| 10 | Тест воркфлоу | Полный прогон на датасете: результаты каждой стадии, lineage, поиск виновного узла | Эксперимент воркфлоу | Гейты §12 |
| 11 | Улучшение | Claude читает провалы через MCP, правит промты, контекст, архитектуру или модели и доказывает эффект экспериментом | Предложение версии | Гейты §12 |
| 12 | Выпуск | Shadow, canary, мониторинг; прод-семплы возвращаются в датасеты | Версия в проде | L3–L4 |
| 13 | Экспорт (по необходимости) | Бандл для воссоздания 1:1 или codegen в VoltAgent; LLM воссоздаёт воркфлоу в целевом фреймворке и прогоняет конформанс-набор | Бандл, отчёт конформанса | Round-trip, конформанс 100% |

Этапы 2–3 идут раньше промтов: сначала понимаем, какой контекст нужен каждому решению и откуда он берётся, и только потом пишем текст.

## 2. Исходные факты и активы

**Рынок, сентябрь 2026:**
- Готового продукта, который закрывает весь цикл для типизированных LLM-пайплайнов, нет.
- **n8n.** Нативный MCP строит, валидирует и тестирует воркфлоу из любого клиента — хороший образец цикла. Но ветки исполняются последовательно, метрические evals ограничены тарифами, данные слабо типизированы.
- **Mastra.** JSON-воркфлоу (stored workflows, бета) с валидацией, Studio, датасеты и эксперименты через REST. Управляющего MCP для агентов нет.
- **Kestra.** MCP отдаёт агенту схемы тасков, поэтому спека валидна с первой попытки при серверной валидации. Образец для каталога узлов.
- **Langfuse.** Трассы, датасеты, эксперименты, очереди разметки, доступ агентов через MCP, CLI и skill; open source.
- **OpenAI Agent Builder** закрывается 30.11.2026, экспорт не переносит граф. Урок: источник правды — своя открытая спека.
- **Constrained decoding.**
  - Strict-режимы есть у основных провайдеров.
  - XGrammar — бэкенд по умолчанию в vLLM и SGLang.
  - С ограниченным декодированием 3B-модель обгоняет неограниченную 70B на BFCL.
- **CaMeL (Google DeepMind).** Интерпретатор отслеживает происхождение каждой переменной и гарантирует соблюдение политик ценой части гибкости.

**Твои активы:**
- **Опыт.** Десятки собранных воркфлоу, опыт с VoltAgent и Pydantic AI — знание, где именно всё ломается.
- **Фреймворк валидации LLM-выхода.** DynamicSchemaBuilder, стохастический консенсус и согласованность с ORM становятся рантайм-стражами (§10).
- **Скилл `agentic-process-spec`.** Девять вопросов на каждый шаг и правила валидности становятся входной дверью платформы и источником правил компилятора (§13.4).
- **Скилл `architecture-implementation-loop`** — образец цикла фикса с лимитом итераций (§13.3).

## 3. Принципы — инварианты платформы

1. **Топология — данные, узлы — контракты.** Воркфлоу — это типизированная спека (IR). Код живёт только в узлах `code` и `load` как чистые типизированные функции.
2. **Нет проверки — нет степени свободы.** Агенту доступно только то, что проверяет компилятор.
3. **Ядро доверия маленькое и детерминированное:** компилятор, интерпретатор, стражи, гейты. Агент, модели и внешние данные считаются недоверенными.
4. **Модель выбирает — код подставляет.** Факты из данных не генерируются: модель выбирает ID, текст фактов подставляет код.
5. **Всё воспроизводимо.** Каждый прогон записан, любой узел переигрывается, любая версия восстанавливается.
6. **Любое изменение — это версия, доказательство и аппрув.** Доказательство — эксперимент на датасете.
7. **Агностичность через контракт.** Интерфейс MCP/HTTP и адаптеры, а не «поддержка всего подряд».
8. **Агент владеет текстом, платформа — данными.** Промт пишет агент; подстановку данных, их представление, блок формата вывода и расшифровку enum делает только платформа.
9. **Маленькое ядро, всё остальное — композиция.** В ядре несколько примитивов и комбинаторов. Судьи, панели, циклы, каскады, агенты и архетипы — компоненты, собранные из них: логику видно до примитивов, её можно править и собирать новую.

## 4. Варианты архитектуры и выбор

### Вариант A — собрать из готового

n8n (нативный MCP) + Langfuse + BAML в Code-нодах.

- **Плюсы:** почти ничего не строить; цикл «собрал → проверил → прогнал» уже есть.
- **Минусы:**
  - последовательные ветки ломают дивергенцию;
  - нет типизированных слотов и провенанса;
  - гарантии держатся на договорённостях, а не на проверках;
  - evals ограничены тарифом;
  - лицензия допускает только внутреннее использование.
- **Риск:** потолок на первом же 15-шаговом пайплайне.
- **Когда выбирать:** только как интеграционную обвязку вокруг ядра.

### Вариант B — тонкий слой поверх Mastra

Свои IR, компилятор и MCP; исполнение — stored workflows Mastra.

- **Плюсы:** быстрее всего до работающего цикла; durability и Studio даром.
- **Минусы:**
  - две семантики исполнения: твоя в узлах, Mastra в графе;
  - join-политики кроме «все», провенанс и видимость делаются обёртками;
  - Studio показывает граф Mastra, а не твой IR;
  - зависимость от беты.
- **Риск:** гарантии протекают на стыке двух семантик.
- **Когда выбирать:** если нужно проверить только агентский цикл, а рантайм заведомо временный.

### Вариант C — своё ядро исполнения на готовых кирпичах

Свои IR, компилятор и интерпретатор; провайдеры, constrained decoding, durable execution, Langfuse и React Flow — готовые.

- **Плюсы:**
  - семантика спеки совпадает с семантикой исполнения;
  - провенанс, политики, бюджеты и record/replay нативны;
  - отладчик показывает ровно спеку;
  - настоящая агностичность.
- **Минусы:** больше кода в ядре; свой UI отладчика.
- **Риск:** расползание объёма — лечится жёстким MVP (§17).
- **Когда выбирать:** если это продукт и гарантии — его суть.

### Рекомендация: вариант C, фазами

- **Почему не A.** Нет параллельной дивергенции и типизированного контекста, а это ядро твоих пайплайнов.
- **Почему не B.** Главные гарантии — провенанс, видимость, join-политики, воспроизводимость — живут в исполнителе. В чужом оркестраторе они становятся обёртками, и отладчик их не видит.
- **Как удержать объём.** Исполнение берём у VoltAgent: наш «интерпретатор» — это сборщик цепочек VoltAgent из IR и исполнители узлов, в которых живут гарантии (§20).

## 6. Модель воркфлоу (IR)

### 6.0. Ядро и принцип композиции

Платформа — это язык программирования с жёсткими рамками: маленькое ядро, строгая типизация, а всё остальное собирается из ядра так же, как функции из примитивов.

Судьи, панели, циклы, каскады, агенты и архетипы — не встроенные сущности, а компоненты стандартной библиотеки:
- их логика видна до примитивов;
- их можно править и форкать;
- новые Claude собирает тем же способом.

| Понятие языка | В платформе |
|---|---|
| Типы | Реестр типов: записи, enum, union, списки, optional, ID с разрешённым множеством, тип компонента `Component<In, Out>` |
| Ввод-вывод и эффекты | Примитивы `llm`, `tool`, `human` |
| Чистые функции | `code` |
| Управляющие конструкции | Комбинаторы `seq`, `parallel`, `map`, `switch`, `loop`, `race`, `try`, `gate` |
| Функции и модули | Компоненты: именованная, типизированная, версионированная композиция |
| Стандартная библиотека | `judge`, `judge_panel`, `diverge`, `aggregate`, `verify_fix`, `cascade`, `bounded_agent`, архетипы |
| Компилятор | Типизация, правила ядра, контракты компонентов |
| Рантайм | Интерпретатор |
| Отладчик | Studio |
| Тесты | Evals |
| Пакеты | Версии компонентов в библиотеке |

**Из чего состоит компонент:**
- **Сигнатура** — входной и выходной типы.
- **Параметры,** в том числе другие компоненты: компоненты высшего порядка.
- **Дженерики,** например `verify_fix<T>`.
- **Контракты:**
  - `requires` — предусловия, проверяются при каждом использовании;
  - `ensures` — постусловия, проверяются статически или в рантайме.
- **Тело** — композиция из примитивов, комбинаторов и других компонентов.
- **Документация и тесты по умолчанию.**

Пример — панель судей, собранная из ядра:

```yaml
component: judge_panel
type_params: [C]                                   # тип кандидата
params:
  judges:          Component<{candidate: C, rubric: Rubric}, Verdict>[]
  aggregate:       Component<Verdict[], PanelVerdict>
  on_disagreement: Component<Verdict[], PanelVerdict>
in:  { candidate: C, rubric: Rubric }
out: PanelVerdict
requires:
  - distinct(families(judges)) >= 2
  - disjoint(families(judges), provenance_families($in.candidate))   # судьи не из семейства генератора
body:
  verdicts:
    map: { over: $judges, concurrency: all, on_item_error: skip, do: { call: $item, in: $in } }
  spread:
    code: verdict_spread
    in: { verdicts: $verdicts }
  result:
    switch:
      on: $spread.level                            # enum SpreadLevel: low | high
      cases:
        low:  { call: $aggregate, in: $verdicts }
        high: { call: $on_disagreement, in: $verdicts }
  return: $result
```

Здесь нет ничего специального: только `map`, `code`, `switch` и вызовы компонентов. Любую другую архитектуру — дивергентного судью с каскадом, дебаты, двухуровневую проверку — Claude собирает так же.

**Что даёт ядро без спецсущностей:**
- **Выразительность.** Любая придуманная архитектура собирается без изменений платформы.
- **Маленький компилятор.** Правила ядра общие для любой композиции: типы, эффекты, полнота `switch`, ограниченность `loop`, провенанс, политики, бюджеты. Специфичные защиты живут в контрактах компонентов.
- **Прозрачность.** Любой компонент раскрывается на канвасе до примитивов.
- **Меньше выдумок.** Claude учит около 15 понятий, а не десятки типов сущностей. Всё, чего нет в ядре, в библиотеке или в его собственных компонентах, — ошибка компиляции.
- **Библиотека растёт из практики.** Компонент, собранный Claude для одного воркфлоу, после аппрува становится общим.

**Рамки ядра:**
- без рекурсии компонентов;
- без замыканий над изменяемым состоянием;
- `code` — только чистые функции без эффектов, с типами и тестами;
- язык контрактов — маленький набор предикатов над статическими свойствами: типы, семейства моделей, кардинальность, класс происхождения, бюджет.

### 6.1. Примитивы ядра

| Примитив | Что делает | Обязательно |
|---|---|---|
| `llm` | Вызов модели по шаблону (§7.6) | шаблон, роль модели, слоты, тип выхода |
| `tool` | Внешний вызов: БД, API, поиск по базе знаний, MCP | схема, таймаут, класс эффекта `read \| write \| external`, ключ идемпотентности для `write` и `external` |
| `code` | Чистая TS-функция | типы входа и выхода, отсутствие эффектов, тесты |
| `human` | Запрос к человеку | форма по типу, таймаут, политика по таймауту |
| `const` | Статическое значение или фрагмент по версии | тип, версия |

Всё остальное — сахар или компоненты:
- `load` и `retrieve` — это `tool` с эффектом `read` и TTL;
- `subflow` — это вызов компонента по версии;
- `agent` — компонент библиотеки `bounded_agent`: `loop` над вызовами `llm` и `tool` с лимитами и типизированным итогом.

### 6.2. Комбинаторы ядра

| Конструкция | Семантика | Обязательные параметры |
|---|---|---|
| `seq` | Последовательность | — |
| `parallel` | Разные ветки одновременно | `join: all \| any \| quorum(k) \| first_success`, `on_branch_error: fail \| skip \| default` |
| `map` | Один шаг над каждым элементом списка | `over`, `concurrency`, `on_item_error`; порядок результатов сохраняется |
| `reduce` | Сахар: свёртка списка через `code` или компонент `aggregate` | — |
| `switch` | Ветвление по enum | `on: <enum>`; все варианты обязательны, `default` — только с обоснованием; все ветки возвращают один тип |
| `loop` | Повтор до условия | `until` (DSL предикатов), `max_iter`, `carry`, `select: last \| best(score)` |
| `race` | Первый успешный из веток | `timeout`; остальные ветки отменяются |
| `gate` | Ожидание события или человека | `timeout`, `on_timeout` |
| `try` | Перехват типизированной ошибки и запасной путь | тип ошибки; запасная ветка возвращает тот же тип |

### 6.3. Стандартная библиотека: дивергенция, конвергенция, архитектуры

Это не встроенные сущности, а компоненты стандартной библиотеки, собранные из ядра (§6.0). Их код виден до примитивов, защиты записаны в контрактах. Claude может взять их как есть, форкнуть или собрать свои.

- **`diverge`** — N независимых генераций.
  - Источник разнообразия обязателен: `vary: temperature | seed | persona | model | prompt_variant`. `vary` — это переопределения агента на каждую ветку (§7.3); краткая форма `{ temperature: [0.4, 0.8, 1.1] }` разворачивается в список.
  - Ветки не видят друг друга — это политика видимости.
- **`judge`** — оценка или сравнение кандидатов.
  - Режим `mode: pointwise | pairwise | ranking`, рубрика `rubric: <тип>`.
  - Для pairwise обязательна перестановка позиций (`swap_positions`) с усреднением.
  - Число судей задаётся `judges: n`; модель судьи из другого семейства, чем генератор.
- **`aggregate`** — свести N результатов в один: `strategy: vote | rank | merge(key) | best_of(score)`, дедупликация по ключу.
- **`critic_loop`** — цикл «генерация → критика → ревизия».
  - Обязательны `max_iter` и `stop_when`.
  - Выбирается лучший вариант (`select: best`), а не последний.
- **`consensus`** — N прогонов одного экстрактора и согласование полей; для фактов и ID. Берётся прямо из фреймворка валидации.

**Библиотека архитектур.** Паттерны — это сохранённые параметризуемые подворкфлоу с описанием. Claude получает их через `architecture.search` по признакам задачи или собирает свою композицию из примитивов §6.1–6.2.

| Паттерн | Схема | Когда брать | Главные параметры |
|---|---|---|---|
| `extract_validate` | Экстракция → валидация → консенсус для критичных полей | Факты и ID из текста | Критичные поля, N |
| `map_reduce` | Обработка каждого элемента → свёртка | Списки, пакеты, длинные документы | `concurrency`, стратегия свёртки |
| `generate_verify_loop` | Генерация → проверка → доработка до прохождения | Результат можно проверить | Верификатор, `max_iter`, остановка |
| `diverge_judge_select` | N кандидатов → судья → лучший | Открытая генерация, нужен лучший вариант | N, источник разнообразия, рубрика |
| `diverge_merge` | N кандидатов → синтез | Нужен полный охват идей | Стратегия слияния, дедупликация |
| `judge_panel` | K судей разных моделей параллельно → агрегация → политика разногласий | Важная оценка, нужна устойчивость | Состав панели, агрегация, порог разногласий |
| `cascade` | Дешёвая модель → проверка уверенности → сильная модель | Большие объёмы, неравная сложность | Порог эскалации |
| `router_experts` | Классификация → специализированный подворкфлоу | Разные типы входов | Enum маршрутов |
| `retrieve_ground_answer` | Поиск по базе знаний → ответ с цитатами → проверка опоры | Ответы по документам | Индекс, top_k, требование цитат |
| `plan_execute_check` | План → `map` по задачам → проверка → перепланирование | Многошаговые задачи | Лимит перепланирований |
| `self_consistency` | N решений одной задачи → голосование | Задачи с одним верным ответом | N, правило голосования |
| `human_escalation` | Автоматическая ветка + эскалация по порогу | Высокие ставки | Порог, форма, таймаут |

Паттерны комбинируются: например, `map_reduce`, внутри которого `cascade`, а на выходе `judge_panel`.

### 6.4. Слоты и привязки

- **Слоты.** Каждый вход узла — слот `name: Type`.
- **Привязка.** `from:` указывает ровно один источник:
  - `$input.path` — вход прогона;
  - `<node>.out.path` и `<node>.out[*].path` — выходы узлов;
  - `<load>.out` — загруженный контекст;
  - `const` — константа;
  - `run.context.*` — дата, часовой пояс, локаль, tenant.
- **Преобразования.** Только чистые `code`-узлы или встроенные типизированные проекции: `pick`, `omit`, `map`, `flatten`.
- **Метки происхождения.** В рантайме каждое значение несёт узел, путь, версию и уровень доверия.

### 6.5. Политики и бюджеты

- **Видимость.** Дивергенты не видят соседей. Судья не видит, какая ветка или модель породила кандидата.
- **Доверие.** Уровни `trusted | untrusted`; веб-страницы и текст пользователя — `untrusted`. Такие данные влияют на ветвление только через типизированный enum экстрактора, а инструкции из них никогда не исполняются (принцип CaMeL).
- **PII.** Типы с меткой `pii` уходят только к провайдерам из allowlist и маскируются в трассах.
- **Бюджеты.** Токены, деньги и время — на узел и на прогон. Превышение останавливает прогон с сохранённым состоянием.

### 6.6. Пример спеки

```yaml
flow: hotel_pitch
version: 7
input: TourRequest
context: [run.date, run.locale]
budget: { usd: 0.40, seconds: 120 }

nodes:
  load_hotels:
    kind: load
    fn: db.hotels_by_filters
    in: { filters: $input.filters }
    out: Hotel[]
    ttl: 1h

  score_hotels:
    kind: map
    over: $load_hotels.out
    concurrency: 8
    on_item_error: skip
    do:
      kind: llm
      archetype: scorer
      model_role: small_fast
      in: { hotel: $item, request: $input }
      out: HotelScore

  top3:
    kind: code
    fn: pick_top_k
    in: { scores: $score_hotels.out, hotels: $load_hotels.out, k: 3 }
    out: Hotel[]

  pitches:
    kind: diverge
    n: 3
    vary: { temperature: [0.4, 0.8, 1.1] }
    do:
      kind: llm
      archetype: generator
      model_role: writer
      in: { hotels: $top3.out, request: $input }
      out: Pitch              # ссылается на FeatureId из allowed_set этих отелей, фактов не пишет

  pick:
    kind: judge
    mode: pairwise
    swap_positions: true
    model_role: judge_strong
    in: { candidates: $pitches.out, request: $input }
    out: PitchVerdict

  final_pitch:
    kind: switch
    on: $pick.out.decision     # enum PitchDecision: accept | revise | escalate
    cases:
      accept:   { value: $pick.out.best }
      revise:   { do: fix }
      escalate: { do: review }
    out: Pitch                 # все ветки обязаны вернуть Pitch — иначе ошибка компиляции

  fix:
    kind: critic_loop
    max_iter: 2
    stop_when: $.score >= 0.8
    select: best
    model_role: writer
    in: { pitch: $pick.out.best, request: $input }
    out: Pitch

  review:
    kind: human
    form: PitchReviewForm
    in: { pitch: $pick.out.best, verdict: $pick.out }
    timeout: 24h
    on_timeout: escalate_to_manager
    out: Pitch

  render:
    kind: code
    fn: render_pitch           # подставляет факты из load_hotels по FeatureId
    in: { pitch: $final_pitch.out, hotels: $load_hotels.out }
    out: PitchText
```

В примере `diverge`, `judge` и `critic_loop` — вызовы компонентов стандартной библиотеки, а не встроенные конструкции.

### 6.7. Контекстная модель

Контекст — не отдельная подсистема. Потребность в контексте — это входной тип компонента плюс контракт на происхождение значения. Граф контекста — представление потока данных, окрашенное по классам происхождения.

Проектирование начинается не с промтов, а с вопроса: **какая информация нужна каждому решению, откуда она берётся и от чего зависит.** Промты пишутся уже поверх ответа.

**Виды контекста:**

| Вид | Пример | Как получается | Обязательные свойства |
|---|---|---|---|
| `static` | Правила направления, глоссарий, определения, тон | Фрагменты и константы по версии | Версия |
| `data` | Карточка отеля, цены, наличие | Типизированный `load` из БД или API на каждый прогон | TTL, схема, уровень доверия |
| `knowledge` | Досье отелей, FAQ, документы | Узел `retrieve`: запрос, индекс, фильтры, top_k, rerank | ID источника у каждого фрагмента; требование цитат там, где нужна опора |
| `generated` | Извлечённые требования клиента, оценки, резюме | Выход предыдущего LLM-узла | Валидация до использования в решениях, пометка уверенности |
| `human` | Уточнение, правка, аппрув | Узел `human` | Форма по типу, таймаут |
| `run` | Дата, локаль, tenant, настройки пользователя | Контекст прогона | — |

**Потребность в контексте — отдельная сущность:**

```yaml
context_needs:
  - id: family_constraints
    for: [pick.decision]                 # какое решение без этого нельзя принять
    description: Возраст детей, нужен ли детский клуб и пологий вход в море
    type: FamilyConstraints
    required: true
    source: { kind: generated, from: extract_request.out.family }
    verify: [schema, completeness]
  - id: hotel_facts
    for: [score_hotels, render]
    type: Hotel.view(brief)
    source: { kind: data, from: load_hotels.out, ttl: 1h }
  - id: destination_rules
    for: [pitches]
    type: PolicyText
    source: { kind: static, fragment: egypt_rules@v3 }
  - id: similar_cases
    for: [pitches]
    type: Passage[]
    source:
      kind: knowledge
      index: kb.hotel_dossiers
      query_from: extract_request.out.intent   # запрос зависит от генеративного контекста
      top_k: 5
      rerank: true
```

**Граф контекста** строится из потребностей и источников. В нём видно:
- на чём держится каждое решение;
- где контекст генеративный, а где статичный;
- какие есть цепочки зависимостей — например, «извлечённое намерение → запрос к базе знаний → найденные кейсы → генерация».

**Правила компилятора:**
- **R-C1.** У каждого решения (`switch`, `judge`, роутер) объявлены потребности, и каждая привязана к источнику.
- **R-C2.** У источника указан вид; тип совпадает с потребностью.
- **R-C3.** Генеративный контекст проходит валидацию или верификацию до того, как на нём принимается решение.
- **R-C4.** Источники `knowledge` возвращают фрагменты с ID источника; архетипы с опорой на вход требуют цитат.
- **R-C5.** У `data` задан TTL, у `static` — версия.
- **R-C6.** Граф зависимостей контекста ацикличен; цикл допустим только внутри `loop`.
- **R-C7.** Суммарный размер контекста узла не превышает окно профиля; стратегия сжатия задана явно.
- **R-C8.** Потребность без потребителя и потребитель без объявленной потребности — ошибки.

Качество поиска по базе знаний меряется отдельно: recall@k на датасете запросов с эталонными документами.

### 6.8. Судьи и панели судей

Судья — не встроенная сущность, а компонент библиотеки: вызов модели с типом вердикта. Панель — композиция из `map` по судьям, агрегирующего компонента и `switch` по разногласию (§6.0). Конфигурация ниже — это параметры компонента `judge_panel`.

```yaml
judge_panel: pitch_quality
mode: pointwise                    # pointwise | pairwise | ranking
rubric:
  factual_consistency: { weight: 0.4, scale: 1-5, hard_fail_below: 3 }
  fit_to_request:      { weight: 0.4, scale: 1-5 }
  tone:                { weight: 0.2, scale: 1-5 }
judges:                            # дивергентный судья: разные семейства моделей параллельно
  - { model_role: judge_a }
  - { model_role: judge_b }
  - { model_role: judge_c }
bias_controls: { swap_positions: true, blind_labels: true, shuffle: true }
aggregate: { method: median, per_criterion: true }      # median | mean | max | majority | min
disagreement: { metric: spread, threshold: 1.5, on_exceed: tie_break(judge_strong) }   # или human
output: PanelVerdict               # вердикт-enum, оценки по критериям, обоснование до оценки
calibration: { dataset: pitch_human_labels@v2, min_agreement: 0.8 }
```

Панель — это не только устойчивость. В исследовании PoLL панель из нескольких меньших моделей разных семейств обошла одного большого судью, показала меньше внутримодельного смещения и оказалась более чем в семь раз дешевле. Проверено на трёх типах задач и шести датасетах.

**Контракты компонента `judge_panel`** — компилятор проверяет их при каждом использовании:
- **R-J1.** Рубрика типизирована: критерии, веса, шкалы, описания уровней.
- **R-J2.** Семейство модели судьи отличается от семейства генератора; в панели — минимум два семейства.
- **R-J3.** Обоснование в выходе стоит до оценки.
- **R-J4.** Для pairwise включена перестановка позиций; метки кандидатов слепые.
- **R-J5.** Задана политика разногласий: тай-брейк или эскалация.
- **R-J6.** Судья гейтит выпуски только после калибровки с согласием не ниже порога.

### 6.9. Циклы (loop engineering)

Цикл — не «повторять, пока не получится», а конструкция с типизированной обратной связью и явными условиями остановки. В ядре один примитив `loop` с типизированным состоянием; `verify_fix`, `critique_revise`, `task_completion` и `search` — компоненты библиотеки поверх него.

| Тип | Схема | Верификатор | Остановка |
|---|---|---|---|
| `verify_fix` | Генерация → проверка → доработка | Детерминированный (код, схема, тесты) или судья | Проверка пройдена / `max_iter` / стагнация |
| `critique_revise` | Генерация → критика → ревизия | Судья-критик | Оценка ≥ порога / `max_iter` |
| `retry_with_feedback` | Ретрай с текстом ошибки валидации | Валидаторы | Валидно / k попыток |
| `task_completion` | Работа до закрытия чеклиста | Проверка пунктов чеклиста | Все пункты закрыты / бюджет |
| `search` | Расширение кандидатов → оценка → top-k (best-of-N, beam) | Скорер | Бюджет / глубина |

```yaml
fix:
  kind: loop
  type: verify_fix
  generator: { archetype: generator, model_role: writer }
  verifier:  { kind: code, fn: check_pitch_facts }   # детерминированный, если проверку можно выразить кодом
  feedback:  Issue[]                  # типизированный список проблем идёт в слот генератора
  carry: { history: last_2 }          # сколько истории переносить — рост контекста ограничен
  stop_when: $.issues.length == 0
  max_iter: 3
  budget: { usd: 0.10 }
  stagnation: { window: 2, min_delta: 0 }
  select: best
```

**Правила ядра для `loop` (R-L1–R-L4) и контракты компонента `verify_fix` (R-L5–R-L6):**
- **R-L1.** Заданы `max_iter` и бюджет.
- **R-L2.** Выход верификатора типизирован и привязан к слоту обратной связи генератора.
- **R-L3.** Условие остановки — типизированный предикат.
- **R-L4.** История, переносимая между итерациями, ограничена.
- **R-L5.** LLM-верификатор — из другого семейства, чем генератор; детерминированный верификатор предпочтителен, если проверку можно выразить кодом.
- **R-L6.** Выбирается лучший вариант, а не последний; включена защита от стагнации и зацикливания — повторяющиеся кандидаты детектируются по хэшу.

В отладчике у цикла есть таймлайн: оценка и проблемы на каждой итерации, дифф между кандидатами.

## 7. Реестры

### 7.1. Типы

```yaml
enums:
  PitchDecision:
    description: Решение судьи по питчу
    values:
      accept:   { description: Питч готов к показу клиенту }
      revise:   { description: Есть исправимые проблемы, нужна доработка }
      escalate: { description: Конфликт фактов или риск, нужен человек }
  BeachEntry:
    description: Тип входа в море
    values:
      sand:    { description: Песчаный вход }
      pontoon: { description: Понтон }
      rocks:   { description: Камни или риф }

ids:
  HotelId:   { source: db.hotels,   allowed_set: dynamic }
  FeatureId: { source: db.features, allowed_set: dynamic }

entities:
  Hotel:
    id: HotelId
    fields:
      name:        { type: string,     description: Название отеля }
      beach_entry: { type: BeachEntry, description: Тип входа в море }
      pool_heated: { type: boolean,    description: Подогрев бассейна }
    views:
      brief: [name, beach_entry, pool_heated]   # как отель показывается модели
```

- **Описания обязательны** у каждого enum-значения и поля; в промт они попадают автоматически.
- **`allowed_set: dynamic`.** В каждом вызове в схему подставляется список разрешённых ID, поэтому выдуманный ID невыразим (constrained ID decoding).
- **Поиск использования.** Для любого типа видны все узлы, слоты, роутеры и промты, где он участвует.

### 7.2. Профили моделей

```yaml
profiles:
  small_fast:
    primary:  { provider: vllm, model: <small-open-model>, structured: grammar }
    fallback: [ { provider: <api>, model: <mid-model>, structured: strict } ]
    params:   { temperature: 0.1, max_tokens: 800 }
    limits:   { rpm: 600, concurrency: 16 }
    cost:     { in_per_mtok: <x>, out_per_mtok: <y> }
    caps:     { strict_json: true, context: 32k, tools: false }
  judge_strong:
    primary:  { provider: <api>, model: <strong-model>, structured: strict }
    policy:   { family_differs_from: [writer] }
```

- **Роли вместо моделей.** Узлы ссылаются на роль (`model_role`), а не на модель. Замена модели — это правка профиля плюс eval-гейт.
- **Проверка возможностей.** Компилятор сверяет, что профиль умеет всё, что требует узел: строгий JSON, размер окна против оценки промта, тулы.
- **Фолбэки и версии.** Фолбэки обязаны быть совместимы по возможностям. Версии моделей закреплены; депрекейт вызывает алерт.
- **Политики параметров по архетипу.**
  - Экстрактор с температурой выше порога — предупреждение.
  - `diverge` без источника разнообразия — ошибка.

### 7.3. Агенты и переопределение на вызове

**Агент — переиспользуемый набор настроек:**
- роль или модель, параметры;
- тулы, память, лимиты;
- шаблон по умолчанию, режим строгого вывода;
- фолбэки и маршрутизация.

Отдельной машинерии у агента нет: `llm` и компонент `bounded_agent` просто ссылаются на него.

```yaml
agents:
  writer:
    model_role: writer
    params: { temperature: 0.7, max_tokens: 1200 }
    tools: [kb.search]
    memory: { scope: run, window: 20 }       # run | user | tenant
    limits: { max_steps: 6, usd: 0.05, timeout: 30s }
    locked: [memory.scope]                   # эти поля нельзя переопределить на вызове
```

**Переопределение на каждом вызове:**

```yaml
pitches:
  call: diverge
  n: 3
  vary:                                      # переопределение на каждую ветку
    - { params: { temperature: 0.4 } }
    - { params: { temperature: 0.9 } }
    - { model_role: writer_alt }
  do:
    kind: llm
    agent: writer
    override:                                # переопределение для этого вызова
      params: { max_tokens: 1600 }
      tools: { remove: [kb.search] }
```

**Порядок применения** — каждый следующий уровень сильнее предыдущего:
1. умолчания платформы;
2. определение агента;
3. умолчания компонента — например, `judge_panel` ставит судьям низкую температуру;
4. переопределения на уровне воркфлоу;
5. переопределение на вызове, включая `vary` для веток;
6. переопределение прогона — эксперимент, матрица моделей, окружение.

Поля из `locked` и политики (видимость, доверие, PII, семейства моделей) переопределениями не меняются.

**Что можно переопределить:**
- модель — роль или конкретную модель из каталога;
- параметры;
- тулы — добавить, убрать или заменить список;
- память — окно и хранилище;
- лимиты;
- вариант шаблона;
- фолбэки и маршрутизацию провайдеров.

Переопределение прогона затрагивает только модель, параметры и лимиты; бюджеты там можно лишь ужесточить.

**Эффективная конфигурация** вычисляется при компиляции для каждого вызова и попадает в план и в каждую трассу вместе с происхождением каждого поля. Например: `temperature = 0.9 ← vary[1] узла pitches`, `tools = [] ← writer, минус kb.search на вызове`.

**Правила компилятора:**
- **R-O1.** Переопределение соответствует схеме, поля существуют.
- **R-O2.** Поля из `locked` не переопределяются.
- **R-O3.** После переопределения модель по-прежнему умеет всё, что требует вызов: строгий JSON, окно против оценки промта, тулы.
- **R-O4.** Тулы, на которые ссылаются шаблон и контракты, остаются доступны.
- **R-O5.** Scope памяти не расширяется (`run → user → tenant`) без политики аппрува.
- **R-O6.** Контракты перепроверяются с эффективной конфигурацией — например, судья по-прежнему не из семейства генератора.
- **R-O7.** Переопределение прогона меняет только разрешённые поля; бюджеты — только в сторону ужесточения.

**Общие требования:**
- Агент без типизированного результата, лимитов и allowlist тулов не компилируется.
- Тул с побочным эффектом требует `gate` или ключ идемпотентности.
- Компонент `bounded_agent` можно раскрыть до примитивов, форкнуть и собрать свой вариант.

### 7.4. Тулы

- **Контракт тула:**
  - схема входа и выхода;
  - класс эффекта `read | write | external`;
  - таймаут;
  - шаблон ключа идемпотентности.
- **MCP-серверы** подключаются с закреплённым хэшем схемы. Изменение схемы на сервере даёт ошибку компиляции, а не тихую поломку.
- **Секреты** — только ссылки на хранилище, никогда не значения в спеке или промте.

### 7.5. Архетипы узлов

| Архетип | Назначение | Зашито в скелет | Параметризует агент | Проверки по умолчанию |
|---|---|---|---|---|
| `extractor` | Извлечь поля из текста | запрет домыслов, значение «нет данных», формат из типа | тип выхода, инструкция | схема, обязательные поля, опора на цитату из входа |
| `classifier` | Выбрать значение enum | описания значений из реестра | enum, инструкция | принадлежность enum |
| `scorer` | Оценить по рубрике | шкала, порядок «обоснование → оценка» | рубрика | диапазон, заполненность обоснования |
| `generator` | Создать текст или объект | структура, формат | тип, стиль, инструкция | схема, язык, длина |
| `judge` | Сравнить или оценить кандидатов | перестановка позиций, модель другого семейства | режим, рубрика | согласованность при перестановке |
| `aggregator` | Свести N результатов в один | стратегия слияния | ключ дедупликации | потери и дубли элементов |
| `critic_reviser` | Критика и правка | лимит итераций, выбор лучшего | критерии | рост оценки по итерациям |
| `summarizer` | Сжать с сохранением фактов | запрет новых фактов | длина, фокус | факты выхода ⊆ факты входа |
| `planner` | Декомпозировать задачу | выход — список задач типа | тип задачи | покрытие, отсутствие циклов |
| `router` | `classifier` + `switch` | полнота вариантов | enum | принадлежность enum |
| `bounded_agent` | Агент с тулами | лимиты, типизированный итог | тулы, цель | лимиты, итог по схеме |
| `consensus_extractor` | N экстракций и согласование | правило согласования полей | порог согласия | согласие, доля эскалаций |

Архетипы — тоже компоненты библиотеки: шаблон по умолчанию, типы, контракты и проверки. Механику — формат вывода и защиты — обеспечивают ядро и контракты. Текст шаблона агент может переписать целиком по правилам §7.6, а сам архетип — форкнуть.

### 7.6. Промты: свобода текста, контроль динамики

**Граница ответственности.** Агент владеет текстом, платформа — данными, типами и форматом.
- Агент может переписать шаблон целиком.
- Он не может подставить данные в обход слотов, описать формат вывода руками или сослаться на то, чего нет в контракте.

**Шаблон — это типизированная функция.** Модель та же, что у BAML: типизированный вход, шаблон, формат вывода из типа.

```yaml
prompt: score_hotel
version: 4
in:
  hotel:   Hotel.view(brief)          # представление типа из реестра (§7.1)
  request: TourRequest.view(scoring)
  date:    run.date
out: HotelScore
body: |                               # текст пишет агент
  Ты подбираешь отель под запрос клиента. Сегодня {{ date }}.
  Запрос:
  {{ request }}
  {% if request.with_kids %}
  Отдельно оцени детскую инфраструктуру.
  {% endif %}
  Отель:
  {{ hotel }}
  {{ output_format }}                 # генерирует платформа из HotelScore вместе с расшифровкой enum
```

**Чем владеет платформа:**
- **Подстановка данных** — только через объявленные слоты. Данные литералами в тексте запрещены.
- **Представления типов (views).** Как сущность показывается модели: поля, порядок, подписи. Задаются в реестре один раз, поэтому `Hotel` выглядит одинаково во всех промтах, а скрытые поля — внутренние ID, оценки других веток — в текст не попадают.
- **Блок формата вывода и расшифровка enum** генерируются из типа выхода.
- **Разрешённые множества ID и enum** живут в схеме вызова, а не в тексте.
- **Системный контекст** — дата, локаль, часовой пояс.
- **Обёртка под модель** — роли сообщений, теги, кэшируемый префикс. Один шаблон рендерится под разные профили.

**Динамика — только типизированными конструкциями:**

| Конструкция | Для чего | Ограничение |
|---|---|---|
| `{% if %}` | Условный блок | Только по bool, optional или enum-полю |
| `{% switch %}` | Вариант текста по значению enum | Полнота по всем значениям |
| `{% for %}` | Перечисление кандидатов, фактов, пунктов | Только по массивам; внутри — поля элемента |
| `{% include fragment@v %}` | Переиспользуемые куски: тон, доменные определения, правила | По версии; изменение фрагмента перекомпилирует все шаблоны, где он включён |
| слот `examples` | Динамические few-shot из узла-ретривера | Тип `Example<In, Out>[]`; каждый пример валидируется |
| метки кандидатов | `A / B / C` для судьи | Порядок и метки перемешивает платформа |

Произвольных выражений и функций в шаблоне нет — только разрешённые фильтры.

**Правила компилятора для шаблонов:**
- **R-T1.** Плейсхолдер ссылается на объявленный слот; поле существует, тип совместим.
- **R-T2.** Каждый слот использован в тексте или помечен `unused` с причиной.
- **R-T3.** Условия только по типизированным полям; сравнение с enum — только со значениями из реестра.
- **R-T4.** `switch` в шаблоне полный по enum.
- **R-T5.** `for` только по массивам.
- **R-T6.** `output_format` встречается ровно один раз; ручного описания формата и JSON-примеров в тексте нет.
- **R-T7.** Упомянутые в тексте значения enum совпадают с реестром: `revise` в тексте при `needs_revision` в реестре — ошибка.
- **R-T8.** В статическом тексте нет данных-литералов: названий, цен, ID из справочников.
- **R-T9.** Верхняя оценка размера отрисовки не превышает окно профиля.
- **R-T10.** Политики видимости соблюдены: в шаблон судьи нельзя подставить ветку или модель кандидата, в шаблон дивергента — соседей.
- **R-T11.** Шаблон объявляет язык вывода.
- **R-T12.** В архетипах с опорой на вход запрещены инструкции вроде «используй свои знания» или «придумай, если данных нет».

**Что остаётся открытым и как это закрыто:**
- Опасные классы — формат вывода, не тот контекст, выдуманные значения — остаются на L0–L1: ими владеет платформа.
- Свободным остаётся только качество формулировок. Его ловят snapshot отрисованных промтов на фикстурах с диффом в ревью, golden-тесты узла и eval-гейт (L3).
- Если текст просит у модели что-то вне схемы, строгий вывод этого не пропустит. Пострадает качество, а не корректность, и это увидят evals.

### 7.7. Провайдеры и каталог моделей

**Провайдеры:** OpenRouter, Together AI, прямые API (Anthropic, OpenAI, Google и другие), свои модели через vLLM или SGLang. Провайдерный слой — AI SDK или OpenAI-совместимый клиент: и OpenRouter, и Together AI отдают OpenAI-совместимый API.

**Синхронизация каталога** — по расписанию, из API провайдеров:
- **OpenRouter:**
  - модели с ценами за токен, длиной контекста, лимитом вывода и списком поддерживаемых возможностей (tools, JSON mode, structured outputs, reasoning);
  - запросы, требующие конкретной возможности, уходят только к провайдерам, которые её поддерживают;
  - у цен бывают условные переопределения, например для длинного контекста; незнакомые условия синхронизатор пропускает.
- **Together AI:**
  - модели с типом, длиной контекста и ценами input / output / cached input;
  - batch-инференс со скидкой до 50% — дешёвый способ гонять эксперименты и датасеты.

**Что хранится по каждой модели:**
- провайдер, ID, длина контекста, лимит вывода;
- цены, включая кэш;
- заявленные и проверенные возможности;
- латентность и надёжность по нашим прогонам;
- даты появления и депрекейта.

**Проверенные возможности.** Заявленным флагам не верим на слово. При добавлении модели и после изменений платформа гоняет короткий тест соответствия: строгий JSON по эталонной схеме, вызов тула, длинный контекст. Профиль с требованием `strict_json` компилируется только на модели, прошедшей пробу.

**Где используется каталог:**
- статическая оценка стоимости прогона и бюджеты — по актуальным ценам;
- проверка «узел требует — модель умеет»;
- подбор фолбэков с совместимыми возможностями;
- матрица моделей на узел (§12.2);
- учёт фактической стоимости из ответов провайдеров и сверка с каталогом.

**Маршрутизация** задаётся политикой на профиль:
- сортировка по цене, латентности или надёжности;
- запрет провайдеров без нужной возможности;
- требования к обращению с данными;
- список фолбэков.

**Ключи** хранятся в хранилище секретов, отдельно по окружениям.

## 8. Каталог типовых проблем

**Уровни гарантии:**
- **L0 — невыразимо:** конструкция платформы не позволяет записать ошибку.
- **L1 — компилятор:** ошибку можно записать, но она не пройдёт компиляцию; запуск и выпуск невозможны.
- **L2 — рантайм-страж:** ошибка гарантированно ловится при исполнении и обрабатывается по явной политике.
- **L3 — гейт:** изменение не выпускается без зелёных тестов и экспериментов.
- **L4 — мониторинг:** ошибка ловится статистически в проде.

Каждая строка уровня L1 — это правило компилятора с кодом `R-<номер>` (§9).

### 8.1. Авторство

| № | Проблема | Механизм | Уровень |

## 9. Компилятор

**Этапы:**
1. Парсинг и проверка схемы IR.
2. Разрешение ссылок: типы, профили, агенты, тулы, подворкфлоу по версиям.
3. Проверка типов и кардинальности на каждой привязке.
4. Анализ потока данных: доминирование, доступность, неиспользуемые и непривязанные слоты.
5. Проверка политик: видимость, доверие, PII, семейства моделей.
6. Проверка управляющих конструкций: полнота `switch`, лимиты циклов, `join`, таймауты, достижимость.
7. Сборка промтов под профили моделей, валидация few-shot, lint схем.
8. Статические оценки:
   - максимальный размер промта на узел;
   - число вызовов в худшем случае;
   - верхняя оценка стоимости;
   - критический путь;
   - ширина параллелизма.

**Правила — три слоя:**
- **Ядро** — действует для любой композиции:
  - все строки каталога §8 с уровнем L1, код `R-<номер строки>`;
  - правила шаблонов `R-T1…R-T12` (§7.6);
  - правила контекста `R-C1…R-C8` (§6.7);
  - правила `loop` `R-L1…R-L4` (§6.9);
  - правила переопределений `R-O1…R-O7` (§7.3).
- **Контракты компонентов.** `requires` и `ensures` каждого компонента проверяются при каждом использовании — например `R-J1…R-J6` у `judge_panel` и `R-L5…R-L6` у `verify_fix`.
- **Типизация композиции:** дженерики, типы компонентов-параметров, эффекты.

В спайке — ядро категорий 8.1–8.5, шаблоны, контекст и контракты стандартных компонентов.

**Формат ошибки:**

```json
{
  "rule": "R-09",
  "node": "pick",
  "slot": "candidates",
  "message": "Слот не привязан",
  "candidates": ["pitches.out: Pitch[]"]
}
```

Ошибка без кандидатов на исправление считается багом компилятора.

**Доверие к самому компилятору.** Мутационные тесты в CI: корректные воркфлоу автоматически портятся типовыми ошибками агента, и компилятор обязан поймать 100% мутантов своих классов. Каждый пропуск — это новое правило или баг.

## 10. Рантайм

**Планировщик:**
- очередь готовых узлов;
- лимиты `concurrency` на профиль модели и на `map`;
- политики `join` и отмена веток в `race`;
- батчи и backpressure для больших вееров.

**Конвейер узла `llm`:**
1. **Сборка промта** из скомпилированного шаблона и значений слотов; к каждому значению прикрепляется метка происхождения.
2. **Кэш record/replay** — поиск по хэшу промта, модели, параметров и seed.
3. **Вызов провайдера со строгим выводом:** strict-режим API или грамматика в vLLM/SGLang. Схема дополняется динамическими множествами разрешённых ID и enum.
4. **Парсинг.** Толерантный парсер — только там, где строгий режим недоступен.
5. **Валидация:** схема, межполевые проверки, разрешённые множества, язык.
6. **Ремонт по политике узла:** ретрай с текстом ошибки (не больше k раз) → фолбэк-профиль → консенсус или эскалация человеку.
7. **Выход** с метками происхождения и спаном: отрисованный промт, сырой ответ, распарсенный выход, результаты проверок, токены, стоимость, латентность.

**Состояние:**
- чекпоинт каждого узла в Postgres;
- продолжение после падения;
- `fork` прогона с узла k после правки спеки;
- durable-ожидания для `human` и `gate`.

**Контроль:** бюджеты узла и прогона; проверка политик при каждом перемещении данных.

**Исполнение — VoltAgent (§20):**
- сборщик строит из плана цепочку VoltAgent; узлы исполняют наши исполнители внутри шагов;
- чекпоинты, restart после падения, suspend/resume и time travel — средствами VoltAgent;
- replay-кэш ответов моделей, таймауты человеческих задач и политики — наш слой.

**Рантайм-стражи — это твой фреймворк валидации:**
- DynamicSchemaBuilder даёт динамические множества;
- консенсус становится архетипом `consensus_extractor`;
- согласованность с ORM — межполевыми валидаторами.

## 11. Отладка

- **Живой граф прогона:**
  - статусы узлов;
  - агрегированный вид — повторы свёрнуты, циклы нарисованы циклами;
  - развёрнутый вид — каждый вызов отдельно;
  - группировка по стадиям.
- **Инспектор узла:**
  - вход с провенансом — клик ведёт к источнику;
  - отрисованный промт с подсветкой слотов;
  - сырой ответ и распарсенный выход;
  - результаты проверок, ретраи и фолбэки;
  - стоимость и латентность.
- **Replay узла с правкой входа** и **заморозка выходов верхних узлов** — быстрые итерации над одним шагом без прогона всего пайплайна.
- **Replay всего прогона из записи** — детерминированно и без затрат.
- **Fork с узла k** — продолжить прогон после правки спеки.
- **Дифф двух прогонов или версий** по узлам.
- **Точки останова** — перед узлом или при провале проверки.
- **Панель «почему»** — какое правило или страж сработал, какой фолбэк применён.
- **Водопад** стоимости и латентности, ширина параллелизма.
- **Кластеризация провалов** по узлам и правилам.
- **Матрица стадий:** элементы датасета × стадии, по каждой ячейке — прошла ли проверка стадии.
- **Lineage значения:** как значение преобразовывалось по стадиям и в каких промтах использовалось.
- **Blame через подстановку эталона** (§12.3).
- **Таймлайн цикла** и **согласие панели судей** по каждому элементу.

  - на узел и на воркфлоу;
  - создаются из прогона одним действием;
  - версионируются;
  - делятся на `train / dev / test`, причём `test` недоступен оптимизатору.
- **Скореры:**
  - сначала детерминированные: схема, множества, инварианты, опора на вход;
  - затем LLM-судьи с защитами от смещения и калибровкой;
  - затем люди через очереди разметки.
- **Эксперименты:** версия спеки × датасет × скореры → дельты по узлам с доверительными интервалами.
- **Гейты выпуска:**
  - у каждого изменённого узла есть датасет не меньше минимального размера;
  - нет регрессии на детерминированных скорерах;
  - прирост по LLM-метрикам значим;
  - судья откалиброван.
- **Цикл прода:** семплирование → разметка → датасет.
- **Оптимизатор:** GEPA на слоте инструкции узла. Результат — предложение новой версии, а не автоматический выпуск.
- **Хранилище:** Langfuse (датасеты, эксперименты, разметка) и свои таблицы node-level метрик для гейтов.

### 12.1. Генерация датасетов

Датасеты генерирует Claude через `dataset.generate`; платформа контролирует покрытие и качество.

- **Стратегии генерации:**
  - от типов — валидные входы с каждым значением каждого enum;
  - от сценариев брифа — описанные тобой случаи и крайние ситуации;
  - состязательные — пропуски, противоречия, длинные входы, смешение языков, попытки инъекций;
  - из прода — семплы трасс с маскированием PII;
  - возмущения существующих элементов — перефразы, шум.
- **Цели покрытия:**
  - все значения enum на входах;
  - все ветки `switch`;
  - все причины выхода из циклов: успех, `max_iter`, стагнация;
  - все политики ошибок;
  - варианты контекста: попадание и промах поиска, устаревшие данные.
- **Разметка.** Эталоны даёт сильная модель с верификацией, ты проверяешь выборку — например, 10–20%. У каждого элемента есть флаг синтетичности и уверенность разметки.
- **Контроль качества:**
  - дедупликация;
  - разнообразие;
  - отсутствие пересечений с few-shot примерами;
  - семейство модели-разметчика отличается от семейства судей.
- **Отчёт покрытия** в Studio показывает пробелы, и Claude добирает их следующей генерацией.

### 12.2. Тест узла и матрица моделей

- **Изоляция.** Узел запускается на своём датасете; входы берутся из датасета, верхние узлы не нужны.
- **Варианты шаблона и модели** сравниваются в одном эксперименте.
- **Матрица моделей** — `experiment.model_matrix(node, models, dataset)`:
  - один узел × кандидаты из каталога (OpenRouter, Together AI, прямые API);
  - результат — качество, цена и латентность по каждой модели и граница Парето;
  - платформа предлагает модель на роль, решение фиксируется правкой профиля через гейт.
- **Разбор ошибок:** попарный дифф ответов по элементам и кластеризация провалов.

### 12.3. Тест всего воркфлоу

- **Полный прогон** на датасете воркфлоу — в том числе через batch-API, где он есть.
- **Матрица стадий:** элементы датасета × стадии; в каждой ячейке — прошла ли проверка стадии.
- **Lineage.** Для любого элемента видно, как значение преобразовывалось по стадиям и в каких промтах использовалось.
- **Blame через подстановку эталона.** Выход подозрительного узла заменяется эталонным, и нижняя часть графа переигрывается. Если итог стал верным — виноват этот узел. Так провал на выходе привязывается к конкретной стадии.
- **Доступ для Claude.** Результаты доступны через MCP (`run.stages`, `run.lineage`, `run.blame`): Claude предлагает правки, а их эффект доказывается экспериментом.

### 13.2. Права агента

- **Может:** править черновики и тексты шаблонов промтов, определять свои компоненты внутри воркфлоу, компилировать, запускать, создавать датасеты и скореры, запускать эксперименты, предлагать версии.
- **Не может:** выпускать версии, добавлять компоненты в общую библиотеку, менять реестры и политики без аппрува, читать секреты, использовать что-либо вне ядра, библиотеки и своих компонентов.

### 13.3. Протокол цикла (скилл)

Протокол повторяет сквозной сценарий §1.1:

1. `journal.read`, `brief.get`, `catalog.list`.
2. **Архитектура:** `architecture.search` → выбор паттерна или своя композиция, обоснование в журнал. Если есть только сырое описание процесса — сначала `agentic-process-spec`, затем `flow.import`.
3. **Контекст:** `context.plan` (потребности каждого решения) → `context.bind` (источники) → `context.graph`, пока правила R-C не станут зелёными.
4. **Воркфлоу и промты:** операции над спекой и шаблонами до чистого `flow.compile`.
5. **Судьи и циклы:** конфигурация панелей и циклов, компиляция.
6. **Датасеты:** `dataset.generate` с целями покрытия → `dataset.coverage`.
7. **Тест узлов:** `experiment.run` на узел, `experiment.model_matrix` для выбора моделей.
8. **Тест воркфлоу:** `run.start` на датасете → `run.stages` → `run.blame`.
9. **Улучшение:** правка → эксперимент → сравнение. Не больше 5 итераций; остановка после двух итераций без прогресса.
10. `version.propose` с доказательствами → твой аппрув → `journal.append`.

**Упаковка:** MCP-сервер, скилл по стандарту Agent Skills и блок в AGENTS.md.

### 13.4. Связка со скиллом agentic-process-spec

Раздел 12 спеки (`agent_workflow_spec`) импортируется в черновик IR. Девять вопросов скилла на каждый шаг становятся обязательными полями:

| Вопрос скилла | Поле IR |
|---|---|
| Цель шага | `description` |
| Кто исполняет | `kind` и роль |
| Входные сущности | слоты |
| Выходные сущности | тип выхода |
| Какое решение принимается | `switch` по enum |
| Блокирующий ли шаг | `gate` или `human` |
| Можно ли параллелить | конструкция и `join` |
| Какие проверки | валидаторы и скореры |
| Что при сбое | `on_error`, таймаут, политика |

Неотвеченный вопрос — ошибка компиляции. Твой метод становится машинно проверяемым.

## 15. Версии, публикация, экспорт, окружения, безопасность

- **Версии неизменяемы.** Спека, скомпилированные промты и профили моделей фиксируются вместе; на каждом выходе прогона есть lineage.
- **Выпуск.** Сначала shadow-прогоны на проде без влияния, затем canary; откат одной операцией.
- **Публикация.** Каждая выпущенная версия автоматически становится тулом (MCP/HTTP) со схемой входа. Её можно переиспользовать где угодно, в том числе из агентов VoltAgent.
- **Окружения.** Одна спека, конфигурационные оверлеи dev / stage / prod, секреты по окружениям.
- **Безопасность:**
  - секреты только по ссылке;
  - PII-метки и маскирование;
  - метки доверия и защита от инъекций;
  - изоляция памяти по scope;
  - аппрув для побочных эффектов.

### 15.1. Экспорт для воссоздания 1:1

Платформа — конструктор production-воркфлоу без lock-in. Экспорт рассчитан на то, что любой LLM воссоздаст воркфлоу в любом фреймворке один к одному, а совпадение доказывается тестами, а не на глаз.

**Состав бандла:**

```
project-export/
  manifest.json   версия формата, проект, версии спек, хэши файлов
  README.md       устройство проекта и порядок чтения — для человека и LLM
  semantics/      нормативная семантика ядра: порядок вычислений, привязки, join-политики,
                  ошибки, циклы, ретраи, идемпотентность, провенанс
  reference/      эталонный интерпретатор ядра (TS) — исполняемая спецификация
  schema/         JSON Schema всех форматов
  types/          реестр типов: enum с описаниями, сущности, views, источники ID
  components/     компоненты по версиям с контрактами
  flows/          IR модульный и развёрнутый до примитивов; скомпилированный план; статический отчёт
  prompts/        шаблоны, фрагменты, правила отрисовки, snapshot-отрисовки на фикстурах
  agents/         агенты, профили моделей, переопределения, эффективная конфигурация каждого вызова
  providers/      снимок каталога моделей: цены, возможности, результаты проб — без ключей
  tools/          схемы тулов, закреплённые MCP-схемы
  context/        потребности, источники, граф контекста
  datasets/       JSONL со сплитами и разметкой
  evals/          скореры, судьи, калибровки, результаты экспериментов
  conformance/    конформанс-набор: записанные прогоны и кассеты
  journal/        журнал решений
  targets/        готовый экспорт в VoltAgent и карты соответствия для других фреймворков
```

**Почему это воссоздаётся 1:1:**
- **Нормативная семантика ядра.** Каждый примитив и комбинатор описан так, что двух толкований нет: в каком порядке считаются привязки, что делает `quorum(k)` при сбоях, когда проверяется условие цикла, как ретраи сочетаются с идемпотентностью. Эталонный интерпретатор — исполняемая версия того же текста.
- **Развёрнутые воркфлоу.** Кроме модульной версии, каждый воркфлоу выгружен с компонентами, развёрнутыми до примитивов, — не нужно угадывать поведение библиотеки.
- **Эффективные конфигурации.** Для каждого вызова уже вычислены модель, параметры, тулы, память и лимиты — переопределения повторять не нужно.
- **Конформанс-набор.** Для каждого тест-кейса записан прогон: вход, входы и выходы каждого узла, отрисованные промты, ответы моделей и тулов, ввод людей, время и seed. Кассета отвечает на вызовы моделей и тулов по хэшу нормализованного запроса.

**Критерий 1:1.** Воссозданная реализация проходит конформанс-набор, если на каждом кейсе при ответах из кассеты:
- отрисованные промты совпадают с записанными после нормализации пробелов;
- аргументы вызовов тулов совпадают;
- решения потока совпадают: те же ветки, то же число итераций циклов;
- выходы каждого узла совпадают в каноническом JSON; результаты параллельных веток сравниваются по ключам, а не по порядку.

**Процесс для LLM (скилл воссоздания):**
1. Прочитать `README.md`, `semantics/`, `types/`.
2. Реализовать ядро или отобразить его на примитивы целевого фреймворка по картам из `targets/`.
3. Перенести компоненты, воркфлоу, шаблоны, агентов и тулы.
4. Подключить кассету вместо моделей и тулов.
5. Гонять `conformance/` и чинить до 100%. Это тот же цикл, что в architecture-implementation-loop, только тесты даны заранее.
6. Зафиксировать отчёт: что отображено нативно, что эмулировано, что потеряно.

**Цели:**
- **VoltAgent** — готовый codegen: читаемый TS-проект на `createWorkflowChain`, агентах и тулах VoltAgent, проходящий конформанс-набор (§20).
- **Любой другой фреймворк** — Mastra, LangGraph, Temporal, plain TS или Python — воссоздание силами LLM по бандлу с конформанс-проверкой.
- **Частичные цели** — например, Langfuse для промтов, датасетов и судей. Переносится часть проекта; всё остальное попадает в отчёт потерь.

**Правила бандла:**
- секретов нет, только ссылки;
- PII маскирована;
- порядок детерминирован для диффов в git;
- у формата есть версия;
- round-trip «экспорт → импорт → экспорт» даёт идентичный бандл.

## 18. Kill-критерии

Порог N и базовую линию фиксируешь до теста.

1. **Мутационный тест.** Не меньше 50 мутантов по классам L0/L1 — компилятор ловит 100%.
2. **Сборка агентом.** Claude собирает эталонный 15-шаговый воркфлоу с нуля через MCP до чистой компиляции и зелёного прогона: без единой ручной правки промта, не больше N итераций.
3. **Агностичность.** Тот же сценарий из второго MCP-клиента даёт тот же результат без правок сервера.
4. **Строгий вывод.** 0 невалидных по схеме ответов на 500+ LLM-вызовов.
5. **Воспроизводимость.** Прод-сбой воспроизводится через replay без расхождений.
6. **Enum.** Одна правка → список всех затронутых мест → после исправлений всё зелёное.
7. **Судья.** Согласие LLM-судьи с твоей разметкой выше заданного порога, прежде чем он начнёт гейтить выпуски.
8. **Скорость.** Время от ТЗ до работающего воркфлоу меньше твоего текущего ручного. Базовую линию замерить на прошлом воркфлоу.
9. **Покрытие.** Сгенерированный Claude датасет покрывает 100% значений enum на входах и 100% веток `switch` эталонного воркфлоу.
10. **Матрица моделей.** Хотя бы для одного узла платформа находит модель или провайдера дешевле базовой не меньше чем на X% при качестве в пределах ε.
11. **Blame.** В тестах с подсаженной неисправностью (намеренно испорченный узел) blame указывает на него не меньше чем в 90% случаев.
12. **Композиция.** Архитектуру, которой нет в библиотеке (например, дивергентного судью с каскадом), Claude собирает из ядра и библиотеки без изменений платформы — только компонентами.
13. **Round-trip.** Экспорт → импорт → экспорт даёт идентичный бандл.
14. **Воссоздание 1:1.** LLM по бандлу воссоздаёт эталонный воркфлоу во фреймворке, отличном от VoltAgent (например, Mastra или LangGraph), и реализация проходит конформанс-набор на 100% кейсов.
15. **Экспорт в VoltAgent.** Сгенерированный проект собирается, проходит конформанс-набор и запускается без ручных правок.

## 20. Бэкенд на VoltAgent

**Принцип.** VoltAgent (MIT) закрывает рантайм: исполнение воркфлоу с чекпоинтами, агентов, память, тулы и MCP, сервер и трассировку.

Наш продукт — слой над ним:
- проекты и БД;
- реестры и настройки;
- компилятор;
- сборщик цепочек из IR;
- исполнители узлов с гарантиями;
- MCP для агентов;
- Studio;
- экспорт.

Один маппинг работает в двух режимах. В рантайме сборщик строит цепочку VoltAgent из IR на лету. При экспорте тот же маппинг генерирует читаемый TS-проект VoltAgent.

Сверено с документацией VoltAgent 2.0.x (сентябрь 2026). Workflows там в статусе Preview: стабильны, но возможны breaking changes.

### 20.1. Маппинг ядра

| Конструкция ядра | VoltAgent | Что добавляет наш слой |
|---|---|---|
| Последовательность и привязки | Цепочка `createWorkflowChain`; данные шагов и общее состояние воркфлоу (workflow state) | Выходы узлов хранятся в состоянии по ID узла с метками происхождения; привязки читают оттуда, а не из автослияния данных |
| `llm` | Шаг `andThen` → `agent.generateText(..., { output: Output.object({ schema }) })` | Отрисовка шаблона, эффективная конфигурация, строгий вывод, валидаторы, ремонт, replay-кэш, спан с промтом и провенансом |
| `tool` | `createTool` (Zod); `MCPConfiguration` для внешних MCP | Классы эффектов, ключи идемпотентности, пин схем MCP |
| `code` | `andThen` | Изоляция чистых функций, типы на входе и выходе |
| `human` | `suspend` / `resume` с `resumeSchema`, resume через REST | Формы по типу; таймауты через наш планировщик — сам VoltAgent по таймауту не возобновляет |
| `parallel` | `andAll` — ждать все; `andRace` — первый | `quorum(k)`, `any`, политики ошибок веток: обёртка веток в Result и шаг сведения |
| `map` | `andForEach` с `concurrency`, `items`, `map`; порядок сохраняется | `on_item_error`: обёртка элемента в Result и фильтр по политике |
| `switch` | `andBranch` — все ветки с истинным условием идут параллельно, first-match нет | Условия по значениям enum взаимоисключающие по построению; полноту проверяет компилятор; шаг сведения к одному типу |
| `loop` | `andDoWhile` / `andDoUntil` — минимум одна итерация, лимита итераций нет | `max_iter`, бюджет, стагнация и лучший вариант: счётчики и лучший кандидат в состоянии воркфлоу, условие генерирует компилятор |
| `gate` | `andSleep`, `andSleepUntil`, suspend | Ожидание событий с таймаутом и политикой |
| `try` | `retries` на шаге, `retryConfig` на воркфлоу, хуки ошибок | Типизированные ошибки и запасной путь |
| Компоненты | Вложенные цепочки и шаги; `agent.toTool()`; воркфлоу как MCP-тул | Дженерики и контракты — на этапе компиляции |

### 20.3. Архитектура рантайма

- **Сборщик цепочек.** Для каждой выпущенной версии воркфлоу компилятор выдаёт план. Сборщик строит из плана цепочку VoltAgent с ID вида `flow@version` и регистрирует её. Черновики для тестовых прогонов собираются так же.
- **Исполнители узлов** — наш код внутри шагов VoltAgent: `llm`, `tool`, `human`, `code`. Именно в них живут гарантии: строгий вывод, валидаторы, провенанс, бюджеты, политики, replay-кэш.
- **Состояние прогона** хранится в общем состоянии воркфлоу:
  - выходы узлов по ID с метками происхождения;
  - счётчики циклов и лучшие кандидаты;
  - остаток бюджета.

  После падения `restart` восстанавливает его вместе с данными шагов.
- **Хранилище — Postgres.** История исполнений и память VoltAgent — через адаптер `@voltagent/postgres`. Проекты, спеки, реестры, датасеты, кассеты и журнал — наши таблицы в той же базе.
- **Codegen** — тот же маппинг, но на выходе читаемый TS-проект VoltAgent. Он входит в бандл экспорта и проходит конформанс-набор.

### 20.4. Пробелы и как закрываем

| Пробел | Решение |
|---|---|
| Workflows в статусе Preview | Пин версий; адаптер изолирует VoltAgent; конформанс-набор на каждом обновлении |
| Нет `quorum`, `any` и политик ошибок у параллели и map | Обёртки веток и элементов в Result; шаг сведения по политике |
| `andBranch` запускает все ветки с истинным условием | Взаимоисключающие условия по enum; компилятор проверяет полноту |
| У циклов нет лимита итераций | Счётчики в состоянии воркфлоу; условие генерирует компилятор |
| Human-задачи не возобновляются по таймауту | Наш планировщик вызывает resume с payload таймаута |
| Time travel заново исполняет вызовы моделей | Replay-кэш ответов в исполнителе `llm` |
| Регистрация воркфлоу в рантайме без перезапуска в документации не подтверждена | Проверить в спайке; запасной вариант — воркер на проект с перезагрузкой при выпуске |
| Мультитенантность | Tenant в контексте, префиксы памяти и схемы Postgres, ключи провайдеров на проект |

### 20.5. Встроенные агенты и продажа сервиса

- **Встроенный архитектор.** Агент VoltAgent с нашими MCP-тулами работает внутри продукта: клиент описывает процесс в чате, архитектор собирает, компилирует, тестирует и предлагает версию на аппрув. Внешние Claude и Codex получают тот же контракт через MCP.
- **Встроенный улучшатель** — фоновый агент: разбирает провалы, запускает эксперименты, предлагает правки.
- **Модель продажи:**
  - SaaS по проектам, прогонам и местам;
  - управляемый хостинг выпущенных воркфлоу;
  - свои ключи (BYOK) или оплата моделей с наценкой через наш каталог;
  - библиотека платных компонентов и шаблонов;
  - внедрение как услуга — готовый канал для консалтинга.
- **Изоляция.** Встроенные агенты работают в Workspace с песочницей, политиками тулов и аппрувом на запись.

### 20.6. Спайк: бинарные проверки VoltAgent

1. Цепочка собирается из IR в рантайме и регистрируется без перезапуска процесса.
2. `restart` после убийства процесса восстанавливает состояние воркфлоу с нашими метками и продолжает с чекпоинта.
3. Time travel вместе с replay-кэшем даёт побитово тот же прогон.
4. Динамический агент применяет эффективную конфигурацию вызова: модель, тулы, параметры.
5. OTel-спаны с нашими атрибутами доходят до Langfuse.
6. Сгенерированный codegen-проект проходит конформанс-набор эталонного воркфлоу.
