# Атрибуция правок: видно, кто что изменил

> Решает: человек в любой момент отличает свою правку от правки агента, понимает последний патч Claude за один взгляд и может его отменить.
> Влияет на: [15. Studio §6, §8.3](../15-studio-frontend.md), [14. MCP-контракт §2, §9](../14-mcp-contract.md), [ADR-0009](../adr/0009-op-log-not-crdt.md), [frontend/build.md](build.md), [30. План фронтенда](../30-frontend-plan.md) (Г2, Г6), [04. IR](../04-ir-schema.md)

## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Источник истины атрибуции | `spec_ops.actor` + `rev` из op-лога; UI ничего не вычисляет сам | ADR-0009 уже пишет каждую операцию с автором; второй реестр = рассинхрон |
| Носитель различия | триада на узел: **форма обводки + иконка-бейдж + текст в инспекторе**; цвет — четвёртый, необязательный слой | §8.3: цвет не единственный носитель |
| Гранула атрибуции | узел и поле узла (`path` операции), не «весь граф» | операции адресуют путь, дешевле любой диффалгоритмики |
| Позиции узлов (`ui`) | атрибуцию **не получают вовсе**, LWW по полю | `ui` вне `spec_hash` и вне `rev` (04-IR §4.4) — перетаскивание не событие истории |
| Дифф последнего патча | **слой поверх графа**, а не отдельный экран; переключатель, раскладка на время слоя заморожена | build.md: «дифф последнего патча — на канвасе»; перекладка ELK под диффом убивает узнавание |
| Что значит «последний» | от `seen_rev` — последней ревизии, которую **этот человек видел**, не от `rev-1` | агент делает серию патчей за минуту; «предыдущая ревизия» показала бы 1/12 работы |
| Где живёт `seen_rev` | на сервере, на пару (`user_id`, `spec_id`); в UI оптимистично | переживает перезагрузку и вторую вкладку; иначе дифф врёт после F5 |
| Откат операции агента | **не undo, а инверсный `flow_patch`** поверх текущей `rev`; инверсию считает сервер | единственная точка записи остаётся одна (П1 контракта), история линейна и вперёд-направлена |
| Уведомление в инспекторе | чистые поля обновляются молча с подсветкой, «грязное» (редактируемое) поле **никогда** не перезаписывается — над ним плашка «агент предложил другое значение» | блокировка до подтверждения останавливает работу, молчание теряет ввод |

## 1. Кодировка атрибуции на канвасе

| Состояние | Обводка | Бейдж (lucide) | Цвет | Текст в инспекторе |
|---|---|---|---|---|
| Не менялось | 1px сплошная, базовый токен | нет | нет | «без изменений с `rev N`» |
| Изменено мной в этой сессии | 2px сплошная | `User`, угол слева сверху | `--accent-human` | «вы, `rev 47`, 2 мин назад» |
| Изменено агентом, **не просмотрено** | 2px **штриховая** + точка-индикатор на бейдже | `Sparkles` | `--accent-agent` | «Claude, `rev 52`, не просмотрено» |
| Изменено агентом, просмотрено | 1px штриховая | `Sparkles`, приглушённый | `--accent-agent` (60%) | «Claude, `rev 52`» |
| Удалён агентом | призрак: 50% прозрачности, штриховая заливка, узел не перетаскивается | `Trash2` | нейтральный | «удалён Claude в `rev 52`» |
| Конфликтует (моя правка отклонена) | 2px сплошная + пунктирный внешний контур | `AlertTriangle` | `--destructive` | блок конфликта с `ops_since` |

Различимость без цвета: сплошная = человек, штриховая = агент, призрак = удаление, двойной контур = конфликт.
Иконки совпадают со словарём §8.3 (`human=User`, `generated=Sparkles`) — новый словарь не заводим.

**Затухание — по событию, а не по таймеру:** таймер гасит метку до того, как её увидели.

| Метка | Снимается когда |
|---|---|
| «моя правка» | закрытие спеки / новая рабочая сессия (`session_id` сменился) |
| «агент, не просмотрено» | узел открыт в инспекторе, либо закрыт слой диффа, либо кнопка «всё просмотрено» → `seen_rev := current_rev` |
| «агент, просмотрено» | конец сессии; дальше видно только в ленте ревизий и провенансе поля |
| призрак удалённого | вместе с меткой «просмотрено»; узел исчезает с холста |

## 2. Слой диффа последнего патча агента

Переключатель `Дифф Claude` (клавиша `D`), состояние — в URL (`?diff=52..64`): ссылка шарибельна.

| Элемент | Как показан |
|---|---|
| Незатронутые узлы | приглушены до 40%, остаются на месте (не скрыты — иначе теряется ориентация) |
| Добавленные узлы | полная яркость, штриховая обводка, бейдж `Plus` |
| Удалённые узлы | призраки на прежних координатах, рёбра к ним пунктиром |
| Изменённые поля | на узле — счётчик `3 поля`, раскрытие показывает список `path: было → стало` |
| Добавленные рёбра | двойной штрих; удалённые — призрачный пунктир |
| Перемещения (`ui`) | **не показаны** — это не изменение спеки |

**Раскладка заморожена, пока слой открыт.** ELK не перезапускается: добавленные узлы получают
координаты от инкрементальной раскладки в свободном месте, призраки держат старые. Иначе «дифф»
превращается в «весь граф переехал».

**«Агент сделал 12 операций» одной картинкой.** Над канвасом — сводная плашка:

`Claude · rev 52 → 64 · 12 операций · +3 узла · −1 · 6 полей · 2 связи` + `[по шагам]` `[всё просмотрено]`

Клик по счётчику фильтрует слой до этого класса изменений. Камера — zoom-to-fit по bounding box затронутых
узлов, не по всему графу. Если их > 8 или они в разных кластерах — справа список-ступеньки (операция =
строка, клик = перелёт), маркеры на миникарте. `[по шагам]` проигрывает op-лог по одной операции.

## 3. `seen_rev` — прочитанная ревизия

`spec_read_marks(tenant_id, user_id, spec_id, seen_rev, ts)`: не ревизия спеки, `rev` не двигает, в
`spec_hash` не входит. Продвигается только явными событиями из таблицы затухания — само открытие спеки
`seen_rev` **не** двигает. Границу диффа можно растянуть назад по шкале: `seen_rev` — дефолт, не предел.

## 4. Лента ревизий

Горизонтальная шкала под канвасом: одна засечка = одна ревизия, форма засечки повторяет кодировку
(сплошная = человек, штриховая = агент), группировка серий одного автора в один блок с числом операций.
Стрелки `←/→` — шаг по истории; просмотр прошлой ревизии переводит канвас в явный режим «история, `rev 47`»
с баннером и запретом правки (правка = «восстановить сюда» через инверсный патч, §5).

| Что показываем | Откуда | Что это |
|---|---|---|
| автор, время, состав операций, `path` | `spec_ops_read` (новый тул, §Контракт) | **что** изменилось — механика |
| человекочитаемое «почему» | `journal_read`, привязка по `rev` | **зачем** — решение и обоснование |
| диагностика на ревизии | `flow_compile({ rev })` | было ли состояние валидным |

Описание засечки строится из операций (`добавлен узел extract_line_items`, `изменён промт judge`), а
запись журнала, если она есть на этой `rev`, показывается второй строкой. Нет записи — не выдумываем.

## 5. Откат одной операции агента

`spec_ops_read({ spec_id, rev, invert: true })` возвращает инверсные операции как `candidates[].apply` —
готовый вызов `flow_patch` с текущим `base_rev` (П4 контракта). Откат — новая ревизия вперёд, а не
вычёркивание из истории.

| Случай | Возможно? | Что видит человек |
|---|---|---|
| Инвертируемая операция, `path` не трогали позже | да, в один клик | «Отменить эту операцию» → новая `rev`, засечка «откат `rev 52`» |
| `path` изменён позже мной или агентом | нет, автоматически | «Поверх этого было ещё 2 правки» + их список + выбор: откатить всё до `rev 51` / отменить только моё / править вручную |
| Операция не коммутирует со следующими (`remove` узла, к которому потом привязались) | нет | инверсия проваливает валидатор внутри транзакции; показываем `problems[]` и `candidates[]` — ровно тот же экран, что у ошибки компиляции, без отдельного UI |
| Серия из 12 операций агента | да, как один патч | «Отменить весь патч Claude» — инверсия всей серии одним `flow_patch` |
| `dry_run` перед откатом | всегда | кнопка отката сначала шлёт `dry_run: true`; если валидатор упал, кнопка не «сломается после нажатия», а сразу показана как «откат невозможен» с причиной |

Честная формулировка в UI: «откатить можно то, поверх чего никто не писал». Лгать про «undo как в
редакторе» нельзя — op-лог линейный и вперёд-направленный.

## 6. Провенанс поля

Наведение на поле (400 мс) → поповер: `Claude · rev 52 · 14:03 · было "…"` + ссылки «показать в ленте» и
«отменить эту правку» (механика §5). Источник — последняя операция с этим `path` в `spec_ops`, в v1 на лету
(op-лог спеки — сотни строк), материализация `spec_field_prov` — когда упрётся. Поля без операций в логе
показывают ревизию создания или импорта.

## 7. Агент изменил то, что открыто в инспекторе

| Состояние поля | Поведение |
|---|---|
| Поле чистое (не редактируется) | молча обновляется, подсвечивается на 200 мс, бейдж `Sparkles` у подписи поля до просмотра |
| Поле «грязное» (есть несохранённый ввод) | ввод **не трогаем**; над полем плашка «Claude предложил другое значение» с `[посмотреть]` `[взять его]` `[оставить моё]` |
| Узел удалён агентом | инспектор не закрывается; шапка «узел удалён Claude в `rev 52`», содержимое в режиме чтения, кнопки `[вернуть]` (инверсный патч) и `[закрыть]` |
| Моя отправка патча разошлась по `rev` | ответ `REV_CONFLICT` → плашка с `ops_since`; `rebase: auto` — кнопка «применить поверх», `manual` — построчный разбор пересечения путей |

Блокировки инспектора до подтверждения нет нигде: человек всегда может продолжить печатать.

## Крайние случаи

| Ситуация | Что делает система | Что видит человек |
|---|---|---|
| Агент шлёт патч, пока узел тащат мышью | позиция — `ui`, вне `rev`; структурный патч применяется, перетаскивание завершается нормально | узел доезжает, где отпустили; на нём появляется штриховая обводка |
| Агент удалил узел, который человек тащит | drag завершается в никуда, узел становится призраком на месте отпускания | тост «Claude удалил этот узел» + `[вернуть]` |
| 5 патчей подряд за 10 секунд | SSE-события коалесцируются в одну сводку, счётчики накапливаются | одна плашка «12 операций», а не пять тостов |
| Человек открыл дифф и ушёл на час | `seen_rev` не двигается, дифф растёт | при возврате — «за это время: 41 операция», предложение сузить шкалу |
| Две вкладки одного человека | `seen_rev` серверный, продвижение в одной вкладке приходит по SSE во вторую | метки «не просмотрено» снимаются в обеих |
| Откат отката | обычная инверсия инверсии, новая `rev` | в ленте видно оба шага, история не схлопывается |
| Патч агента одновременно валидный и «не тот» | система не судит о качестве | «просмотрено» ≠ «согласен»; принятие выражается только отсутствием отката |
| Импорт спеки (`flow_import`) | одна ревизия с автором-человеком, атрибуция на все узлы одинаковая | «импортировано, `rev 1`» — узлы не подсвечены как изменённые |

## Открытые вопросы

1. **Мультиагентность.** `actor` в `spec_ops` — это «Claude» или конкретная сессия/скилл? Если параллельных
   агентских сессий станет больше одной, штриховой обводки не хватит: нужен различающий признак на бейдже
   (инициал/номер), и это меняет кодировку §1 — решать до первой реализации, а не после.
2. **Куда писать `seen_rev` при работе без аккаунта.** В прототипе на моках пользователь один; серверная
   таблица требует `user_id`. Либо фиктивный `local-user`, либо `seen_rev` в localStorage с явным долгом.
3. **Текст промта внутри узла.** ADR-0009 допускает точечный CRDT для него. Если он появится, у поля
   промта не будет `rev`-атрибуции по операциям — провенанс §6 для него придётся строить иначе.
4. **Глубина ленты.** Показываем все ревизии черновика или сворачиваем всё до последней опубликованной
   версии? Влияет на то, где проходит граница между лентой ревизий и историей версий из DECISIONS.
