# Кластер: сборка воркфлоу

> Экраны: канвас графа, инспектор узла, палитра добавления узла, редактор шаблона промта, граф контекста, карта промтов, раскрытие компонента до примитивов, панель ошибок компиляции
> Приоритет кластера: P0 — без него прототип не отвечает ни на один продуктовый вопрос

## Что проверяем прототипом

1. **Читается ли граф.** Воркфлоу из 15 узлов с параллелизмом, циклом и свёрнутым `judge_panel` — человек за 30 секунд отвечает «где решение, где цикл, где сломано». Если нет — продукта нет, остальное не важно.
2. **Видно ли руку агента.** После патча Claude человек без чтения журнала понимает: что изменилось, где, почему. Дифф последнего патча — на канвасе, а не в отдельном экране.
3. **Ошибка компилятора как действие, а не как текст.** Гипотеза: `problems[] + candidates[]` достаточно, чтобы чинить в один клик, не открывая редактор. Проверяем на 6 разных кодах.
4. **Компонент как единица мышления.** Гипотеза: свёрнутый `judge_panel` читается как один узел, а раскрытие до примитивов не ломает ориентацию (рёбра наружу, возврат назад).
5. **Порядок «контекст до промта».** Граф контекста и карта промтов — проверяем, ведёт ли непокрытая потребность человека к правке раньше, чем он начал писать текст.

## Экраны

### Канвас графа — P0

- **Зачем:** единственное место, где воркфлоу существует целиком: структура, состояние компиляции и след последнего изменения агента в одном поле зрения.
- **Сценарии:**
  1. Открыл спеку → раскладка готова (`data-layout="ready"`) → скан сверху вниз по слоям.
  2. Увидел красные узлы → открыл панель ошибок → починил кандидатом → узлы позеленели без перезагрузки.
  3. Claude прислал патч (`rev` вырос по SSE) → на канвасе загорелась плашка «Claude: +2 узла, 1 биндинг» → кликнул «показать дифф» → добавленное/удалённое/изменённое подсвечено поверх графа.
- **Ключевые элементы:**

| Элемент | Что показывает | Взаимодействие |
|---|---|---|
| `StageNode` | вид узла, модель, статус компиляции, счётчик проблем | клик → инспектор (View Transition), `⌘K` → палитра |
| `TypedPort` | вид порта (`data`/`control`/`error`) + схема | hover → совместимые порты подсвечены, несовместимые притушены |
| `BindingEdge` | связь и её источник; пунктир — опциональный | клик → подсветка пути, hover → карточка биндинга |
| `CompileErrorOverlay` | бейдж `E`/`W` на узле, топ-кандидат в поповере | «Починить» = `apply.tool` одним кликом |
| `PatchDiffLayer` | дифф последнего патча: добавлено (зелёная рамка), удалено (призрак-узел), изменено (жёлтая метка поля) | тумблер «дифф последнего патча», `[`/`]` — шаг по ревизиям |
| `AgentPresenceBar` | «Claude редактирует, TTL 4:12», `rev`, автор последнего патча | «перехватить» снимает advisory-lock |

- **Режим фазы 0:** руками — навигация, сворачивание/раскрытие, фильтры, применение `candidate` из ошибки компиляции (один клик, с `dry_run` перед записью), правка скалярного поля в инспекторе. Только через агента — добавление/удаление узла, протяжка связи, определение компонента, привязка источников контекста: палитра формулирует запрос, а не пишет в спеку.

- **Состояния:** пусто — «спека пустая, начните с архетипа» + кнопка в палитру архитектур; загрузка — скелет узлов в позициях предыдущей раскладки, оверлей «раскладка…» (не спиннер на пустом поле); ошибка — граф последней успешной ревизии + баннер «не удалось получить rev 44, показан 43»; деградация — ELK-воркер упал → вертикальный список узлов по топосорту с явной плашкой «раскладка недоступна»; нет прав — канвас в read-only, панель ошибок без кнопок «Починить», плашка со скоупом.
- **Операции:** `flow_get`, `flow_compile`, `flow_patch` (`dry_run` + применение кандидата), `flow_lock`, `component_expand`, `agent_effective_config` (для превью в hover-карточке).
- **Мок-данные:** спека из 15 узлов: 3 параллельные ветки, 1 цикл с `max_iterations`, свёрнутый `judge_panel` (внутри 5 примитивов), 1 подворкфлоу; 4 ошибки и 3 предупреждения на 5 разных узлах; op-log с 6 ревизиями, последняя — патч агента на 3 операции; крайние случаи: узел без выходных связей, узел с 4 портами, ребро через границу компонента, конфликтный `rev` (44 против 43).
- **Что проверяем:** можно ли по одному взгляду сказать, что агент только что сделал и что в графе сломано, — без перехода на другой экран.

### Панель ошибок компиляции — P0

- **Зачем:** превращает вывод компилятора в очередь работ: что чинить первым и чем именно.
- **Сценарии:**
  1. Компиляция вернула 7 проблем → список сгруппирован по коду, отсортирован по severity и по глубине в графе (сначала то, что ломает всё ниже).
  2. Навёл на строку → узел подсветился на канвасе; кликнул → вьюпорт долетел до узла.
  3. Раскрыл кандидата → видит `title`, `rationale`, `risk`, `affects[]` и точный `apply` → «Починить» → `flow_patch` с `dry_run` → превью новых проблем → применил.
- **Ключевые элементы:**

| Элемент | Что показывает | Взаимодействие |
|---|---|---|
| `ProblemRow` | `code`, `severity`, `at.node_id`/`path`, сообщение | hover → подсветка на канвасе, `Enter` → переход |
| `CandidateCard` | `confidence`, `risk`, `affects[]`, `rationale`, дифф применения | «Починить» / «Показать дифф» / «Отклонить» |
| `DryRunPreview` | что станет после применения: было 7 проблем — станет 3 | подтвердить / отменить |

- **Состояния:** пусто — «компиляция зелёная, L1 пройден», отчёт по стоимости свёрнут; загрузка — предыдущий список притушен, не исчезает; ошибка — «компилятор недоступен, показан отчёт ревизии 43» + метка возраста; деградация — есть `problems[]`, нет `candidates[]` → только навигация и «Спросить Claude»; нет прав — кандидаты видны, «Починить» заблокирована с причиной.
- **Операции:** `flow_compile`, `flow_patch` (`dry_run=true`, затем применение), `help_contract({topic:'codes'})` для расшифровки кода, `flow_get`.
- **Мок-данные:** 7 проблем по 6 разным кодам: 2 с одним кандидатом высокой уверенности, 1 с тремя конкурирующими кандидатами, 1 `risk: high`, 2 без кандидатов вовсе, 1 предупреждение уровня спеки без `node_id`; один кандидат при `dry_run` порождает новую ошибку — это обязательный крайний случай.
- **Что проверяем:** доверяет ли инженер кнопке «Починить» — и что ему нужно увидеть до клика, чтобы доверять.

### Инспектор узла — P0

- **Зачем:** всё о выбранном узле в одной панели — контракт, промт, эффективная конфигурация, происхождение каждого значения.
- **Сценарии:**
  1. Клик по узлу → панель справа: вкладки «Контракт / Промт / Конфигурация / Проблемы».
  2. Не понял, откуда взялась `temperature` → hover по полю → цепочка `default → agent → node`.
  3. Увидел, что поле изменил последний патч агента → бейдж «изменено в rev 44» с обоснованием из журнала.
- **Ключевые элементы:**

| Элемент | Что показывает | Взаимодействие |
|---|---|---|
| `PortContract` | входы/выходы со схемами и кто к ним привязан | клик по порту → подсветка ребра на канвасе |
| `EffectiveConfigView` | итоговые параметры вызова | hover → `ProvenanceBadge` с источником поля |
| `ChangedInRevBadge` | какие поля тронул последний патч | клик → строка журнала с `rationale` |

- **Состояния:** пусто — «узел не выбран», список последних тронутых узлов; загрузка — скелет по вкладкам, шапка с именем узла уже видна; ошибка — вкладка «Конфигурация» с плашкой «динамические функции агента не вернули конфиг»; деградация — нет провенанса → значения без бейджей и явное «источник неизвестен»; нет прав — поля read-only, видно кем именно правится.
- **Операции:** `flow_get({node_id, depth:1})`, `agent_effective_config`, `agent_get`, `component_get`, `journal_read`, `flow_patch` (правка одного поля).
- **Мок-данные:** 3 контрастных узла: LLM-узел с 4 слотами и переопределением модели на уровне узла, tool-узел с закреплённой MCP-схемой, узел-судья внутри компонента; у одного узла провенанс отсутствует; поле, переопределённое трижды по цепочке.
- **Что проверяем:** достаточно ли провенанса, чтобы инженер согласился с чужим (агентским) значением, не переспрашивая.

### Раскрытие компонента до примитивов — P0

- **Зачем:** доказать, что компонент — не чёрный ящик: любой `judge_panel` разбирается до примитивов ядра и собирается обратно без потери ориентации.
- **Сценарии:**
  1. Свёрнутый `judge_panel` с двумя внешними рёбрами → контекстное меню → «Раскрыть».
  2. Граница компонента осталась контейнером, внутри 5 примитивов, внешние рёбра перецепились на конкретные внутренние порты, вьюпорт доехал плавно, breadcrumb показывает `wf › judge_panel`.
  3. Раскрыл узел на уровень глубже → breadcrumb `wf › judge_panel › vote`; `Esc` сворачивает на уровень вверх.
- **Ключевые элементы:**

| Элемент | Что показывает | Взаимодействие |
|---|---|---|
| `CollapseBoundary` | границу компонента, его имя, контракт и «раскрыто N из M» | клик по заголовку → свернуть |
| `DepthBreadcrumb` | путь раскрытия | клик по уровню → свернуть до него |

- **Состояния:** пусто — компонент без определения примитивов: «внешний компонент, тела нет»; загрузка — граница нарисована, внутренность — скелет, раскладка ещё считается; ошибка — «раскрыть не удалось», компонент остаётся свёрнутым, не пустым; деградация — глубже 2 уровней раскрытие запрещено с явным объяснением, а не молча; нет прав — раскрытие доступно всегда (чтение), правка внутри — нет.
- **Операции:** `component_expand({depth})`, `component_get`, `component_list`, `flow_get`.
- **Мок-данные:** `judge_panel` из 5 примитивов с внутренним ветвлением; вложенный компонент внутри компонента (2 уровня); компонент с 3 внешними рёбрами, одно из которых `error`-порт; компонент без тела (внешний).
- **Что проверяем:** не теряет ли человек контекст после раскрытия — и находит ли дорогу назад без Undo.

### Редактор шаблона промта — P0

- **Зачем:** текст промта правится там, где сразу видно его отрисовку на реальной фикстуре и диагностику компилятора по слотам.
- **Сценарии:**
  1. Открыл шаблон узла → слева код со слотами, в центре отрисовка на выбранной фикстуре, справа дифф с предыдущей ревизией.
  2. Набрал `{{` → автодополнение предлагает только слоты, у которых есть привязанный источник.
  3. Сослался на непривязанный слот → жёлоб зажёгся, quick-fix «привязать к выходу узла N» → тот же `candidate`, что получил бы агент.
- **Ключевые элементы:**

| Элемент | Что показывает | Взаимодействие |
|---|---|---|
| `SlotDecorator` | слот, окрашенный по виду источника (кодировка графа контекста) | клик → источник в графе контекста |
| `RenderPreview` | отрисовку серверным liquidjs на фикстуре | смена фикстуры — `FixturePicker` |
| `RenderDiffPane` | дифф отрисовки между ревизиями, не дифф исходника | переключение «исходник / результат» |

- **Состояния:** пусто — шаблона нет: заготовка из архетипа узла; загрузка — редактор доступен, превью со скелетом; ошибка — «рендер не удался», показан последний успешный результат с меткой устаревания; деградация — компилятор недоступен → подсветка слотов есть, диагностики нет, явная плашка; нет прав — редактор read-only, превью работает.
- **Операции:** `flow_get`, `flow_compile`, `flow_patch` (сохранение шаблона), `context_plan` (список доступных слотов), `dataset_get` (фикстуры).
- **Мок-данные:** 3 шаблона: короткий, длинный (~4k токенов, проверка виртуализации превью), с циклом по массиву; 3 фикстуры, одна — пустой массив, одна — с юникодом и переводами строк; один слот без источника.
- **Что проверяем:** правится ли промт без ухода в другие экраны, и достаточно ли диффа отрисовки вместо диффа исходника.

### Граф контекста — P1

- **Зачем:** до написания промтов показать, у каких решений потребность в контексте не покрыта источником; это проверка этапов 2–3 сквозного сценария.
- **Сценарии:**
  1. Открыл, фильтр по умолчанию — «только непокрытые потребности», а не весь граф.
  2. Hover по потребности → 1-hop соседи ярко, остальное притушено; видно, что источник конфликтный (двойное ребро).
  3. Клик по потребности → переход к узлу-потребителю на канвасе с уже открытым инспектором.
- **Ключевые элементы:**

| Элемент | Что показывает | Взаимодействие |
|---|---|---|
| `NeedNode` / `SourceNode` | вид источника формой + иконкой + цветом | hover → 1-hop подсветка |
| `UnsatisfiedNeedBadge` | непокрытую потребность (красный пунктир) | клик → кандидаты привязки от `context_plan` |
| `ContextKindLegend` | 5 видов источников | toggle-group — фильтр по виду и по стадии |

- **Состояния:** пусто — «потребности не размечены», кнопка «попросить Claude построить план контекста»; загрузка — легенда и фильтры сразу, граф скелетом; ошибка — последний известный граф + метка ревизии; деградация — при >120 узлах граф не рисуется целиком, включается обязательный фильтр по стадии; нет прав — привязка источников только через агента.
- **Операции:** `context_graph`, `context_plan`, `kb_indexes`, `context_bind` (применение кандидата), `flow_get`.
- **Мок-данные:** 40 потребностей, 18 источников всех пяти видов; 4 непокрытые потребности; 1 потребность с двумя конфликтующими источниками; 1 опциональный источник; 1 RAG-индекс в состоянии «переиндексируется».
- **Что проверяем:** заставляет ли экран закрыть контекст до того, как человек начал писать промт.

### Карта промтов — P1

- **Зачем:** показать, из чего собирается каждый промт и какие узлы пострадают от правки одного фрагмента.
- **Сценарии:**
  1. Слева граф «фрагмент → шаблон → узел» сверху вниз; выбрал фрагмент → справа список использований.
  2. Справа — трасса сборки конкретного промта: слоты подсвечены цветами видов источников (та же кодировка, что в графе контекста).
  3. Клик по слоту → источник: узел-предшественник, статика или RAG-индекс.
- **Ключевые элементы:**

| Элемент | Что показывает | Взаимодействие |
|---|---|---|
| `PromptAssemblyTrace` | пошаговую сборку промта со слотами | клик по слоту → источник |
| `FragmentUsageList` | «этот фрагмент в 7 шаблонах, 12 узлах» | клик → узел, «показать влияние правки» |

- **Состояния:** пусто — «общих фрагментов нет, все промты локальные»; загрузка — граф скелетом, панель сборки пустая; ошибка — «сборка недоступна», список использований остаётся; деградация — без данных прогона трасса показывает шаблон, а не фактический текст, и говорит об этом; нет прав — только чтение.
- **Операции:** `flow_get`, `flow_compile`, `run_get_node` (фактически собранный промт, если есть прогон), `context_graph` (кодировка источников).
- **Мок-данные:** 6 фрагментов, 9 шаблонов, 15 узлов; один фрагмент используется в 8 местах; один шаблон собирается из 4 фрагментов + выход соседнего узла; один осиротевший фрагмент без использований.
- **Что проверяем:** отвечает ли экран за 10 секунд на «что сломается, если я перепишу этот фрагмент».

### Палитра добавления узла — P1

- **Зачем:** единая точка «что вообще можно добавить» — архетипы, компоненты, тулы, паттерны; в фазе 0 она формулирует запрос агенту, а не правит спеку.
- **Сценарии:**
  1. `⌘K` на канвасе → поиск по каталогу и библиотеке компонентов, группы: примитивы / компоненты / паттерны архитектуры / тулы.
  2. Выбрал `judge_panel` → превью контракта и типовых сбоев, подсказка о совместимости с выделенным узлом.
  3. В фазе 0 — «Попросить Claude добавить»: формируется точный запрос с `spec_id`, точкой вставки и параметрами; в фазе 3 та же кнопка становится прямым `flow_patch`.
- **Ключевые элементы:**

| Элемент | Что показывает | Взаимодействие |
|---|---|---|
| `CatalogItem` | имя, вид, контракт, стоимость, типовые сбои | `↑↓`+`Enter`, hover → превью |
| `AgentRequestFooter` | текст запроса, который уйдёт агенту | правка запроса перед отправкой |

- **Состояния:** пусто — «ничего не найдено» + «описать словами и отдать Claude»; загрузка — группы с прошлого открытия, поиск активен; ошибка — локальный кеш каталога + метка «список может быть неполным»; деградация — без выделенного узла подсказки совместимости выключены; нет прав — кнопка применения отсутствует, остаётся только запрос агенту.
- **Операции:** `catalog_list`, `catalog_get`, `component_list`, `component_get`, `architecture_search`, `architecture_get`, `provider_models`; применение — `flow_patch` / `architecture_instantiate` (фаза 3).
- **Мок-данные:** ~60 элементов каталога в 4 группах; 3 паттерна архитектуры со стоимостью и типовыми сбоями; 2 компонента, несовместимых с выделенным узлом по схеме порта; один элемент с очень длинным именем.
- **Что проверяем:** ощущается ли «попросить агента» приемлемой заменой прямому добавлению — или это главный источник раздражения в фазе 0.

## Чего на этих экранах НЕ будет в прототипе

| Отложено | Почему | Когда вернём |
|---|---|---|
| Прямое редактирование графа мышью (добавление узла, протяжка связи, drag) | фаза 0 по §14 — просмотр и отладка; контролируемый режим канваса уже включён, чтобы не переписывать его позже | фаза 3, после того как прототип подтвердит, что канвас читается |
| Undo/redo и ручное разрешение конфликта `rev` | нужен op-log на сервере; на моках ребейз честно не сымитировать, а фальшивый Undo даст ложный сигнал о безопасности правок | вместе с бэкендом `flow_patch` |
| Совместное присутствие (курсоры, выделения нескольких актёров) | пользователь v1 — один инженер плюс агент; advisory-lock и плашка «Claude редактирует» закрывают 95% случаев | когда появится второй человек |
| LOD, `onlyRenderVisibleElements`, миграция с DOM-рендера | пороги §6.4 начинаются со 150 узлов; прототип живёт на 15 — оптимизировать нечего, а ранняя оптимизация скроет проблемы читаемости | когда реальная спека перевалит 150 видимых узлов |

## Операции, которых нет в реестре §2 14-mcp-contract (находки)

- **Чтение op-log** (`spec_ops_read` / `flow_history`): дифф последнего патча на канвасе и шаг по ревизиям `[`/`]` неоткуда взять. `journal_read` даёт решения с обоснованиями, но не операции. Без этого центральная гипотеза «видно, что сделал агент» нереализуема.
- **Отрисовка шаблона на фикстуре** (`template_render`): §15 отправляет её «по HTTP к компилятору» — то есть у агента этой возможности нет вовсе, хотя промты правит в основном он. Асимметрия поверхностей.
- **Сборка промта из спеки** (`prompt_assembly`): `run_get_node` даёт собранный промт только для существующего прогона. Карта промтов на неисполненной спеке остаётся без данных.
- **Статус advisory-lock**: `flow_lock` только ставит и снимает. Плашке «Claude редактирует, TTL 4:12» нужен читающий вызов или поле в `flow_get`.
- **Отмена ревизии** (`flow_revert`): применил кандидата — стало хуже; без отката единственный путь назад — просить агента собрать обратный патч.

## Открытые вопросы к заказчику

1. **Дифф последнего патча — слой или режим?** Слой поверх графа (видно и структуру, и изменение, но плотнее) против отдельного режима «дифф ревизий» (чище, но требует переключения). Меняет архитектуру канваса, решать до реализации.
2. **Что считается «последним патчем», если агент прислал 5 подряд?** Дифф от предыдущей ревизии или от последней, которую человек видел? Второе честнее и требует хранить «прочитанную» ревизию на пользователя.
3. **Применение кандидата руками в фазе 0 — можно?** Задача называет фазу 0 read-only, но кандидат — это готовый `flow_patch` от компилятора, а не свободная правка. Если нельзя, ценность панели ошибок падает вдвое и это стоит зафиксировать явно.
4. **Порог раскрытия компонентов.** Раскрывать всё дерево по `depth` сразу или строго по одному уровню? Первое быстрее для отладки, второе спасает ориентацию. Прототип может показать оба, но мок-данные надо готовить под выбранный.
