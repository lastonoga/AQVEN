# Кластер: Прогон и отладка

> Экраны: запуск прогона, живой прогон на канвасе, отладчик прогона, инспектор узла с провенансом, водопад стоимости и латентности, дифф двух прогонов, таймлайн цикла, очередь человеческих задач.
> Приоритет кластера: P0

## Что проверяем прототипом

1. Объяснимость важнее скорости: эксперт выбирает не «где упало», а «почему выдало именно это». Если инспектор не отвечает на второй вопрос — продукт не тот.
2. Провенанс как навигация, а не как украшение: клик по значению ведёт к узлу-источнику. Если по нему не кликают — карту провенанса можно не строить.
3. Replay узла с правкой входа и заморозкой верхних узлов заменяет перезапуск всего прогона. Если всё равно перезапускают целиком — вся механика форков не нужна.
4. Деградация обязана быть громкой: любой сработавший фолбэк виден на канвасе, а не в трассе. Проверяем, что «зелёный молча» невозможен.
5. Одно выделение на весь экран (граф = водопад = лог = URL) — достаточно ли, или нужен второй независимый фокус.

## Экраны

### Запуск прогона (форма входа по типу) — P0

- **Зачем:** дать вход и выбрать ревизию, не собирая JSON руками; отсюда начинается любая отладка.
- **Сценарии:**
  1. Выбирает спеку и ревизию (по умолчанию последняя скомпилированная), видит вердикт компиляции.
  2. Переключает режим — `live` / `replay` из записи / прогон на датасете; форма входа перестраивается.
  3. Заполняет форму из JSON Schema входного типа, видит предполётную оценку стоимости и потолок итераций, ⌘↵ — запуск; вход остаётся в URL как пресет для повтора.
- **Ключевые элементы:**

| элемент | что показывает | взаимодействие |
|---|---|---|
| Пикер ревизии | `rev`, вердикт `flow_compile`, число ошибок L1 | выбор; при FAIL запуск заблокирован, ошибки кликабельны в канвас |
| Переключатель режима | live / replay / dataset | `radio-group`, перестраивает остальную форму |
| Форма входа из схемы | поля входного типа | RHF + ajv, ошибки до отправки |
| Предполётная оценка | стоимость, число вызовов, лимит итераций цикла | раскрытие по узлам |

- **Состояния:** пусто — нет скомпилированных ревизий, CTA «Скомпилировать» · загрузка — скелет формы, пикер уже активен · ошибка — компиляция FAIL, список `problems[]` со ссылками на узлы · деградация — replay-кассета неполна: «часть узлов пойдёт вживую» · нет прав — форма read-only, видна причина по скоупу.
- **Операции:** `flow_get`, `flow_compile`, `catalog_get` (схема входного типа), `dataset_get`, `run_start`.
- **Мок-данные:** 3 ревизии, одна с FAIL на 2 узлах; входной тип на 8 полей — вложенный объект, enum на 5 значений, nullable, массив строк; датасет на 40 элементов; 5 последних входов, один невалидный после смены схемы.
- **Что проверяем:** хватает ли формы из схемы, или эксперту всё равно нужен сырой JSON-редактор рядом.

### Живой прогон на канвасе — P0

- **Зачем:** пока прогон идёт — видеть, где он сейчас и сколько уже стоит, не открывая отладчик.
- **Первые 2 секунды:** граф нужной ревизии уже на экране из RSC-снимка, все узлы в `pending`, шапка показывает `runId` и «подключение». Ни одного скелета на месте графа. Дальше стрим только перекрашивает узлы.
- **Сценарии:**
  1. `step-start` зажигает узел, `step-complete` гасит и проставляет стоимость/длительность; в шапке растут факт и время.
  2. Клик по горящему узлу открывает инспектор справа, поток не прерывается.
  3. Узел ушёл в `suspend` — бейдж «ждёт человека» со ссылкой в очередь; разрыв SSE — «переподключение», после реконнекта состояние досчитывается из снимка.
- **Ключевые элементы:**

| элемент | что показывает | взаимодействие |
|---|---|---|
| Узел стадии | статус, номер попытки, стоимость, длительность | клик → `?node=` |
| Индикатор потока | подключён / переподключение / завершён / отменён | ручной ретрай |
| Счётчики шапки | факт против предполётной оценки, токены, время | hover → разбивка по узлам |
| Бейдж деградации | сработавшее звено: `retry` / `repair` / `truncated` / `degraded` / `escalated` | клик → вкладка «проверки» |

- **Состояния:** пусто — прогон не запускался · загрузка — граф есть, все узлы `pending`, «ожидаем первое событие» · ошибка — `workflow-error`: виновный узел красный, остальные серые и заморожены · деградация — жёлтая рамка + иконка звена, зелёным такой узел не бывает · нет прав — граф виден, replay/fork/отмена скрыты.
- **Операции:** `run_start`, `run_get`, `run_get_trace`. SSE-канал прогона — транспорт, а не операция реестра.
- **Мок-данные:** прогон на 18 узлов с ветвлением и циклом на 6 итераций; один узел `degraded` через `fallback_profile`, один `truncated` с повтором, один в `suspend`; записанный поток событий с паузой 4 с и разрывом на 12-м кадре.
- **Что проверяем:** достаточно ли канваса как главного экрана живого прогона, или человек сразу уходит в водопад и лог.

### Отладчик прогона — P0

- **Зачем:** одно рабочее место после прогона — граф, инспектор, водопад и лог с ОДНИМ выделением на весь экран.
- **Сценарии:**
  1. Открывает завершённый прогон, видит сводку стадий и первый красный узел; панель blame предлагает виновных с `confidence`.
  2. Переключает граф агрегированный ↔ развёрнутый, чтобы увидеть отдельные итерации цикла.
  3. Выделяет узел — граф, водопад и лог подсвечивают одно и то же, выделение в URL; отсюда replay с правкой входа, форк и переход в дифф.
- **Ключевые элементы:**

| элемент | что показывает | взаимодействие |
|---|---|---|
| Шапка прогона | `runId`, статус, ревизия, lineage «форк от…» | replay, fork, отмена, «открыть в Langfuse» |
| Граф прогона | агрегированный (повторы свёрнуты) / развёрнутый | `toggle-group`, выделение в `?node=` |
| Live-tail лога | события с фильтром по узлу и уровню | прилипание к низу, ⌘F |
| Панель blame | узлы-кандидаты с `confidence` и дельтой метрики | клик → узел |

- **Состояния:** пусто — прогонов нет · загрузка — четыре региона под своими границами, появляются независимо · ошибка — упавший регион показывает alert с ретраем, остальные три живут · деградация — в шапке счётчик «N узлов degraded», он же фильтр графа · нет прав — replay, fork и точки останова недоступны.
- **Операции:** `run_get`, `run_get_trace`, `run_get_node`, `run_stages`, `run_lineage`, `run_blame`, `run_replay_node`, `run_fork`, `component_expand`.
- **Мок-данные:** три прогона — зелёный, упавший на 12-м узле, форк от него; трасса на 400 спанов; цикл на 200 итераций × 8 узлов для проверки виртуализации развёрнутого режима.
- **Что проверяем:** держится ли «одно выделение на экран», или эксперту нужны два независимых фокуса, чтобы сравнить два узла рядом.

### Инспектор узла с провенансом — P0

- **Зачем:** ответить «почему узел выдал именно это» — от входа и промта до попыток и исхода — не открывая сырые логи.
- **Сценарии:**
  1. Вкладка «вход»: дерево значений, каждое с бейджем происхождения (`static` / `data` / `knowledge` / `generated` / `human`).
  2. Клик по значению — навигация `?node=<sourceStepId>&tab=raw` на узел-источник; провенанс работает и как пересылаемая ссылка.
  3. Смотрит отрисованный промт с подсветкой слотов, затем сырой ответ и распарсенный выход рядом.
  4. Разворачивает лестницу попыток (какие звенья сработали и почему итог `degraded`), правит вход, замораживает верхние узлы, ⌘↵ — replay и форк.
- **Ключевые элементы:**

| элемент | что показывает | взаимодействие |
|---|---|---|
| Вкладки вход / промт / ответ / проверки / стоимость | состояние сохраняется через `<Activity>` | хоткеи 1…5 |
| Значение с провенансом | `kind` + узел-источник | клик → источник |
| Промт со слотами | какой фрагмент из какой потребности контекста | hover слота → источник и индекс |
| Три исхода вызова | `ok` / `refusal` / `truncated` | различаются формой, не только цветом |
| Лестница попыток | звено, причина, стоимость каждой попытки | раскрытие попытки в её промт и ответ |
| Заморозка + replay | набор замороженных верхних узлов | чекбоксы на узлах графа, ⌘↵ |

- **Три исхода визуально:** `ok` — сплошная рамка, выход отрисован деревом; `refusal` — штриховая рамка, вместо выхода блок «модель отказалась», рядом обязательная метка «токены списаны» и звено `fallback_profile`, которое сработало следом (ретрай той же модели запрещён); `truncated` — обрыв текста с рваным краем, метка лимита вывода и запрет ремонта, следом строка повтора с увеличенным лимитом.
- **Состояния:** пусто — узел не исполнялся (ветка не выбрана), показываем ПОЧЕМУ пропущен · загрузка — «вход» приходит первой, payload'ы догружаются усечёнными · ошибка — payload не сохранён по retention: ссылка в Langfuse вместо содержимого · деградация — шапка инспектора жёлтая, названо звено и что было до фолбэка · нет прав — payload'ы скрыты политикой, метаданные и проверки видны.
- **Операции:** `run_get_node`, `run_get_trace`, `agent_effective_config`, `run_replay_node`, `run_fork`, `component_expand`.
- **Мок-данные:** узел с 4 попытками (429 → `retry`, Zod `Issue[]` → `repair`, `truncated` → повтор с бо́льшим лимитом, `fallback_profile` → `ok`/`degraded`); отдельный узел с `refusal`; вход на 30 полей, у 12 провенанс `generated` со ссылками на 3 разных узла; промт на 6 слотов, один — `knowledge` с 4 чанками; payload на 200 КБ для проверки усечения.
- **Что проверяем:** объясняет ли один клик по значению происхождение ошибки, или для этого всё равно нужен полный трейс.

### Водопад стоимости и латентности — P1

- **Зачем:** увидеть, где ушло время, где — деньги, и что из этого шло параллельно.
- **Сценарии:**
  1. Читает строки спанов: отступ — глубина, две полоски — латентность и стоимость в процентах от окна прогона.
  2. Переключает сортировку «по старту / по длительности / по стоимости», находит дорогой, но быстрый узел, разворачивает его поддерево (ретраи, вложенные тулы) и ведёт по спарклайну параллелизма, где веер сузился до одного.
- **Ключевые элементы:**

| элемент | что показывает | взаимодействие |
|---|---|---|
| Строка спана | узел, глубина, старт, длительность, стоимость | клик → общее выделение экрана |
| Две полоски | время и деньги на одной строке | hover → точные значения |
| Колонка «оценка / факт» | расхождение предполётной оценки с фактом | сортировка по расхождению |

- **Состояния:** пусто — спанов нет · загрузка — виртуализованные скелет-строки, sticky-заголовок сразу · ошибка — часть трассы потеряна: разрыв рисуется явным зазором, а не склейкой соседних спанов · деградация — попытка-фолбэк отдельной под-строкой с меткой звена, а не слитая с основным спаном · нет прав — колонка стоимости скрыта, длительности видны.
- **Операции:** `run_get_trace`, `run_get`, `run_stages`.
- **Мок-данные:** 1000+ спанов, вложенность 4 уровня; узел с 60% времени и 5% стоимости и обратный ему; разрыв трассы в середине; два узла с одинаковым временем, но стоимостью ×20.
- **Что проверяем:** правда ли «дорого» и «долго» — один экран, или это два разных вопроса, задаваемых в разное время.

### Дифф двух прогонов — P1

- **Зачем:** понять, что дала правка, по узлам, а не по финальному ответу.
- **Сценарии:**
  1. Выбирает пару (по умолчанию форк и его родитель из `run_lineage`), включает фильтр «только разошедшиеся».
  2. Открывает узел: структурный дифф выхода, текстовый дифф промта и сырого ответа рядом; вывод кладёт в журнал решений как обоснование правки.
- **Ключевые элементы:**

| элемент | что показывает | взаимодействие |
|---|---|---|
| Пара графов | совпало / разошлось / есть только здесь | синхронный пан-зум, клик → узел |
| Дифф выхода | delta с пометкой полей, у которых сменился провенанс | разворот по путям |
| Дифф промта и ответа | split, word-level | переключение «игнорировать пробелы» |

- **Состояния:** пусто — выбран один прогон · загрузка — графы раньше диффов содержимого · ошибка — прогоны на разных ревизиях спеки: баннер «графы несопоставимы», сопоставление по `node_id`, непарные узлы отдельным списком · деградация — degraded-узел помечен в обеих колонках, чтобы разницу не списали на правку · нет прав — дифф метаданных без payload'ов.
- **Операции:** `run_diff`, `run_get`, `run_get_node`, `run_lineage`, `journal_append`.
- **Мок-данные:** пара «до / после правки промта» с разницей в 3 узлах; пара на разных ревизиях с 2 непарными узлами; пара, где различие только в порядке ключей JSON.
- **Что проверяем:** достаточно ли пары прогонов для решения, или вывод всё равно делается только по эксперименту на датасете.

### Таймлайн цикла — P2

- **Зачем:** понять, почему цикл остановился именно на этой итерации, не читая условие выхода в коде.
- **Сценарии:**
  1. Открывает узел цикла: дорожка на итерацию, внутри спаны; счётчики выхода рядом.
  2. Смотрит, какой счётчик сработал — `max_iter`, бюджет, стагнация, best-of (лимита рантайма нет, пороги наши); клик по итерации уводит выделение в инспектор её узла.
- **Ключевые элементы:**

| элемент | что показывает | взаимодействие |
|---|---|---|
| Дорожка итерации | спаны итерации и её исход | клик → выделение |
| Панель счётчиков | текущее / порог по каждому условию выхода | подсветка сработавшего |
| Кривая best-of | метрика по итерациям | hover → итерация |

- **Состояния:** пусто — в прогоне нет циклов · загрузка — виртуализованные дорожки · ошибка — цикл оборван бюджетом на середине итерации: итерация показана незакрытой, а не отброшена · деградация — итерация с degraded-узлом помечена на дорожке · нет прав — как у водопада.
- **Операции:** `run_get_trace`, `run_stages`, `run_get_node`.
- **Мок-данные:** цикл на 200 итераций с выходом по стагнации; цикл, выбитый бюджетом; цикл best-of, где лучшая итерация третья, а не последняя.
- **Что проверяем:** объясняет ли экран остановку цикла без чтения конфигурации условий выхода.

### Очередь человеческих задач — P1

- **Зачем:** HITL-узел приостанавливает прогон; без этого экрана его нельзя проверить вообще, а прогон стоит.
- **Сценарии:**
  1. Видит список: узел, прогон, обратный отсчёт до дедлайна, политика таймаута, назначенный.
  2. Открывает задачу: слева данные с провенансом и критерии решения, справа форма из `resumeSchema` шага.
  3. Отвечает (хоткеи на вердикты) — прогон возобновляется, исход `answered`; либо пропускает срок и видит применённую политику (`default_value` / `escalate` / `fail` / `continue_without`) с payload'ом `kind: "timeout"`.
- **Ключевые элементы:**

| элемент | что показывает | взаимодействие |
|---|---|---|
| Строка задачи | узел, прогон, дедлайн, политика, попытка | клик → задача |
| Панель данных | вход задачи из `suspendSchema` с провенансом | клик по значению → узел-источник в отладчике |
| Критерии решения | что именно решает человек и по каким правилам | — |
| Форма ответа | поля `resumeSchema` шага | RHF + ajv, ⌘↵ — отправка |

- **Состояния:** пусто — очередь пуста, это норма, не ошибка · загрузка — список раньше формы · ошибка — задача уже разрешена (гонка с дедлайном проиграна): форма блокируется, показано победившее решение · деградация — задача создана звеном `escalate` после исчерпания фолбэков: видно, что модель не справилась и что успела выдать · нет прав — задача видна, форма read-only, кнопка «запросить назначение».
- **Операции:** ни одной подходящей в реестре §2 — см. находки ниже. Косвенно: `run_get` (статус `suspended`), `run_get_node` (вход задачи), `studio_open` (ссылка агента на задачу).
- **Мок-данные:** 12 задач с разными политиками и дедлайнами (истёкший, через 3 минуты, через 2 дня); одна разрешена таймаутом; одна — эскалация после `fallback_profile`; `resumeSchema` с дискриминатором и enum на 4 вердикта.
- **Что проверяем:** успевает ли человек принять решение по показанному, не открывая отладчик отдельной вкладкой.

## Чего на этих экранах НЕ будет в прототипе

| отложено | почему | когда вернём |
|---|---|---|
| Реальное исполнение | бэкенда нет: SSE проигрывается из записанного файла событий с исходными таймингами | фаза 1, вместе с рантаймом |
| Точки останова, реально останавливающие прогон | серверное состояние прогона; в прототипе это только маркер и gutter | фаза 1 |
| Живые логи по WebSocket | эндпоинты VoltAgent `/ws*` не аутентифицированы (15-studio §4.2) | после своего WS-прокси |
| Три числа стоимости (оценка / факт / прогноз) | факт приходит от провайдера; в моках только оценка и факт | вместе с провайдерами |
| Назначение и перехват человеческих задач | v1 — один инженер, очередь однопользовательская | когда появится вторая роль |

## Открытые вопросы к заказчику

1. **HITL отсутствует в контракте.** В §2 нет ни одной операции для человеческих задач, при том что §8 рантайма описывает таблицу `app.human_tasks` и политики дедлайна. Нужны `human_task_list` / `human_task_get` / `human_task_submit` (и `human_task_reassign` под `escalate`) — иначе очередь строится мимо контракта и агент не видит, чего ждёт прогон.
2. **Нет `run_list` и `run_cancel`.** Пикер диффа, история прогонов и счётчик активных в шапке строить не на чем: `run_get` требует известный `run_id`. Отмена живого прогона — операция контракта или только REST Studio?
3. **Точки останова без операции.** §7.4 называет их серверным состоянием, но тула нет. Это `run_*`-операция или чисто студийная настройка, недоступная агенту?
4. **Заморозка верхних узлов.** Покрывает ли `overrides` у `run_replay_node` заморозку НАБОРА верхних узлов, или заморозка — отдельное поле рядом с правкой входа?
5. **Запись обратной связи.** В реестре только `feedback_list` (чтение). Вердикт человека из очереди задач и пометка «этот узел виноват» из blame — куда пишутся?
6. **Retention payload'ов.** От срока хранения зависит, сколько состояний «данных больше нет» рисовать в инспекторе и диффе.
