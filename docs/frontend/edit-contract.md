# Срез: чего не хватает в контракте для двустороннего редактирования

> Решает: точный список правок [14. MCP-контракт](../14-mcp-contract.md), без которых канвас нельзя сделать редактируемым руками одновременно с агентом.
> Влияет на: [14. MCP-контракт](../14-mcp-contract.md) §2/§3/§6, [16. Модель данных](../16-data-model.md) §2.2–2.3, [04. IR](../04-ir-schema.md) ОВ-7, [30. План фронтенда](../30-frontend-plan.md), [frontend/build.md](build.md), [frontend/shell.md](shell.md), [frontend/manage.md](manage.md)

## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Чем человек правит граф | тем же `flow_patch` с тем же `ops[]`; UI ходит в REST `PATCH /api/specs/:id` с `If-Match`, но в тот же use-case | §9.4 уже приравнял `base_rev` и `If-Match`; два кода применения операций = два набора инвариантов |
| Как сопоставить оптимистичное применение с ответом сервера | обязательный `client_op_id` (ULID, генерит инициатор) в `flow_patch`, возвращается в конверте и в событии op-log | без него UI не знает, чей патч прилетел по SSE — свой откатывать нельзя, чужой надо подсветить |
| Позиции узлов и свёрнутость групп | не операция графа: `flow_layout_get` / `flow_layout_set`, LWW по полю, своя ревизия `layout_rev`, не влияет на `rev` и на `content_hash` | [ADR-0009](../adr/0009-op-log-not-crdt.md) прямо допускает LWW для позиций; [04. IR](../04-ir-schema.md) §50 держит `ui` вне хеша, ОВ-7 требует выбрать хранилище |
| Текст промта внутри узла | в P0 — обычный `set` в `flow_patch` по завершении правки (blur/debounce), не посимвольная синхронизация | LWW-текст — фаза 2; в P0 конкуренция за один узел редка, а цена ошибки — потерянный абзац |
| Канал изменений спеки | SSE `/api/specs/:id/events`, **транспорт вне MCP-реестра**; агенту та же информация через `flow_history(since_rev)` | у Claude Code нет server-initiated push и idle timeout 5 мин (§7); агент по природе поллит между своими ходами |
| Перехват лока и откат чужого | `flow_lock_takeover` в MCP-поверхности **отсутствует**; `flow_revert` агенту доступен только для ревизий, где `actor` = этот же агент | тот же приём, что «заявка вместо записи» (§6.2): решение о чужой работе принимает человек |
| Анализ влияния типа | отдельные `type_usages` / `type_impact`, а не `view` у `catalog_get` | K6 требует, чтобы человек и агент видели один отчёт; `view` у каталога не даёт `problems[]`/`candidates[]` |

## 1. Новые операции

`И` = идемпотентность. Чистое чтение идемпотентно по определению и в колонке помечено `—`.

| Имя | Назначение | Вход | Выход | Кто | И | Группа/фаза |
|---|---|---|---|---|---|---|
| `flow_list` | Список спек воркспейса — стартовый экран и «за что взяться» у агента | `project_id?`, `kind?`, `filter?`, `limit=20`, `cursor?` | `items[{spec_id,name,rev,head_version,lock,updated_at}]`, `next_cursor` | оба | — | flow / core |
| `flow_history` | Чтение op-log: что сделал агент, шаг по ревизиям, дифф патча | `spec_id`, `since_rev?`, `until_rev?`, `limit=20`, `cursor?`, `view='summary'` | `items[{rev,base_rev,actor,tool_name,client_op_id,ops[],summary,at}]`, `next_cursor` | оба | — | flow / core |
| `flow_revert` | Обратный патч к ревизии N: применяется как новый `rev+1`, история не переписывается | `spec_id`, `base_rev`, `to_rev`, `client_op_id`, `dry_run=false` | `version`, `focus`, `problems[]`, `reverted_revs[]` | оба (агент — только свои ревизии) | по `client_op_id` | flow / author |
| `flow_lock_status` | Кто держит лок, до когда, можно ли перехватить | `spec_id` | `lock{holder,holder_kind,reason,expires_at,takeover_allowed}` | оба | — | flow / core |
| `flow_lock_takeover` | Принудительный перехват мягкого лока | `spec_id`, `reason` | `lock`, `evicted{holder,at}` | **только человек** (REST, не MCP) | по `(spec_id, holder)` | — |
| `flow_layout_get` | Раскладка канваса: позиции, свёрнутые группы, пины | `spec_id` | `layout{nodes{},groups{}}`, `layout_rev` | оба | — | flow / core |
| `flow_layout_set` | Запись раскладки, LWW по полю, без валидации графа | `spec_id`, `layout_rev`, `entries[{path,value,at}]` | `layout_rev`, `dropped[]` (проигравшие LWW) | оба | по `(path, at)` | flow / author |
| `type_usages` | Где используется тип: узлы, порты, биндинги, промты | `type_id`, `scope?`, `limit=20`, `cursor?` | `items[{spec_id,node_id,path,kind}]`, `next_cursor` | оба | — | catalog / author |
| `type_impact` | Что сломает изменение типа (R14) | `type_id`, `change{...}` | `breaks[]` как `problems[]`, `candidates[]`, `verdict` | оба | — | catalog / author |

Чего сюда **не** добавляем: `flow_events` как тул (см. §3), `presence`/курсоры (фаза 2), `spec_ops_read` как отдельное имя — это и есть `flow_history`, одно имя на два потребителя.

## 2. Изменения существующих операций

| Операция | Добавить на вход | Добавить на выход | Зачем |
|---|---|---|---|
| `flow_patch` | `client_op_id` (обязателен), `intent?` (человекочитаемая причина, идёт в ленту), `expect_lock?=false` | `client_op_id`, `applied_ops[]`, `conflict{current_rev, their_ops[], overlapping_paths[]}` | сопоставление оптимистичного применения, дедуп ретраев, подсветка «это сделал агент», содержательный отказ вместо голого `stale_rev` |
| `flow_get` | `rev?` (чтение исторической ревизии для диффа) | `version{rev,etag}` явно, `lock`, `layout_rev` | UI обязан знать `rev` до первой правки; без `rev?` дифф «до/после патча агента» неоткуда взять |
| `flow_lock` | `reason`, `holder_kind:'human'\|'agent'` | `takeover_allowed`, `previous{holder,expires_at}` | человек видит, кто и зачем держит документ; агент узнаёт, что его выселили |
| `flow_compile` | — | `rev` в `version` (уже есть `rev?` на входе) | отчёт компиляции устаревает при чужом патче |
| `catalog_list(kind='type')` | — | `usage_count` | список типов без «где используется» ведёт к лишнему `type_usages` на каждую строку |
| Конверт `Envelope` §3.1 | — | `actor{kind,id}` и `client_op_id` в `version` | одно поле решает «кто сделал» и для UI, и для аудита |

## 3. Канал изменений спеки

Отдельный от стрима прогона: у прогона своя сущность (`run_id`), свой жизненный цикл и своя частота;
мультиплексировать их в один поток — значит держать подписку на прогон ради правок графа.

**Это транспорт, а не операция контракта.** MCP-тул не может толкать события клиенту без запроса, а
клиент агента рвёт стрим по idle timeout 5 минут (§7). Поэтому: человек — SSE, агент — `flow_history(since_rev)`
перед каждым своим патчем. Событие типизируется в `@aqven/contracts` рядом с конвертом MCP, чтобы форма
была одна на оба канала.

```
GET /api/specs/:id/events        Accept: text/event-stream
Last-Event-ID: <rev>             переигрывает пропущенные ревизии из op_log

event: spec_patched
data: { "spec_id","rev","base_rev","actor":{"kind":"agent|human","id"},
        "client_op_id","tool_name","ops":[...],"etag","at" }

event: spec_layout        data: { "spec_id","layout_rev","entries":[...],"actor" }
event: spec_lock          data: { "spec_id","lock":{...},"evicted?" }
event: heartbeat          data: { "rev" }
```

`ops[]` в событии — те же операции, что ушли в `flow_patch`: Studio применяет их инкрементально к кэшу
(§9.4), полный `flow_get` — только если `base_rev` события не равен локальному `rev` (пропуск).
`Last-Event-ID` = `rev`, поэтому переподключение после сна вкладки не требует отдельного протокола.

## 4. Права

| Операция | Человек в UI | Агент по MCP | Почему |
|---|---|---|---|
| `flow_patch`, `flow_layout_set`, `flow_lock`, `flow_list`, `flow_get`, `flow_history`, `flow_lock_status`, `flow_layout_get`, `type_usages`, `type_impact` | да | да | ядро симметрии: человек и агент правят и читают одно и то же одинаково |
| `flow_revert` своей ревизии | да | да | откат собственной ошибки — часть цикла агента, иначе он чинит патч патчем |
| `flow_revert` чужой ревизии | да | **нет** → `FORBIDDEN`, `next[] = studio_open(elicit)` | агент, откатывающий правку человека, незаметно уничтожает работу; это решение человека |
| `flow_lock_takeover` | да | **нет** (тула не существует) | выселение человека из документа не должно быть доступно автоматике; агент ждёт TTL или просит через `studio_open` |
| SSE-канал изменений | да | нет (не нужен) | агент читает `flow_history` |

Принуждение — уровнями §6.2 без новых механизмов: скоуп `workflows:write` покрывает `flow_patch`,
`flow_layout_set`, `flow_revert`; разделение «своя/чужая ревизия» и отсутствие `flow_lock_takeover` —
уровень 4 (домен и поверхность), как «заявка вместо записи».

## 5. Приоритет

| Операция / изменение | Приоритет | Почему |
|---|---|---|
| `client_op_id` в `flow_patch`, `rev`+`lock` в `flow_get`, `actor` в конверте | **BLOCKER P0** | без них оптимистичное применение неотличимо от чужого патча — главная гипотеза среза не проверяется |
| SSE `spec_patched` + `flow_history` | **BLOCKER P0** | «человек видит, что сделал агент» держится ровно на этих двух |
| `flow_layout_get/set` + `layout_rev` | **BLOCKER P0** | без них перетаскивание узла рождает ревизию графа и конфликтует с каждым патчем агента |
| `flow_lock_status`, `holder_kind`/`reason` у `flow_lock` | **BLOCKER P0** | индикатор «Claude редактирует» — единственная дешёвая профилактика коллизий |
| `flow_list` | **BLOCKER P0** | стартовый экран прототипа ([shell.md](shell.md) ОВ-1) |
| `flow_revert` | **BLOCKER P0** | демо «агент сделал хуже» без отката упирается в тупик ([build.md](build.md)) |
| `flow_lock_takeover` (REST) | фаза 2 | пока держит TTL 300 с и один пользователь |
| `type_usages`, `type_impact` | фаза 2 | R14 проверяется на экране реестра, не на канвасе |
| `conflict.their_ops[]` и авто-ремап операций | фаза 2 | в P0 достаточно честного `stale_rev` + перечитать |
| LWW-текст промта, presence-курсоры | позже | нужна реальная многопользовательность |

## 6. Влияние на модель данных

| Что | Изменение в [16. Модель данных](../16-data-model.md) | Зачем |
|---|---|---|
| op-log | `app.op_log` + `client_op_id text NOT NULL`, `actor_kind text NOT NULL CHECK (actor_kind IN ('human','agent','system'))`, `intent text`; `UNIQUE (spec_id, client_op_id)` | дедуп ретраев превращается в возврат уже записанной ревизии, а не во второй патч; `actor_kind` — источник цвета в UI |
| раскладка | новая `app.flow_layouts (spec_id PK, tenant_id, layout jsonb, layout_rev bigint, updated_at)` + `app.flow_layout_entries` только если понадобится пофилдовый LWW; вне `spec_versions.ir` и вне `content_hash` | закрывает ОВ-7 [04. IR](../04-ir-schema.md): правка раскладки не создаёт версию спеки |
| прочитанная ревизия | новая `app.spec_cursors (spec_id, actor_id, seen_rev, seen_at, PRIMARY KEY (spec_id, actor_id))` | «новое с моего последнего взгляда» на канвасе и бейдж непрочитанных патчей; иначе счётчик живёт в localStorage и врёт между вкладками |
| лок | `app.spec_locks (spec_id PK, holder_id, holder_kind, reason, acquired_at, expires_at)` — сейчас лок описан только словами в §9.5 | `flow_lock_status` и событие `spec_lock` нечего читать |
| публикация SSE | `NOTIFY spec_<id>` в той же транзакции, что `UPDATE specs SET rev = rev + 1`, payload = `rev` | подписчик добирает операции из `op_log` по `rev`, payload не упирается в лимит 8 кБ |

Ретеншн `op_log` становится значимым: history — продуктовая функция, а не аудит, поэтому срок жизни
строк op-log должен быть не меньше срока жизни спеки (сейчас в §3 не оговорён).

## Крайние случаи

| Ситуация | Что делает система | Что видит человек |
|---|---|---|
| Человек тащит узел, агент шлёт `flow_patch` | ортогонально: перетаскивание идёт в `flow_layout_set`, `rev` не трогается | узел едет за курсором, на канвасе подсвечиваются изменённые агентом узлы |
| Человек правит поле узла, агент патчит тот же узел | сервер применяет первого, второму — `stale_rev` + `conflict.overlapping_paths` | «Claude изменил этот узел, пока вы печатали» + дифф двух значений, выбор одного |
| Ретрай патча после сетевого таймаута | `UNIQUE (spec_id, client_op_id)` → возвращается ревизия первого применения | ничего: правка применена один раз |
| Событие SSE с `base_rev` ≠ локального `rev` | клиент не применяет дельту, делает `flow_get` | короткая перерисовка канваса, без потери выделения |
| Агент пытается откатить ревизию человека | `FORBIDDEN`, `next[] = studio_open(elicit)` | запрос агента в «Входящих»: «откатить вашу правку rev 42?» |
| Лок человека истёк по TTL, агент пишет | запись проходит: лок мягкий, решает `base_rev` | баннер «Claude продолжил редактирование» и лента патчей |
| Два узла двинуты в одной раскладке разными акторами | LWW по `(path, at)`, проигравшие возвращаются в `dropped[]` | узел, который двинул агент, встаёт на его место; свой узел остаётся |
| Откат раскладки | `flow_revert` её не трогает — у раскладки нет истории | позиции сохраняются, содержимое графа откатывается |

## Открытые вопросы

1. **`flow_revert` как обратный патч или как копия ревизии?** Обратный патч не всегда существует
   (удалённый узел + вложенные биндинги). Альтернатива: «применить IR ревизии N как новый `rev+1`»,
   что переписывает и чужие правки, сделанные после N. От выбора зависит, нужен ли `flow_revert`
   диапазон `reverted_revs[]` или только `to_rev`.
2. **Раскладка на сервере или у клиента?** Серверная нужна, чтобы агент мог сказать «я поставил новый
   узел вот сюда» и человек увидел то же самое. Если её нет, `elkjs` пересчитывает раскладку локально
   и позиции у человека и агента расходятся — тогда `flow_layout_*` не нужны вовсе, а вопрос
   «что изменил агент» решается только подсветкой.
3. **Кто владелец `client_op_id` при откате по инициативе UI кандидата?** Кандидат из `candidates[]`
   несёт готовый `apply.arguments`; если его применяет человек, `actor_kind` — `human`, но авторство
   решения — агента. Нужно ли третье поле `origin` для честной ленты.
4. **Гранулярность подсветки.** Помечать изменённым узел или конкретное поле? Поле точнее, но требует
   хранить `ops[]` в клиентском кэше дольше одной ревизии.
