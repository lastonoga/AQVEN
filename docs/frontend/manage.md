# Кластер: Управление

> Экраны: реестр типов с анализом влияния, реестр профилей моделей, реестр агентов, реестр тулов с дрейфом MCP-схем, версии и семантический дифф, журнал решений, экспорт бандла, настройки проекта и провайдеров
> Приоритет кластера: P0 — здесь человек решает, доверять ли тому, что сделал агент; без этого прототип показывает только «красиво рисует граф»

## Что проверяем прототипом

1. **R14 как экран, а не как теория.** Гипотеза: отчёт влияния по индексу использования (§05.5) даёт человеку решение «правлю / не правлю» за один взгляд, без открытия воркфлоу. Если он листает отчёт и всё равно идёт смотреть графы — формат отчёта неверен.
2. **Заявка вместо правки.** Агент не меняет реестры, человек аппрувит. Гипотеза: очередь заявок с обоснованием и доказательствами — рабочий ритм для одного инженера, а не бюрократия, которую он обойдёт правкой YAML мимо UI.
3. **Дифф версий убеждает.** Гипотеза: семантический дифф + доказательства эксперимента + вердикт гейта в одном экране достаточны, чтобы нажать «выпустить», не открывая evals. Если человек всё равно уходит в эксперименты — состав EvidencePanel неверен.
4. **Откат — одна операция.** Проверяем, что человек в состоянии регресса находит кнопку отката за <10 секунд и понимает, что именно откатится (указатель версии или новая ревизия — см. вопрос 4).
5. **Происхождение поля важнее значения.** Гипотеза: `default → agent → node → run` на hover снимает 80% вопросов «почему модель другая». Если человек не наводит — провенанс надо показывать всегда, а не по hover.
6. **Дрейф схемы виден до компиляции.** Гипотеза: баннер расхождения `pinned ↔ live` в реестре тулов ловится раньше, чем ошибка компиляции. Если нет — дрейфу нужен свой инбокс.
7. **Журнал читается как лента поступков агента.** Проверяем, отвечает ли журнал на «что Claude сделал за ночь и на каком основании» без перехода в прогоны.

## Экраны

### registry-types — P0

- **Зачем:** единственное место, где видно, кто использует тип и что сломается от правки значения enum; без него R14 — обещание на бумаге.
- **Сценарии:**
  1. ⌘K → `OrderStatus` → карточка типа: схема, ревизия, статус `approved`.
  2. Вкладка «Использование»: 217 мест, фильтр по виду (`switch`, шаблон, датасет, правило судьи, история).
  3. Выбирает значение `pending` → «Что сломается» → `ImpactTree` с вердиктами BLOCK / WARN / OK по каждой группе.
  4. Жмёт «Предложить правку», пишет обоснование → заявка `pending_approval`, ссылка уходит в журнал.
  5. Возвращается на вкладку «Заявки», аппрувит свою же заявку, видит новую `rev`.
- **Ключевые элементы:**

| элемент | что показывает | взаимодействие |
|---|---|---|
| `TypeSchemaView` | JSON Schema ревизии, значения enum, описания | выделение значения задаёт scope отчёта влияния |
| `UsageList` (virtual) | плоский список использований: воркфлоу@rev, узел, вид | клик — переход к узлу на канвасе в новой вкладке |
| `ImpactTree` | группы затронутого: неполные `switch`, шаблоны с `{% case %}`, статические упоминания (R-T7), покрытие датасетов, правила судей, записи истории | разворот до конкретного места, бейдж вердикта |
| `ChangeKindBar` | класс правки: аддитивная / с семантикой / breaking | выбор класса меняет вердикт и текст подтверждения |
| `ProposalDrawer` | заявка: payload, rationale, вердикт гейта | отправка, аппрув, отклонение |

- **Состояния:** пусто — тип без использований, кнопка удаления значения активна; загрузка — скелет таблицы, отчёт влияния считается отдельно и приходит позже (прогресс-строка); ошибка — отчёт недоступен, правка блокируется, а не разрешается по умолчанию; деградация — индекс использования устарел (`stale_at`), баннер «отчёт от последней компиляции N ч назад»; нет прав — заявка доступна, аппрув задизейблен с подписью «выпуск делает человек со скоупом registry:approve».
- **Операции:** `catalog_list(kind='type')`, `catalog_get(kind='type')`, `registry_propose(kind='type')`, `journal_append`. **Нет в реестре:** `type_usages`, `type_impact`, `registry_approve`, `proposal_list`.
- **Мок-данные:** 40 типов; один с 217 использованиями (проверка виртуализации), enum из 7 значений: одно в 3 воркфлоу + 2 датасетах (BLOCK), одно только в архивных ревизиях (удаление разрешено), одно в 1 400 записях истории (требует алиас), одно неиспользуемое; один тип без использований; один с устаревшим индексом; одна отклонённая заявка с причиной.
- **Что проверяем:** достаточно ли отчёта влияния, чтобы принять решение о правке enum, не открывая ни одного воркфлоу.

### registry-tools — P0

- **Зачем:** тулы приходят с чужих MCP-серверов и молча меняют схему; экран — место, где расхождение `pinned ↔ live` становится видимым и чинится перезакреплением.
- **Сценарии:**
  1. Открывает реестр, сверху — 2 тула с баннером дрейфа, остальные зелёные.
  2. Разворачивает `crm/create_lead`: дифф `pinned` и `live` (jsondiffpatch), видно добавленное обязательное поле.
  3. Жмёт «Показать влияние» → список узлов, связанных с этим тулом, и ревизий, которые перестанут компилироваться.
  4. «Перезакрепить» → заявка на новую ревизию записи тула с новым `schema_hash`.
- **Ключевые элементы:**

| элемент | что показывает | взаимодействие |
|---|---|---|
| `SchemaDriftBanner` | число расхождений, время последнего синка | переход к первому дрейфу, повтор проверки |
| `McpSchemaPin` | `schema_hash`, сервер, транспорт (`http`/`stdio`), дата пина | копирование хэша, перезакрепление |
| дифф `pinned ↔ live` | добавленные/удалённые/изменённые поля JSON Schema | разворот по полю |
| `ToolBindingList` | какие узлы и агенты связаны с тулом | клик — узел на канвасе |
| класс тула | `internal` / `external`, `piiSink` | только чтение, влияет на R-S14 |

- **Состояния:** пусто — сервер подключён, тулов нет; загрузка — скелет + «сверяем с живым сервером»; ошибка — сервер недоступен, дрейф **неизвестен**, статус `unknown`, а не «ок»; деградация — проверка по расписанию просрочена, показываем возраст данных; нет прав — перезакрепление задизейблено.
- **Операции:** `catalog_list(kind='tool')`, `catalog_get(kind='tool')`, `registry_propose`. **Нет в реестре:** `tool_verify_pins`, `tool_repin`, `mcp_server_list`.
- **Мок-данные:** 3 сервера (http, streamable-http, stdio), 18 тулов; 1 дрейф ломающий (новое обязательное поле), 1 безопасный (новое описание), 1 сервер недоступен (`unknown`), 1 тул с `piiSink: true`, 1 тул без привязок.
- **Что проверяем:** понимает ли человек за один экран, опасен ли дрейф, или ему всё равно надо открыть узел.

### versions-diff — P0

- **Зачем:** решение о выпуске и об откате принимается здесь: что изменилось, чем доказано, что сказал гейт.
- **Сценарии:**
  1. `VersionRail`: лента ревизий с авторством (человек / Claude) и статусом гейта.
  2. Выбирает пару `?diff=v12..v15` → `SemanticDiffTree` по узлам, а не по строкам JSON.
  3. Разворачивает изменённое поле → провенанс поля и ссылка на запись журнала.
  4. Вкладка «Доказательства»: дельты эксперимента, стат-значимость, вердикт `PASS / WARN / BLOCK / GATE_UNAVAILABLE`.
  5. `ApprovalGate` → подтверждение → выпуск; при регрессе — «Откатить» одной операцией с подтверждением.
- **Ключевые элементы:**

| элемент | что показывает | взаимодействие |
|---|---|---|
| `VersionRail` | ревизии, автор, гейт, текущая прод-версия | выбор пары, пин базовой |
| `SemanticDiffTree` | изменения по узлам/полям, свой рендер delta | разворот до поля, провенанс на hover |
| `EvidencePanel` | эксперименты, дельты метрик, датасет, число элементов | переход в сравнение экспериментов |
| `ApprovalGate` | вердикт гейта, блокеры | аппрув, отказ с причиной |
| `LineageGraph` | дерево происхождения ревизий и форков | навигация по lineage |
| `RollbackButton` | на какую ревизию вернёмся | подтверждение с перечнем последствий |

- **Состояния:** пусто — одна ревизия, диффа нет, показываем состав; загрузка — рельса мгновенно, дифф отдельной границей Suspense; ошибка — дифф не построился, доступен сырой JSON обеих ревизий; деградация — `GATE_UNAVAILABLE`: аппрув разрешён, но требует явного «выпускаю без гейта» и пишется в журнал отдельным типом; нет прав — аппрув и откат недоступны, дифф читается.
- **Операции:** `version_propose`, `version_status`, `experiment_compare`, `journal_append`, `flow_get(rev)`, `flow_compile(rev)`. **Нет в реестре:** `version_list`, `version_diff`, `version_approve`, `version_rollback`, `version_lineage`.
- **Мок-данные:** 15 ревизий; пара с 30 изменениями (правка промта, смена модели, новая ветка `switch`); одна с `BLOCK` и двумя блокерами; одна с `GATE_UNAVAILABLE`; одна выпущенная и откаченная (чтобы откат был виден в ленте); автор — Claude в 9 из 15.
- **Что проверяем:** хватает ли диффа и доказательств, чтобы выпустить, ни разу не открыв evals.

### journal — P0

- **Зачем:** лента решений с обоснованиями — единственный способ понять, что делал агент и почему, без чтения трасс.
- **Сценарии:**
  1. Открывает журнал за сутки, видит 40 записей, из них 31 — Claude.
  2. Фильтрует по типу «смена архитектуры» → 3 записи, разворачивает обоснование.
  3. Переходит по ссылке доказательства на эксперимент, оттуда на версию.
- **Ключевые элементы:** `DecisionFilterBar` (дата / автор / тип) — сужает ленту; `DecisionEntry` — решение, автор, время, ссылки на артефакты; `RationaleExcerpt` — обоснование свёрнуто до 2 строк, разворот целиком; счётчик «решения агента / человека».
- **Состояния:** пусто — «решений нет», подсказка про `journal_append`; загрузка — скелет строк, курсорная догрузка; ошибка — тост + повтор, уже загруженное остаётся; деградация — обоснование пришло усечённым (§4.4 бюджета ответа), бейдж `truncated` и ссылка на полный текст; нет прав — чужие тенанты не видны вообще, а не задизейблены.
- **Операции:** `journal_read`, `journal_append`.
- **Мок-данные:** 300 записей за 30 дней для курсора; записи обоих авторов; одна с 5 доказательствами; одна с усечённым обоснованием; одна со ссылкой на удалённую сущность (битая ссылка).
- **Что проверяем:** отвечает ли лента на «что агент сделал за ночь» без перехода в прогоны.

### registry-agents — P1

- **Зачем:** агент — набор инструкций, параметров и привязанных тулов; здесь же — эффективная конфигурация вызова с происхождением каждого поля.
- **Сценарии:**
  1. Список агентов → карточка: инструкции, профиль модели, тулы, память.
  2. Переключает «определение ↔ эффективная» в контексте конкретного узла спеки.
  3. Hover по полю `temperature` → цепочка `default → agent → node → run`, видно, кто перебил.
  4. Правит параметр формой из схемы профиля (RJSF) → заявка на аппрув.
- **Ключевые элементы:** `AgentCard` — инструкции и параметры, разворот; `EffectiveConfigView` — итоговая конфигурация вызова; `ProvenanceBadge` — источник значения поля; `OverrideChain` — цепочка перебиваний; `ToolBindingList` — привязанные тулы и их дрейф.
- **Решение о размещении:** `EffectiveConfigView` — не экран, а панель одного компонента, смонтированная в трёх местах: здесь (в контексте узла), в инспекторе узла отладчика (в контексте прогона) и в `versions-diff` при разворачивании поля конфигурации. Канонический URL — `/agents/:id?spec=&node=&run=`; `studio_open` ведёт сюда.
- **Состояния:** пусто — нет агентов, предложение создать из архетипа; загрузка — карточка сразу, эффективная конфигурация позже (она считается динамическими функциями агента); ошибка — «эффективную не посчитать без spec+node», показываем определение и говорим почему; деградация — нет контекста прогона, `run`-слой цепочки пуст и помечен «неприменимо»; нет прав — правка задизейблена.
- **Операции:** `agent_get`, `agent_effective_config`, `provider_models`, `registry_propose(kind='agent')`. **Нет в реестре:** `agent_list` (`catalog_list` не перечисляет вид `agent`).
- **Мок-данные:** 6 агентов; один с 12 тулами и дрейфом у одного из них; конфигурация, где 3 поля перебиты на узле и 1 на прогоне; один агент без профиля (незакрытая ссылка); инструкция на 4 000 символов.
- **Что проверяем:** снимает ли провенанс вопрос «почему на этом узле другая модель» без чтения IR.

### registry-models — P1

- **Зачем:** профили моделей — возможности, лимиты, цена, цепочки фолбэков; узел не компилируется, если профиль не обещает нужную возможность.
- **Сценарии:**
  1. Таблица профилей: возможности матрицей, цена тиром, контекст, провайдер.
  2. Фильтрует по `structured_output` + цене → 4 кандидата.
  3. Переставляет цепочку фолбэков drag-and-drop, видит предупреждение «фолбэк слабее по возможностям».
  4. Включает возможность вручную → требование подтвердить, потому что проверка (`provider_probe`) её не подтверждала.
- **Ключевые элементы:** `CapabilityMatrixCell` — заявлено / проверено / опровергнуто; `FallbackChain` — порядок фолбэков; `PriceTierBadge` — цена за 1M токенов; «использован в» — узлы на этом профиле.
- **Состояния:** пусто — каталог не синхронизирован; загрузка — скелет таблицы; ошибка — каталог провайдера недоступен, показываем закэшированный со временем; деградация — возможность «заявлена, но не проверена» (жёлтая), `parallel_tool_calls` у большинства отсутствует; нет прав — правка через заявку.
- **Операции:** `provider_models`, `provider_probe`, `catalog_list(kind='model_profile')`, `registry_propose(kind='profile')`.
- **Мок-данные:** 30 профилей, из них 443-подобная выборка по `parallel_tool_calls` (9 поддерживают); один профиль с опровергнутой возможностью; цепочка из 3 фолбэков, где последний слабее; один профиль дороже остальных в 20 раз.
- **Что проверяем:** видно ли различие «заявлено» и «проверено» без чтения документации провайдера.

### export — P2

- **Зачем:** доказать, что воркфлоу переносим: бандл, отчёт потерь, конформанс против воссозданной реализации.
- **Сценарии:**
  1. Выбирает цель (`bundle`, `voltagent-codegen`, чужой рантайм) → сразу видит предварительный отчёт потерь.
  2. Запускает экспорт, смотрит прогресс тем же SSE-форматом, что прогон.
  3. Разворачивает потери по пунктам: что не переносится и чем заменяется.
  4. Запускает конформанс-набор против endpoint воссозданной реализации, видит 100% или список падений с diff'ом.
- **Ключевые элементы:** `ExportTargetPicker` — цели карточками с предупреждениями; `LossReport` — потери по пунктам и вердикт; `ConformanceRunReport` — кейсы, падения, сравнение по правилам §6; ссылка на бандл и его Merkle-корень.
- **Состояния:** пусто — нечего экспортировать (нет выпущенной версии); загрузка — прогресс по стадиям упаковки; ошибка — экспорт упал на канонизации, показываем узел-виновник; деградация — цель поддерживает не всё, вердикт `WARN` и экспорт всё же разрешён; нет прав — экспорт только из выпущенной версии.
- **Операции:** `project_export`, `project_verify_migration`, `project_conformance`, `project_import`. **Нет в реестре:** скачивание бандла — не MCP-операция, а route handler потоком.
- **Мок-данные:** 3 цели; отчёт с 6 потерями (2 блокирующие); конформанс на 40 кейсов с 2 падениями (одно по числовому допуску, одно по порядку элементов); бандл на 4 МБ с манифестом и Merkle-корнем.
- **Что проверяем:** верит ли человек отчёту потерь настолько, чтобы не проверять бандл руками.

### settings — P2

- **Зачем:** проект, окружения, провайдеры и ссылки на секреты — место, где включается доступ к моделям и внешним MCP-серверам.
- **Сценарии:**
  1. Вкладка «Провайдеры»: подключённые провайдеры, статус ключа (`SecretRef` разрешён / не разрешён), allowlist для PII.
  2. Добавляет MCP-сервер: транспорт, URL, ссылка на секрет — значения ключа не вводятся и не показываются.
  3. Вкладка «Проект»: имя, тенант, политики удержания, лимиты бюджета.
- **Ключевые элементы:** список провайдеров со статусом резолва секрета; `SecretRefField` — только ссылка `secret://env/project/name`, поле ввода значения отсутствует; allowlist провайдеров для `pii ≠ none`; лимиты бюджета и удержания.
- **Состояния:** пусто — провайдеров нет, ничего не запустится, прямая подсказка; загрузка — скелет; ошибка — секрет не резолвится, провайдер помечен нерабочим; деградация — провайдер с `retention: unknown` нельзя добавить в PII-allowlist; нет прав — всё только чтение.
- **Операции:** **нет ни одной из 57** — весь экран живёт на HTTP-API вне MCP-поверхности, и это правильно: агент не читает секреты (T1).
- **Мок-данные:** 4 провайдера (один с нерезолвящимся секретом, один с `retention: unknown`), 3 MCP-сервера, 2 окружения (`dev`, `prod`), бюджет с превышением на 30%.
- **Что проверяем:** очевидно ли, что платформа не хранит значения ключей, а только ссылки.

| отложено | почему | когда вернём |
|---|---|---|
| Реальный аппрув-воркфлоу (роли, очередь, уведомления) | пользователь один и аппрувит сам себя; ролевая модель — часть ядра доверия | v1.1, после скоупов MCP-токена |
| Живой опрос MCP-серверов на дрейф | нет бэкенда; дрейф берём из фикстуры `pinned/live` | вместе с синком по расписанию |
| Алиасы переименованных значений enum и миграция истории | механика миграции, не UI-вопрос | после §05.5 в коде |
| Расчёт Merkle-корня и реальная упаковка бандла | детерминированная упаковка — серверная работа | вместе с `project_export` |
| Реальный прогон конформанса против endpoint | нужен воссозданный рантайм | фаза экспорта |
| Ввод и хранение секретов | значения ключей в UI не появляются никогда | не вернём |
| Мультитенантность и RLS | один тенант в прототипе; состояние «нет прав» рисуем, но не принуждаем | вместе с auth |
| Массовые операции над реестрами (bulk-аппрув, импорт CSV) | не сценарий одного эксперта | по запросу |
| Правка типа напрямую, минуя заявку | ломает главную проверяемую гипотезу кластера | не вернём |

## Открытые вопросы к заказчику

1. **Анализ влияния — отдельные операции или `view` у `catalog_get`?** В §14 их нет, в 06-registries §632 они названы (`type_usages`, `type_propose_change`) как незакрытый вопрос. От ответа зависит, видит ли Claude ровно тот же отчёт, что человек — а K6 требует именно этого.
2. **Аппрув, отклонение и откат — операции MCP или только HTTP+UI?** Агенту они запрещены по скоупу, но «запрещено» и «не существует» — разные вещи: в первом случае агент получает `TOOL_FORBIDDEN` и понимает, что надо позвать человека, во втором молча не знает о механизме.
3. **Откат — возврат указателя на старую `rev` или forward-fix новой ревизией?** Меняет и `VersionRail` (ветка или линия), и текст подтверждения, и запись в журнале.
4. **Дрейф схем нужен отдельным инбоксом?** Сейчас он живёт в реестре тулов; если проверка идёт по расписанию, человеку нужно место, куда приходят новые расхождения, иначе он их не увидит до компиляции.
5. **Сколько целей экспорта в v1?** Если одна (`bundle`), `ExportTargetPicker` не нужен и экран схлопывается в кнопку с отчётом.
6. **Журнал: одна лента или две?** Нужна ли атрибуция `actor: claude | human` фильтром первого класса и разделение «предложил / применил».
7. **Что показываем на `GATE_UNAVAILABLE`?** Разрешаем выпуск с явной распиской в журнале или блокируем как `BLOCK`. Разные экраны и разный уровень доверия.
