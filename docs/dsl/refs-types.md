# Срез 3: цена типов и качество ошибок — строковые пути против лексических ссылок

> Статус: draft. Зависит от: [shape.md](shape.md) §3, [type-ergonomics.md](type-ergonomics.md), [ADR-0018](../adr/0018-typescript-authoring.md), [research/ts-types-flow.md](../research/ts-types-flow.md) §5.

## Методика

Проба: `scratchpad/probe-dsl/slice3`, TypeScript **6.0.3**, `strict`, `skipLibCheck`, Node 20.19, M-серия.
Два проекта одной семантики, общий реестр типов (6 доменных типов, без инлайновых схем — правило
type-ergonomics), одинаковое число файлов (115).

| Форма | Ссылка | Проверка |
|---|---|---|
| `str` (shape.md §3) | `"$n7.out.title"`, `"$n0.out[*].name"`, `"$input.filters.city"` | `defineFlow<const S extends FlowSpec>(spec: S & Validate<S>)` + `Resolve<S, P>` — тип-level парсер грамматики 04 §3.1 (`$`, `.out`, поля, `[*]`) |
| `ref` (лексическая) | `n7.out.title`, `n0.out.all.name`, `$in.filters.city` | `node<const S extends Sig>(spec: { sig: S; in: Slots<S> })`; `Slots<S>` — мапленный тип, без условных ветвей и разбора строк |

`ref` — **не прокси-билдер**: `node()` возвращает значение `{ kind, sig, out }`, тело узла остаётся
литералом один-к-одному с IR, `out` — фантомный `Ref<T>`. Числа — `tsc --extendedDiagnostics`,
холодный прогон, три повтора, разброс ≤ 0,02 s.

## 1. Стоимость типов

| Конфигурация | Форма | Types | Instantiations | Check | Память |
|---|---|---|---|---|---|
| 50 × 20 | str | 22 481 | **267 038** | **0,37 s** | 114,7 MB |
| 50 × 20 | ref | 18 899 | **130 645** | **0,28 s** | 101,8 MB |
| 50 × 40 | str | 43 921 | 531 378 | 0,67 s | 198,8 MB |
| 50 × 40 | ref | 36 919 | 262 645 | 0,55 s | 126,0 MB |
| 50 × 80 | str | 86 801 | 1 060 058 | 1,47 s | 367,4 MB |
| 50 × 80 | ref | 72 959 | 526 645 | 1,03 s | 185,5 MB |

Гипотеза **подтвердилась, но не драматически**: `ref` дешевле по инстанциациям ровно вдвое
(2,04× на всех трёх размерах), по времени — в 1,3–1,4 раза, по памяти — в 1,1–2,0. Рост у обеих
форм линейный. Абсолют мал: 0,37 s против 0,28 s на 1000 узлов. Драйвер стоимости — не форма
ссылки, а инлайновые схемы (type-ergonomics: 3,75 s против 0,38 s, порядок величины).

### Один воркфлоу, много узлов (нагрузка на один литерал)

| Узлов в одном литерале | str: Instantiations / Check | ref: Instantiations / Check |
|---|---|---|
| 100 | 58 728 / 0,14 s | 14 785 / 0,13 s |
| 300 | 175 688 / 0,36 s | 41 185 / 0,19 s |
| 600 | 351 128 / 0,54 s | 80 785 / 0,40 s |
| 1000 | 585 048 / 0,89 s | 133 585 / 0,79 s |

Разрыв по инстанциациям растёт до **4,4×**: `Validate<S>` — мапленный тип по всем узлам литерала,
каждый слот заново разбирает строку в контексте всего `S`. Лексическая ссылка проверяется точечно,
в позиции аргумента. По времени разрыв всё равно скромный.

## 2. Изоляция парсера путей

Тот же проект 50 × 20 со снятой проверкой слотов (`spec: S` вместо `spec: S & Validate<S>`; у `ref` — `in: Record<string, unknown>` вместо `Slots<S>`):

| Форма | Instantiations без проверки | С проверкой | Цена проверки | Check без / с |
|---|---|---|---|---|
| str | 338 | 267 038 | **+266 700** | 0,15 s → 0,37 s (**+0,22 s**) |
| ref | 12 652 | 130 645 | +117 993 | 0,24 s → 0,28 s (**+0,04 s**) |

**Машинерия проверки у строковой формы стоит в 5,5 раза дороже по времени.** Оговорка: базы
не идентичны — у `ref` выражения `n7.out.title` проверяются даже при `unknown` в цели, её база
завышена, поэтому разрыв скорее занижен.

## 3. Потолок

| Проверка | str | ref |
|---|---|---|
| Глубина пути `$a.out.f0…fN` | OK до **300** сегментов; на 400 — RangeError в `scan()` (стек парсера самого типа данных) | идентично |
| Узлов в одном воркфлоу | 1000 без ошибок, 0,89 s | 1000 без ошибок, 0,79 s |
| `TS2589` | не воспроизведён | не воспроизведён |

Сопоставление с research/ts-types-flow.md §5 (`Acc<1000>` проходит, `Acc<1200>` → `TS2589`): `Walk`
рекурсирует раз на сегмент, стена — ~1000 сегментов, и она недостижима: вложенный тип данных
глубиной 400 кладёт парсер TS раньше и одинаково у обеих форм. Реальный путь — 2–4 сегмента.
**Потолок не аргумент ни за, ни против**: запас ~100×.

## 4. Качество ошибок

Четыре случая, тексты `tsc` дословно (сокращены только абсолютные пути).

| Случай | str | ref |
|---|---|---|
| Несуществующий узел | TS2322, бренд `NoNode`, есть список объявленных, подсказки нет | TS2552, **«Did you mean»** |
| Несовместимый тип слота | TS2322, бренд `Mismatch` с `want`/`got` | TS2322, разворот до `'Hotel[]' … to type 'string'` |
| Несуществующее поле выхода | TS2322, бренд `NoField` | TS2551, **«Did you mean»** |
| Циклическая ссылка | **не ловится, компилируется** | TS2448 + TS7022 + TS2454 — **ловится** |

```
e1-str.ts(5,76): error TS2322: Type '"$lod_hotels.out[*].name"' is not assignable to type
  '"$lod_hotels.out[*].name" & Mismatch<"$lod_hotels.out[*].name", "label", string,
   NoNode<"lod_hotels", "load_hotels" | "top3">>'.
e1-ref.ts(4,93): error TS2552: Cannot find name 'lod_hotels'. Did you mean 'load_hotels'?

e2-str.ts(5,76): error TS2322: Type '"$load_hotels.out"' is not assignable to type
  '"$load_hotels.out" & Mismatch<"$load_hotels.out", "label", string, Hotel[]>'.
e2-ref.ts(4,86): error TS2322: Type 'Ref<Hotel[]>' is not assignable to type
  '{ readonly [REF]: string; } | Konst<string>'. … Type 'Hotel[]' is not assignable to type 'string'.

e3-str.ts(5,76): error TS2322: Type '"$pick.out.dcision"' is not assignable to type
  '"$pick.out.dcision" & Mismatch<"$pick.out.dcision", "label", string,
   NoField<"$pick.out.dcision", "dcision">>'.
e3-ref.ts(4,102): error TS2551: Property 'dcision' does not exist on type 'Ref<Verdict>'.
  Did you mean 'decision'?

e4-str.ts: (ошибок нет)
e4-ref.ts(3,90): error TS2448: Block-scoped variable 'b' used before its declaration.
e4-ref.ts(3,7):  error TS7022: 'a' implicitly has type 'any' because it does not have a type
  annotation and is referenced directly or indirectly in its own initializer.
```

Обе формы дают позицию с точностью до столбца и называют узел. Разница в трёх местах. **Спеллчек**:
у `ref` он от компилятора (TS2552/TS2551) — ровно та потеря, что записана в type-ergonomics как цена
формы (б); у `str` вместо подсказки список объявленных узлов внутри бренда — информативнее, но это
третий аргумент generic. **Глубина generic**: у `str` первая строка всегда пересечение
`"литерал" & Бренд<…>`, четыре параметра, полезны два. **Ацикличность**: `str` цикл пропускает
(граница из type-ergonomics), `ref` ловит структурно — `const` нельзя использовать до объявления.

## 5. Автодополнение и отзывчивость

Прямой замер через `tsserver` (`completionInfo`), проект 50 × 20, файл `wf_25.ts`, середина файла, слот набираемого прямо сейчас узла. Холодный — первый запрос после `open`, тёплый — повтор. Это то же, что делает редактор, а не оценка через `tsc`.

| Позиция курсора | Форма | Холодный | Тёплый | Предложений | Что предложено |
|---|---|---|---|---|---|
| `in: { zz: "$` | str | 94 ms | 7 ms | **0** | — |
| `in: { yy: "$n7.out.` | str | 93 ms | 8 ms | **0** | — |
| `in: { zz: n` | ref | 50 ms | 8 ms | 1086 | `n0 … n19`, `$in`, узлы файла |
| `in: { yy: n7.out.` | ref | 48 ms | 1 ms | **3** | `body`, `hotels`, `title` |

Записанная в shape.md цена подтверждена дословно: **внутри набираемого узла строковая форма
не подсказывает ничего**. Причина структурная — ожидаемый тип слота выводится из самого литерала
(`const S`), в момент набора цель не union литералов, и `tsserver` предлагать нечего; трюк
с `Validate` этого не чинит. У `ref` работают обе подсказки, вторая точная: три поля `Pitch`.
Холодная отзывчивость вдвое выше, тёплая неотличима.

## 6. Вердикт по числам

**Берём лексические ссылки.** Строковые пути не выигрывают ни по одному замеренному показателю.

| Показатель | Кто лучше | Насколько |
|---|---|---|
| Instantiations, 50 × 20 | ref | 2,04× |
| Instantiations, 1000 узлов в одном литерале | ref | 4,4× |
| Check time, 50 × 20 | ref | 1,3× (0,28 s против 0,37 s) |
| Память, 50 × 80 | ref | 2,0× (185 MB против 367 MB) |
| Цена самой проверки | ref | 5,5× по времени |
| Холодное автодополнение | ref | 1,9× (48 ms против 93 ms) |
| Подсказки в набираемом узле | ref | 3 против 0 |
| Спеллчек имени узла и поля | ref | есть против нет |
| Циклическая ссылка | ref | ловится против не ловится |
| Полнота списка узлов в тексте ошибки | str | `NoNode` перечисляет объявленные |
| Потолок | ничья | обе упираются в парсер типа данных на глубине 400 |

Единственный плюс строк — перечисление кандидатов в тексте ошибки, и он покрывается «Did you mean».
Разница по времени мала в абсолюте (90 ms на 1000 узлов), поэтому **решающий аргумент
не производительность, а автодополнение и спеллчек**: 93 ms до нуля предложений хуже, чем 48 ms
до трёх. Исчезновение `Resolve<S, P>` — реальный выигрыш: минус одна из трёх реализаций
грамматики 04 §3.1 и минус 266 700 инстанциаций на 1000 узлов.

## 7. Чего этот срез не решает

Замеры отвечают на «дороже ли типы» и «хуже ли ошибки» — ответ «нет, лучше». Они **не** отвечают
на возражения срезов 1–2, которые надо закрыть до принятия формы:

- **Порядок объявления.** `ref` требует топологического порядка; `hotel_pitch` придётся переставить
  (`fix` выше `final_pitch`). Свободный порядок был явной причиной выбора (б) ради канваса.
- **Идентификатор узла.** В пробе id — ключ записи `nodes: { n0, n1 }` (shorthand), имя переменной
  и есть id; формально id живёт в двух местах, переименование обязано править оба.
- **Кодмод.** Добавление узла правит объявление и запись `nodes` — два места вместо одного.
- **`$item` в `map`.** Не воспроизведён: тело `map` — вложенный литерал, лексической переменной
  для элемента нет без замыкания, а замыкания ограничены ADR-0018/0019.

UNVERIFIED: поведение на вложенных телах (`map.do`, `switch.cases`, `try.catch`) — замерена только плоская запись узлов; `findRenameLocations` через tsserver не проверялся.
