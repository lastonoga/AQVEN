# Срез 4: приёмы Cube.js, переносимые в декларативный DSL

Дата 2026-09-14. Источник по Cube — `docs/research/esc-cube-patterns.md`; семантика ядра —
`docs/03-core-language.md`. Здесь только перенос: что берём, во что превращаем, чего не берём.

## 1. Верхний уровень и секции

У Cube верхний уровень — `cube(name, { … })`: имя плюс объект с закрытым списком зарезервированных
ключей. Ключи не произвольные — транспайлер и валидатор знают каждый по имени, и именно поэтому
Visual Modeler может править модель. Берём ровно эту форму, но верхним уровнем делаем не источник
данных, а воркфлоу, и секции ставим один-в-один с полями корня IR ([04](../04-ir-schema.md) §1.1):
всё, что у Cube выведено из SQL-модели, у нас выведено из IR.

| Cube | Наш ключ | Почему параллель держится |
|---|---|---|
| `cube(name, …)` | `flow(id, …)` | имя — стабильный идентификатор, не путь в дереве (урок CDK, ADR-0018) |
| `sql` / `sql_table` | `input` + `output` + `returns` | что на входе и что отдаётся наружу |
| `measures`, `dimensions` | `nodes` | единственное место, где живут «члены»; ключ объекта = идентичность |
| `joins` | биндинги `$node.out` внутри `nodes` | у нас рёбра — данные, отдельной секции не нужно |
| `segments` | `policies` | видимость, доверие, PII |
| `pre_aggregations` | `determinism` на узле (§5) | свойство узла, а не отдельная секция |
| `extends` | `extends` у `prompt`, `from()` у узла (§3) | наследование по членам |
| — | `uses` | пины версий: у Cube их нет, и это его дефект |

```ts
export default flow('hotel_pitch', {
  input: t.Brief,
  output: t.Pitch,
  context: ['date', 'locale'],
  budget: { usd: 0.5, ms: 60_000 },
  uses: { search: 'tool:tavily@2', panel: 'component:judge_panel@7' },
  policies: { visibility: 'brief_only', pii: 'deny' },
  nodes: {
    find: {
      kind: 'tool', use: 'search', effect: 'read',
      determinism: stable({ ttl: '6h', refresh: { etag: $.find.out.etag } }),
      in: { q: $.input.city }, out: t.Hotel.array(20),
    },
    score: { kind: 'map', over: $.find.out, concurrency: 4, on_item_error: 'skip', do: 'score_one' },
    score_one: {
      kind: 'llm', archetype: 'scorer@4', role: 'reasoning', fn: scoreHotel,
      slots: { hotel: $.item.pick(['name', 'beach_entry']), rubric: $.input.rubric },
    },
  },
  returns: $.score.out,
});
```

Три решения, вытекающие из формы, а не из вкуса:

1. **`nodes` — объект, не массив.** Как `measures` у Cube: ключ и есть `NodeId`, перестановка
   ключей не может выглядеть подменой узла (04 §1.1). Поле `order` в IR берётся из порядка ключей
   литерала — кодмод переставляет ключи, дифф классифицирует это как `COSMETIC`.
2. **Комбинаторы — такие же записи в `nodes`.** `map` ссылается на тело по `NodeId` (`do: 'score_one'`),
   а не принимает колбэк: тело адресуемо, значит канвас рисует его узлом, а `$item` остаётся
   символическим биндингом. JS-ного цикла в DSL нет вообще.
3. **`uses` — то, чего Cube не сделал.** Ссылки на чужие кубы у него плавающие; у нас ссылка на тул,
   компонент, фрагмент и реестр типов всегда пиненая (`name@rev`), и пин лежит в одной секции,
   чтобы `aqven.lock.yaml` и анализ влияния читались без обхода всего дерева.

## 2. Ссылки: граф строится синтаксически, без исполнения

Механика Cube: транспайлер превращает шаблонную строку в функцию, **аргументы которой и есть список
зависимостей**, и граф членов известен до генерации SQL. Наш эквивалент уже есть — `globalFullVariablesSync`
над AST liquidjs ([08](../08-prompts.md) §7, R-T1/R-T2) и грамматика `Binding` (04 §3.1). Это один
и тот же алгоритм, поэтому переносить нечего — надо зафиксировать инварианты, которые Cube соблюдает
неявно, а у нас должны быть правилами.

| Инвариант Cube | У нас | Проверка |
|---|---|---|
| имя члена — ключ объекта, никогда не строка из рантайма | `NodeId` и имя слота не вычислимы | ADR-0019 правило 1 |
| зависимость видна в аргументах, до исполнения | `$node.out.field` — литерал, парсится регекспом `$defs/ref` | 04 §3.1 |
| словарь имён фиксирован (`CUBE`, `FILTER_PARAMS`, …) | источники: `$input`, `$item`, `$acc`, `$run.context.*`, `$node.out` | 04 §3.1, грамматика закрыта |
| выражение над членами, а не «здесь можно JS» | проекции `pick/omit/map/flatten` плюс `code`-узел | 04 §3.2 |

Разница, ради которой всё это: у Cube доступ к членам даёт `vm` с глобалями, поэтому анализ держится
на транспайлере. У нас `$` — обычное значение, возвращаемое билдером (`Ref<T>`, ADR-0018), и синтез
вызывается один раз чистой функцией. Никакого `vm`, никакого многофазного реэкзекьюта: цепочка
`.pick(...)` не исполняет ничего, а накапливает `via` — тот же список проекций, что ляжет в IR.

## 3. Наследование: `extends` по членам, составные промты

У Cube `extends` копирует все члены базового куба и позволяет переопределить их **поимённо**; текст
SQL при этом не патчится — заменяется целый член. Это и есть приём, который переносится: наследование
по именованным частям, никогда по позиции и никогда текстовой склейкой.

LLM-функция — тройка `{ in, body, out }` с одной версией и одним хешем (решение заказчика). Блок
формата вывода генерируется из `out`, поэтому «версии текста» отдельно от типов не существует.
`body` — **объект именованных частей**, а не строка: именно это делает наследование и кодмод
возможными, а `IncludeTag` с пином версии (08 §5) остаётся механикой резолва части.

```ts
export const scoreHotel = prompt('score_hotel', {
  in: { hotel: view(t.Hotel, 'brief'), rubric: t.Rubric },
  body: {
    role: fragment('role_scorer@3'),
    tone: fragment('tone_neutral@2'),
    task: md`Оцени {{ hotel }} по {{ rubric }}.`,
  },
  out: t.HotelScore,
});

export const scoreHotelRu = prompt('score_hotel_ru', {
  extends: scoreHotel,
  body: { tone: fragment('tone_ru_formal@1') },
  out: t.HotelScore.extend({ evidence: t.Quote }),
});
```

| Свойство | Правило | Причина |
|---|---|---|
| Переопределение | только по ключу `body`; новый ключ разрешён, вставка «после» — нет | позиция не адресуема, значит дифф и кодмод устойчивы к правке базы |
| Порядок частей | порядок ключей базы; добавленные идут после | стабильный префикс = попадание в кэш промта (08 §6) |
| Слоты | `in` наследника ⊇ `in` базы; сузить нельзя | иначе часть базы получает непокрытый слот, R-T2 |
| Выход | `out` только расширяется полями в конец | порядок полей — часть семантики (03 §5): обоснование раньше решения |
| Версия и хеш | один хеш на тройку, считается по **раскрытой** цепочке `extends` с пинами частей | правка `tone_ru_formal@1` меняет хеш всех наследников — fan-out виден |
| Глубина | не более одного уровня `extends` | цепочки наследования у Cube — известный источник непонятных моделей; композиция частей уже даёт всё |

Узел наследуется тем же приёмом, но через архетип: `from('archetype:scorer@4', { … })` форкает скелет
IR ([06](../06-registries.md) §6) и переопределяет поля поимённо. Разница с промтом одна: у архетипа
переопределяемы параметры и проверки, но не примитивы скелета — иначе `scorer` перестаёт быть `scorer`.
Композиция целых кусков графа — не `extends`, а параметр-компонент `Component<In, Out>` (03 §4.1):
там, где Cube вынужденно копирует члены, у нас есть высший порядок с контрактами.

## 4. Слои: cube против view — у нас `flow` против опубликованного тула

У Cube нижний слой (`cube`) описывает источник и не предназначен потребителю; верхний (`view`)
собирает из членов нескольких кубов фасад с собственными политиками доступа. Аналог у нас точный:
`flow` — определение, опубликованный тул (MCP/HTTP, R10) — фасад. Слой стоит ввести в DSL явно,
потому что иначе входной и выходной типы воркфлоу начинают обслуживать сразу двух потребителей.

```ts
export const pitchTool = published('hotel_pitch_api', {
  of: 'flow:hotel_pitch@12',
  in: view(t.Brief, 'public'),
  out: view(t.Pitch, 'client'),
  access: { members: 'union', rows: 'intersect' },
});
```

Что берём дословно: решётку композиции политик — **члены объединяются, строки пересекаются,
member-level фасада переопределяет уровень источника, row-level комбинируется** (esc-cube-patterns §3).
`view()` из реестра типов (05 §3) уже даёт нужную половину: проекция выполняется при связывании,
поэтому скрытого поля нет физически. Что **не** берём: у Cube view — ещё и место джойнов; у нас фасад
не вправе вводить новые узлы, он только сужает типы и объявляет доступ. Иначе появляется вторая
точка, где рождается граф, и канвас перестаёт быть полным.

## 5. Пре-агрегации → класс детерминированности узла

Ключевое у Cube: право предрассчитать даёт не флаг автора, а **алгебраическое свойство меры** —
аддитивная отвечается из rollup, прочая нет. Переносим свойство, не механизм: у узла объявляется
класс из ADR-0019 (`pure` / `stable(ttl)` / `volatile`), и без него узел с эффектом не компилируется.

| Cube | DSL | Семантика кэша |
|---|---|---|
| аддитивная мера | `determinism: pure` | ключ — хеш входа, срока нет |
| `refresh_key: { every }` | `stable({ ttl: '6h' })` | ключ — хеш входа плюс срок |
| `refresh_key: { sql }` | `stable({ ttl, refresh: { etag: $x.out.etag } })` | инвалидация по внешнему признаку, а не по таймеру |
| неаддитивная мера | `volatile` | кэш только внутри прогона |
| матчинг «пре-агрегация покрывает запрос» | компилятор сверяет класс с эффектом узла | `write`/`external` не бывают `pure`; `code` — всегда `pure` |

Свойство выводится, а не объявляется, везде, где выводимо: `code` и `const` — `pure` по построению
(03 §2.1), `llm` с `temperature: 0` и `seed` — максимум `stable`, `tool` с эффектом `write` —
`volatile` принудительно. Объявление автора только сужает вывод; расширение — ошибка компиляции.
Это и есть перенос алгебры: класс — свойство узла, кэш и replay читают его, а не доверяют автору.

## 6. Чего у Cube брать не надо

| Приём | Почему нет |
|---|---|
| Многофазный реэкзекьют исходника (4 прохода) | у нас ссылки — данные, граф читается из IR; синтез вызывается **один раз** чистой функцией (ADR-0018), иначе `plan_hash` невоспроизводим |
| `vm`-глобали без импортов (`cube()`, `CUBE`, `FILTER_PARAMS`) | убивает типы, автодополнение и статический анализ в IDE; у нас всё импортируется, а `$` — обычное значение |
| Отсутствие типов у JS-модели (issue #4202, открыт с 2022) | тайпчекер ловит полноту `switch` до компилятора (проба ADR-0018); отказ от типов обнуляет главную выгоду TS |
| Два формата авторинга (YAML + JS) | ручная синхронизация валидатора, транспайлера и YAML-ветки — капслок-«ATTENTION» в их `CubeValidator.ts`; у нас один язык и один машинный артефакт |
| Визуальный редактор только для YAML-подмножества | у нас кодмод по литералам TS, а деградация до чтения — видимая плашка, а не другой формат |
| `asyncModule` с походом в API на компиляции | синтез без сети и часов; динамика выражается узлом рантайма, а не формой модели |
| `sql` как свободная строка | шаблон не склеивается: значение входит только через именованный слот (R-T8) |

Последнее, что стоит забрать целиком, — оговорка самой доки Cube: интенсивное использование
`FILTER_PARAMS` она называет плохой практикой. Наш эквивалент — бюджет escape-узлов (ADR-0019 §6).
