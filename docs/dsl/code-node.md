# `code`-узел: escape hatch, который не ломает канвас

Статус: черновик среза 3. Контекст: ADR-0018 (TS — единственный язык авторинга), ADR-0019 (код
даёт значение, но не форму), ADR-0017 (байтовый фикспойнт), `03-core-language.md` §2.4.

## 1. Образец: n8n Code node и соседи

| Свойство | n8n Code node | Retool JS query / transformer | Zapier Code |
|---|---|---|---|
| Вход | `$input.all()` / `$json` — массив «items» `{ json, binary }`, форма произвольная | всё дерево приложения: `{{ query1.data }}`, компоненты, глобальные переменные | `inputData` — плоский объект строк, маппится руками |
| Выход | массив items той же формы; форма нигде не объявлена | значение; у transformer обязателен `return` | объект; **лимит 250 элементов**, I/O 6 МБ (AWS Lambda) |
| Режимы | `Run Once for All Items` (дефолт) и `Run Once for Each Item` | query (async, может дёргать другие queries) и transformer (read-only, sync) | один режим, 512 МБ RAM, до 10 минут на платных планах |
| Модули | JS и Python (Pyodide); внешних нет по умолчанию, self-hosted включает `NODE_FUNCTION_ALLOW_BUILTIN` / `NODE_FUNCTION_ALLOW_EXTERNAL`, на cloud недоступно | JS, штатный набор библиотек платформы | JS (ESM) и Python, публичные npm/PyPI, install 30–120 с |
| Типы | **нет**: автодополнение есть, контракта выхода нет, следующий узел ничего не знает | нет; ошибки видны только в State/Console во время прогона | нет |
| Побочные эффекты | не запрещены: с разрешёнными модулями доступны `fs` и сеть | query ходит в API; transformer нарочно лишён async | сеть доступна |

Критика в самой экосистеме n8n — это порядок предпочтения expression → Edit Fields → Code node
и «try to avoid the Code node unless you really need it»: код прячет логику, которая должна быть
видна на канвасе. Контраргумент сообщества честный — один Code node заменяет цепочку из 10–15 узлов
и быстрее её. Правы обе стороны, потому что третьего варианта нет: узел либо декларативный и слабый,
либо код и невидимый. Тот же диагноз у Airflow `PythonOperator` (`research/esc-escape-hatch.md` §5).
У Retool разница между read-only transformer и async JS query не выражена в типе и всплывает
в рантайме; Zapier честен про лимиты и молчит про контракт.

Вывод: антипаттерн не «код в узле», а **код без объявленного контракта**. Лечим контрактом, а не
запретом; `switch`, `map`, `loop` при этом остаются данными IR и внутри `code` невыразимы
(инвариант 1), поэтому «10–15 узлов в одном» у нас физически не собирается.

## 2. Наша форма

Тело живёт **в отдельном файле `code/*.ts` рядом с определением**, узел ссылается на именованный
экспорт. Обоснование: кодмод ts-morph правит объектные литералы, а тело в литерале — произвольный
AST внутри цели правки (ADR-0018: «тела `code`-узлов в подмножество не входят и кодмодом
не трогаются никогда»); длинная функция в литерале убивает читаемость файла-определения, ради
которой и выбран декларативный стиль; обычный экспорт тестируется и типизируется обычными средствами.

```ts
import { pure } from "@wf/code";
import * as T from "../types.js";

export const pickTopK = pure({
  in: { scores: T.HotelScore.array(), hotels: T.Hotel.array(), k: T.Int },
  out: T.Hotel.array().max(3),
})(({ scores, hotels, k }) => {
  const byId = new Map(hotels.map((h) => [h.id, h]));
  return scores
    .toSorted((a, b) => b.score - a.score)
    .slice(0, k)
    .map((s) => byId.get(s.hotelId))
    .filter((h) => h !== undefined);
});
```

`pure({ in, out })` — единственное место, где объявлен контракт: zod-схемы из реестра типов, а не
TS-аннотации. Узел переиспользует их, а не повторяет (03 §2.4: сигнатура выведена из `in`/`out`).

```ts
const top3 = code("top3", {
  fn: pickTopK,
  reason: "no_archetype",
  in: { scores: scoreHotels.out, hotels: loadHotels.out, k: konst(3, T.Int) },
  tests: "./code/pitch.cases.ts#pickTopK",
  limits: { timeoutMs: 5_000, memoryMb: 64 },
});
```

**Исключение — инлайн-форма для одного выражения**, разрешена, когда у тела нет свободных
идентификаторов кроме параметров: извлечение исходника на синтезе тогда безошибочно, а замыкание
над модулем невозможно (закрывает открытый вопрос `research/ts-code-isolation.md` §7).

```ts
const ids = code("ids", {
  fn: pure({ in: { hotels: T.Hotel.array() }, out: T.HotelId.array().max(200) })(
    ({ hotels }) => hotels.map((h) => h.id),
  ),
  reason: "no_archetype",
  in: { hotels: loadHotels.out },
});
```

Граница проверяемая, а не вкусовая: `E-ESC4` требует вынести тело в файл, если у стрелки есть блок
`{ … }`, больше одного выражения или хоть один свободный идентификатор. Кодмод в обеих формах
трогает только `in`, `reason`, `limits`; ключ `fn` для него непрозрачен.

## 3. Чистота: три эшелона

Механизм изоляции выбран в `research/ts-code-isolation.md` §1–2 и не переизобретается: **пул
`worker_threads` + пустой `node:vm`-контекст внутри воркера**, за фасадом `@wf/sandbox` (19 §9),
fail-closed. Профиль угроз: защищаемся от ошибки автора, не от побега.

| Эшелон | Что ловит | Когда | Диагностика |
|---|---|---|---|
| Статический анализ AST модуля `code/*.ts` | `import` вне белого списка чистых модулей; `fetch`, `fs`, `process`, `globalThis`, `require`, `Date.now`, `new Date()`, `Math.random`, `performance.now`, `crypto.randomUUID`, любой `await` | синтез, до IR | ошибка компиляции с файлом и строкой |
| Пустой глобал воркера | косвенный доступ через зависимость и вычисленное имя (`globalThis['Ma'+'th']`) | первый прогон и прогон тестов | `NondeterminismError` с именем API |
| Лимиты воркера | бесконечный цикл (`worker.terminate()`), утечка (`maxOldGenerationSizeMb`) | прогон | `E-CODE-TIMEOUT` / `ERR_WORKER_OUT_OF_MEMORY` на узле |

Белый список импортов: только `@wf/std` (чистые проекции, числовые хелперы, детерминированный хеш)
и модуль типов; `node:crypto` не входит. Первый эшелон бесплатен и закрывает почти всё, второй нужен
против динамики, невидимой AST, третий — потому что чистая функция может не завершиться.

Границы значений принуждает R-42 (ADR-0019): `out` без `max`/`maxLength` не компилируется, иначе
верхняя оценка размера промта ниже по течению перестаёт существовать. Выход проверяется zod-парсом
**на границе песочницы**, а не приводится кастом. Вход и выход обязаны быть JSON-сериализуемыми
(10 §2): `Map`, `Date` и классы не переживают чекпоинт, и `pure` ловит это схемой.

## 4. Типизация: чем мы отличаемся от n8n

У n8n выход Code node — `items`, следующий узел получает `any`, ошибка формы всплывает в прогоне
на живых данных. У нас `code(...)` возвращает `Ref<z.infer<typeof out>>` — он же значение слота
`in:` следующего узла, и цепочка типизируется тайпчекером до компилятора IR.

```
pure.out: T.Hotel.array().max(3)  →  top3.out: Ref<Hotel[]>  →  llm("gen").in.hotels: Ref<Hotel[]>
```

Подстановка `top3.out` в слот `Ref<Pitch>` даёт `TS2322` в редакторе, без прогона. Три следствия,
которых у образца нет: автодополнение по полям выхода `code`-узла в биндингах; `allowedSets` (08)
ссылается на путь внутрь этого выхода, потому что путь существует в типе; сужение `out` — ломающее
изменение, видимое в семантическом диффе версий, а не сюрприз в рантайме.

Проверок две: `tsc` отвечает за форму на авторинге, zod-парс на границе песочницы — за факт
в прогоне. Провенанс выхода наследует `trust` входов по `mergeTags` (`untrusted` поглощает),
поэтому `code` не отбеливает недоверенные данные (09 §3.1, `kind: computed`).

## 5. Тесты обязательны

Файл `code/<module>.cases.ts` рядом с телом, `tests:` — ссылка `путь#экспорт`. Кейсы декларативные, чтобы их читал и канвас, и раннер:

```ts
export default cases(pickTopK, [
  { name: "k больше длины", in: { scores: s2, hotels: h2, k: 5 }, out: h2 },
  { name: "пустой вход", in: { scores: [], hotels: [], k: 3 }, out: [] },
]);
```

Два пути из одного источника: `vitest --project core` в CI (`cases` разворачивается в `test.each`)
и та же песочница `@wf/sandbox` при `flow_compile` — второе ловит «прошло в Node, упало в пустом
контексте» и есть второй эшелон §3.

**Отсутствие тестов — ошибка компиляции `E-ESC3`, не предупреждение**: без непустого набора теряет
смысл мутационный тест ядра (03 §5, kill-критерий 1), а детерминизм реплея перестаёт быть
проверяемым. Предупреждением остаётся только неполнота покрытия вариантов входного enum — `W-ESC5`.

## 6. На канвасе

Иная рамка и значок уровня `E1` (`research/esc-escape-hatch.md` §4, урок Tailwind: произвольное
значение обязано выглядеть иначе токена). Тело **не редактируется в узле**: три строки превью
`monospace` и кнопка, открывающая в редакторе тот же файл, что в git, а не копию. Индикатор тестов
трёхпозиционный: зелёный счётчик, красный «упали», серый «не запускались после смены `body_hash`».
Рядом — `reason` из закрытого перечня (`no_archetype | perf | external_format | migration |
experiment`), по нему считается метрика §19 в трёх числах: `escape_ratio`, `escape_duplication`,
`escape_age`. Рёбра и `in:` правятся как у обычного узла — кодмод трогает только литерал.

## 7. Хеш и версия

Хешируем не исходник: переформатирование сменило бы `release_hash` и заставило перевыпускать релиз
без изменения поведения — нарушение байтового фикспойнта ADR-0017.

| Хеш | Формула | Устойчив к | Куда идёт |
|---|---|---|---|
| `body_hash` | `sha256('wf/node-body/v1+esbuild@0.28.2', esbuild.transform(src, { loader:'ts', minifyWhitespace:true }))` | форматирование, отступы, точки с запятой, TS-аннотации (стираются) | `spec_hash` → `release_hash` (04 §4.3) |
| alpha-хеш | то же с `minify:true` | плюс переименование локальных переменных | детект переименования и семантический дифф (04 §7), **не** в релиз |

Версия esbuild — часть домена хеша, её апгрейд есть миграция хешей, как у канонизатора JCS.
Типы в `body_hash` не входят: контракт живёт в IR (`in`/`out` из реестра), поэтому смена границы
`out` двигает `spec_hash` через поля узла, а не через тело. Правка тела — класс `BEHAVIORAL`:
инвалидирует replay-кэш узла и всё ниже; переименование переменных опознаётся совпадением
alpha-хеша и показывается в диффе как косметическое.
