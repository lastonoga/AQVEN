# Ответ на записку Studio: что закрыто, что осталось

Ответ от 2026-09-18 на [studio-api-integration.md](studio-api-integration.md). Аудитория — сессия,
которая ведёт `apps/studio`. Контракт обновлён в [23. API локальной студии](23-studio-api.md),
три ваших вопроса закрыты решением владельца и записаны в
[ADR-0030](adr/0030-local-browser-backend.md) `A18`.

Коротко: из шести расхождений закрыты все шесть, оба пункта «чего нет вообще» — тоже.
Нерешённым осталось только то, что упирается в зависимости и в реестр тулов; список внизу.

## 1. По вашей нумерации

### 2.1. Контекст прогона в `run_start` — закреплено

`RunStartRequest.context: RunContext | null` остался и теперь покрыт тестами на всех путях. Спека
догнала реализацию: §6.4 перечисляет `context?` в теле запуска, §6.1 — в строке маршрута. Тот же
контекст принимает MCP-тул `run_start` и CLI: `aqven run <flow> --input f.json --context date=2026-09-18
--context tenant_id=acme` (флаг повторяемый, пара без `=` — ошибка использования).

### 2.2. Флоу публикует ключи контекста — сделано

`FlowSummary.context` и `FlowDetail.context` — обязательное поле `RunContextKey[]`;
`GET /api/flows/{id}/schemas` отдаёт в `context` тот же список (тип сменился со `string[]` на
`RunContextKey[]`). Список выводит компилятор, как вы и предлагали:

- ключи собираются из всех привязок `$run.context.*` — `in`/`out` узла, `returns` флоу, `on` и `bind`
  у `switch`, `over` у `map`, `from` у `narrow`, `init` у `loop`;
- замыкание по графу вызовов: флоу с узлом `call` публикует и ключи вызываемых флоу (контекст у прогона
  один на всё дерево);
- объявление `context:` в `flow.yaml` стало необязательным; прежнее правило «ключ не объявлен в контексте
  флоу» снято, объявленный и ни разу не связанный ключ — предупреждение `W_CONTEXT_KEY_UNUSED`;
- `$run.context.weather` по-прежнему `E_REF_SYNTAX`.

На lumen без единой правки файлов: `support_case` → `["date", "tenant_id"]`, `judge_panel` → `[]`.
Форма запуска строится ровно по этому списку, все ключи обязательны.

### 2.3. `aqven check` и контекст — закрыто

Симуляция подставляет ровно те ключи, которые флоу объявил или которые вывел компилятор, и `None`, если
флоу контекст не читает. Раньше она подставляла фиксированные четыре значения — из-за этого гейт давал
зелень флоу, который гарантированно падал на первом `$run.context.*` по HTTP. Подробности — `A18` в ADR-0030.

### 2.4. Фильтры и сортировка `run_list` — реализованы

`GET /api/runs` принимает `flow_id`, `status`, `mode`, `assignee`, `parent_run_id`, `deadline_before`,
`overdue`, `since`, `until`, `sort`, `cursor`, `limit`. `sort` — `started_at` (по умолчанию, как было)
или `deadline_at`. Важное для инбокса: порядок и отбор по сроку задаёт индекс ожиданий в SQLite целиком,
а не страница — `ORDER BY deadline_at, run_id` идёт в индекс, и только найденные `run_id` уходят в запрос
прогонов. Клиентская досортировка страницы больше не нужна и будет неверной. `overdue=false` — открытые
ожидания, срок которых ещё не наступил; `since`/`until` — окно по `started_at` прогона. Таблица правил — §6.7.

### 2.5. Контракт событий в рантайме — закрыто

`GET /api/schemas/events` отдаёт настоящие схемы: `schemas{dialect, spec, run, chat}`, где каждый ключ —
карта «тип события → самодостаточный JSON Schema 2020-12 с `const` на `type`». Сейчас это 3 схемы spec-канала,
17 run-канала и 14 чата.

Одна деталь, чтобы не удивляться: массивы `spec`, `run`, `chat` остались пустыми **намеренно**. Они —
единственный якорь, который заводит `RunEvent`/`SpecEvent`/`ChatEvent` в `components.schemas`, то есть
ровно то, из чего вы выводите тип элемента (`components["schemas"]["EventCatalog"]["run"][number]`,
23 §2). `chat` стал обязательным, чтобы этот вывод работал и для чата. Переименовать их без вашей
правки нельзя, поэтому не переименовывали.

`GET /api/events/spec` остался на своём пути, но в OpenAPI у операции теперь честные `summary` и
`description`: это `text/event-stream`, который не завершается, а схемы — по соседнему адресу.

### 2.6. Видимость секретов — сделано

`GET /api/settings/secrets` отдаёт все секреты, которые объявляет проект: `{name, env_var, declared_by,
scope: provider|tool|mcp_server, declared_in, setting_key, source: environment|dotenv|null, masked, set}`.
Значение не отдаётся никогда, только маска. Источники: ключи провайдеров из `aqven.yaml` и провайдеров,
на которые ссылаются модели агентов; `secrets[]` тулов; ссылки на секреты в заголовках MCP-серверов.

Плюс два хвоста: `POST /api/runs` теперь отвечает `warnings[]` с записью
`{path: ["secrets", ENV_VAR], code: "SECRET_MISSING"}` на каждый незаданный секрет — прогон стартует,
но вы показываете нехватку сразу; и то же самое без сервера печатает `aqven secrets [путь] [--format json]`.
Раздел настроек описан в 23 §8.1 (раньше его в документе не было вообще).

### 3.1. Эвалы и датасеты по HTTP — есть

`GET /api/evals`, `GET /api/evals/{eval_id}`, `GET /api/datasets`, `GET /api/datasets/{dataset_id}`,
`POST /api/eval-runs` (202 + `poll`), `GET /api/eval-runs`, `GET /api/eval-runs/{id}`,
`GET /api/eval-runs/{id}/cases`, `GET /api/eval-runs/{id}/gate`. Модели и правила — 23 §9.1.

Имена не `/api/experiments*`, как в §9.2 спеки: сущность здесь — эвал из файлов, а не эксперимент в базе,
версий датасета нет, сплит читается из `metadata.split` кейса. Каждый кейс исполняется обычным движком,
поэтому у `CaseRecord` есть `run_id` — из строки кейса можно открыть полноценный вьюер прогона.
Вердикт гейта приходит `GATE_UNAVAILABLE` с `reason_code: statistics_unavailable`, пока в окружении нет
`numpy`, `scipy` и `statsmodels`: статистику не выдумываем.

### 3.2. Схемы моделей описания — есть

`GET /api/spec-schemas` и `GET /api/spec-schemas/{kind}` отдают ровно то, что `aqven schema` пишет в
`.aqven/schema/<kind>.schema.json` (сверено побайтно тестом). Публикуются все виды `SpecKind`; у `Node`
и `Type` в `variants` лежит документ на каждый вариант (по одному на `NodeKind`; `record`, `enum`,
`union`, `id`, `value`). Неизвестный `kind` отвечает 422 `REQUEST_INVALID` с
`problems[0].path = ["path","kind"]`, а не 404 — так enum видов уезжает в OpenAPI и список видов вы
получаете из типов; скажите, если предпочитаете 404 с `candidates`.

## 2. Ответы на ваши три вопроса

1. **Чат-сессия — на проект**, но несёт необязательный ярлык `flow_id`: он принимается в
   `POST /api/chat/sessions`, возвращается в `ChatSession` и фильтрует `GET /api/chat/sessions?flow_id=`.
   Ярлык — только для группировки: доступ он не ограничивает, по индексу проекта не проверяется
   (опечатка даст пустую выборку, а не 422), перевесить его нечем — `resume_session_id` открывает сессию
   с исходным ярлыком. Заодно `chat_turn_started` и `chat_turn_finished` теперь несут `backend` и `model`
   (в конце хода — фактическая модель ответа, даже если сессия создана с `model: null`). Контракт — 23 §15.
2. **`me` — локальный пользователь**: настройка `user.assignee` области `project`, иначе имя пользователя
   ОС. Сервер разворачивает `me` до планирования запроса, одинаково для REST, MCP и библиотеки; само
   значение отдаёт `GET /api/settings/user` → `{assignee, source: setting|os_user, setting_key}`, его же
   можно показать в шапке инбокса. Индекс ожиданий сравнивает `assignee` точно — прежнее «`me` совпадает
   с любым» снято.
3. **Движок контекст не выдумывает** — ваш вариант принят. Запуск флоу, которому нужны ключи, без них
   отвечает 422 `CONTEXT_MISSING` и перечисляет недостающее:
   `problems[] = {path: ["context", <ключ>], code: "CONTEXT_KEY_MISSING"}`. Проверка стоит в
   `EngineFacade.launch` — единственной точке старта для HTTP, MCP, CLI, библиотеки и симуляции.
   `date = сегодня` подставляет ваша форма; ни сервер, ни CLI значений по умолчанию не подставляют.

## 3. Одна поправка факта

В §3.1 записки сказано, что CLI умеет гонять эвалы: «`aqven eval --eval <id> <path>`». До этой работы
`aqven eval` был заглушкой — `PendingCommand` в таблице команд, `run_eval` бросал `EvalsUnavailable`.
Ничего не запускалось и не считалось. Теперь команда настоящая:
`aqven eval [путь] --eval <id> [--dataset <id>] [--baseline <eval_run_id>] [--repeats N] [--json]`,
история одна и та же с HTTP — она лежит в `.aqven/aqven.sqlite` проекта. Это меняет и вашу оценку
приоритета: HTTP-эвалы были не «обёрткой над работающим CLI», а новым слоем целиком.

## 4. Чего пока нет и почему

| Чего нет | Почему |
|---|---|
| Статистика гейта: BCa-бутстрап, Уилкоксон, McNemar, Holm, BH | `numpy`, `scipy`, `statsmodels` в окружении не стоят. Порт `Statistics` написан, адаптер — нет: его нельзя написать чисто под pyright strict, пока пакетов нет. Нужна группа зависимостей и пересборка `uv.lock` — решение владельца, 23 ОВ 33 |
| Тулы MCP `dataset_get`, `experiment_run`, `experiment_compare` | не зарегистрированы; маршруты §9.1 помечены `x-aqven-rest-only` с причиной «тула ещё нет», чтобы не обещать несуществующее. Решается при пересборке [14](14-mcp-contract.md), 23 ОВ 34 |
| Прогресс и отмена прогона эвала | только 202 и опрос `poll`; SSE-канала у прогона эвала нет, стоимость и токены видны по завершении |
| Версии датасетов, дисциплина train/dev/test | датасет — файл, версий в базе нет; `splits` считаются по `metadata.split` только для показа, эвал гоняет весь датасет |
| Сужение предупреждений о секретах | `warnings[]` в `run_start` перечисляет все объявленные проектом секреты, а не только достижимые из этого флоу: для сужения нужно замыкание скомпилированного флоу |
| Ускорение листинга прогонов без ожиданий | индексом ускорен инбокс; запросы вида `flow_id`/`mode`/`status=completed` по-прежнему сворачивают события всех подходящих прогонов, потому что `flow_id` и режим лежат внутри входа workflow |
| Перевесить ярлык чат-сессии | операции нет: нужен метод журнала и маршрут. Скажите, если это нужно экрану |
| Схема `Dataset` в `/api/spec-schemas` | отдаётся схема нашей модели файла датасета, а не `Dataset.model_json_schema_with_evaluators()` pydantic-evals, как требуют ADR-0026 §11 и ADR-0029. Так уже писал `aqven schema`, HTTP лишь сделал это видимым; нужно решение владельца |

## 5. Что сделать на вашей стороне

Регенерировать типы: `pnpm --filter @aqven/api-types pull` против запущенного сервера, затем `gen`;
`typescript` держать на 6.0.3 — ваш вывод про падение `openapi-typescript` 7.13.0 на TypeScript 7 мы
учли и никуда от него не уходим. `export_openapi(path)` остаётся публичным API пакета, как вы просили.

Что изменилось в схеме (всё поднимет регенерация, часть — несовместимо):

- `FlowSummary`/`FlowDetail`: новое обязательное `context: RunContextKey[]`; `FlowSchemas.context` сменил
  тип со `string[]` на `RunContextKey[]`;
- `RunStartRequest.context?`, `RunStarted.warnings[]`;
- `RunListQuery`: пять новых параметров (`deadline_before`, `overdue`, `since`, `until`, `sort`);
- `EventCatalog`: новое обязательное `schemas`, поле `chat` стало обязательным;
- `ChatSession`/`ChatSessionCreate`: `flow_id`; `chat_session_list` — параметр `flow_id`;
  `chat_turn_started`/`chat_turn_finished`: `backend`, `model`;
- новые пути: `/api/spec-schemas`, `/api/spec-schemas/{kind}`, `/api/settings/secrets`,
  `/api/settings/user`, `/api/evals*`, `/api/datasets*`, `/api/eval-runs*`;
- новый код ошибки `CONTEXT_MISSING` (422); `CHAT_STATE_CONFLICT` (409) в сервере был и раньше, но в
  таблице кодов его не было — теперь обе строки в 23 §12.5.
