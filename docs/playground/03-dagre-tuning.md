# 03. Настройка dagre и вложенность

Срез 2. Проверено запуском на `@dagrejs/dagre` 3.1.1 (latest по `npm view`) и React Flow 12.11.6.

## 0. Главная находка: кросс-уровневые рёбра выкинуты из раскладки

`layout.ts:layoutLevel` фильтрует: `if (!inside.has(edge.source) || !inside.has(edge.target)) continue`.
Ребро из `deduped` (корень) в узел внутри `call/map` не попадает **ни в один** прогон dagre: он его
не ранжирует, не разводит и не даёт `points`; React Flow рисует дефолтную безье из хэндла в хэндл —
сквозь карточки. **Это причина дефектов 1 и 2, а не стиль ребра.**

## 1. Параметры графа: что реально делает каждый

Дефолты из бандла 3.1.1: `{ranksep:50, edgesep:20, nodesep:50, rankdir:"TB", rankalign:"center"}`.
Читаются только: граф — `nodesep, edgesep, ranksep, marginx, marginy, acyclicer, ranker, rankdir,
align, rankalign`; узел — `width, height, rank`; ребро — `minlen, weight, width, height,
labeloffset, labelpos` (дефолты `labeloffset:10, labelpos:"r"`). Остальное игнорируется.

| Ключ | Что делает при `rankdir:"LR"` | Нам |
|---|---|---|
| `rankdir` | ось потока; `LR` — колонки слева направо | `"LR"` |
| `ranksep` | **горизонтальный** зазор между колонками; при метке ребра делится пополам вокруг метки | `160` |
| `nodesep` | **вертикальный** зазор между карточками одной колонки | `72` |
| `edgesep` | вертикальный зазор между параллельными рёбрами в одном зазоре ранга | `28` |
| `marginx/marginy` | поле вокруг всего графа | корень `32`, вложенные `0` |
| `rankalign` | `center/top/bottom` — выравнивание карточек **внутри колонки** по ширине. Проверено: при LR `top` = по левому краю колонки. Замер: на наших графах разница 0,03 % площади — карточки одной ширины, центрировать нечего | `"center"` (дефолт dagre) |
| `acyclicer` | `"greedy"` — снимает циклы жадной эвристикой вместо DFS; обратные рёбра помечаются `reversed:true` | `"greedy"` (нужно для `loop`) |

### ranker — сейчас у нас худший вариант

- `longest-path` — один DFS, узел уезжает на максимально поздний ранг: много длинных рёбер и дыры
  в колонках. **Сейчас в `layout.ts` стоит он — это причина дефекта 3.**
- `tight-tree` — longest-path плюс подтягивание по slack до плотного дерева; компромисс.
- `network-simplex` — минимизирует суммарную взвешенную длину рёбер. Дефолт dagre.
- `none` (в 3.x, в вики нет) — ранги не считаются, берётся `node.rank` как есть.

Замер: 100 узлов + 10 кластеров на `network-simplex` → **55 мс**. Берём его.

## 2. Составные графы работают. Проверено

`new dagre.graphlib.Graph({ compound: true })` + `g.setParent(child, parent)` в 3.1.1 работает и
**возвращает габариты кластера**. Вывод (карточки 224×150, `map` внутри `call`):

```
NODE call x=908 y=310 w=600 h=540 | NODE map x=778 y=310 w=260 h=500 parent=call
NODE a1 x=778 y=470 w=180 h=120 parent=map | NODE m1 x=1078 y=310 w=180 h=120 parent=call
```

1. Кластеру нужен `g.setNode(id, {})` **без** width/height — dagre запишет их сам.
2. Координаты детей — в глобальной системе, как у родителя. Для React Flow с `parentId` перевести
   в относительные: `child.x - parent.x + parent.width/2 - child.width/2`.
3. **Вложенность любой глубины** (`a1 → map → call`) — за один прогон.
4. Паддинг кластера **не настраивается**: `paddingLeft/...` игнорируются (150×120 с ними и без).
   Формула, проверена на трёх парах `nodesep/ranksep`: по оси ранга `ranksep/2` на сторону,
   поперёк `(nodesep + edgesep)/2`. Под шапку группы места нет — добирать постобработкой.
   См. §2.1: одной постобработки мало, когда потомок сам группа.
5. **`setParent(id, null)` — ловушка**: graphlib приводит к строке и создаёт узел с именем `"null"`.
   Для корневых узлов parent не трогать вообще.
6. **Ребро обходит кластер.** Ребро `a → z` мимо группы `grp` (y 7.5..117.5) получило маршрут
   `y = -12.5` — над рамкой, не сквозь неё. Это ровно дефект 2, решённый бесплатно.
7. **Свой `rankdir` у кластера** (3.x, в доках нет): `g.setNode('grp', { rankdir: 'TB' })` — группа
   ляжет сверху вниз внутри LR-графа; решение для веера `diverge` внутри `loop`. Цена: у рёбер
   **внутри** такого кластера `points` не возвращается (`undefined`).
8. Болячка сообщества: ребро **из ребёнка в сам кластер-родитель** ломает раскладку (dagre#238,
   PR #293, форк `dagre-cluster-fix@0.9.3`). Инвариант для `expand.ts`: вход/выход группы идёт
   в конкретный узел, не в рамку.

### 2.1 Отступ рамки зависит от того, что внутри

Постобработка «расширить рамку вверх на шапку» тихо ломается на группе внутри группы. Поперёк оси
ранга dagre даёт кластеру всего `(nodesep + edgesep)/2 = 32`, а вложенной рамке нужно её собственные
`GROUP_HEADER = 40` плюс зазор `GROUP_NEST = 16`. Рамка, расширенная за пределы кластерного
прямоугольника, съедает `nodesep` у соседей — так вложенная группа садится на нижнюю границу
родителя (скриншот заказчика, `diverge_judge_select`).

Механика в `layout.ts`:

| Шаг | Что делает |
|---|---|
| `framePadOf(nested)` | требуемый отступ рамки: лист — `40 / 18 / 18`, группа — `56 / 34 / 34` (верх / низ / бок) |
| `insetAt(depth)` | дефицит относительно паддинга dagre, накопленный по цепочке предков: `max(0, 40 − 32)` за свой уровень и `max(0, 56 − 32)` за каждый уровень выше |
| `compoundGraph` | лист уходит в dagre **раздутым** на этот дефицит; кластерам размер по-прежнему считает dagre |
| чтение `graph.node` | реальный прямоугольник ставится внутрь раздутой коробки со сдвигом `inset.left / inset.top` |
| `growFrames` | рамка группы считается **только по потомкам** с их `framePadOf`, без объединения с кластерным прямоугольником |

Инвариант: рамка каждой группы лежит внутри её кластерного прямоугольника. Кластеры dagre не
пересекаются, значит и рамки не пересекаются — вместо того чтобы отвоёвывать место у соседей,
группа забирает заранее зарезервированный запас внутри себя. По оси ранга дефицита нет
(`ranksep/2 = 45 > 34`), раздувается только высота: 8 px для листа на первом уровне, 32 px на втором,
56 px на третьем. Проверяется в `layout.test.ts` (`squeezed`, `crossedFrames`).

### Вердикт: составной граф лучше нашей рекурсии

`frame-layout.ts` + `layoutNested` дают три вещи, которых у compound нет: явный `GROUP_PAD`,
`GROUP_HEADER`, независимую раскладку группы. Взамен теряют кросс-уровневые рёбра (п. 0), обход рамок (п. 6) и общие ранги: узел внутри
группы не встанет в одну колонку с внешним, группа разложена отдельно. Отсюда дефект 5
(`map` «оторван» от `call`) и дефект 3 (рекурсия суммирует зазоры на каждом уровне).

**Менять на compound.** Шапку добираем постобработкой: расширить рамку кластера на `GROUP_HEADER`
вверх и сдвинуть потомков на ту же дельту вниз — арифметика над `rects`, пересечений не создаёт.

## 3. `edge.points` — они есть, мы их выбрасываем

Реальный вывод для длинного ребра `deduped → end` (наш дефект 1): 13 точек, маршрут уходит на
`y = 10` поверх всего графа и обратно вниз к цели —
`[{x:467.8,y:155},{x:568,y:10},…,{x:1552,y:10},{x:1628,y:85}]`.
Короткое ребро — 3 точки, через 4 ранга — 9: выход из источника, по одной на промежуточный ранг
(dummy-узлы), вход в цель. Система координат та же, что у узлов. React Flow multi-point ребра не
имеет (xyflow#980 открыт с 2021 без ответа; `getSmoothStepPath` берёт только source/target +
`borderRadius`, `offset`, `stepPosition`).

`points` кладём в `edge.data.points` (`edges.ts:toFlowEdge`); кастомное ребро собирает путь
`M x y` + на каждую среднюю точку `L … Q px py …` (скругление 8 px) и рисует
`<BaseEdge path={path} markerEnd={markerEnd} style={style} />`. Фолбэк на `getSmoothStepPath(props)`,
если точек меньше трёх (рёбра внутри кластера со своим `rankdir`, п. 2.7).

Две поправки: (а) крайние точки dagre — центры граней, заменить их на `sourceX/sourceY` и
`targetX/targetY` из пропсов ребра, средние оставить; (б) при `acyclicer:"greedy"` обратное ребро
помечается `reversed:true` — UNVERIFIED, разворачивает ли undo-фаза `points`; если нет, для
`kind === "loop"` разворачивать массив перед отрисовкой.

## 4. Порядок веток в колонке

Проверено (`t5.cjs`): порядок задаётся **порядком вставки узлов/рёбер**, детерминирован (5 прогонов
подряд — один результат), но **инвертирован**: вставленный первым уходит вниз.

Вставка `best_of, merge, rank, vote` → `y: 295, 205, 115, 25`; вставка в обратном порядке даёт
те же `y`, т.е. `best_of` наверху. Значит: **ветки `switch` вставлять в обратном порядке относительно желаемого сверху вниз.**
Входного атрибута `order` нет — с узла читаются только `width, height, rank`.

- `weight` (дефолт 1) на порядок в симметричном веере **не повлиял** — он выпрямляет цепочку
  в фазе позиционирования. `weight: 4` на `data`-магистраль, `1` на `branch`: магистраль пойдёт прямо.
- `minlen` (дефолт 1) — на сколько рангов минимум развести концы. `minlen: 2` для `fanin`-ребра
  отодвигает сборщик на колонку вправо, освобождая место под подписи веера.
- `ranker: "none"` + `node.rank` — закрепление стадии: узлы одной стадии с одним `rank` встают
  в одну колонку (проверено: `rank: 0` и `rank: 2` → две колонки, дырки нормализуются).
  Замена эвристике `ranks.ts`/`StageRail`.

## 5. Метки рёбер как узлы — прямое решение дефекта 4

dagre резервирует место под подпись, если у ребра заданы `width`/`height`: метка становится
dummy-узлом промежуточного ранга, `ranksep` делится вокруг неё, а в метку ребра пишутся `x`/`y` —
центр зарезервированного места. Проверено:
`g.setEdge('sw','vote',{ label:'vote', width:70, height:18, labelpos:'c' })` → `lbl x=300 y=25`,
зазор между колонками вырос с `ranksep` до `ranksep/2 + 70 + ranksep/2`.

- `labelpos: "c"` — подпись **на** ребре, место выделено в самом маршруте. Это нужный нам режим
  для подписей веток `switch`: `best_of`, `merge`, `rank`, `vote` встают каждая у своего ребра.
- `labelpos: "l" | "r"` + `labeloffset` (дефолт 10) — сбоку; `labeloffset: 24` сдвинул `y=25`→`y=58`.
- `edgesep` разводит соседние подписанные рёбра: `24` при высоте плашки 18.
- Ширина не на глаз: тот же шрифт (`ui-monospace`, 10 px), `width = label.length * 6 + 8`, `height = 18`.
- Метку в React Flow ставим по `edge.x/edge.y` через `EdgeLabelRenderer`
  (`translate(-50%,-50%) translate(Xpx,Ypx)`), **не** через `edge.label` — иначе она уедет
  в середину пути, мимо зарезервированного места.

## 6. Готовый блок для `layout.ts`

```ts
export const GRAPH_OPTIONS: GraphLabel = {
  rankdir: "LR",
  ranker: "network-simplex",
  rankalign: "top",
  acyclicer: "greedy",
  nodesep: 40,
  edgesep: 24,
  ranksep: 90,
  marginx: 24,
  marginy: 24,
}
```

| Значение | Обоснование |
|---|---|
| `ranker: "network-simplex"` | вместо `longest-path`: минимизирует суммарную длину рёбер, убирает дыры (дефект 3). 100 узлов — 55 мс |
| `rankalign: "top"` | карточки 224 и группы 600 в одной колонке выравниваются по левому краю, а не разъезжаются от центра |
| `nodesep: 40` | 0.27 высоты карточки. Паддинг кластера поперёк выходит `(40+24)/2 = 32` — рядом с нынешним `GROUP_PAD = 18`, с запасом под рёбра |
| `edgesep: 24` | высота плашки подписи 18 + 6; соседние подписи веера не наезжают |
| `ranksep: 90` | было 56 при ширине карточки 224 — тесно. Подпись шириной 70 превращает зазор в `45+70+45` |
| `acyclicer: "greedy"` | обратные рёбра `loop` не ломают ранжирование |
| `marginx/marginy: 24` | воздух под рамку корневого графа; во вложенных прогонах не нужны — прогон теперь один |

Порядок правки: (1) `layoutNested` → один составной граф, `setParent` по `node.parentId`,
кросс-уровневые рёбра **не фильтровать**; (2) постобработка `GROUP_HEADER`; (3) координаты детей
в относительные для `parentId`; (4) `points` и `x/y` меток в `edge.data`; (5) кастомное ребро
по точкам; (6) в `layout.test.ts` добавить «ни одна точка ребра не внутри чужого прямоугольника».


## 9. Срез 4: перебор `align` и сравнение с elkjs

Повод — «раскладка генерируется странно, её нужно центрировать; может, взять elkjs».

### 9.1 `align` — единственный параметр dagre, который реально что-то меняет

Перебор на 16 воркфлоу, 262 ребра. Считались: срезы (сегмент ребра проходит сквозь чужую карточку),
изломы (вертикальные участки), прямые рёбра (маршрут из двух точек), площадь канваса.

| ranker | align | acyclicer | срезов | изломов | прямых | площадь |
|---|---|---|---|---|---|---|
| network-simplex | — | greedy | 2 | 262 | 45 | 92 013k |
| network-simplex | **UR** | **greedy** | **2** | **219** | **82** | 92 615k |
| network-simplex | DR | greedy | 2 | 220 | 80 | 91 305k |
| network-simplex | UL | greedy | 5 | 218 | 68 | 98 481k |
| tight-tree | UR | greedy | 3 | 238 | 66 | 104 873k |
| longest-path | UR | greedy | 12 | 235 | 65 | 120 828k |

`align: "UR"` **удваивает число прямых рёбер** (45 → 82) и снимает 43 излома — бесплатно, одной
строкой. `UL`/`DL` дороже по площади и дают лишние срезы. `rankalign` не влияет (см. таблицу выше).

### 9.2 elkjs 0.12.0 — замерено, отклонено

Поставлен, прогнан на тех же 16 воркфлоу, затем удалён.

Первый замер был нечестным: маршруты dagre проходят наш пост-обход препятствий (`reroute.ts`),
маршруты ELK — нет. Честное сравнение — одна и та же раскладка рёбер (`channels.ts` + `reroute.ts`)
поверх обеих раскладок узлов:

| раскладка узлов | прямых | канальных | с обходом | изломов | срезов | площадь | время |
|---|---|---|---|---|---|---|---|
| **dagre** `align:UR` | **82** | 130 | 50 | **219** | 2 | 92 615k | ~30 мс |
| elkjs `BRANDES_KOEPF` | 57 | 157 | 48 | 253 | **0** | **69 363k** | 171 мс |

Вывод: **остаёмся на dagre.** По прямизне рёбер dagre лучше (82 против 57 прямых, 219 против 253
изломов). ELK выигрывает только компактностью (−25 % площади) — а нам заказчик прямо сказал, что
место есть и плотность не нужна. Цена перехода при этом реальная: асинхронный API (перестройка
`FlowCanvas` с `useMemo` на состояние), 8 МБ зависимости против 1,3 МБ, лицензия EPL-2.0 OR GPL-3.0
вместо MIT, пятикратное замедление раскладки.

Отдельная находка: собственный ORTHOGONAL-роутер ELK давал 112 прямых рёбер — больше, чем ELK с
нашим роутером (57). Разница не в раскладке узлов, а в **свободном размещении портов**: ELK двигает
точку крепления вдоль стороны карточки, мы всегда крепим по центру. Если понадобится ещё прямизны —
рычаг здесь, а не в смене библиотеки.

## 10. Нормализация маршрутов: каналы

`channels.ts`. Раньше вертикальный участок ребра стоял там, где его поставил dagre, — у каждого
ребра в своём месте; на экране это читалось как «стрелки то посередине идут вверх, то вниз».

Теперь для каждого ребра, идущего вперёд по рангу, вертикальный участок ставится в **общий канал**:
середины межранговых зазоров собираются в кластеры с допуском `RANK_PAD`, канал — среднее кластера.
Рёбра с совпадающими центрами концов идут прямой линией без излома вовсе. Если два ребра попадают в
один канал и их вертикальные участки перекрываются по `y`, второе смещается на `EDGE_SEP`.

Канальный маршрут применяется, только если он не режет чужие карточки (`clean`); иначе берётся
прежний путь dagre с обходом. Итог на 16 воркфлоу: 82 прямых, 130 канальных, 50 с обходом,
2 среза — те же 2, что и были.
