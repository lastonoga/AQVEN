# Круговорот «TypeScript-код ↔ визуальный редактор»

> Вопрос среза: может ли правка мышью на канвасе менять TypeScript-файл — и есть ли хоть один прод-прецедент?

## 1. Кто сделал круговорот, а кто провалился

| Инструмент | Направление | Что является источником топологии | Итог |
|---|---|---|---|
| **WinForms Designer** | **двусторонний, по настоящему коду** | C# внутри `InitializeComponent` в designer-owned файле | **работает 20+ лет**; цена — явный контракт «парсим только то, что сами сериализовали» |
| Delphi / Interface Builder | двусторонний | **отдельный ресурсный файл** (`.dfm`, `.xib`), не код | работает, потому что круговорот идёт не по коду вообще |
| Windmill | двусторонний | YAML флоу, редактируемый прямо в редакторе графа | работает; TS — только тела шагов |
| n8n / Node-RED / Flowise / Langflow | односторонний (UI → JSON) | JSON | работает, но кода как топологии нет в принципе |
| Retool ToolScript | **односторонний по факту** | `.rsx`, генерируемый из UI | текст сделан читаемым для ревью, **не для правки руками** |
| FlutterFlow ↔ VS Code | ручной копипаст в зоне `lib/custom_code/` | проект FlutterFlow | круговорота нет, есть шлюз |
| Blockly / Scratch | **односторонний** (блоки → код) | блоки | обратного разбора нет; сделан только на суженном подмножестве (`blockly-text2code`) |
| Onlook, Lovable Visual Edits | двусторонний по TSX через AST | файлы проекта | **работает в проде, но периметр — атрибуты JSX/className**, не структура программы |
| Pagedraw, UML round-trip | пытались — отказались/деградировали | — | причина одна: на вход приходит произвольный код, а не тот, что сгенерировали |

Закономерность без исключений: **круговорот выживает там, где у designer-а исключительное владение
куском текста и явно суженная грамматика этого куска.** Все провалы — попытки разобрать произвольный код.

## 2. AST-правка TypeScript: что реально гарантируется

Проба (ts-morph 28.0.0 + prettier 3.9.6, Node 20): файл в стиле нашего DSL — `workflow(...)` с массивом
`step(...)`, внутри шага стрелочная функция `code`, рядом комментарий и пустая строка. Кодмод сдвинул
`layout` у `transform` и добавил `step("notify", …)`. Дифф после `prettier --write`:

```
+    // TODO: вынести в отдельный компонент
     step("transform", {
       code: (input) => {
         const rows = input.items.filter((i) => i.total > 0);
         return { rows, sum: rows.reduce((a, b) => a + b.total, 0) };
       },
-      layout: { x: 120, y: 200 },
+      layout: { x: 640, y: 310 },
     }),
+    step("notify", { channel: "slack", layout: { x: 640, y: 470 } }),
   ],
```

Проверено фактами пробы:

| Вопрос | Ответ |
|---|---|
| Тело `code`-узла уцелело? | да, байт в байт — ts-morph переписывает только затронутые диапазоны |
| Комментарий рядом с узлом уцелел? | да |
| Пустые строки-разделители уцелели? | да |
| Отступ вставленного элемента корректен? | **нет** — ts-morph поставил его на чужой уровень и вынес `]` в нулевую колонку |
| Чем лечится | прогон `prettier --write` по изменённому файлу; на уже prettier-форматированном репозитории это no-op для нетронутых строк |

| Инструмент | Когда брать |
|---|---|
| **ts-morph 28** | наш случай: типизированный обход, `Project`/`SourceFile`, правка по месту, переписывает только изменённые диапазоны |
| recast 0.24 | точное сохранение форматирования нетронутых узлов ценой работы через Babel-AST без типов TS |
| jscodeshift 17.4 | пакетные одноразовые миграции по многим файлам, не интерактивные правки из UI |
| голое Compiler API | `ts.transform` печатает файл заново `Printer`-ом и **теряет исходное форматирование**; для нашей задачи не подходит |
| magicast 0.5.5 | правка конфигов-литералов; наш DSL сложнее, но идея «трогаем только литералы» ровно его |

Вывод по инструменту: **безопасно — да, но только для механических правок над известными узлами AST,
и только с обязательным Prettier-проходом после.** Переписать произвольное выражение безопасно нельзя.

## 3. Три модели и их цена

| | (а) код — единственный источник, канвас читает | (б) IR — источник, код генерируется | (в) двусторонний круговорот через AST на подмножестве |
|---|---|---|---|
| Правка мышью | невозможна, канвас read-only | пишет в IR, код перегенерируется целиком | пишет в те же файлы кодмодом |
| Ручные правки кода | сохраняются полностью | **теряются при следующей генерации** | сохраняются вне зоны кодмода |
| Что ломается | продукт теряет визуальный редактор как инструмент правки — а он у нас заявлен как отладчик и способ авторинга | инженер перестаёт держать код: любой его комментарий, хелпер, импорт — расходник | сложность реализации + риск «парсим не то, что сами написали» |
| Стоимость сборки | низкая (нужен только парсер кода → IR) | низкая (нужен только принтер IR → код) | высокая: парсер + кодмод + Prettier + тесты идемпотентности |
| Прецедент | Pulumi, CDK, Cube.js (`.js`-модели) | Retool ToolScript, старые UML-генераторы | WinForms Designer, Onlook, Lovable |
| Главная скрытая цена | правка мышью деградирует до «сгенерируй мне патч LLM-ом» | git-дифф перестаёт отражать намерение человека | контракт «designer парсит только то, что сериализовал» надо держать вечно |

Ключевая ошибка при выборе — считать (в) более рискованным, чем (б). Модель (б) теряет данные
детерминированно и каждый раз; (в) теряет их только там, где нарушен явный контракт грамматики.

## 4. Где проходит граница подмножества

Наша архитектура уже сдвинула границу в нужную сторону, и это надо зафиксировать явно.

| Класс правки на канвасе | Трогает ли файл | Почему |
|---|---|---|
| Двигать узел, зум, панорама | **нет, не трогает вообще** | по [ADR-0017](../adr/0017-files-as-source-of-truth.md) раскладка канваса живёт в Postgres, LWW-канал, и не является частью определения |
| Добавить/удалить узел | да: создать/удалить `nodes/<node_id>.*` + одна правка списка | файл на узел по ADR-0017 — структурная правка почти не требует AST |
| Перепровести ребро, сменить биндинг | да: один `PropertyAssignment` внутри объектного литерала | механическая замена значения |
| Сменить параметр узла (модель, ретраи, температура) | да: одно скалярное значение | то же |
| Переименовать узел | да: ключ + все ссылки | нужен typed-обход, ts-morph справляется |
| **Править тело `code`-узла** | **нет, канвас не трогает никогда** | это произвольный TS; редактируется только в редакторе кода |
| Править импорты, хелперы, произвольный TS вокруг | **нет** | вне зоны designer-а |

Граница подмножества (draft): **объектные литералы, массивы литералов, вызовы известных функций DSL,
строковые и числовые литералы, ссылки на импортированные идентификаторы.** Всё остальное — включая
циклы, условия, вычисляемые ключи, spread, тернарники внутри аргументов DSL — **не в подмножестве**.

Что делать с кодом вне подмножества: не ломать и не переписывать, а **отказывать в визуальной правке**
с явным сообщением. Прецедент WinForms ровно про это: designer парсит то, что сериализовал, и честно
падает в «code view» на остальном. Технически проверка дешёвая — валидатор подмножества, прогоняемый
парсером до открытия канваса; узел, не прошедший его, показывается как read-only.

## 5. Прецедент: есть ли инструмент, где мышь меняет TypeScript-файл в проде

**Есть, два.** Onlook (open-source) и Lovable Visual Edits (коммерческий прод) пишут правки мышью
в TSX через AST — [Onlook](https://onlook.com/features/visual-editor), [Lovable](https://lovable.dev/blog/visual-edits).
Но прецедент **слабее, чем нужен нам**: их периметр — атрибуты JSX-элементов (`className`, стили),
а сопоставление DOM↔код держится на вставленном в разметку маркере `data-oid`. Правки **структуры
программы** (добавить вызов, перепровести данные между вызовами) публично не заявлены ни у одного из них.

Прецедент на структуру есть, но не на TypeScript: **WinForms Designer** — 20+ лет продакшена, правка мышью
переписывает реальный C#. Формулируя честно: **круговорот «мышь → структура программы в файле исходника»
доказан на C# с CodeDOM и на суженных грамматиках; на TypeScript он доказан только для атрибутов.
Мы будем первыми в этой точке, и планировать надо соответственно.**

## Вывод для нас

1. **Берём (в), но в сильно облегчённом виде** — не потому что смелые, а потому что ADR-0017 уже снял
   самую тяжёлую половину задачи: **перетаскивание узлов не пишет в файл вообще**. Остаётся узкий класс
   структурных правок, каждая из которых — механическая замена в объектном литерале или создание файла.
2. **Файл на узел — главный рычаг.** Большая часть «правок графа» превращается в файловые операции,
   а не в AST-хирургию. Эту раскладку из ADR-0017 при переходе на TypeScript сохраняем: `nodes/<id>.ts`.
3. **Тела `code`-узлов канвас не трогает никогда.** Это должно быть записано как инвариант продукта,
   а не как текущее ограничение реализации. Проба подтвердила: ts-morph правит соседние поля, не касаясь
   тела стрелочной функции ни на байт.
4. **Инструмент: ts-morph 28.0.0 + обязательный Prettier-проход.** Один отступ ts-morph ставит неверно;
   без Prettier дифф будет шумным. Записать в DECISIONS третью ось версий: TS внутри `@ts-morph/common`
   вшит и не равен TS 6.0.3 проекта.
5. **Нужен валидатор подмножества как отдельный компилятороподобный проход** — до канваса, не во время
   правки. Узел вне подмножества показывается read-only с причиной. Это цена, которую WinForms заплатил
   открыто и за счёт этого выжил.
6. **Чего не делаем:** не пытаемся разбирать произвольный TypeScript в граф (Blockly, Pagedraw, UML —
   три независимых провала на одном и том же); не генерируем код из IR поверх ручных правок (Retool
   прямо предупреждает, что такие правки теряются); не делаем канвас read-only (модель (а) убивает
   заявленную ценность Studio).
7. **Kill-критерий для этого среза:** цикл «прочитать TS → IR → правка кодмодом → прочитать снова» должен
   быть идемпотентен по `spec_hash` и не менять ни одного байта вне затронутых диапазонов. Проба на
   игрушечном файле это свойство показала; на реальном DSL — проверять тестом, а не верой.
