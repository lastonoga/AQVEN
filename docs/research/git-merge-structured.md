## 1. Почему текстовый three-way merge ломается на YAML/JSON

Git мерджит строки, не смысл. Четыре класса поломок, каждый воспроизводим на нашем IR:

| Класс | Что происходит | Почему git не спасёт |
|---|---|---|
| Переупорядочивание ключей | Ветка A переписала узел через сериализатор с другим порядком полей → diff на весь блок | git видит удаление+вставку N строк, конфликт с любой правкой B |
| Отступы и стиль YAML | flow vs block стиль, кавычки, `>-` vs `\|` | то же: перезапись блока |
| Списки | вставка узла в середину `nodes:` в обеих ветках | git склеит оба **и не заметит**, что порядок теперь бессмысленный; для map-подобных списков это классический ложный auto-merge |
| Позиционные ссылки | `edges[3].from` указывает на индекс | смысловая порча без текстового конфликта |

Что реально работает в 2026:
- **Канонизация на записи.** Один сериализатор, отсортированные ключи, фиксированный стиль. У нас это уже есть: JCS/`canonicalize` 5.0.0 и `sortMapEntries: true` (04-ir-schema.md §hash, §YAML). Это убирает классы 1–2 целиком и стоит ноль.
- **Merge-драйвер.** Mergiraf — единственный живой универсальный (tree-sitter + GumTree, PCS-тройки, «коммутативные родители» для списков без порядка). Ограничение архитектурное и жёсткое: **драйвер живёт в `.git/config` разработчика**. На сервере (GitLab MR, GitHub merge button) он не работает — [gitlab#18830](https://gitlab.com/gitlab-org/gitlab/-/issues/18830) открыт с 2016. Значит на драйвер нельзя опереться как на инвариант продукта: у половины пользователей merge пройдёт построчно.
- Вывод: **merge-драйвер — это UX-улучшение для тех, кто редактирует руками в IDE, а не механизм корректности.** Корректность обязана жить в валидаторе, который гоняется после merge.

## 2. Слияние графа: что берём из соседних дисциплин

| Подход | Идея | Применимо к нам |
|---|---|---|
| k8s SSA / structured-merge-diff | Поведение merge объявлено **в схеме**: `listType: map` + `listMapKeys` (что считать идентичностью элемента), `atomic` vs `granular` (кто владеет блоком целиком) | Да, прямо. Наш IR уже схематизирован: пометить `nodes` как map по `id`, `edges` как map по `(from,to,slot)`, тело промта — `atomic` (частичное слияние текста промта бессмысленно) |
| EMF Compare / Diff-Merge | 20 лет model-driven: матчинг по ID быстрый и надёжный, эвристики/graph-matching — медленные и шаткие | Да: **стабильный `id` узла — не удобство, а предусловие слияния.** Без ID мы обречены на эвристику схожести |
| CUE | `&` коммутативна/ассоциативна/идемпотентна; слияние = сужение множества значений, конфликт = пустое множество | Частично. Красиво для конфигов-констрейнтов, но граф — не решётка: «удалил узел» в CUE не выражается (unification только сужает, никогда не удаляет). Как модель merge для IR не годится; как идея «конфликт = формально пустое значение, а не текстовые `<<<<<<<`» — годится |
| Миграции БД | Не сливают состояние, сливают **последовательность операций**; конфликт ловится линеаризацией (одна ветка миграций) | Это ровно наш op-log. Схождение отраслей: и k8s, и БД, и мы пришли к «слияние по операциям + декларативная схема владения» |

Практический вывод по графу: **три-путевое слияние графа = три-путевое слияние двух map'ов** (`nodes` по id, `edges` по составному ключу) плюс per-node merge полей. Это ~200 строк кода поверх уже существующей канонизации, а не исследовательская задача. Тяжёлое остаётся тяжёлым: слияние, валидное по структуре, может быть невалидно семантически (дважды подключили один слот, цикл, оборванная ссылка). Ответ тот же, что у нас в ADR-0009: **валидатор в той же транзакции**, merge-результат не принимается без компиляции.

## 3. Гранулярность: один файл или каталог

| | Один YAML на воркфлоу | Каталог, файл на узел |
|---|---|---|
| Конфликты при параллельной правке разных узлов | Всегда в одном файле; спасает только структурный драйвер (которого на сервере нет) | **Git решает сам**: разные файлы = нет конфликта, вообще без драйвера |
| Переименование/перемещение узла | невидимо | rename-детект git, чистая история |
| Читаемость воркфлоу целиком | одна страница, видно всё | нужен генерируемый обзор (`flow.yaml` с рёбрами) |
| Порядок узлов | значим в файле → ложные конфликты | не существует как понятие: порядок выводится из `edges` |
| Атомарность коммита | естественная | тоже естественная (коммит = набор файлов) |
| Прецедент | Kestra (flow = один YAML) | Windmill (`<path>__flow/` — каталог) |

Оба прецедента живые, но они решают разные задачи: Kestra флоу — декларативный YAML на 50 строк, Windmill — флоу с инлайн-скриптами, которые обязаны быть отдельными файлами, чтобы работал LSP и линтер. Наш случай ближе к Windmill: узел несёт промт (многострочный текст) и схему типа — то, что хочется редактировать как файл.

Рекомендуемая раскладка, если идём в файлы:
```
flows/<flow_id>/
  flow.yaml            # метаданные + edges (единственное место, где связи)
  nodes/<node_id>.yaml # тело узла; имя файла = стабильный id, не имя
  prompts/<frag>.md    # длинные тексты — отдельными файлами, дифф построчный и читаемый
```
Три правила, без которых это не работает: (1) имя файла = **стабильный неизменяемый id**, человекочитаемое имя — поле внутри; (2) ключи отсортированы канонизатором на записи, форматирование недопустимо ставить руками; (3) `edges` — единственное место со связями и **отсортированы детерминированно** (по `(from,slot,to)`), иначе вернулись к ложным конфликтам.

## 4. Дифф для человека

| Кто | Как показывает | Урок |
|---|---|---|
| n8n | Визуальный дифф **на канве**: N/M/D-бейджи на узлах и связях, клик по узлу → JSON-дифф параметров; инстанс vs ветка git | Единственный найденный образец настоящего графового диффа в проде. Бейдж на узле + дифф деталей по клику — ровно тот UX, который нам нужен |
| Kestra | Monaco side-by-side по тексту YAML между двумя ревизиями из БД + Restore | Даже git-native продукт для человека показывает **текстовый** дифф ревизий из своей БД, а не `git diff` |
| Terraform | `plan` как список действий над ресурсами с префиксами `+/-/~/-+`, `show -json` для машин | Дифф как **план действий с идентичностью объектов**, не как текст |
| k8s SSA | Дифф как набор полей с владельцами (`managedFields`) | Дифф отвечает не только «что», но и «кто владеет» — важно, когда правят и UI, и агент |

Вывод: семантический дифф нам всё равно писать (он уже в плане), и **git его не даёт** — git даёт хранение и merge, а «что изменилось для человека» строится поверх IR обоими лагерями одинаково.

## 5. Terraform-парадигма: что стоит взять

| Элемент TF | Суть | Брать? |
|---|---|---|
| `plan` → `apply` | Изменение сначала предъявляется как список действий, применяется отдельным шагом; `plan -out` фиксирует **ровно тот** набор действий | **Да.** «Применить воркфлоу» = показать план (узлы +/~/-, влияние на триггеры и расписания), затем apply по сохранённому плану. Kestra ровно это назвала `dryRun: "writes a diff without applying changes"` |
| state file | Отдельный слепок «что применено», против которого считается дифф | **Частично.** У нас роль state играет `specs.head_version` + `compiled`. Отдельный файл-состояние заводить незачем — это была бы третья копия истины |
| drift | Реальность разошлась с декларацией; ловится `-refresh-only` | **Да, но узко:** дрейф у нас = «в UI поправили, в git не закоммитили» и наоборот. Нужна команда «показать расхождение git ↔ head», иначе двусторонний sync тихо теряет правки |
| import | Затянуть существующий объект под управление | **Да**, как «импорт бандла/чужого воркфлоу в проект с сохранением id» — это уже есть в 18-export-and-conformance |
| destructive by default | `delete` в Kestra по умолчанию `false` | **Да**, копируем дословно: отсутствие файла в git ≠ команда удалить прогоны и расписания |

## Вывод для нас

**Главный результат среза: git не решает ту задачу, ради которой его предлагают взять.** Три-путевое слияние графа git не умеет ни в каком виде; структурный драйвер (Mergiraf) существует, работает и хорош, но по архитектуре git он локальный и на серверном merge не применяется ([gitlab#18830](https://gitlab.com/gitlab-org/gitlab/-/issues/18830)) — то есть не может быть инвариантом продукта. Семантический дифф для человека git не даёт вообще: n8n и Kestra строят его сами поверх своей модели. Остаётся хранение, история и откат — ровно то, что уже есть в `spec_versions` (§16-data-model: content_hash, parent_id, lineage) и op-log (ADR-0009).

Берём:

| Что | Откуда | Почему именно это |
|---|---|---|
| Декларация merge-поведения в схеме IR: `nodes` — map по `id`, `edges` — map по `(from,slot,to)`, тело промта — `atomic` | k8s SSA `x-kubernetes-list-type`/`list-map-keys` | Превращает «слияние графа» в слияние двух map'ов; это код на день, а не исследование. И это работает одинаково и для git-merge, и для merge двух op-log-веток в БД |
| Стабильный неизменяемый `id` узла как ключ матчинга, имя — отдельным полем | EMF Compare/Diff-Merge: match by ID (fast) vs эвристики (slow) | Предусловие любого осмысленного диффа и merge. Проверить, что в 04-ir-schema id узла действительно неизменяем при переименовании |
| Канонизация на записи (JCS + `sortMapEntries`, детерминированный порядок `edges`) | §1 | У нас уже есть — это отсекает 2 из 4 классов ложных конфликтов бесплатно, независимо от того, где хранится истина |
| `plan → apply` с предпросмотром и `dryRun` | Terraform `plan -out`; Kestra `dryRun: "writes a diff without applying changes"` | Наш `flow_revert` и применение импорта должны показывать план (+/~/-) до записи. Сейчас в DECISIONS этого шага явно нет |
| `delete: false` по умолчанию при синхронизации | Kestra | Отсутствие воркфлоу в бандле/ветке ≠ разрешение удалить его прогоны и расписания |
| Дифф как бейджи N/M/D на узлах канвы + JSON-дифф по клику | n8n compare-versions | Готовый, проверенный в проде UX семантического диффа. Копировать целиком, не изобретать |
| Каталог `flows/<id>/nodes/<node_id>.yaml` — **для экспортного представления**, не для хранения | Windmill `<path>__flow/` | Если бандл раскладывается в git (18-export §«В git бандл кладётся распакованным»), пусть раскладывается по файлу на узел: тогда параллельные правки разных узлов git сольёт сам, без драйвера |

Не берём:

| Что | Почему |
|---|---|
| Git как источник истины спеки | Он не даёт merge графа, не даёт семантический дифф, не даёт транзакционную валидацию «невалидная ревизия физически не может попасть в историю» (ADR-0009 §101). Взамен он забирает транзакцию с прогонами/кассетами/расписаниями, которые в git не положишь |
| Mergiraf как обязательный merge-драйвер | Локальность драйвера = корректность зависит от настройки рабочей станции. Можно предложить как опциональный DX-бонус для тех, кто правит YAML руками; нельзя закладывать в инварианты |
| CUE-модель слияния | Unification только сужает и не выражает удаление узла; граф — не решётка. Идею «конфликт = формальное пустое значение, а не `<<<<<<<` в тексте» берём, язык — нет |
| `json-merge-patch` / `fast-json-patch` как основа операций | RFC 7386 не умеет патчить элемент массива, RFC 6902 адресует по индексу (нестабильно при вставке). Обе библиотеки без изменений с 2022. Наши ops по `node_id` строго лучше |
| Отдельный state-файл по образцу Terraform | Третья копия истины. Роль state уже играет `specs.head_version` + `compiled` |

Что это меняет в решениях: ничего в базовом выборе (JSONB остаётся истиной), но добавляет три обязательства — (1) объявить merge-семантику коллекций прямо в схеме IR, (2) ввести шаг `plan` перед применением изменений спеки и при импорте, (3) при экспорте в git раскладывать воркфлоу по файлу на узел, чтобы git-merge был осмысленным хотя бы на экспортном представлении. Отдельным пунктом — команда «показать расхождение git ↔ head», иначе двусторонний sync теряет правки молча.
