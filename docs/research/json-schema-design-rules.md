# Правила проектирования JSON Schema для надёжного structured output — референс (сентябрь 2026)

> Дополняет разделы «Модели и провайдеры» и «Архетипы узлов» основной архитектуры: это не про API-механики провайдеров, а про дизайн самой схемы — как писать её, чтобы модель давала качественный и валидный результат.

## TL;DR

- **Порядок полей — не косметика, а логика.** В constrained decoding модель генерирует токены слева направо; поле, объявленное раньше, эмитится без доступа к тому, что будет позже. Reasoning-поле после answer-поля превращается в post-hoc рационализацию уже сделанного выбора. Правило: reasoning/evidence-поля всегда идут до answer/label-поля.
- **Глубина вложенности бьёт по качеству резко и предсказуемо.** DeepJSONEval (сентябрь 2025) зафиксировал систематическую деградацию у всех протестированных LLM между уровнями 3–4 и 5–7 с падением строгой оценки на 17–30+ процентных пунктов. ExtractBench (2026) получил 0% валидного вывода на схеме с 369 полями у всех фронтир-моделей.
- **Strict constrained decoding — не бесплатная гарантия.** Маскирование недопустимых токенов лишает модель «черновика»: если схема открывается полем answer, модель обязана вынести вердикт на первом токене без права сначала порассуждать. На open-weight моделях это даёт задокументированное падение точности на 3–9 п.п., на математическом reasoning — заметно больше.
- **Provider-specific различия существенны.** OpenAI strict mode требует все поля в `required` и запрещает `oneOf`; Gemini использует только `anyOf` и управляет порядком эмиссии через `propertyOrdering`, а не порядок в схеме; Anthropic не enforce-ит числовые/строковые ограничения и рекурсию нативно. Портируемое между всеми тремя подмножество уже — только `anyOf`, `required`+nullable вместо true-optional, без рекурсии, без числовых constraint-keyword'ов.

## 1. Порядок и структура полей

### 1.1 Reasoning-before-answer

Идея восходит к chain-of-thought prompting (Wei et al., 2022) и формализована для structured output как принцип «не ставь телегу впереди лошади»: если reasoning-поле идёт после answer-поля, оно становится побочным продуктом уже данного ответа, и chain-of-thought реально превращается в zero-shot промпт.

Механизм на уровне токенов: под strict constrained decoding первый эмитируемый токен схемы (например, значение поля `label`) сэмплируется из контекста, который содержит только вход и системный промпт — модель ещё ничего не написала. Всё, что говорится в rationale после, было обусловлено уже сделанным выбором `label`, а не наоборот. Поле, объявленное до ответа, — это реальный scratchpad; поле после ответа — постмортем, который модель пишет, чтобы оправдать уже принятое решение. С unconstrained-генерацией эта проблема часто маскируется, потому что модель может проигнорировать заявленный порядок ключей и написать их в удобном себе порядке; strict-режим убирает эту лазейку, потому что порядок enforced на уровне логитов.

BAML систематизировал четыре техники встраивания reasoning в structured output: (1) reasoning перед объектом жёстким блоком, (2) гибкое reasoning перед объектом, (3) reasoning как поле внутри объекта, (4) reasoning как комментарии внутри JSON5. Для большинства случаев рекомендована техника 2.

**Правило именования enum-значений и label:** значения должны различаться уже на первом токене (`urgent/normal/low`, а не `p0/p1/p2`), иначе logprobs по такому полю бессмысленны для расчёта confidence.

### 1.2 Gemini: propertyOrdering

У Gemini порядок эмиссии полей управляется отдельным ключом `propertyOrdering`, а не порядком в JSON Schema. Без явного `propertyOrdering` порядок для Python SDK следует порядку, заданному в схеме; для остальных случаев — алфавитному порядку с группировкой required-полей первыми. Если в промпте есть примеры/описания с одним порядком полей, а в `responseSchema` — другим, рассинхрон путает модель и может привести к некорректному выводу.

Продакшн-измерение (сентябрь 2026, независимый практик, не подтверждено официальной документацией Google) показало более тонкий эффект: если `propertyOrdering` не задан явно, реальный порядок эмиссии определяется позицией поля в массиве **`required`**, а не в `properties`. Поле, стоящее третьим в `required`, эмитировалось третьим независимо от позиции в `properties`. Известный workaround без доступа к `propertyOrdering` (например, в некоторых SDK) — называть ключи так, чтобы алфавитный порядок совпадал с желаемым (`reasoning` и `solution` вместо `reasoning` и `answer`).

**Правило для линтера:** если целевой провайдер — Gemini, порядок полей в `required` должен совпадать с желаемым порядком эмиссии (reasoning-поля первыми), независимо от порядка в `properties`. У `propertyOrdering` нет эквивалента у OpenAI/Anthropic — для мультипровайдерных схем канонический порядок полей держится в одном месте и адаптируется под конкретный API, а не поддерживается как две отдельные схемы.

## 2. Глубина вложенности и сложность схемы

### 2.1 Эмпирика деградации

| Источник | Метрика | Данные |
|---|---|---|
| DeepJSONEval (сентябрь 2025) | strict score, medium (3–4 уровня) vs hard (5–7 уровней) | системная деградация у всех 12 протестированных LLM, падение до 17–30+ процентных пунктов |
| The Structured Output Benchmark (2026) | Value Accuracy (точное совпадение leaf-значений) | 83.0% на тексте, 67.2% на изображениях, 23.7% на аудио — при этом schema compliance близка к идеальной у всех |
| ExtractBench (2026) | доля валидного вывода | 0% на схеме с 369 полями у GPT-5/5.2, Gemini-3, Claude 4.5 Opus/Sonnet |

### 2.2 Практический потолок

Консенсус практики: **2 уровня вложенности — комфортная зона, 3 — предел, 4+ — систематические ошибки** (значения попадают не на тот уровень, вложенные объекты пропускаются целиком). Отдельный количественный ориентир по совместимости с движками constrained decoding: схемы до **20 свойств и глубины до 3** компилируются быстро на всех бэкендах (XGrammar, Guidance, llguidance).

Провайдерские жёсткие потолки: у OpenAI strict — до 5 уровней вложенности и до 100 свойств во всей схеме суммарно.

### 2.3 Flattening и разбиение на несколько вызовов

Если целевой API требует глубокой вложенности (например, чтобы соответствовать существующей data-модели), практика — держать плоскую альтернативу как основную LLM-схему, а вложенную структуру собирать кодом после парсинга.

**Когда разбивать одну сложную схему на несколько последовательных LLM-вызовов вместо одной глубокой:** когда суммарное число полей приближается к провайдерским потолкам, либо когда breadth-тест (аналог 369-полевой схемы ExtractBench) показывает нулевую или близкую к нулю валидность. В этом случае архитектурно правильнее декомпозировать на несколько extractor-узлов по логическим секциям, а не пытаться удержать всё в одной мега-схеме.

## 3. Enum и constrained values

### 3.1 Оптимальное число значений

Разные источники сходятся на пороге ~10–20 значений как комфортной зоне: свыше ~20 расход токенов на «обдумывание» вариантов заметно растёт. Более production-ориентированный порог, учитывающий не точность, а компиляцию грамматики: держать enum-списки под ~50 значений — большие enum в сочетании с жёсткими `minItems`/`maxItems` и множеством межполевых ограничений могут вызывать таймауты компиляции у некоторых constrained-decoding движков (задокументировано в JSONSchemaBench: Outlines таймаутил на схемах, которые Guidance обрабатывал без проблем). Для наборов значений от полусотни и выше практика — заменять `enum` на свободный `string` с post-генерационной валидацией по полному справочнику.

### 3.2 Enum vs открытая генерация — контринтуитивный эффект

Принуждение к фиксированной схеме в среднем ухудшает reasoning-способности модели (см. раздел 8), но при этом **улучшает** классификационную точность именно потому, что enum обнуляет вероятность всех невалидных токенов. Отсюда практический вывод: где возможно превратить свободный текстовый ответ в enum — это единственный keyword, который одновременно повышает точность и снижает риск галлюцинации значения (хотя не снимает риск неверного *выбора* среди валидных значений).

### 3.3 Description каждого enum-значения

Прямой количественный бенчмарк на этот счёт не найден, но логика согласуется с общим правилом о field description (раздел 7): расшифровка значения (`"revise": "есть исправимые проблемы, нужна доработка"`) должна попадать в промпт автоматически через описание типа, а не полагаться на то, что модель угадает семантику из одного слова. Многословность описания подчиняется той же логике «dilution», что и общая длина description (раздел 7) — прямых данных о конкретном пороге нет.

### 3.4 Динамический allowed_set (список ID из базы данных)

Прямых бенчмарков по этому конкретному паттерну не найдено; вывод синтезирован из смежных данных:

- **Передавать нужно `id` + короткий человекочитаемый label, а не голый ID.** Паттерн статических/динамических enum с человекочитаемыми ключами и display-title подтверждён в LinkML: динамические enum задают допустимые значения через запрос к внешнему источнику на этапе валидации, но представление модели — читаемый ключ плюс заголовок, а не сырой код.
- **Токен-бюджет — реальное узкое место при сотнях/тысячах ID.** Каждый описанный тул/схема стоит порядка 550–1400 токенов только на структуру (имя, описание, JSON schema, описания полей, enum), и это накапливается: 40 инструментов легко съедают 55 000+ токенов ещё до первого сообщения пользователя. Для тысяч допустимых ID вывод: не пихать весь `allowed_set` в промпт/схему при каждом вызове целиком — сужать множество через retrieval перед вызовом (top-K релевантных кандидатов) и передавать в схему только их, либо использовать динамически регенерируемую грамматику на узкое подмножество для constrained ID decoding.

### 3.5 Известные баги enum-выбора

Специфичного bias'а типа recency/primacy именно в enum-полях, отдельного от общего field-order эффекта (раздел 1), в источниках не задокументировано как самостоятельное явление. Сама постановка enum-поля рано в схеме (до reasoning) воспроизводит ту же проблему форсированного раннего коммита, что и с любым другим полем.

## 4. Unions, anyOf, oneOf, discriminated unions

### 4.1 Провайдерская несовместимость

| Провайдер | Union-поддержка |
|---|---|
| OpenAI strict | `oneOf`/`allOf` не поддерживаются ни на root, ни во вложенных контекстах (например, внутри `array.items`); Pydantic по умолчанию генерирует `oneOf` для дискриминированных union — это вызывает ошибку валидации при отправке в OpenAI, нужна явная конвертация в `anyOf` |
| Gemini | использует только `anyOf`; `oneOf`/`allOf` молча игнорируются без ошибки |
| Anthropic (strict tool use) | рекурсия не поддерживается; числовые/строковые ограничения (`maxItems`, длины строк, числовые диапазоны) не enforced на уровне decoding и должны выражаться текстом в `description` вместо ключевых слов-ограничений |

**Практический вывод:** портируемое между всеми тремя провайдерами подмножество — это только `anyOf`, никогда `oneOf`. Для мультипровайдерной схемы `oneOf` нужно программно конвертировать в `anyOf` перед отправкой каждому провайдеру.

### 4.2 Discriminated union — правильный паттерн

Наивная схема с одним общим объектом, где все поля разных вариантов сделаны опциональными, провоцирует модель заполнить несовместимые поля одновременно (например, поля и для «email»-ветки, и для «phone»-ветки сразу). Tagged/discriminated union с явным полем-дискриминатором (`kind`/`type` + `const`-значение на каждом варианте) заставляет модель выбрать одну ветку целиком. Pydantic прямо рекомендует discriminated union как более производительный и предсказуемый вариант по сравнению с untagged union — он позволяет валидатору выбирать, против какого члена union проверять данные, вместо перебора всех вариантов.

**Готовые линтер-правила** (реализованы в независимом линтере schemago для генерации кода из JSON Schema, применимы и к LLM-контексту):
- ошибка — у union нет дискриминирующего поля;
- ошибка — варианты используют разные имена поля-дискриминатора;
- ошибка — вариант union не имеет `const`-значения для дискриминатора;
- ошибка — несколько вариантов имеют одинаковое `const`-значение дискриминатора;
- предупреждение — union из более чем 10 вариантов;
- предупреждение — union вложен более чем на 2 уровня;
- предупреждение — вариант union имеет `additionalProperties: true`.

### 4.3 Optional-поля: null vs отсутствие поля vs default

В strict mode у OpenAI настоящих опциональных полей не существует — всё, что концептуально опционально, должно быть типизировано как nullable union (`anyOf: [{type: string}, {type: null}]`) и всё равно перечислено в `required`. Поле присутствует в выводе всегда, но его значение может быть `null`.

Критично для дизайна: **required-поле без nullable-альтернативы заставляет модель галлюцинировать значение, когда данных в источнике нет.** Non-nullable `price: number` вынуждает модель придумать число, если в документе цены нет. Правило: любое поле, которое может отсутствовать во входных данных, обязано быть типизировано как nullable, а не просто задокументировано как «желательно заполнить».

## 5. Массивы и списки

### 5.1 minItems/maxItems — поддержка сильно разнится

OpenAI Structured Outputs исторически не поддерживал `minItems`/`maxItems` вовсе — это была прямая жалоба в сообществе разработчиков; Gemini документирует их поддержку. Даже там, где провайдер заявляет поддержку, инструментальные SDK (например, Vercel AI SDK) добавляют независимую пост-валидацию поверх провайдерского enforcement, потому что нельзя полагаться только на модель в соблюдении границ во время генерации — если провайдер не enforce-ит ограничение, SDK всё равно обязан отклонить финальный результат вне заданных границ.

**Правило:** для списков с ограничением на длину не полагаться на `minItems`/`maxItems` как единственный guardrail — всегда добавлять пост-генерационную валидацию длины в коде, независимо от того, что заявляет провайдер.

### 5.2 Пустой массив — известная патология

Под constrained decoding грамматика взвешивает пути, производящие объекты, тяжелее, чем путь к пустому массиву — из-за структуры автомата пустой результат статистически менее вероятен, чем результат хотя бы с одним элементом. Когда схема требует поле-массив, модель склонна фабриковать элементы вместо того, чтобы честно вернуть пустой список — в extraction-задачах это создаёт «призрачные» находки: пайплайн репортит «найдено 3 совпадения», когда правильный ответ — ноль.

**Митигация:** явно инструктировать в `description` поля, что пустой массив — валидный и ожидаемый результат при отсутствии совпадений; добавлять отдельное булево поле (`no_matches_found`), дублирующее ту же информацию не через массив — это устойчиво к описанной патологии.

### 5.3 Устойчивый порядок элементов

Прямых данных о стабильности сортировки массивов не найдено. Практическая рекомендация, вытекающая из общей field-order-логики (раздел 1): каждый элемент массива должен нести собственный `source_id`/`source_span`, чтобы порядок в выводе не был единственной привязкой к источнику — downstream-код сопоставляет элементы по этому ID, а не по позиции в массиве.

## 6. Рекурсивные и self-referential схемы

### 6.1 Движок constrained decoding имеет значение критически

FSM-based движки (Outlines) либо отклоняют рекурсивную схему целиком, либо разворачивают рекурсию до фиксированной глубины. Для рекурсивных структур (вложенные комментарии, древовидные данные, рекурсивные `$ref`) нужен CFG-based движок — XGrammar или llguidance.

- **XGrammar** конвертирует CFG/regex/JSON-шаблон в pushdown automaton (PDA), поддерживающий как рекурсивные, так и нерекурсивные схемы, с предвычислением большинства масок токенов для скорости.
- **llguidance** через Earley-парсер вычисляет маски токенов на лету на каждом шаге генерации, а не предвычисляет их заранее — это осмысленно именно для больших/бесконечных/рекурсивных схем, где допустимость следующего токена зависит от состояния стека, неизвестного заранее (например, от того, сколько скобок уже открыто на предыдущих шагах).

### 6.2 Практические лимиты глубины

Это инженерные лимиты рантайма, а не эмпирика деградации качества модели:
- типовой рантайм-лимит на разрешение цепочек `$ref` — порядка 64 итераций, с явной ошибкой валидации вместо переполнения стека при патологически глубоких/бесконечных входах;
- property-based тест-генераторы для рекурсивных данных обычно разворачивают ссылку лишь на 5 уровней, дальше терминируют явным `null` — этого достаточно для property-тестов, но не заменяет вручную написанные генераторы для действительно глубоких структур.

### 6.3 Паттерн ограничения рекурсии

Прямого готового паттерна в источниках не найдено, но логически он следует из ограничений грамматических движков и рантайм-лимитов выше: рекурсивная схема без явного стоп-сигнала для модели рискует либо не завершиться корректно, либо упереться в непредсказуемо обрезанную рантаймом глубину. Практический вывод: ограничивать глубину рекурсии явным полем `depth`/`level` в самом объекте и явно инструктировать модель прекращать рекурсию по достижении лимита.

**Линтер-правило:** циклическая `$ref`-схема без «продвигающегося» условия (structure, гарантирующая, что каждый уровень рекурсии потребляет часть входных данных) — ошибка компиляции. Продуктивные рекурсивные схемы (где каждый уровень действительно продвигает генерацию вперёд) продолжают приниматься.

## 7. Descriptions и prompt-в-схеме

### 7.1 Description — часть промпта, а не документация для разработчика

Field-level `description` напрямую влияет на то, как модель интерпретирует семантику поля. Классический пример: описание `score` как «0 = negative, 1 = positive» предотвращает использование моделью произвольной шкалы от 1 до 10, которую она могла бы угадать по умолчанию. Отсутствие description вынуждает модель угадывать семантику поля по одному лишь имени.

**Количественный кейс до/после:** нетипизированное строковое поле без ограничений (`origin: string` для кода аэропорта) привело к четырём подряд неудачным попыткам вызова тула — модель поочерёдно пробовала «NYC» (код метрополии, а не аэропорта), «New York», «NewYork», «NEWYORK». После добавления regex-паттерна (`^[A-Z]{3}$`), примеров значений («JFK», «LAX», «LHR») и явного description («3-буквенный IATA-код аэропорта») частота галлюцинации формата упала почти до нуля.

Description тула/схемы стоит трактовать буквально как промпт: начинать с действия («получить текущую погоду…» работает лучше, чем «инструмент погоды»), явно указывать триггер использования.

### 7.2 Признаки избыточности

Прямых бенчмарков «dilution от слишком длинного description» не найдено, но логика согласуется с эффектом enum-verbosity (раздел 3.1): каждый лишний токен description увеличивает и cognitive load схемы для модели, и суммарный контекстный бюджет — уже без учёта многословности description один тул стоит 550–1400 токенов. Практическое правило: description должен быть коротким, конкретным, содержать единицы измерения/формат/граничные случаи, но не дублировать то, что уже явно закодировано в `enum`/`pattern`/`format` этого же поля.

### 7.3 Имена полей как side-channel prompting

Это не анти-паттерн, а признанная техника. Само имя поля, вынужденно эмитируемое моделью в JSON, оседает в KV-cache и работает как встроенная инструкция: forced-ключ вида `step_by_step_reasoning` физически впрыскивает эту фразу в контекст непосредственно перед тем, как модель начинает писать значение этого поля. Это осознанно используется как приём для управления поведением модели через саму структуру схемы, а не только как побочный эффект.

### 7.4 Examples внутри схемы

Работающая техника, представленная как «Technique 1» в подходе BAML: few-shot-пример прямо в промпте с явным примером итоговой JSON-структуры («Например: если мы думаем шаг за шагом, мы видим, что… Следовательно, вывод: {...}»). Относится больше к prompt-инжинирингу вокруг схемы, чем к самой JSON Schema как формату — сам BAML использует не нативный constrained decoding, а собственный Schema-Aligned Parsing, что делает технику применимой к любой модели независимо от того, поддерживает ли она native structured output.

## 8. Strict mode: трейд-оффы детально

### 8.1 Систематизированные случаи деградации

| Источник | Находка |
|---|---|
| Lee et al. (цит. в обзоре failure modes) | на open-weight моделях принудительный формат structured output даёт падение точности на 3–9 процентных пунктов, особенно заметное на задачах математического reasoning |
| «Let Me Speak Freely?» (EMNLP 2024) | снижение качества reasoning под форматными ограничениями |
| «Structured Outputs Create False Confidence» (BAML) | деградация точности под constrained decoding создаёт ложную уверенность модели в собственном выводе |
| «The Format Tax» | измерение стоимости structured-output форматов в 3–9 п.п. точности |
| ExtractBench (2026) | 0% валидного вывода на схеме с 369 полями у всех фронтир-моделей |

### 8.2 Механизм — почему именно вредит

Два независимых объяснения из источников:

1. **Потеря scratchpad.** Каждый промежуточный сгенерированный токен — это дополнительный forward pass модели, ещё один шанс правильно маршрутизировать вычисление через нужные внутренние цепочки. Принуждение к немедленному коммиту на первом же поле схемы отбирает этот вычислительный бюджет: chain of thought — это не стилистическая особенность, а способ модели потратить больше forward pass'ов на задачу прежде, чем взять на себя обязательство по ответу.
2. **Токенизационный mismatch.** Грамматические ограничения constrained decoding действуют на уровне символов, а модель физически генерирует многосимвольные токены (BPE). Когда принудительная грамматика толкает модель по необычному пути токенизации, результат может оказаться неканонической последовательностью токенов, которую модель редко видела при обучении — это незаметно снижает качество генерации даже при формально валидном выводе.

### 8.3 Митигация: two-pass / thinking-then-structured

Устоявшийся паттерн: первый вызов — свободный reasoning без какого-либо формата (не платит format tax); второй вызов — constrained-генерация только финальной структуры на основе результата первого. Программа получает гарантированно валидный объект без потери качества reasoning модели. Это прямое развитие BAML Technique 2 (гибкое reasoning перед объектом), доведённое до архитектурного паттерна из двух отдельных LLM-вызовов вместо одного.

### 8.4 Когда strict безопасен, когда опасен

- **Относительно безопасен:** простая extraction с малым числом полей; задачи, где классификационная точность важнее качества reasoning (constrained decoding сам по себе может улучшать классификацию за счёт обнуления вероятности невалидных токенов, раздел 3.2).
- **Опасен:** сложный многошаговый reasoning и математика, где ответ форсируется рано в схеме (раздел 1); широкие схемы, близкие к провайдерским лимитам (раздел 2).

## 9. Антипаттерны при проектировании схем

| Антипаттерн | Симптом | Фикс |
|---|---|---|
| Answer-поле до reasoning-поля | Post-hoc рационализация; ответ логически не связан с приведённым обоснованием | Reasoning/evidence всегда первыми в схеме (раздел 1) |
| Deep nesting (4+ уровня) | Значения попадают не на тот уровень, вложенные объекты пропускаются целиком | Максимум 2–3 уровня, flatten (раздел 2) |
| Oversized schema (50+ полей) | Резкое падение доли валидного вывода вплоть до 0% на широких схемах | Разбить на несколько extractor-узлов (раздел 2.3) |
| Missing descriptions | Модель угадывает семантику по именам полей, неверная шкала/формат | Обязательный `description` с единицами/шкалой (раздел 7) |
| Required-поле без nullable там, где данные могут отсутствовать | Манифестированная галлюцинация значения на пустом месте | Nullable-union для потенциально отсутствующих данных (раздел 4.3) |
| `oneOf` в мультипровайдерной схеме | 400-ошибка у OpenAI во вложенном контексте, молчаливо игнорируется у Gemini | Использовать только `anyOf` + поле-дискриминатор (раздел 4) |
| `additionalProperties: true` на write/side-effect тулах | Модель может подсунуть лишние поля без единой ошибки валидации | `additionalProperties: false` обязателен на всех side-effect тулах |
| Vague untyped string-поле без pattern/format/enum | Модель галлюцинирует формат методом проб и ошибок | Явный `pattern`/`format`/`enum` + примеры значений (раздел 7) |
| Confidence-поле, застывшее на одном значении | Ложная уверенность модели — «плоская» дистрибуция (например, 0.98 на всех выводах подряд) как сигнал сломанного пайплайна | Отдельный статистический мониторинг распределений полей (раздел 10) |
| Схема механически скопирована из OpenAPI со стилем `oneOf` без `const`-дискриминатора | Провайдерская несовместимость, неоднозначность для линтера/движка | Переписывать под LLM-специфичное подмножество, не копировать бездумно |
| Пустой массив трактуется как «неудобный» результат | Модель фабрикует несуществующие элементы вместо честного `[]` | Явный `description` + дополнительное булево поле (раздел 5.2) |
| Field-name mismatch (schema-valid, но не туда) | Например, `user_email` вместо ожидаемого `email` — семантически неверно, но валидация проходит | Более узкие/специфичные имена полей + downstream контракт-тесты |
| Излишние regex/format-ограничения без реальной нужды | Моделям сложно точно интерпретировать сложные keyword'ы, валидация усложняется без прироста надёжности | Простейшее представление типов там, где точный regex не критичен |

## 10. Тестирование и валидация схем до продакшена

### 10.1 Раздельные метрики — не одна общая «валидность»

Устоявшаяся практика (ExtractBench, The Structured Output Benchmark) — разделять **schema compliance** (синтаксическая валидность по схеме) и **value/field-level accuracy** (семантическая правильность содержимого каждого поля). Модели регулярно достигают почти идеальной schema compliance, при этом реальная точность значений (Value Accuracy) заметно ниже — например, 83% на тексте против почти 100% валидности по схеме. Это разные оси измерения, и линтер/eval-набор должен покрывать обе, а не только факт парсимости JSON.

### 10.2 Консистентность при повторных генерациях

STED-фреймворк (Semantic Tree Edit Distance) предлагает измерять консистентность между повторными прогонами одной и той же схемы через семантическое, а не буквальное сравнение JSON-деревьев — и на бенчмарке шести LLM показал, что модели радикально различаются по устойчивости даже при высокой температуре: одни модели сохраняют почти идеальную структурную надёжность даже при T=0.9, другие деградируют существенно и требуют тщательной настройки параметров.

Практическое применение: прогнать схему N раз (например, N=10–20) на одном фиксированном входе при рабочей температуре, измерить дисперсию результатов. Высокая дисперсия — диагностический сигнал о конкретной модели/схеме, а не повод сразу переписывать саму схему.

### 10.3 Чек-лист правил линтера (машинно-проверяемые правила для компилятора)

**Ошибки (блокируют компиляцию):**
1. Union без явного поля-дискриминатора.
2. Разные имена поля-дискриминатора между вариантами одного union.
3. Вариант union без `const`-значения дискриминатора.
4. Дублирующееся `const`-значение дискриминатора между вариантами одного union.
5. Циклическая `$ref`-схема без продвигающегося условия (не сходится).
6. Reasoning/evidence-поле объявлено ПОСЛЕ answer/label/decision-поля в том же объекте.
7. `oneOf` где-либо в схеме, предназначенной для мультипровайдерного использования (требуется `anyOf` + discriminator).
8. `additionalProperties: true` на объекте, связанном с write/side-effect туром.

**Предупреждения:**
9. Union из более чем 10 вариантов.
10. Вложенность union глубже 2 уровней.
11. `additionalProperties: true` на отдельном варианте union.
12. Общая глубина вложенности схемы больше 3.
13. Число полей схемы больше 20 (совет) / больше 100 (жёсткий провайдерский потолок у OpenAI).
14. `enum` с числом значений больше 20 (рекомендация перейти на retrieval+validation) / больше 50 (риск таймаута компиляции грамматики).
15. Поле без `description`.
16. `required`-поле без явной пометки «может отсутствовать в источнике» там, где источник заведомо неполон — риск forced hallucination.
17. `pattern`/`minLength`/`maxLength`/`minimum`/`maximum` заданы для Anthropic-таргетированной схемы (не enforced нативно — только эмулируется через текст в description).
18. `minItems`/`maxItems` заданы для OpenAI-таргетированной схемы без независимой пост-генерационной проверки в коде.
19. Массив без явного `description`, разрешающего пустой результат, там, где ноль совпадений — валидный исход.
20. Целевой провайдер — Gemini, но порядок `required` не совпадает с желаемым порядком эмиссии полей.

### 10.4 Как эмпирически тестировать схему до прода

1. Golden-набор входов, покрывающий boundary-случаи каждого поля (типовые/edge/adversarial/входы без данных для required-в-теории-но-nullable-на-практике полей).
2. Раздельно измерять: **schema-adherence rate** (доля синтаксически валидных ответов), **field-level accuracy** (доля семантически верных значений на элемент/поле), **consistency-score** через N повторов при рабочей температуре (раздел 10.2).
3. Мониторинг распределений в проде: значений enum, числовых диапазонов, длин строк, частоты присутствия полей. Сдвиг распределения сигнализирует либо новый тип входа, для которого схема не проектировалась, либо тихую деградацию качества модели после незаметного апдейта у провайдера — формат вывода при этом остаётся валидным, а значения дрейфуют.

## Консенсус vs развивающиеся области

**Устоявшийся консенсус:** reasoning-до-answer работает и объясняется механически (несколько независимых источников, включая практику мейнтейнера BAML); `additionalProperties: false` обязателен почти везде, кроме случаев, требующих явной гибкости; глубокая вложенность (4+ уровня) и широкие схемы (50+ полей) систематически ухудшают качество; discriminated union предсказуемее и производительнее naive-optional-объекта; strict mode платит измеримый «format tax» на reasoning-тяжёлых задачах.

**Развивающиеся/неполные данные:**
- Количественных данных по «description dilution» (когда длина description начинает вредить) в чистом виде не найдено — вывод получен по аналогии с эффектом enum-verbosity, не прямое измерение.
- Специфика recency/primacy bias именно в enum-выборе, отдельного от общего field-order эффекта, не задокументирована как самостоятельное явление.
- Паттерн передачи больших динамических `allowed_set` (id+label vs голый id) синтезирован по смежным данным (LinkML, token-budget-практика); прямого A/B-бенчмарка именно этого сравнения не найдено.
- Gemini `propertyOrdering`-через-порядок-`required` — задокументированное продакшн-измерение одного независимого практика (сентябрь 2026), не подтверждено официальной документацией Google и не воспроизведено независимо другими источниками.
