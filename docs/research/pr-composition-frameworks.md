## 1. Priompt — «React для промтов» в чистом виде

Что это: JSX-дерево, которое рендерится не в DOM, а в `ChatCompletionMessage[]`. Ключевая идея — не композиция ради
переиспользования, а **вытеснение по бюджету**: каждый кусок текста помечен приоритетом, а рендерер бинарным поиском ищет
минимальный порог `p_opt`, при котором `|Prompt(p ≥ p_opt)| ≤ T`.

| Примитив | Что делает | Наша оценка |
|---|---|---|
| `<scope p={n}>` / `prel={-n}` | абсолютный / относительный (от родителя) приоритет поддерева | **нужно**, но не как приоритет — как **слот с политикой усечения** |
| `<first>` | берёт первого ребёнка, который влез (fallback-цепочка: полный текст → краткий → заглушка) | **нужно**, статически выразимо: `degradations: [full, short, omit]` |
| `<isolate tokenLimit={n}>` | поддерево рендерится в своём бюджете, не влияя на глобальный порог | **нужно** — это единица кэша: стабильный префикс не двигается от роста истории |
| `<empty tokens={n}>` | резерв места под генерацию (`max_tokens`) | нужно, но у нас это поле бюджета в IR, а не узел |
| `<capture>` | парсер вывода прямо в дереве промта | **лишнее** — у нас тип результата даёт формат (08-prompts, 05-type-system) |
| `<config>` | параметры модели из дерева | частично: у нас это уровень шага/IR, а не промта |
| `<br/>` | форс границы токенизации | лишнее |

Ограничения, названные авторами: «примерно 10 000 scope» на дерево; бинарный поиск **не гарантирует** идеальный порог при
вложенных `<first>`; **встроенного кэширования нет**, и злоупотребление приоритетами само по себе ломает кэш-префикс
(«hard-to-cache prompts, which may increase your cost or latency»). Прод-статус: MIT, живой репозиторий Anysphere;
UNVERIFIED: прямого утверждения «Cursor рендерит этим прод-промты» в README нет — есть только авторство Anysphere.

Что берём / что нет с учётом статической оценки размера (08-prompts, gpt-tokenizer):

| Механизм Priompt | Берём? | Почему |
|---|---|---|
| JSX как синтаксис | **нет** | ADR-0018: авторинг TS → IR. JSX даёт дерево, но узлы-функции непрозрачны для синтеза; нам нужен сериализуемый узел, а не замыкание |
| дерево слотов с детьми | **да** | прямое соответствие слотам 08-prompts; ребёнок-слот = вложенный шаблон с собственным `spec_hash` |
| `isolate` как граница кэша | **да** | ложится на кэш-точки 08-prompts: изолят = сегмент с собственным префиксом, меняется независимо |
| приоритеты + рантайм-вытеснение | **частично** | у нас размер оценивается статически; вытеснение нужно только там, где размер зависит от данных (история, RAG-чанки) |
| бинарный поиск порога на каждый вызов | **нет** | недетерминированно относительно `behavior_hash`: один и тот же промт даёт разный текст при разном объёме данных |
| `capture` / парсинг в дереве | **нет** | форму задаёт тип (R-42, ADR-0019) |

Вывод по Priompt: берём **топологию** (дерево, слоты, изоляты, деградации `<first>`), не берём **динамику**
(рантайм-бинпоиск). Наша замена: у каждого слота с данными переменного размера — объявленный `budget` и упорядоченный
список деградаций; выбор деградации детерминирован и логируется в трассу, а не ищется поиском.

## 2. Genkit dotprompt — «промт знает про свою модель»

Формат: файл `.prompt` = YAML-frontmatter + Handlebars-тело. Frontmatter несёт `model`, `config` (temperature, topK, topP,
`maxOutputTokens`, `stopSequences`, `version`), `input.schema` + `input.default`, `output.format` (`json`/`text`) +
`output.schema`, `tools: [...]`, `name`/`variant`, `metadata`/`ext`. Схемы пишутся на **Picoschema** — компактный YAML,
компилирующийся в JSON Schema. Тело — мультимесседж через `{{role "system"}}` / `{{role "user"}}`, мультимодальность через
`{{media url=...}}`. Партиалы: файл `_personality.prompt`, вызов `{{>personality style=style}}` с именованными
аргументами. Варианты: `myPrompt.gemini25pro.prompt`, грузится как `ai.prompt('myPrompt', { variant: 'gemini25pro' })`,
и вариант **попадает в трассу** — сравнение вариантов встроено. Рантайм-конфиг перекрывает файловый.

Что важно для нас:

| Механизм | Оценка |
|---|---|
| `model` + `config` в самом промте | идея верна, но у нас связь обратная: **шаг выбирает модель, промт объявляет требования к модели** (capability requirements), иначе промт нельзя переиспользовать на двух провайдерах |
| `variant` по имени файла | **это и есть адаптация под модель у Google** — плоский namespace, без наследования: вариант дублирует весь промт. Нам не подходит: нужна дельта, а не копия |
| партиалы с именованными аргументами | **берём** — прямой аналог наших слотов; в liquidjs это `{% render 'x', arg: v %}` (изолирует scope, в отличие от `include`) |
| `output.schema` → блок формата | совпадает с нашей генерацией блока формата из типа (08-prompts) |
| вариант в трассе | **берём** — вариант/локаль/профиль модели должны быть измерениями в трассе, а не растворяться в тексте |

Вывод: dotprompt даёт правильный *состав метаданных* промта, но неправильный *механизм вариативности* (копия файла вместо
дельты). Мультиязычность через варианты у них тоже вылилась бы в N копий файла.

## 3. BAML — пер-клиентские различия и тесты

BAML — отдельный DSL (v1 в публичной бете, `@boundaryml/baml` 0.226.2, MIT), компилируется в типизированные клиенты для
TS/Python. Разделение: `function` (сигнатура + Jinja-промт + возвращаемый тип) отдельно от `client<llm>` (провайдер и его
опции). Стратегии на уровне клиента: `fallback` (упорядоченный список клиентов, следующий берётся при ошибке),
round-robin, `retry_policy`, вложенные fallback-цепочки. Промт не знает, какой клиент его исполнит.

Адаптация под модель: **явной нет**. Различия провайдеров BAML прячет в своём парсере (SAP — schema-aligned parsing):
вместо того чтобы подстраивать промт под structured-output конкретного провайдера, он просит текст и чинит его парсером.
Это противоположная нашей ставка: мы опираемся на нативный structured output и профили схем (ADR-0004), BAML — на
устойчивый парсер поверх «сырого» вывода.

Тесты: блок `test Name { functions [F] args { ... } }` прямо в `.baml`-файле, многострочные литералы `#"..."#`,
проверки `@@assert` / `@@check` на Jinja-выражениях, в контексте доступна `_` с полями `result`, `checks`, `latency_ms`;
запуск через `baml test` (фильтры, параллельность) и из VSCode-расширения. **Берём идею**: тест-кейс промта живёт рядом с
промтом и является частью артефакта, а не отдельной папкой; ассерты — выражения над типизированным результатом.

## 4. LangChain JS — что живо, что мертво

| Механизм | Статус | Комментарий |
|---|---|---|
| `ChatPromptTemplate.fromMessages([...])` | жив (`@langchain/core` 1.2.11) | канонический вход |
| `ChatPromptTemplate.fromPromptMessages` | **удалён в v1** | миграция на `fromMessages` |
| `new MessagesPlaceholder("chat_history")` | жив, но вытесняется кортежем `["placeholder", "{chat_history}"]` | placeholder = дырка под `BaseMessage[]` |
| `.partial({ ... })` | жив | частичное применение: часть переменных зафиксирована, шаблон остаётся шаблоном |
| `FewShotChatMessagePromptTemplate` + `exampleSelector` | жив | few-shot как отдельный примитив с рантайм-выбором примеров |
| композиция через `+` (`PipelinePromptTemplate`) | помечено legacy | конкатенация шаблонов оказалась слабой абстракцией |

Ценные идеи ровно две: **partial application шаблона** (промт остаётся промтом после частичной подстановки — у нас это
даёт каррирование при наследовании) и **placeholder под список сообщений** (единственное честное место, где размер
неизвестен статически). Остальное — рантайм-строки без типов, для нас регресс относительно ADR-0018.

## 5. Langfuse prompt management — что переиспользуем

Реестр: каждый промт — цепочка версий (инкрементальный integer) + перемещаемые **labels** (`production`, `latest`,
произвольные). SDK v4 — `@langfuse/core` / `@langfuse/client` 5.11.1 (MIT, 2026-09-09); legacy `langfuse` 3.38.20.
Композиция: внутри текста промта ставится тег `@@@langfusePrompt:name=X|version=1@@@` либо
`@@@langfusePrompt:name=X|label=production@@@`, SDK разворачивает ссылку при компиляции; в UI есть кнопка «Add prompt
reference». UNVERIFIED: лимит глубины вложения и защита от циклов в доке не указаны. На версии промта висит произвольный
`config` (модель, температура, что угодно) — тот же приём «промт знает про модель», но нетипизированный. Связь с
трассами: сгенерации линкуются к конкретной версии промта, по ней считаются метрики.

Что берём: **labels как способ раскатки** (`production` двигается независимо от кода — это единственный источник
вариативности, который не обязан проходить через сборку) и **линк версии промта в трассу**. Что не берём: композицию
строковыми тегами — это динамическая ссылка, которую нельзя проверить при сборке; у нас ссылка на вложенный промт должна
быть типизированной и входить в `spec_hash` родителя. Langfuse у нас — витрина и реестр раскатки, не компилятор.

## Вывод для нас

Ни один из разобранных не решает задачу заказчика целиком: Priompt даёт дерево без знания о модели, dotprompt — знание о
модели без дельт, BAML — клиенты без адаптации промта, Langfuse — версии без статики, POML — разделение формы и контента
без типов. Собираем из кусков.

**Модель композиции: не JSX, а «шаблон + стилевой слой + профиль».** Три ортогональные оси, ни одна не смешивается с
двумя другими:

| Ось | Что варьирует | Где живёт | Статично? |
|---|---|---|---|
| **Контент** (`lang`, R-T11) | язык и формулировки | набор строковых ресурсов на одну структуру шаблона | да: структура и слоты общие, меняются только литералы; `spec_hash` включает id ресурса |
| **Форма** (идея POML) | как отрендерить структуру под провайдера: prefill и форс тула для Anthropic, слово «JSON» в сообщениях для `json_object` OpenAI, обязательная фраза Qwen | **рендерер**, выбираемый по профилю модели (11-providers + ADR-0004) | да: конечный набор профилей, выбор — по capability probe, а не по данным |
| **Данные** | значения слотов | контекст рендера | да по форме, нет по размеру |

Правило-инвариант, продолжающее R-42 (ADR-0019): **ось формы не имеет доступа к данным, ось контента не имеет доступа к
профилю модели.** Иначе мультиязычность и адаптация под модель перемножаются в N×M копий — ровно та беда, к которой ведут
`variant`-файлы dotprompt.

Что из «React-модели» выразимо статически, а что требует рантайма:

| Механизм | Статически | Механика у нас |
|---|---|---|
| **наследование** | **да** | базовый шаблон + именованные слоты; потомок переопределяет подмножество слотов. Проверяется при синтезе TS → IR: неизвестное имя слота — ошибка компиляции, как R-T1 для путей. Это `partial application` из LangChain, а не строковая конкатенация `+` |
| **слоты-дети** | **да** | ребёнок — отдельный типизированный шаблон со своим `spec_hash`; родитель хранит ссылку, хеш ребёнка входит в хеш родителя (04-ir-schema §4.3). Нативно ложится на `IncludeTag`/`{% render %}` и уже существующий учёт версий фрагментов (08-prompts §2.1). В отличие от `@@@langfusePrompt@@@` ссылка разрешается при сборке, а не при вызове |
| **условная сборка по профилю/языку** | **да** | выбор ветки — функция от `(model_profile, lang)`, оба известны при сборке релиза: раскрываем все комбинации и считаем токены для каждой; в трассу пишем, какая комбинация ушла (как `variant` в трассах dotprompt) |
| **условная сборка по данным** | **да, уже есть** | `{% if %}`/`{% case %}` с ограничениями R-T3/R-T4; оценка размера — верхняя граница по всем веткам |
| **приоритеты и вытеснение** | **нет** | нужен рантайм, но только для слотов с неизвестным статически размером: история диалога (`MessagesPlaceholder` LangChain) и наборы чанков. Для них объявляем `budget` + упорядоченный список деградаций (`<first>` Priompt); выбор детерминирован по порядку, без бинарного поиска — иначе `behavior_hash` перестаёт описывать поведение |
| **изоляция бюджета** (`isolate`) | **да, как разметка** | сегмент с собственным бюджетом = граница кэш-точки (08-prompts §5.2): рост переменного сегмента не сдвигает стабильный префикс |
| **`capture` / парсинг в дереве** | — | **не берём**: форму даёт тип (R-42) |

Проектируем конкретно: (1) `PromptTemplate` как типизированная функция с именованными **слотами** и **деградациями**
вместо приоритетов; (2) **профиль рендера** — отдельный объект на провайдера, единственное место, где живут фразы Qwen,
слово «JSON» для OpenAI и prefill/`tool_choice` Anthropic; (3) **тест-кейсы рядом с промтом** с ассертами над
типизированным результатом (BAML), гоняются по всем профилям; (4) **Langfuse — реестр раскатки и трасса**, лейбл
`production` двигает версию без пересборки, но сама композиция уже разрешена компилятором.
