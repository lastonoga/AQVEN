# Срез 4: версионность внутри базы — честная альтернатива git-файлам

> Вопрос среза: если не класть спеки в git-файлы, какой механизм версионирования внутри БД даёт диффы, откаты, ветки и запросы по содержимому — и во что это обходится?

## 1. Dolt / DoltgreSQL как основное хранилище

Dolt — это не «Postgres с ветками», это отдельный движок (MySQL-совместимый) с prolly-tree
хранилищем, где коммит, ветка, мерж и построчный дифф — операции SQL (`dolt_commit()`,
`dolt_diff_<table>`, `dolt_merge()`). За 2026 год он перестал быть игрушкой: 2.0 обгоняет MySQL
на sysbench, GC включён по умолчанию, archive-сжатие срезает 30–50% диска
([Dolt 2.0](https://www.dolthub.com/blog/2026-05-11-dolt-2-dot-0/)). Лицензия Apache-2.0 — рисков нет.

Почему он нам всё равно не подходит как **основное** хранилище:

| Препятствие | Детали |
|---|---|
| Диалект | Dolt = MySQL. Наша модель данных построена на PG: `jsonb` + GIN `jsonb_path_ops`, `lz4` compression на колонках, `DEFERRABLE INITIALLY DEFERRED` FK, партиционирование прогонов (16-data-model). Переписывать всё под MySQL — не «сменить драйвер». |
| Doltgres | снимает диалект, но платим 2.7x по скорости (запись 3.4x) и «ограниченной поддержкой расширений» ([doltgresql](https://github.com/dolthub/doltgresql)). Расширения нам нужны: `pgcrypto`, `pg_trgm`, вектора для семантического поиска. |
| Гранулярность версионирования | Dolt версионирует **всю базу целиком**: один коммит = снимок всех таблиц. У нас версионируется одна сущность (спека), а прогоны/трассы/кассеты должны быть **вне** версионирования. Ветка в Dolt утащит с собой и таблицу прогонов. |
| Мультитенантность | ветка — глобальный объект БД, не строка. 500 проектов × N черновиков = тысячи веток в одном репо; это не тот масштаб, на который рассчитан branch namespace. UNVERIFIED: официального лимита на число веток не публикуют, но модель «база-репозиторий» это предполагает. |
| Транзакции с невersioned данными | коммит захватывает всё состояние; развести «спека версионируется, прогон нет» внутри одной БД нельзя без разделения на две БД — и тогда теряется транзакция между ними. |

**Где Dolt был бы уместен** — публичный реестр компонентов с форками и PR-ами как отдельный сервис. Не MVP.

## 2. Версионность штатным PostgreSQL

Главный факт: **PG 18 не даёт system-versioning**. То, что добавили, — это application-time:
`PRIMARY KEY (..., period WITHOUT OVERLAPS)` и `FOREIGN KEY ... PERIOD`
([Aiven](https://aiven.io/blog/exploring-how-postgresql-18-conquered-time-with-temporal-constraints)).
Это про «бронь не пересекается с бронью», а не про «покажи строку, какой она была вчера».
`FOR SYSTEM_TIME AS OF` и `FOR PORTION OF` в ядре нет, конкретных планов тоже
([Tom Lane, pgsql-hackers](https://www.postgresql.org/message-id/842239.1732389267%40sss.pgh.pa.us)).

Расширения закрывают это триггерами, но оба в режиме поддержки, не развития:
`temporal_tables` (arkhipov) — «новая разработка остановлена несколько лет назад»
([PGXN](https://pgxn.org/dist/temporal_tables/)); `periods` — «очень мало активности»
([PG wiki](https://wiki.postgresql.org/wiki/Temporal_Extensions)). Ставить в фундамент MVP
расширение, которое может не собраться под PG 19, — плохой размен ради того, что мы и так пишем.

Что важнее: **system-versioning решает не нашу задачу**. Он даёт «строка во времени» —
последнее значение на момент T. Нам нужны именованные версии с автором, evidence, diagnostics,
lineage форка и явной публикацией (`spec_versions.version`, `parent_id`, `content_hash` —
16-data-model §2.2). Это уже не история строки, а доменная сущность. Темпоральная таблица
над `spec_versions` дала бы историю **истории** — лишний слой.

Практический вывод: `app.spec_versions` уже **и есть** append-only темпоральная таблица,
только с доменными полями вместо `sys_period`, с `REVOKE UPDATE, DELETE` вместо триггера
(16-data-model §1, «Неизменяемость»). Стоимость нулевая сверх уже написанного.

## 3. Event sourcing: op-log как единственный источник истины

Соблазн реальный: op-log у нас уже есть (ADR-0009), остаётся объявить его единственной правдой,
а `spec_versions.ir` — проекцией, материализуемой свёрткой.

| Даёт | Платим |
|---|---|
| Полная история намерений, а не только результатов | чтение спеки = свёртка N операций; нужен снапшот-слой, то есть та же таблица версий, что и сейчас, плюс логика инвалидации |
| Time travel в любую точку, не только в опубликованные версии | **миграция схемы событий**: upcasting/downcasting/stream transformation ([event-driven.io](https://event-driven.io/en/simple_events_versioning_patterns/)) — старые `add_node` придётся уметь читать вечно |
| Аудит и «кто что сделал» бесплатно | нельзя просто поправить кривое событие: события неизменяемы, исправление — это компенсирующее событие |
| Проекции под разные задачи из одного лога | запрос «все воркфлоу с узлом типа X» невозможен по логу — нужна та же проекция с GIN-индексом |

Автор темы формулирует прямо: «лучший подход — вообще не нуждаться в версионировании событий»
([event-driven.io](https://event-driven.io/en/simple_events_versioning_patterns/)). У нас схема
операций — это MCP-контракт (`Op` из ADR-0009), он меняется с каждым новым типом узла. То есть мы
гарантированно попадаем в самый дорогой сценарий.

Библиотеки живы, но не спасают от этой цены:

| Пакет | Версия | Лицензия | Изменён | Замечание |
|---|---|---|---|---|
| `@event-driven-io/emmett` | 0.42.4 | (не объявлена в npm-метаданных) | 2026-09-11 | активный, PG-бэкенд; **0.x** — API не стабилизирован |
| `@castore/core` | 2.4.2 | MIT | 2025-04-18 | ~1.5 года без релиза |

Главное возражение: в нашем домене **источник истины по природе — состояние графа, а не поток
событий**. ADR-0009 уже принял server-authoritative op-log именно потому, что операции надо
**валидировать против текущего состояния** и отклонять (биндинг на удалённый узел, цикл в DAG).
Event sourcing в чистом виде это не отменяет, но и ничего не добавляет: валидация всё равно
требует материализованного состояния в транзакции. Мы получим ES-издержки без ES-выгод.

## 4. Content-addressed хранилище — сколько нам осталось до «своего git»

Считаем честно по тому, что уже спроектировано.

| Элемент git | Что у нас есть | Источник |
|---|---|---|
| blob | канонический JSON версии спеки + `sha256-...` с доменной сепарацией (`hashOf('aqven/flow-spec/v1', …)`) | 04-ir-schema §4.2–4.3 |
| tree | `manifest.files[]` с хешом каждого файла и **Merkle-корнем** бандла | 18-export §manifest.json |
| commit | `spec_versions` (`content_hash`, `author`, `created_at`, `parent_id`) | 16-data-model §2.2 |
| parent / lineage | `parent_id uuid REFERENCES spec_versions(id)` | там же |
| dedupe по содержимому | `spec_versions_hash_idx` (hash-индекс по `content_hash`), большие тела в `blobs/<sha256>.bin` | 16-data-model, 18-export §8 |
| diff | `jsondiffpatch` 0.7.6 с `objectHash` по `id` + семантическая классификация COSMETIC/BEHAVIORAL/STRUCTURAL | 04-ir-schema §7 |
| checkout / revert | `flow_revert` через op-log | ADR-0009 |
| verify | пересчёт `specHash` и `merkleRoot` при импорте; round-trip `sha256(bundleA) === sha256(bundleB)` | 18-export §2, §8 |
| **чего нет** | ветки как first-class объект, трёхсторонний мерж, GC недостижимых объектов, packfile | — |

То есть «своего git» мы написали не наполовину, а **процентов на восемьдесят — и написали ту часть,
которой у git нет**: доменный дифф (git не знает, что переименование узла косметично, а смена
модели — поведенческая правка), валидация инвариантов при записи, транзакция со связанными таблицами.
Не написана ровно та часть, которая в git есть даром: ветки и мерж. И именно она в MVP не нужна —
ADR-0009 зафиксировал линейную историю ревизий сознательно, потому что одновременных редакторов
единицы.

Вывод по пункту: дописывать «свой git» дальше **не надо**. Надо признать, что `spec_versions` +
`content_hash` + Merkle бандла — это уже content-addressed store, и не изобретать поверх него
ветки, пока не появился спрос.

## 5. Сравнение по нашим требованиям

Оценки: ++ даром / + есть, дописать немного / ± возможно, дорого / − не даёт.

| Требование | git-файлы | Dolt/Doltgres | Event sourcing | JSONB + op-log (текущее) |
|---|---|---|---|---|
| Дифф **семантический** (узлы, порты, класс правки) | − текстовый дифф YAML | − построчный дифф таблицы | ± из событий, но нужен свой | ++ `jsondiffpatch` + классификация |
| Откат к версии | ++ | ++ | + свёртка до N | + `flow_revert`, уже спроектирован |
| Ветки | ++ | ++ | ± | − нет (и не нужны в MVP) |
| Трёхсторонний мерж | + (текстовый, ломает YAML-граф) | + (по строкам) | − | − |
| Запрос «все флоу с узлом типа X» | − grep по файлам | + SQL, но без JSONB-индексов PG | − нужна проекция | ++ GIN `jsonb_path_ops` |
| Транзакция со связанными таблицами (runs, releases) | − две системы, нет атомарности | ± одна БД, но коммит захватывает всё | + | ++ одна транзакция PG |
| Мультитенантность | ± репо на тенанта, права вне БД | − ветка ≠ строка, RLS нет | + | ++ `tenant_id` + RLS |
| Агент правит 50 раз в минуту | − коммит на правку, мусорная история | ± коммит = write-amplification | ++ | ++ op-log, версия только при публикации |
| Оптимистическая блокировка + отклонение невалидной правки | − | ± | + | ++ `base_rev` + инварианты в транзакции (ADR-0009) |
| Операционная стоимость | + (но нужен git-сервер, auth, квоты) | − новый движок в проде | ± | ++ уже есть Postgres |

## Вывод для нас

**Берём:**
1. Ничего не меняем в решении: JSONB + op-log + `spec_versions` остаётся источником истины.
   Ни одна из четырёх альтернатив не выигрывает по совокупности, а три из них проигрывают
   по ключевому для нас пункту — семантический дифф и валидация инвариантов при записи.
2. Переформулируем аргумент в DECISIONS. Сейчас звучит как «мы пишем свой git» (слабо).
   Правильно: «мы пишем **доменный** слой версий поверх content-addressed хранилища; git-часть
   (хеши, Merkle, lineage) у нас уже есть и стоит дёшево, а недостающая часть git (ветки, мерж)
   в MVP не требуется по ADR-0009».
3. Из PG 18 берём `WITHOUT OVERLAPS` там, где это про application-time — например, окна
   действия env-оверлеев или расписаний. Это дешёвое ядровое ограничение, не расширение.
4. Из event sourcing берём один приём: **upcasting** для схемы операций op-лога. Op-контракт
   будет меняться, а op-лог нужен для `flow_revert` и воспроизведения истории — значит версия
   схемы операции должна быть записана в строке `op_log` с первого дня.

**Не берём:**
- **Dolt/Doltgres** — диалект MySQL или 2.7x штраф + ограниченные расширения; версионирование
  всей базы вместо одной сущности; ветка как глобальный объект несовместима с мультитенантностью.
- **temporal_tables / periods** — оба в режиме поддержки, оба решают «строка во времени»,
  а не «именованная версия с evidence». `spec_versions` уже покрывает нашу задачу.
- **Event sourcing как единственный источник истины** — платим миграцией схемы событий и
  снапшотами, получаем ровно то, что уже даёт пара `op_log` + `spec_versions`.
- **Ветки и мерж внутри БД** — не строим, пока нет спроса. Если спрос появится, дешёвый путь —
  не мерж, а `parent_id` + форк проекта (он уже в модели).

**Граница**: она уже проведена бандлом с round-trip байт-в-байт (18-export §8). Бандл можно
положить в git клиента — но как **выход**, а не как хранилище.
