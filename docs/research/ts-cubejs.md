> Вопрос среза: правда ли «код строит граф, а не исполняет его» — и что заставляет Cube держать YAML рядом с JS?

## 1. Гипотеза «код строит граф» подтверждается — но у Cube это JS, а не TS

Гипотеза верна буквально: файл модели не исполняет запросы, он вызывает глобаль `cube(name, {...})`,
которая **push'ит объект в массив**. Дальше массив отдают компиляторам. Никакой ты-пишешь-раннер тут нет.

```js
cube: (name, cube) => {
  const file = ctxFileStorage.getStore();
  return !cube ? this.cubeFactory({ ...name, fileName: file.fileName })
               : cubes.push({ ...cube, name, fileName: file.fileName });
}
```

Но два уточнения ломают наивный перенос на TypeScript:

| Ожидание | Реальность Cube |
|---|---|
| «Cube — пример TS-авторинга» | TS у модели нет вообще: только `.js`, `.yml`, `.jinja`. `cube.ts` в конфиге **удалили** 2026-09-04 ([PR #11763](https://github.com/cube-js/cube/pull/11763)) |
| «JS и YAML — равноправные варианты» | YAML компилируется **в JS**, а не наоборот. JS — низ стека, YAML — фасад |
| «JS-файл это модуль» | Это скрипт в `vm`-контексте: `cube`, `view`, `asyncModule`, `require`, `COMPILE_CONTEXT` — инжектированные глобали, не импорты |
| «Выбор — вкусовщина» | Официально: «default to YAML», JS — только за динамикой |

## 2. Конвейер: четыре прохода по одному и тому же исходнику

| Фаза | `stage` | Что компилируется | Зачем |
|---|---|---|---|
| 1 | 0 | `cubeNameCompilers` | собрать имена кубов |
| 2 | 1 | `preTranspileCubeCompilers` + `viewCompilationGate` | символы кубов, решить, нужны ли представления |
| 3 | 2 | `viewCompilers` | развернуть представления (условно) |
| 4 | 3 | `cubeCompilers`, `contextCompilers`, `viewGroupCompilers`, `metaCompilers` | финальная модель и мета |

Каждая фаза: `cleanup()` → **заново транспилировать все файлы** → **заново исполнить их в vm** → скормить
компиляторам. Причина — `CubePropContextTranspiler` переписывает `sql: () => ...` в функции с
dependency injection по именам других кубов, а словарь имён известен только из предыдущей фазы.
Это цена того, что ссылки живут внутри кода, а не в данных: чтобы узнать рёбра графа, приходится
исполнить граф — и не один раз.

Артефакт компиляции — **не файл**, а объект в памяти (`cubeEvaluator` + мета). Кэшируются вход и
промежутки, а не выход: `LRUCache<string, vm.Script>` на скомпилированные скрипты, per-file кэш рендера
Jinja с инвалидацией по md5-fingerprint всех макрофайлов сразу («over-invalidating … which is rare»,
комментарий CUB-2357 в исходнике). Транспиляция вынесена в `workerpool` и в Rust (`@cubejs-backend/native`,
SWC вместо Babel, ×10-13).

## 3. Динамика и её цена

`asyncModule(fn)` регистрирует async-функцию, исполняемую в конце фазы компиляции — можно сходить в API
и сгенерировать кубы. Три ограничения из официальных доков:

1. только JS (в YAML — Jinja+Python, другой механизм и другой рантайм);
2. у динамически созданных полей `sql`/`drill_members` обязаны быть функциями `() => string` — потому что
   транспайлер, который делает это автоматически для статического кода, до сгенерированных объектов не
   добирается. **Статический анализ теряется ровно там, где начинается динамика**;
3. `asyncModule` вызывается один раз на компиляцию — модель меняется только пересборкой.

Мультитенантность (`COMPILE_CONTEXT`) означает отдельную компиляцию модели на каждый набор контекста —
поэтому у компилятора есть `compilerId` и кэш компиляторов.

## 4. Типобезопасности нет — ни у модели, ни у клиента

`cube()` — vm-глобаль. К ней невозможно привязать `import`, а значит и вывод типов: IDE не знает, что
`measures.count.sql` обязателен, а `dimenson` — опечатка. Валидация модели — рантайм, через `joi` внутри
`CubeValidator`, ошибки видны только после компиляции. Инференс типов результата запроса для клиента —
[открытый запрос с 2022](https://github.com/cube-js/cube/issues/4202). Иными словами: **JS-авторинг в Cube
даёт гибкость, но не даёт ничего из того, ради чего мы вообще смотрим на TypeScript.**

## 5. Версионирование и окружения

Модель — файлы в git, это единственный источник правды; Cube Cloud поверх этого даёт ветки и dev-mode:
отдельная git-ветка = отдельный API-эндпоинт с горячей перезагрузкой модели, ветки общие для команды,
мерж в production-ветку делается из UI ([dev mode](https://cube.dev/docs/product/workspace/dev-mode),
[continuous deployment](https://cube.dev/docs/product/deployment/cloud/continuous-deployment)).
Версионируется **исходник**, не скомпилированная модель: артефакта деплоя как отдельной сущности нет,
на каждом инстансе модель компилируется заново. Семантического диффа версий модели у Cube нет —
дифф это git-diff текста. Для нас это анти-паттерн: §18.1 требует байтовой воспроизводимости экспорта,
а §7 — семантического диффа по узлам.

## 6. Самый ценный факт: почему Cube не может выкинуть YAML

Визуальный редактор модели работает **только по YAML**:

> «Visual Modeler only allows editing of cubes and views that are defined using the YAML syntax
> (not JavaScript)» … «it does not allow editing of dynamic data models or models which use Jinja»
> — [docs: Visual Modeler](https://docs.cube.dev/docs/data-modeling/visual-modeler)

То есть YAML у Cube — не «для простых случаев», а **единственный формат, который машина умеет читать и
переписывать обратно**. Как только автор ушёл в JS или в Jinja, модель становится write-only для
инструментов: no-code редактор отключается, остаётся текстовый. Ровно та цена, которую заказчик
предлагает заплатить у нас — только у нас на этой стороне стоят канвас, семантический дифф,
`flow_patch` от Claude и экспорт 1:1.

Цена двух форматов видна прямо в исходнике `CubeValidator.ts`: joi-схема несёт капслок-комментарий
«ATTENTION: In case of adding/removing/changing any `Joi.func()` field that needs to be transpiled …
update `CubePropContextTranspiler.transpiledFieldsPatterns`» и набор `nonStringFields` с пометкой
«Update this whenever schema is updated otherwise YAML will be broken». Синхронизация валидатора,
транспайлера и YAML-ветки — ручная. Каждый новый формат авторинга у нас будет стоить того же.

## 7. Где аналогия работает, где рвётся

| Аспект | Cube | Мы | Переносимо |
|---|---|---|---|
| Код строит описание, не исполняет его | да | да, обязательно | **да** |
| Что является истиной | файлы в git | файлы в git ([ADR-0017](../adr/0017-files-as-source-of-truth.md)) | **да** |
| Смешение форматов в одном проекте | «mix YAML and JavaScript» | YAML-IR + TS-авторинг рядом | **да** |
| Динамика | генерация описаний на этапе компиляции | параметризация компонентов, `map`/`loop` — уже в IR | **да**, но нам нужно меньше |
| Обратная запись из UI | только YAML | обязательна всегда (канвас, `flow_patch`) | **нет** |
| Дифф версий | git-diff текста | семантический по узлам, `spec_hash` | **нет** |
| Предмет описания | статическая схема, граф джойнов без циклов | граф исполнения: параллелизм, циклы, провенанс, бюджеты | **нет** |
| Анализ | вычисление SQL при запросе | доминаторы, достижимость, полнота `switch`, оценки стоимости до запуска | **нет** |
| Цена «кода как ссылок» | 4 прохода транспиляции + исполнения | у нас ссылки — данные (`Binding`), проходов ноль | **нет** |

Рвётся аналогия там, где у Cube нет нашей главной сущности: у него модель — словарь, у нас — **программа**.
Словарь можно пересобирать целиком на каждый запрос; программу, под которой идёт живой прогон, нельзя.
Поэтому у Cube нет проблемы Temporal (nondeterminism при правке под прогоном) — и это не заслуга JS-авторинга,
а следствие того, что у модели вообще нет состояния исполнения.

## Вывод для нас

**Берём:** (1) принцип «TS — язык авторинга, IR — язык платформы», подтверждённый Cube на уровне архитектуры:
код вызывает фабрики, фабрики наполняют структуру, структура компилируется. (2) Право смешивать: часть
воркфлоу — YAML-IR, часть — синтезирована из TS. (3) Синтез выполняется **на этапе сборки**, результат —
IR-файл на диске, проходящий все 8 этапов компилятора ([07](../07-compiler.md)) без изменений.

**Не берём:** (1) vm-глобали без импортов — у нас авторинг = обычные `import` из типизированного SDK,
иначе теряется ровно то, ради чего берём TypeScript. (2) Многофазный реэкзекьют исходника: ссылки между
узлами у нас данные (`Binding`), а не свободные идентификаторы, поэтому граф читается из IR без исполнения.
(3) `asyncModule`-подобные обращения в сеть во время синтеза: `compile(spec, registries)` обязан остаться
чистой функцией, иначе `planHash` перестаёт быть воспроизводимым.

**Жёсткое следствие для продукта:** TS-авторинг может быть только **односторонним** (TS → IR). Обратной
записи TS ← канвас не будет — Cube это доказал своим Visual Modeler'ом, отключающимся на JS-моделях.
Значит, у воркфлоу должен быть флаг источника: `authoring: "ir"` (полный канвас, `flow_patch`, семантический
дифф) или `authoring: "ts"` (канвас read-only, дифф по сгенерированному IR, правки — только в исходнике).
Третьего не дано; попытка дать обе стороны кончится тем же, чем у Cube — вторым форматом.

**Чего в срезе нет:** сравнения с CDK/Pulumi/SST и разбора того, как TS-DSL выражает `parallel`/`loop`/
дженерик-компоненты с сохранением вывода типов — это следующий срез.

  API-based статического анализа с TS 7 не проверялась. [DECISIONS](../DECISIONS.md) пинит 6.0.3 — при
  TS-авторинге это становится решением не про dev-tooling, а про ядро продукта.
- UNVERIFIED: загрузчик TS на этапе синтеза (`tsx@4.23.13` / `jiti@2.7.0`) не проверялся на детерминизм
