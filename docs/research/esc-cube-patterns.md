# Срез A: приёмы Cube.js для генеративных промтов и escape hatch

Дата 2026-09-14. Источники — docs.cube.dev, локальные доки проекта. Гипотеза ведущего (escape hatch =
узел графа, а не дыра в шаблоне) **подтверждается** механикой Cube, но ломается в пяти местах (§8).
Главное: **Cube держит гарантии не потому, что код безопасен, а потому что код исполняется на другой
фазе, чем генерация SQL, и не может влиять на форму модели — только на значения.**

## 1. `sql` как функция, а не строка

| Что | Как | Где живёт |
|---|---|---|
| `sql_table: public.orders` | простой случай, рекомендован по умолчанию | декларация |
| `sql: SELECT ... FROM {users.sql()}` | произвольный SQL с подстановкой другого куба | декларация + ссылки |
| `sql` у меры/измерения | выражение над членами: `1.0 * ${purchases} / ${orders_count}` | декларация + ссылки |
| `sql` как функция | **обязательно** внутри `asyncModule()`: `sql` и `drill_members` должны быть функциями, возвращающими строку | код |

Механизм не в синтаксисе, а в транспайлере: Cube применяет его к **зарезервированным свойствам**
(`sql`, `measures`, `dimensions`, `segments`, `time_dimension`) и «автоматически превращает шаблонные
строки в функции с разрешёнными аргументами». Автор пишет шаблон — компилятор получает функцию,
чьи **аргументы и есть список зависимостей**:

```js
cube(`orders`, {
  sql_table: `public.orders`,
  measures: {
    purchases_ratio: { sql: `1.0 * ${purchases} / ${orders_count}`, type: `number` }
  }
})
```

Внутри доступны `CUBE`, члены своего и присоединённых кубов, `SQL_UTILS` (документирован только
`convertTz()`), `FILTER_PARAMS`, `FILTER_GROUP`, `COMPILE_CONTEXT`; недоступны `process`/`console` —
Node VM с кастомным `require`. Дыра работает потому, что имеет фиксированную форму и словарь имён:
не «здесь можно писать JS», а «выражение над объявленными членами».

## 2. Ссылки между членами — прямая аналогия слотам

| Cube | Наш аналог | Статус у нас |
|---|---|---|
| `${CUBE.column}` | `{{ self.field }}` внутри шаблона узла | есть |
| `${measure_name}` | `{{ slot }}`, привязанный к `context_need` | есть |
| `${other_cube.field}` | слот с `source.kind = data/generated` из другого узла | есть |
| транспайлер → функция с аргументами | `globalFullVariablesSync(ast)` из liquidjs | **есть, симметрия точная** |

Cube строит граф зависимостей **до** генерации SQL: имена членов извлекаются из шаблона
синтаксически, а не исполнением — поэтому модель анализируема, несмотря на JS внутри. У нас это
уже есть (08-prompts.md §7: R-T1/R-T2 как разность множеств `globalFullVariablesSync(ast)` и
объявленных слотов, R-C8 — привязка в обе стороны). **Не аналогия, а тот же алгоритм.**
Отсюда инвариант: escape hatch порождает *значение* слота, но не *имя*. Cube держит это даже
в `asyncModule` — имена мер остаются ключами объекта, а не строками из рантайма.

## 3. Security context, `query_rewrite`, access policies

| Механизм | Когда исполняется | Что делает |
|---|---|---|
| `check_auth` | на каждый запрос | парсит JWT, кладёт `securityContext` |
| `query_rewrite(query, ctx)` | на каждый запрос, **до** обращения к данным | дописывает фильтры, может бросить исключение и запретить запрос |
| `context_to_app_id` | на каждый запрос | ключ кэша скомпилированной модели |
| `access_policy` | при построении запроса | `member_level` + `row_level` + маскирование, декларативно |
| `scheduled_refresh_contexts` | планировщик | контексты для фоновых пересборок (`SECURITY_CONTEXT` в SQL — deprecated) |

Точка вмешательства — **вне модели, в конвейере запроса**: `query_rewrite` работает со
структурированным объектом запроса после компиляции, поэтому автор модели не может обойти политику.
Композиция политик (копировать дословно): **члены объединяются** (union по подходящим политикам),
**строки пересекаются** (union фильтров на член, затем intersection по запрошенным членам),
безусловный полный доступ побеждает маскирование, member-level у view **переопределяет** уровень
куба, row-level — **комбинируется**. Наш `view` из реестра типов ведёт себя как Cube-view.

## 4. Динамическая генерация модели — аналог «синтеза IR из TS»

```js
asyncModule(async () => {
  const defs = await fetchDefinitions();
  defs.forEach((d) => cube(d.name, {
    sql: () => `SELECT * FROM ${d.table}`,
    data_source: d.dataSource, measures: d.measures, dimensions: d.dimensions
  }));
});
```

| Свойство | Значение |
|---|---|
| Когда | фаза компиляции модели, при старте и при смене `schema_version` |
| Сколько раз | **один раз на компиляцию модели**, не на запрос |
| Кэш | результат компиляции кэшируется, ключ — `context_to_app_id` |
| Инвалидация | `schema_version` (может быть async-функцией) |
| Ограничение | `sql` и `drill_members` обязаны стать функциями |
| Контекст | `COMPILE_CONTEXT` — `securityContext` + `extendContext`, **вычисляется один раз на ключ `context_to_app_id`, то есть per-tenant, а не per-user** |
| Ошибка | компиляция модели падает целиком; частично собранной модели не бывает |

Cube разводит два контекста: `COMPILE_CONTEXT` (тенант, форма модели) и `securityContext` в
`query_rewrite` (пользователь, содержимое запроса). RLS через `COMPILE_CONTEXT` отравляет кэш модели.

## 5. Пре-агрегации — аналог кэша и TTL у `load`

Типы: `rollup` (основной, максимум выигрыша на **аддитивных** мерах — `count`, `sum`, `min`, `max`,
`count_distinct_approx`), `original_sql` (материализация сложного `sql` куба: окна, воронки),
`rollup_join` (join предрасчётов между источниками, preview, требует индексов по ключам),
`rollup_lambda` (склейка исторического rollup со свежими данными).

Матчинг: пре-агрегация обязана содержать **все** измерения и меры запроса; аддитивность решает,
можно ли ответить без сырых данных. Инвалидация — `refresh_key` (`every` как интервал или CRON плюс
опциональный `sql` для детекта изменений; по умолчанию раз в час). Партиции —
`partition_granularity` + `build_range_start/end`, до 500–1000 штук; агрегирующие индексы — только
с аддитивными мерами. **Перенос:** «что можно предрассчитать» решается не флагом автора, а
**алгебраическим свойством** меры. У `load` с `ttl` (R-C5) такого свойства нет — нужен класс
детерминированности узла.

## 6. `FILTER_PARAMS` и `COMPILE_CONTEXT` — аналог R-T8

```yaml
cubes:
  - name: events
    sql: SELECT * FROM events WHERE {FILTER_PARAMS.events.ts.filter('ts')}
```

| Переменная | Что подставляет | Ограничение |
|---|---|---|
| `FILTER_PARAMS.cube.member.filter(expr)` | значение фильтра **из запроса** в SQL, строкой или функцией | дока: «интенсивное использование `FILTER_PARAMS` считается плохой практикой» |
| `FILTER_GROUP` | обязательная обёртка при нескольких `FILTER_PARAMS` в одном `WHERE` | иначе ломается приоритет `AND`/`OR` |
| `COMPILE_CONTEXT` | тенантные переменные, Jinja `{{ }}` | per-tenant, не per-user |

Параметр запроса попадает в SQL **только** через именованный канал, привязанный к конкретному члену
конкретного куба; склейки строк с пользовательским вводом в модели нет вообще. Это дословно R-T8.
Ценна и оговорка про плохую практику: канал есть, но его избыток — запах, и это надо линтить.

## 7. Итоговая таблица: приём → наш аналог → что спроектировать

| # | Приём Cube.js | Наш аналог | Что надо спроектировать |
|---|---|---|---|
| 1 | зарезервированные свойства (`sql`, `measures`…) как единственные места кода | слот шаблона + `code`-узел за ним | закрытый список «дыр»: значение слота, пост-проверка, компрессия. Больше нигде код в промт не входит |
| 2 | транспайлер шаблон → функция с аргументами-зависимостями | `globalFullVariablesSync(ast)`, R-T1/R-T2/R-C8 | ничего нового; зафиксировать инвариант «имена слотов не вычислимы в рантайме» отдельным правилом |
| 3 | `${CUBE}` / `${member}` | `context_need` + `source.kind` | адаптер промта = объект с теми же 6 `kind`, что у `ContextSource`; рендер не знает, откуда пришло значение |
| 4 | `{users.sql()}` — ссылка на SQL другого куба | `IncludeTag` с пином версии фрагмента | наследование промтов по `extends`, а не копипаст; ключ кэша префикса считается по цепочке |
| 5 | `query_rewrite` на каждый запрос | политики доступа и PII | хук `context_rewrite(needs, ctx)` **после** резолва источников и **до** рендера; бросает — узел блокируется |
| 6 | `access_policy`: члены union, строки intersection | `view` в реестре типов, R-T10 | перенести решётку дословно: view переопределяет member-level, комбинирует row-level |
| 7 | `asyncModule`, один раз на компиляцию | синтез IR из TS | фаза `model_compile` с явным ключом кэша и атомарностью: либо вся модель, либо ошибка |
| 8 | `COMPILE_CONTEXT` per-tenant | контекст синтеза IR | **запрет** на попадание per-user данных в фазу синтеза; линт на это |
| 9 | `schema_version` как async-функция | версия IR | вычисляемая версия IR как триггер перекомпиляции и как часть replay-ключа |
| 10 | аддитивность меры решает матчинг rollup | `ttl` у `load`, replay-кэш | **класс детерминированности узла** (`pure` / `stable(ttl)` / `volatile`); кэш и replay читают его, а не флаг автора |
| 11 | `refresh_key: { sql }` — детект изменений запросом | TTL по времени | инвалидация по внешнему признаку (etag, max(updated_at)), не только по таймеру |
| 12 | `FILTER_PARAMS` как единственный канал значений | R-T8 | оставить как есть; добавить бюджет/линт на число escape-каналов в одном промте |
| 13 | Node VM, нет `process`/`console`, кастомный `require` | чистота `code`-узла (§2.4, эффект `pure`) | тот же уровень изоляции для узла-адаптера; реестр разрешённых модулей |
| 14 | `data_source` у динамических кубов | провенанс значения | метка происхождения обязательна и для значений из escape-узла |

## 8. Где гипотеза ломается

1. **Фаза.** У Cube код исполняется на компиляции и даёт *статическую* модель. Наш escape-узел
   работает в рантайме: провенанс, трасса и TTL сохраняются (гипотеза верна), но **верхняя оценка
   размера R-T9/R-C7 — нет**. Лечится обязательным `out`-типом с `maxItems`/`maxLength` — это
   условие надо внести в формулировку гипотезы явно.
2. **Форма против значения.** Если escape-узел влияет на *набор* слотов (условная вставка блока,
   склейка текста), рушатся R-T1/R-T2 и весь статический анализ. Граница: код даёт значение
   объявленного слота, никогда — структуру шаблона.
3. **Два контекста.** Разделение per-tenant / per-user у нас не проведено: если синтез IR из TS
   увидит пользовательские данные, кэш модели станет каналом утечки. Самый недооценённый риск.
4. **Кэш без алгебры.** R-C5 требует TTL, но не свойства, делающего переиспользование корректным;
   Cube тут держит аддитивность. Без класса детерминированности replay-кэш `load` несоунден.
5. **Пролиферация.** Дока Cube сама называет интенсивное `FILTER_PARAMS` плохой практикой.
   Escape hatch без бюджета превращает «90/10» в «10/90».
