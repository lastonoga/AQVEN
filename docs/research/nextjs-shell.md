# Studio: архитектура Next.js-приложения

Статус: В РАБОТЕ. Дата: 2026-09-11. Источники: официальные блог-посты и доки nextjs.org, `npm view`.

## 1. Next.js 16.3 — что реально важно для Studio

Источники: https://nextjs.org/blog/next-16 (2025-10-21), https://nextjs.org/blog/next-16-3 (2026-08-03),
https://nextjs.org/blog/next-16-3-instant-navigations.

### 1.1 Cache Components заменили PPR и dynamicIO
- Флаг `experimental.ppr` **удалён**. Route-level `export const experimental_ppr` **удалён**.
  `experimental.dynamicIO` **переименован** в `cacheComponents`.
- Включение: `next.config.ts` → `{ cacheComponents: true }` (top-level, не experimental).
  В 16.3 к нему добавился `{ partialPrefetching: true }` — вместе это «Instant Navigations».
- Модель: **всё динамическое по умолчанию**, кэш — только явный opt-in через директиву `'use cache'`
  (на уровне файла, компонента или функции). Ключ кэша генерирует компилятор из замыканий/аргументов.
- ВАЖНО для нас: старый неявный App Router кэш (fetch-кэш, Router Cache) больше не «спасает» —
  никакой скрытой стейл-выдачи в отладчике прогонов не будет. Это ровно то, что нам нужно.

### 1.2 Каскад API ревалидации (breaking)
- `revalidateTag(tag, profile)` — **второй аргумент обязателен** (иначе deprecated-путь).
  Принимает имя built-in cacheLife-профиля (`'max'`, `'hours'`, `'days'`), либо inline `{ expire: 3600 }`.
  Семантика — stale-while-revalidate. Рекомендация Vercel: `'max'` для долгоживущего контента.
- `updateTag(tag)` — **новое, только внутри Server Actions**. Семантика **read-your-writes**:
  инвалидирует и тут же читает свежие данные в том же запросе. Это наш случай для мутаций реестров
  (промпт-шаблоны, провайдеры, датасеты): человек нажал «Сохранить» — видит своё изменение сразу.
- `refresh()` — **новое, только Server Actions**. Обновляет ТОЛЬКО некэшированные данные, кэш не трогает.
  Серверный аналог `router.refresh()`. Наш случай: после «Запустить прогон» освежить счётчик активных
  прогонов в шапке, не сбрасывая закэшированные оболочки.
- `cacheLife(profile)` / `cacheTag(tag)` — вызываются внутри `'use cache'`-скоупа.

### 1.3 proxy.ts вместо middleware.ts
- `middleware.ts` **deprecated**, заменён на `proxy.ts` с экспортом функции `proxy`.
- `proxy.ts` работает **на Node.js runtime** (не Edge). Это снимает у нас главную боль: в edge-middleware
  нельзя было дергать нормальные Node-библиотеки (jose-only, никакого pg). Теперь авторизация/проверка
  сессии в proxy может пользоваться обычным Node-стеком.
- `middleware.ts` ещё жив ради Edge-кейсов, но будет удалён. Пишем сразу `proxy.ts`.

### 1.4 Turbopack
- Стабилен и **дефолтный бандлер** (`next build --webpack` — аварийный выход).
- 16.3: disk cache для `next build` **включён по умолчанию** (до 5.5x быстрее повторные сборки на CI),
  memory eviction в dev → до **90% меньше RAM** в долгих dev-сессиях. Конфиги:
  `turbopackFileSystemCache`, `turbopackMemoryEviction`.
- Практика для монорепы (turbo 2.10.12): кэш Turbopack на диске надо класть в кэшируемые пути CI.

### 1.5 React Compiler
- `reactCompiler: true` — **top-level стабильный флаг** с 16.0, но **выключен по умолчанию** (Babel → медленные сборки).
- 16.3: экспериментальный Rust-порт внутри Turbopack:
  `{ reactCompiler: true, experimental: { turbopackRustReactCompiler: true } }` — −34% cold / −46% warm
  до готовой страницы на больших приложениях.
- ВЕРДИКТ для Studio: **включать**. У нас канвас + таблицы + отладчик — тонны ре-рендеров, которые иначе
  придётся руками заворачивать в `memo`/`useMemo`. Rust-путь держит время сборки приемлемым.
  Требование: полностью уйти от Babel (иначе выигрыш частичный).

### 1.6 Прочее из 16.3, что нам пригодится
- **Custom error boundaries**: `import { catchError, type ErrorInfo } from 'next/error'` — клиентский
  компонент, обёрнутый `catchError(Fallback)`; получает `{ error, retry }`, `retry()` **перефетчит
  серверные компоненты границы**, и при этом не перехватывает `notFound()`/`redirect()`.
  Наш случай: панель «прогон не загрузился» с кнопкой «Повторить», без полного релоада Studio.
- **Root params**: `import { lang } from 'next/root-params'` — доступ к параметрам выше root layout
  из любого Server Component без prop-drilling. Наш случай: `app/[workspaceId]/...` →
  `workspaceId()` в любом серверном компоненте и **внутри `'use cache'`-скоупов**.
  Ограничение: пока только Server Components (не route handlers, не Server Actions).
- **`import.meta.glob`** (Vite-совместимый) в Turbopack — можем грузить встроенные шаблоны/пресеты
  воркфлоу из файлов с HMR.
- **Node.js native streams** в App Router рендере → +22% RPS без изменений кода.
- **TypeScript 7** поддерживается для type-check в `next build` (`typescript@^7`, конфиг `useTypeScriptCli`).
  10x быстрее — важно для монорепы.
- **`experimental.useOffline`** + хук `useOffline` из `next/offline`: софт-навигации и Server Actions
  не падают при обрыве сети, а ждут и ретраятся. Для внутреннего инструмента с длинными прогонами —
  интересно, но экспериментально; UNVERIFIED в проде, помечаем как «попробовать позже».
- **DevTools**: Instant Insights (ловит не-мгновенные навигации), Navigation Inspector (пауза на shell),
  `instant()` helper из `@next/playwright` для регрессионных e2e на скорость навигации.

### 1.7 Breaking, о которые споткнёмся при бутстрапе
- Node.js **≥ 20.9**, TypeScript **≥ 5.1**, браузеры Chrome/Edge/FF 111+, Safari 16.4+.
- `params`, `searchParams`, `cookies()`, `headers()`, `draftMode()` — **только async** (`await`).
- **`next lint` удалён**; `next build` больше не линтит. Ставим ESLint flat config или Biome отдельным шагом turbo.
- **Parallel routes требуют явный `default.js` в каждом слоте**, иначе билд падает. У нас параллельные
  слоты почти наверняка будут (инспектор/канвас/логи) — заложить сразу.
- `serverRuntimeConfig`/`publicRuntimeConfig` удалены → только env.
- `next/image`: `qualities` по умолчанию `[75]`, `minimumCacheTTL` 4h, локальные src с query требуют
  `images.localPatterns`. Для внутреннего инструмента почти неважно.

## 2. RSC-heavy или SPA внутри Next? — честный вердикт

**Вердикт: ни то, ни другое в чистом виде. Берём «серверная оболочка маршрута + клиентские острова,
владеющие живыми данными».** Формулировка правила: *у каждой поверхности ровно один владелец данных —
либо сервер (RSC + Server Actions + `updateTag`), либо клиент (TanStack Query + REST/SSE). Смешивать
на одних и тех же данных запрещено.*

### Почему не RSC-heavy
- Отладчик прогона (§11) меняется несколько раз в секунду. RSC-ре-рендер = round-trip на каждое
  изменение. Для живого графа прогона это заведомо проигрышно против SSE + локального стора.
- Канвас (React Flow + ELK, §14.1) — 60 fps pointer-события, виртуализация рёбер, layout в воркере.
  Серверу тут делать нечего; RSC-сериализация большого IR на каждое действие убьёт интерактив.
- Studio — **аутентифицированный внутренний инструмент**. Ни SEO, ни холодного первого визита
  анонима. Главный козырь RSC (готовый HTML без JS) почти не монетизируется.

### Почему не «SPA внутри Next» (один catch-all client route)
- Теряем route-level code splitting: Monaco/CodeMirror, React Flow, ELK, таблицы, чарты грузились бы
  одним бандлом. У нас тяжёлых подсистем 5+.
- Теряем 16.3 Partial Prefetching и instant loading shells — а это ровно то, что делает переходы
  между прогонами мгновенными.
- Теряем Server Actions как естественный транспорт для мутаций реестров и human-задач.
- Теряем серверную проверку прав до отрисовки (гейт на аппрув побочных эффектов, §15).

### Карта маршрутов (конкретно)

| Маршрут | Тип | Где грузятся данные |
|---|---|---|
| `proxy.ts` (Node runtime) | сервер | только сессия/редирект на workspace. **Никакой загрузки данных** |
| `app/layout.tsx` | RSC | шрифты, `<ThemeProvider>` (клиентский островок), ничего не фетчит |
| `app/[workspaceId]/layout.tsx` | RSC | членство в workspace, навигация, флаги. `'use cache'` + `cacheTag('ws:'+id)`. Доступ к id через `import { workspaceId } from 'next/root-params'` — работает и внутри `use cache` |
| `.../workflows` (список) | RSC + Suspense | сервер, `'use cache'` + тег, таблица — клиентский островок с `initialData` |
| `.../workflows/[id]` (канвас) | RSC-оболочка | сервер отдаёт IR+спеку **один раз** пропом; сам канвас `'use client'` + `next/dynamic({ ssr:false })` |
| `.../runs` (список прогонов) | RSC + Suspense | сервер; фильтры через nuqs → ключ TanStack Query |
| `.../runs/[runId]` (отладчик) | RSC-оболочка | сервер отдаёт **снимок** прогона; дельты — SSE в клиент. Терминальный прогон кэшируем (`cacheTag('run:'+id)`), живой — нет |
| `.../prompts/[templateId]` (редактор) | RSC-оболочка | сервер отдаёт шаблон + фикстуры; редактор client-only |
| `.../registry/(types\|models\|agents\|tools)` | RSC | сервер владеет: Server Actions + `updateTag('registry:types')` — read-your-writes |
| `.../evals/...` (датасеты, эксперименты) | RSC + streaming | сервер для списков, клиент для виртуализованных таблиц результатов |
| `.../tasks/[taskId]` (human-задача) | RSC-оболочка | сервер отдаёт JSON Schema + контекст; форма client-only; сабмит Server Action → resume воркфлоу |
| `.../versions/compare` (дифф) | RSC | сервер, полностью читающий; пара версий в URL через nuqs |
| `app/api/*` (route handlers) | Node | SSE-стрим прогона, проксирование к VoltAgent REST, выгрузка экспорта |

### Client-only (обязательно `dynamic(..., { ssr: false })`)
React Flow канвас, ELK-раскладка (в Web Worker), редактор CodeMirror, чарты водопада,
виртуализованные таблицы с бесконечной прокруткой, live-tail логов.

### Про `cacheComponents: true` — честно
- Включённый флаг делает **всё динамическое по умолчанию** и требует явной `<Suspense>`-границы
  вокруг любого чтения `cookies()`/`headers()`/некэшированного фетча — иначе сборка падает.
  У нас сессия читается практически везде → это не «флаг», а рефакторинг дерева границ.
- **План:** фаза 0 — без флага, но дерево `<Suspense>` проектируем сразу так, будто он включён.
  Фаза 1 — включаем `{ cacheComponents: true, partialPrefetching: true }` (есть официальный гайд
  `/docs/app/guides/migrating-to-cache-components` и агентский путь миграции).
  Обоснование срочности: Vercel заявил, что поведение Instant Navigations станет дефолтом в следующем
  мажоре, так что откладывать дорого.
- Настоящая ценность флага для нас — **не кэш, а извлечение loading shell** из любого маршрута:
  переход между прогонами показывает каркас отладчика мгновенно.

## 3. Разделение состояния: TanStack Query v5 / zustand v5 / nuqs

Версии (npm, 2026-09-11): `@tanstack/react-query@5.102.8`, `zustand@5.0.15`,
`nuqs@2.10.1` (MIT, peer `next >= 14.2.0`, `react >= 18.2 || ^19`).

### Правило разделения (одно, простое)
1. **Можно ли дать ссылку коллеге и он увидит то же самое?** → URL (nuqs).
2. **Обновляется чаще ~10 раз/сек или это сугубо «мои настройки вида»?** → zustand (плюс `persist`
   в localStorage для настроек вида).
3. **Источник истины на сервере и может измениться без меня?** → TanStack Query.

Данные **никогда не дублируются** между тремя хранилищами. Дублирование состояния — источник
рассинхронов, которые в отладчике прогона выглядят как «баг платформы».

### 3.1. Канвас: вьюпорт и выделение
- **Вьюпорт** (`x, y, zoom`), перетаскивание, рамка выделения, hover, рисуемое соединение →
  **внутренний стор React Flow**. Не копировать в zustand и тем более не в URL: pointer-move частота.
  Если нужен доступ извне — `useReactFlow()` / `useStore(selector)` самого React Flow.
- **Первичный выделенный узел** (тот, что открыт в инспекторе) → **nuqs**, параметр `?node=<nodeId>`,
  обязательно `{ history: 'replace', shallow: true }`. Это делает ссылку «посмотри вот этот узел»
  рабочей — прямое требование §11 (провенанс, клик ведёт к источнику).
- **Мультивыделение** (набор id при box-select), режим канваса до фиксации, локальные раскрытия
  подворкфлоу → **zustand**. Слишком волатильно для URL.
- **Режим просмотра** (агрегированный / развёрнутый, §11) и **группировка по стадиям** → **nuqs**
  (`?view=aggregated`, `parseAsStringLiteral(['aggregated','expanded'])`), потому что это часть
  «что я показываю».
- **Результат ELK-раскладки** → не состояние вообще: считаем в Web Worker, мемоизируем по хешу IR,
  держим в `useRef`/Query-кэше как derived data.

### 3.2. Состояние отладчика прогона
- **Снимок прогона + результаты узлов** → TanStack Query, ключ `['run', runId]`.
  - Терминальный прогон: `staleTime: Infinity`, `gcTime` большой — прогоны иммутабельны.
  - Живой прогон: `staleTime: 0`, **но без polling**. SSE-события применяем
    `queryClient.setQueryData(['run', runId], applyDelta)`. Поллинг тут — антипаттерн: события
    и так идут, а рефетч полного снимка на каждое событие убьёт и клиент, и бэкенд.
  - Реплей узла / форк с узла k → `useMutation`, при успехе `invalidateQueries(['run'])` либо
    навигация на новый runId.
- **Черновик правки входа для replay** и **замороженные выходы верхних узлов** → локальная форма
  (react-hook-form) + zustand для «заморожено/нет» по узлам. На сервер уходит только при сабмите.
- **Точки останова** (перед узлом / при провале проверки) → это **серверное** состояние прогона
  (рантайм должен о них знать) → Query + мутация. В zustand держать нельзя: иначе после релоада
  прогон встанет не там, где показывает UI.
- **Открытая вкладка инспектора** (промт / сырой ответ / проверки / стоимость) → nuqs
  (`?tab=prompt`), чтобы ссылка вела в нужную вкладку.
- **Раскрытые строки водопада, высоты панелей, «показывать свёрнутые повторы»** → zustand + persist.

### 3.3. Фильтры таблиц (прогоны, датасеты, эксперименты, очередь разметки)
- **Все фильтры, сортировка, пагинация/курсор → nuqs.** Работает «назад», работает релоад, работает
  «скинь ссылку на этот срез провалов».
  - `useQueryStates({ status: parseAsArrayOf(parseAsString), node: parseAsString, q: parseAsString.withOptions({ throttleMs: 300 }), cursor: parseAsString })`.
  - `shallow: true` — **обязательно**, иначе каждое нажатие клавиши в поиске бьёт в сервер.
    `shallow: false` оставить только там, где список реально рендерит RSC.
- **Ключ TanStack Query строится из распарсенных nuqs-значений** — один источник истины:
  `useQuery({ queryKey: ['runs', filters], ... })`. Никакого зеркалирования фильтров в zustand.
- Выделенные строки для батч-действий (например, «добавить в датасет») → zustand, эфемерно.

### 3.4. Открытые панели
- **Какие панели открыты и их размеры** (левый реестр, правый инспектор, нижние логи) → zustand
  с `persist` в localStorage. Это личная настройка рабочего места, не часть ссылки.
- **Исключение:** если панель — это «что я сейчас изучаю» (инспектор открыт на узле X), то её
  открытость **выводится** из наличия `?node=` в URL, а не хранится отдельно. Иначе получим два
  источника истины и мигание.
- **Модалки/диалоги, которые надо шарить** (например, «дифф версий A↔B») → nuqs
  (`?diff=v12..v15`), а не локальный `useState`.

### Интеграция с Next 16 / Turbopack
- **Monaco: главный блокер.** Monaco требует Web Workers на язык (`editor.worker`, `json.worker`,
  `ts.worker`…). Канонический путь — `monaco-editor-webpack-plugin`, **которого для Turbopack нет**,
  а Turbopack в Next 16 — дефолтный бандлер. Известная проблема:
  vercel/next.js#72613 «Truly dynamic imports with Turbopack, i.e. support for Monaco editor».
  Альтернатива `@monaco-editor/react` по умолчанию грузит Monaco **с CDN через `loader`** — для
  внутреннего инструмента за корпоративным периметром это неприемлемо; self-host требует ручного
  копирования `monaco-editor/min/vs` в `public/` и ручной настройки `MonacoEnvironment.getWorkerUrl`.
  UNVERIFIED: работает ли путь `new Worker(new URL('monaco-editor/esm/vs/editor/editor.worker.js', import.meta.url))`
  в Turbopack 16.3 — надо спайкать, если вдруг понадобится Monaco.
- **CodeMirror 6: ESM-нативный, без воркеров, без плагинов бандлера.** Кладётся в клиентский компонент
  под `dynamic(() => import('./Editor'), { ssr: false })` и просто работает. Tree-shaking честный.

### Что нам реально нужно от редактора (§14.7, §7.6) и как это делается
1. **Подсветка своего синтаксиса шаблона промта** (проза + `{{slot}}` + директивы).
   - CM6, самый дешёвый путь: `new MatchDecorator({ regexp, decoration })` (класс есть в
     `@codemirror/view`) внутри `ViewPlugin` — подсветка слотов в 40–60 строк, без грамматики вообще.
   - Для полноценного языка (IR/DSL): `StreamLanguage.define(spec: StreamParser<State>)` из
     `@codemirror/language` — простой построчный токенайзер; либо Lezer-грамматика, если понадобится
     дерево разбора.
   - Monaco-эквивалент — Monarch (`setMonarchTokensProvider`), тоже удобно, но регистрация **глобальная
     на весь Monaco**, а не на инстанс — с HMR и несколькими редакторами на странице это ломается.
2. **Автодополнение слотов из нашего реестра типов.** CM6 (проверено в .d.ts):
   ```ts
   type CompletionSource = (context: CompletionContext) =>
     CompletionResult | null | Promise<CompletionResult | null>;
   interface CompletionResult { from: number; to?: number; options: readonly Completion[]; /* + validFor */ }
   autocompletion({ override: [mySlotSource] })   // override?: readonly CompletionSource[] | null
   ```
   Асинхронный источник «из коробки» → дергаем наш API типов/провенанса прямо из функции.
   `CompletionResult.validFor` (regexp/предикат) гасит лишние запросы при дальнейшем наборе.
3. **Инлайн-диагностика от нашего компилятора.** CM6 (проверено в .d.ts):
   ```ts
   interface Diagnostic { from: number; to: number; severity: Severity; message: string;
     source?: string; markClass?: string; renderMessage?: (v: EditorView) => Node; actions?: readonly Action[] }
   type LintSource = (view: EditorView) => readonly Diagnostic[] | Promise<readonly Diagnostic[]>;
   declare function linter(source: LintSource | null, config?: LintConfig): Extension;
   declare function setDiagnostics(state: EditorState, diagnostics: readonly Diagnostic[]): TransactionSpec;
   declare function forceLinting(view: EditorView): void;
   declare function lintGutter(config?): Extension;
   ```
   **Два режима — оба нужны:** `linter(async view => fetchDiagnostics(...))` для «сам сходи и проверь»
   и `view.dispatch(setDiagnostics(view.state, diags))` для «компилятор прислал диагностику по WS/SSE
   сам» (например, после сохранения версии). `Diagnostic.actions` даёт quick-fix («создать слот»,
   «привязать к выходу узла N») — ровно то, что нужно для правки ошибок компиляции.
   Monaco-эквивалент — `monaco.editor.setModelMarkers(model, owner, markers)`; тоже нормально,
   но marker-owner привязан к модели глобально.
4. **Дифф отрисовки между версиями (§14.7).** Monaco даёт готовый `DiffEditor` — это его единственное
   честное преимущество. Для CM6 берём `@codemirror/merge` (`unifiedMergeView` / `MergeView`) —
   официальный пакет из того же репозитория. UNVERIFIED: версия `@codemirror/merge` — проверить перед
   использованием.
5. **JSON/YAML-редактирование IR** — `@codemirror/lang-json` (0.8 KB gz) + `jsonParseLinter`; YAML —
   `@codemirror/lang-yaml`.

### ВЕРДИКТ: CodeMirror 6
Собираем **своими руками** на `@codemirror/{state,view,language,autocomplete,lint,commands,search}`,
**без `@uiw/react-codemirror`**. Обёртка `@uiw` тянет `@babel/runtime`, навязывает свой набор
расширений и тему `one-dark`, и лишает контроля над жизненным циклом `EditorView` — а нам нужен
точный контроль (императивный `dispatch(setDiagnostics(...))` из стрима). Своя обёртка на
`useRef` + `useEffect` над `EditorView` — это ~80 строк и ноль зависимостей.

**Monaco брать не будем** по трём причинам, в порядке важности:
1. Turbopack-воркеры — нерешённая инфраструктурная проблема, а Turbopack у нас дефолт.
2. Нам не нужен TypeScript language service. Наша диагностика приходит **от нашего компилятора**
   по сети, а не от встроенного tsserver — то есть главная фича Monaco не используется.
3. Вес и CDN-загрузка по умолчанию.

**Когда пересмотреть:** если в IR появятся полноценные TS-выражения для мапперов с типовой
подсказкой по нашим типам. Тогда либо Monaco + `@typescript/vfs`, либо CM6 + LSP-мост. Оба пути
дорогие — лучше избежать TS в IR (это же требование §15.1 про экспорт 1:1).

## 5. Формы из JSON Schema в рантайме (human-задачи, редакторы реестров)

### Постановка, чтобы не сравнивать разное
Схема приходит **в рантайме**, с сервера: VoltAgent задаёт `suspendSchema`/`resumeSchema` (zod),
наружу по REST это JSON Schema. Редакторы реестров (типы, профили моделей, тулы с закреплёнными
MCP-схемами, §7.4) — тоже произвольные схемы, известные только в рантайме.
Значит нужен **генератор UI из схемы**, а не просто движок форм.

| Пакет | Версия | Лицензия | Свежесть | Что это на самом деле |
|---|---|---|---|---|
| `@rjsf/core` + `@rjsf/utils` + `@rjsf/validator-ajv8` | **6.10.0** | Apache-2.0 | **2026-09-09 (2 дня)** | Настоящая рантайм-генерация из JSON Schema. peer `react >= 18` |
| `@rjsf/shadcn` | **6.10.0** | Apache-2.0 | **2026-09-09** | Официальная shadcn-тема RJSF. peer: `react>=18`, `@rjsf/core ^6.10.0` |
| `react-hook-form` | 7.87.0 | MIT | 2026-08-30 | **Движок**, не генератор. UI пишем сами |
| `@hookform/resolvers` | 5.9.1 | MIT | 2026-08-17 | Есть `ajv`-резолвер → валидация **прямо по JSON Schema**, плюс `standard-schema` и `zod` |
| `@tanstack/react-form` | 1.33.5 | MIT | 2026-08-21 | **Движок**, headless. Генерации UI из схемы нет |
| `@autoform/react` | 5.0.0 | MIT | 2026-07-08 | Генерация из **zod**, не из JSON Schema |
| `@autoform/zod` | 6.0.0 | MIT | 2026-07-08 | — |

| `json-schema-to-zod` | 2.8.1 | ISC | 2026-04-01 | Мост JSON Schema → zod (для autoform-пути) |

Пакета `@autoform/json-schema` в npm **нет** (проверено).

### Разбор вариантов
- **AutoForm — отпадает.** Требует zod-схему, то есть нам пришлось бы в рантайме гонять
  JSON Schema → zod через `json-schema-to-zod` (а он генерирует **строку кода**, которую надо
  `eval`-ить — в продовом внутреннем инструменте это прямой запрет). Плюс версии ядра (5.x/6.x)
  и shadcn-темы (1.0.1, 2 года) разъехались — это уже не «живая поддерживаемая библиотека».
- **@tanstack/react-form — отпадает для генерации.** Отличный типизированный движок, но UI из схемы
  он не строит; нам пришлось бы писать собственный резолвер «JSON Schema → дерево виджетов»,
  то есть ровно тот велосипед, который запрещено изобретать.
- **react-hook-form + ajv-резолвер** — годится там, где форма **известна на этапе разработки**
  (логин, настройки воркспейса, форма запуска прогона, правка входа для replay). Сюда же ложится
  `@hookform/resolvers/ajv` для валидации по JSON Schema, если схема всё-таки динамическая,
  но UI фиксированный.
- **@rjsf/core v6 — единственный, кто реально решает задачу.** Apache-2.0, релизы неделю назад,
  архитектура: ядро + `@rjsf/utils` + отдельный валидатор (`@rjsf/validator-ajv8`) + тема.
  Точки расширения, которые нам критичны:
  - `widgets` / `fields` / `templates` — подменяем рендер конкретных типов (секретные поля «только
    по ссылке» §15, PII-метки, поля с выбором из реестра моделей);
  - `uiSchema` — приходит с сервера вместе со схемой, задаёт порядок/группировку/подсказки;
  - `customValidate` / `extraErrors` — **сюда кладём ошибки нашего компилятора и серверные проверки**,
    в том числе после сабмита;
  - `formContext` — прокидываем провенанс и контекст прогона в виджеты.
  UNVERIFIED: качество `@rjsf/shadcn` под Tailwind v4 / shadcn текущей ревизии — проверить на спайке
  одной сложной схемой (oneOf + array of objects + $ref).

### ВЕРДИКТ
- **Рантайм-генерация из JSON Schema → `@rjsf/core@6` + `@rjsf/validator-ajv8@6` + `@rjsf/shadcn@6`.**
  Применение: human-задачи (resume-формы), редакторы реестров, формы входа опубликованных воркфлоу
  как тулов (§15), формы параметров скореров.
- **Статически известные формы → `react-hook-form@7` + `zod@4`** (через `@hookform/resolvers/standard-schema`
  или zod-резолвер). Это 90% «обычного» UI Studio, и тут shadcn `<Form>` даёт готовые компоненты.
- **Два движка форм в одном приложении — сознательное решение, а не недосмотр.** Граница простая:
  *схему знает компилятор на этапе сборки → RHF; схему знает только рантайм → RJSF.*
  Смешивать их в одной форме запрещено.
- **zod 4.6.2 → JSON Schema** для обратного направления (наш IR-тип → схема для RJSF) —
  `z.toJSONSchema()` встроен в zod 4; отдельный пакет не нужен. UNVERIFIED: покрытие всех наших
  конструкций (discriminated unions → oneOf) — проверить на спайке.

## 6. Темизация, Suspense-границы, виртуализация

### 6.1. Темизация
- `next-themes@0.4.6`, MIT, peer `react ^19` — совместим. **РИСК: последний релиз 2025-03-11 (~18 мес).**
  Библиотека фактически feature-complete (≈300 строк: класс на `<html>`, `localStorage`,
  блокирующий inline-скрипт против FOUC, `matchMedia`). Митигация: если она сломается на будущем
  мажоре React — заменяется своим провайдером за полдня. Форк не нужен, но зависимость фиксируем точной версией.
- Обязательно: `<html suppressHydrationWarning>` и `<ThemeProvider attribute="class" …>` как
  **клиентский** компонент в root layout. `children` при этом остаются серверными — они передаются
  пропом и не втягиваются в клиентский бандл.
- Tailwind v4 + shadcn: тема живёт в CSS-переменных (`@theme` / `:root` + `.dark`), плюс
  `color-scheme: light dark` для нативных скроллбаров, полей и `<select>` — во внутреннем инструменте
  с плотным UI это заметно.
- **Отдельная проблема, о которую спотыкаются: канвас и чарты рисуются в JS**, а токены — в CSS.
  Правило: **единственный источник истины — CSS-переменные**. В React Flow/чарты цвета прокидываем
  хуком, который читает `getComputedStyle(document.documentElement).getPropertyValue('--...')`
  и переподписывается на смену темы (через `useTheme()` из next-themes). Дублировать палитру в TS —
  гарантированный рассинхрон светлой и тёмной темы.

### 6.2. Suspense-границы и streaming
Правила (они же — правила для будущего `cacheComponents: true`):
1. **Одна граница на один независимо загружающийся регион**, а не одна на страницу. Одна общая
   граница = пустая страница до прихода самых медленных данных и никакого instant shell.
2. **Граница ставится ВЫШЕ чтения данных.** Под `cacheComponents` любое некэшированное чтение
   (`cookies()`, `headers()`, fetch без `'use cache'`) без границы над ним — ошибка сборки.
3. **`fallback` — это не спиннер, а настоящий скелет.** Под `partialPrefetching` именно fallback
   становится префетченной оболочкой, которую пользователь видит мгновенно при клике на ссылку.
   Спиннер в fallback = «мгновенная навигация в никуда».
4. Конкретная нарезка для отладчика прогона (`/runs/[runId]`):
   - layout — шапка прогона (id, статус, версия спеки) — рендерится сразу;
   - `<Suspense>` #1 — граф прогона (скелет = серая сетка узлов);
   - `<Suspense>` #2 — инспектор узла (скелет = каркас вкладок);
   - `<Suspense>` #3 — водопад стоимости/латентности;
   - `<Suspense>` #4 — лог/трасса.
   Каждая тянет свои данные и появляется независимо.
5. **Клиентские тяжеловесы (канвас, редактор, чарты) — не через Suspense, а через
   `next/dynamic(..., { ssr: false, loading: Skeleton })`.** Suspense вокруг них не помогает:
   проблема не в данных, а в загрузке чанка.
6. Проверять результат новыми DevTools: **Instant Insights** сам покажет не-мгновенные навигации,
   **Navigation Inspector** позволит поставить навигацию на паузу на shell. Регрессии закрываем
   e2e-тестом с `instant()` из `@next/playwright`.

### 6.3. Где виртуализация обязательна
Кандидаты: `@tanstack/react-virtual@3.14.12` (MIT, релиз 2026-09-11 — сегодня; peer react ^19) —
headless, поддерживает вертикаль+горизонталь и динамические размеры; `react-window@2.3.1` (MIT,
2026-09-05) — проще, но менее гибкий. **Берём `@tanstack/react-virtual`**: он единственный нормально
делает 2D и динамические высоты строк, а обе фичи нам нужны.

Обязательна в:
1. **Развёрнутый вид графа прогона (§11)** — «каждый вызов отдельно»: цикл на 200 итераций × 8 узлов
   = 1600 элементов. Плюс `onlyRenderVisibleElements` у React Flow для самого канваса.
2. **Матрица стадий (§11)**: элементы датасета × стадии. Это **2D-виртуализация** (и строки, и
   колонки) — сюда `useVirtualizer` дважды, по обеим осям.
3. **Таблицы датасетов и результатов экспериментов (§12)** — тысячи строк.
4. **Live-tail логов и трасс прогона** — растущий список, нужен ещё и «прилипание к низу».
5. **Карта промтов и lineage значения (§14.9)** — длинные списки использований.
6. **Очередь разметки (§12)** — бесконечная прокрутка.
7. Сырой ответ модели в инспекторе — виртуализация **не нужна**: CodeMirror сам рендерит только
   видимую часть документа.

**ВАЖНО про shadcn:** компонент `table` (registry:ui, проверено через shadcn MCP) — это тонкая
обёртка над нативным `<table>`, а `data-table` в реестре **не компонент, а пример**
(`data-table-demo`, registry:example) поверх TanStack Table. Виртуализировать нативный `<table>`
корректно нельзя. Значит: **для больших таблиц строим свой div-грид на TanStack Table +
TanStack Virtual**, стилизуя токенами shadcn, а shadcn `<Table>` оставляем для мелких
статичных таблиц (свойства узла, эффективная конфигурация вызова §14.13).
Панели — shadcn `resizable` (registry:ui, поверх `react-resizable-panels`), размеры persist в zustand.

### 6.4. Производительность — что включить сразу
- `reactCompiler: true` (+ `experimental.turbopackRustReactCompiler: true` как эксперимент).
- **React 19.2 `<Activity>`** для скрытых вкладок инспектора: DOM остаётся, эффекты чистятся,
  состояние (скролл, выделение в редакторе) сохраняется. Лучше, чем размонтировать вкладку и
  лучше, чем `display:none` руками.
- **View Transitions** (React 19.2) для перехода «узел на канвасе → инспектор».
- **ELK-раскладка только в Web Worker** — `elkjs@0.12.0` синхронно блокирует main thread на больших графах.
- React Flow: `nodeTypes`/`edgeTypes` объявлять **вне компонента** (иначе полный ре-маунт всех узлов),
  в фазе 0 ставить `nodesDraggable={false} nodesConnectable={false}`.
- SSE вместо поллинга; дельты через `queryClient.setQueryData`, батчинг событий по кадру
  (`requestAnimationFrame`), иначе живой прогон на 50 узлов затопит React.
