# Срез 6: двусторонняя синхронизация UI ↔ файлы ↔ агент

> Вопрос среза: кто источник истины, когда в одну спеку пишут UI, агент и `git push` — и по какому протоколу они не затирают друг друга.

## Что нашли

| Продукт | Модель истины | Как решают двусторонность | Ссылка |
|---|---|---|---|
| **Argo CD** | Git — единственный источник. Live-состояние кластера считается «дрейфом» | Контроллер в цикле (по умолчанию 120 с) сравнивает целевое и живое состояние, ставит `OutOfSync`; `selfHeal: true` **автоматически откатывает** ручные правки (kubectl) обратно к git, повтор через self-heal timeout 5 с | [auto_sync](https://argo-cd.readthedocs.io/en/latest/user-guide/auto_sync/) |

## Три модели и чем платим

| Модель | Кто так делает | Что получаем | Чем платим |
|---|---|---|---|
| **A. Git — единственный источник** | Argo CD (`selfHeal`), Flux | Дрейфа нет по определению; откат = `git revert`; ревью обязателен | UI становится либо просмотрщиком, либо «песочницей, которую откатят через 5 секунд»; редактирование мышью с задержкой PR-цикла; живое совместное редактирование невозможно |
| **B. БД — источник, git — экспорт/ревью-контур** | n8n (dev→prod one-way), Retool (Protected+PR) | Мгновенный UI и MCP-агент, транзакционные инварианты, git как аудит и промоушен | Git-история — производная, правку «прямо в репозитории» некуда применить без импорта; два формата diff (op-log и git) |
| **C. Двусторонняя** | Windmill (EE), Grafana Git Sync (experimental) | Обе двери открыты, «как код» и «как UI» одновременно | Петли синка (Windmill лечит префиксом `[WM]`), «не включайте CI/CD и авто-синк одновременно», отсутствие семантики конфликтов (n8n честно: «не умеем детектировать»), Grafana сама пишет «не для прода» |

Эмпирика: **никто не отдаёт C без оговорки**. Самые зрелые (Argo, Flux) — это A, но с явной отдушиной (`CorrectDrift=false`, ignore rules по путям). Самые «продуктовые» (n8n, Retool) — это B с git-контуром для промоушена и ревью.

## Наш случай: три писателя одновременно

Дано: человек тащит узел мышью (десятки мелких правок в секунду), агент через MCP делает 20 операций
`flow_patch`, из редактора кода прилетает `git push` в ветку репозитория.

У нас **уже есть** механика, которая у продуктов выше отсутствует: `op_log` с `base_rev`,
CAS `UPDATE specs SET rev = rev + 1 WHERE rev = $base`, авто-ребейз непересекающихся путей и
конверт `conflict { your_base_rev, current_rev, ops_since, rebase }`
([ADR-0009](../adr/0009-op-log-not-crdt.md), [16 §2.3](../16-data-model.md)). Именно её n8n не имеет —
отсюда «Pull and override».

Что происходит без протокола: человек и агент разруливаются `base_rev` (это уже спроектировано), а
`git push` — третий писатель **без ревизии**: у коммита нет `base_rev`, он не знает, что спека уехала.
Это ровно кейс Argo CD «live state разошёлся с git», только направление обратное.

### Предлагаемый протокол: git — это ещё один актор op-log, а не второй источник истины

| Шаг | Правило |
|---|---|
| 1 | Каждый импорт из git — это **не запись файла в БД**, а `flow_patch` от актора `git:<commit_sha>` с `base_rev` = ревизия, из которой был сделан последний экспорт в git (храним `spec_git_sync(spec_id, branch, last_exported_rev, last_commit_sha)`) |
| 2 | `base_rev` совпал — патч применяется, как любой другой, `rev++`, SSE-дельта долетает в открытый Studio без перезагрузки |
| 3 | `base_rev` не совпал — работает тот же авто-ребейз: git-правка трогала `nodes.summarize.prompt`, человек двигал `ui.position` → пересечения нет, обе применяются |
| 4 | Пересечение путей — конфликт **по путям IR**, а не по строкам YAML. Разрешение в Studio: «в git — X, у вас — Y», как Grafana спрашивает save/discard на provisioned-ресурсе |
| 5 | Экспорт в git идёт **только из опубликованных версий** (`spec_versions` c `content_hash`), не из каждой ревизии: коммит несёт `spec_hash` в trailer, обратный импорт по совпадению `spec_hash` — no-op (аналог `[WM]`-префикса Windmill, защита от петли) |
| 6 | Позиции узлов на канве в git **не едут** (или едут в отдельный файл `*.layout.json`, не участвующий в `spec_hash`): это LWW-поле без инвариантов ([ADR-0009](../adr/0009-op-log-not-crdt.md)) — иначе перетаскивание мышью генерирует коммиты |

Ключевое заимствование — **SSA field ownership**: конфликт объявляется на уровне пути, а не документа,
и у него есть три честных исхода (force / отказаться / принять чужое), а не один «override».
Flux ignore rules — второй кирпич: список путей, которые импорт из git не трогает никогда
(`ui.*`, `secrets.*`, пины окружения) — это наш `Strip`.

## Частота коммитов

| Практика | Кто | Применимо нам |
|---|---|---|
| Коммит на каждый деплой айтема | Windmill | Нет: у агента 20 операций = 20 коммитов мусора. У Windmill «деплой» — это уже осознанное действие человека, у нас — операция агента |
| Авто-снимок рабочей копии с амендом в одно изменение | jj | **Да, как модель**: `op_log` = поток снимков, `spec_versions` = стабильная «change», git видит только её |
| Ветка на задачу агента + аппрув человека перед PR | Copilot coding agent | Да для «агент переписывает воркфлоу целиком»; избыточно для «поправь температуру у одного узла» |
| Draft-состояние до аппрува | Grafana (save/discard на provisioned), Retool (Protected → branch → PR) | Да: правки живут в `op_log` как черновик, в git уезжает только публикация |

Вывод по частоте: **коммит = публикация версии, не операция**. `op_log` уже играет роль
«мелкой истории», и дублировать её в git незачем — ровно та связка `commit_id`/`change_id` из jj,
только `change_id` у нас — это `spec_hash` + `rev`.

## Ветки и окружения

| Практика | Вердикт |
|---|---|
| Ветка на задачу агента | Полезно, когда агент правит **несколько** спек связно (рефакторинг) — иначе накладные расходы больше пользы. У Windmill это форк воркспейса → ветка `wm-fork/*`, у Copilot — ветка + явный аппрув PR |
| PR-ревью воркфлоу человеком | Полезно и подтверждено дважды (Retool ToolScript, Grafana «сохранение через PR») — **но ревьюить надо семантический дифф IR, а не YAML-диff**. Retool специально выпилил YAML из ревью. У нас семантический дифф уже спроектирован — это его главный потребитель |
| dev/stage/prod как **ветки** | Так делают n8n и Windmill (ветка на инстанс/воркспейс). Работает, пока окружения отличаются только пинами. Дальше — дрейф веток и вечные merge-конфликты на одних и тех же строках |
| dev/stage/prod как **оверлеи** | У нас уже есть правильная гранулярность: `release_hash = hash(spec_hash, prompt_pins, model_profile_pins, component_lock)` ([04 §1.2](../04-ir-schema.md)). Спека одна, окружение — набор пинов. Ветка на окружение при таком дизайне — карго-культ |
| Protected instance / read-only прод | n8n имеет такой флаг явно; Retool — `Protected` объекты. Нам нужно: на prod-проекте `flow_patch` запрещён, только промоушен релиза |

## Оффлайн и конфликты: UI правил документ, пока репозиторий уехал вперёд

Что делают другие: n8n предлагает **Pull and override** (тихо теряете свои правки) и признаётся, что
конфликты на воркфлоу не детектит; Argo CD с `selfHeal` просто **откатывает** живое состояние через 5 с;
Grafana ловит момент save/discard и выталкивает изменение в PR.

Что можем мы, потому что у нас есть op-log: при импорте коммита с устаревшим `base_rev` считаем
`ops_since` (ровно то поле, что уже есть в конверте конфликта ADR-0009) и делим по путям IR:

| Ситуация | Действие |
|---|---|
| Пути не пересекаются | Авто-ребейз, обе стороны применяются, `rev++`. Экспортируем merge-коммит с новым `spec_hash` |
| Пересечение на LWW-поле (`ui.position`, свободный текст промта) | Побеждает более поздний по времени; в git такие поля либо не едут, либо едут в отдельный файл |
| Пересечение на структуре графа | Конфликт человеку, с обеими версиями пути и семантическим диффом. Авто-резолв запрещён: инварианты (типы портов, DAG, биндинги) валидируются транзакционно, «сойтись, но битым» нельзя |
| Импорт роняет валидатор инвариантов | `ROLLBACK`, спека остаётся на прежней `rev`, в git-ветке заводится «отвергнутый импорт» с `problems[]`. Git-коммит **не** авторитет: невалидная спека не становится состоянием системы |

Отдельный случай — оффлайн-редактирование в UI без сети. Мы его **не поддерживаем**: server-authoritative
по ADR-0009 означает, что без сервера нет `rev`. Это осознанный отказ, а не пробел.

## Вывод для нас

**Берём:**
1. Модель **B** (БД — источник, git — экспорт/ревью/промоушен) как базовую — её выбрали оба продукта,
   ближайшие к нам по форме (n8n, Retool). C-модель на рынке существует только с дисклеймерами.
2. **Git как ещё один актор op-log**: импорт коммита = `flow_patch` с `base_rev`, а не запись файла.
   Это даёт нам то, чего нет ни у кого из найденных: конфликт по путям IR с авто-ребейзом вместо
   «Pull and override».
3. **Field-ownership из SSA**: конфликт на уровне пути, три исхода (force / отказаться / принять чужое).
4. **Ignore rules из Flux**: список путей, которые импорт не трогает (`ui.*`, пины окружения, секреты).
5. **Anti-loop из Windmill**: `spec_hash` в trailer коммита, импорт своего же хеша — no-op.
   И их же предупреждение: **не включать одновременно** два механизма записи в одну сторону.
6. **Коммит = публикация версии** (jj-модель: много снимков → одно изменение), не операция агента.
7. **Ревью семантического диффа, а не YAML** — прямой урок Retool, выпилившего YAML из ревью.
8. **Protected/read-only прод**: на prod-проекте `flow_patch` запрещён, только промоушен релиза.

**Не берём:**
- Argo-подобный `selfHeal` (git затирает UI) — у нас UI и агент, а не деплой-пайплайн;
  откат правки человека через 5 секунд — это продуктовая катастрофа.
- Ветки под окружения: у нас `release_hash` с пинами даёт оверлеи дешевле.
- Коммит на операцию (Windmill-подход) — история превратится в мусор.
- Оффлайн-редактирование и CRDT на структуру графа — отдельно отвергнуто в ADR-0009.

**Где протокол ломается (честно):**
- Импорт из git с большим `ops_since` (ветка недели давности) — авто-ребейз выродится в ручное
  разрешение по десяткам путей. Смягчение: TTL на «живость» ветки, форс-реимпорт как новая спека.
- Переименование узла в git (`id` — часть `spec_hash` и целей биндингов) — для нас это delete+create,
  и любой конкурентный патч по старому `id` конфликтует. Нужна отдельная операция `rename` в op-log,
  иначе git-путь будет генерировать ложные конфликты.
- Две спеки, связанные одним компонентом из реестра: git-коммит атомарен по репозиторию, наш
  `flow_patch` атомарен по **одной** спеке. Кросс-спековый атомарный импорт не покрыт — UNVERIFIED,
  требует отдельного решения (транзакция на набор спек или явный отказ).
- Git-провайдеры не дают транзакционности между «принять патч в БД» и «пушнуть коммит»: любой
  падающий шаг оставляет расхождение. Лечится только тем, что источник — БД, а git догоняет
  (idempotent re-export по `spec_hash`).
