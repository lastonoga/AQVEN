# Проверенные факты о реальных экранах Studio для Wave 3

> Один параллельный проход по `apps/studio/src/` перед планированием Wave 3, 2026-09-22. Каждый пункт
> ниже — то, что реально в коде на момент прохода, с `file:line`. Код меняется быстрее, чем эта
> инвентаризация обновляется — перед тем как цитировать конкретную строку на опубликованной странице
> (что запрещено правилами `apps/site/CONVENTIONS.md` в любом случае), автор страницы обязан открыть
> файл заново и подтвердить, что факт ещё верен.

## Поправка, найденная при выполнении Task 1.1 (не было в исходном проходе)

`{{CLI_COMMAND}} studio`/`dev` **не открывает `/setup` первым делом**. Корень `/` редиректит на
`/project`, только если во флоу-проекте вообще нет флоу; иначе — сразу на канвас самого недавно
запущенного флоу (при равенстве — с наибольшим числом узлов), см. `apps/studio/src/routes/-landing.ts`
и тест `shell.test.tsx` («opens the most recently run workflow of the launched project»). `/setup`
реален и работает так, как описано ниже, но сейчас доступен только по прямому вводу URL — ни одной
ссылки на него из остального приложения нет. Не описывать `/setup` как экран, на который Studio
приводит автоматически.

## 1. `/setup` — онбординг

Route `apps/studio/src/routes/setup.tsx:15`, поиск-параметр `step: "agent"|"providers"|"workflow"`
(`SETUP_STEPS`, `domain/setup.ts:6`), по умолчанию `"agent"`. Loader грузит `project.info`+`project.flows`
всегда, `settings.providers` только на шаге `providers` (`setup.tsx:18-26`). `settings.secrets()` НЕ
вызывается здесь — только на отдельном экране `/settings`.

Компонент `OnboardingScreen` (`features/setup/onboarding-screen.tsx:140-155`):
1. Брендовая строка + опциональная кнопка «skip» на канвас landing-флоу.
2. Заголовок «Set up {package|root}».
3. `StepNav` — сегментированные вкладки agent/providers/workflow.
4. Тело по таблице `STEP_BODY` (стратегия, не if/else):
   - `agent` → `ChatStatusPanel` (статус входа в чат-бэкенд, кнопка «check again»).
   - `providers` → `ProviderKeys` (список провайдеров: маскированный ключ · env var, тег источника) +
     предупреждение, если ни один ключ не резолвится.
   - `workflow` → список флоу проекта как кликабельные карточки (или `Empty`, если флоу нет).
5. Футер Back/Continue.

`domain/setup.ts` содержит большой набор типов (`SetupOverview`, `AgentProbe`, `ServerInfo` и т.д.),
которые НЕ импортируются ни одним реальным компонентом — похоже на неиспользуемый/запланированный код,
не источник истины для этого экрана.

## 2. `/project` — обзор проекта

Route `apps/studio/src/routes/project.tsx:4-10`, loader — `project.info`+`project.flows` параллельно.
Рендерит `ProjectScreen` (`features/project/project-screen.tsx:127-143`), 4 блока:
1. Заголовок — имя пакета или папка.
2. Панель «Project» — 8 строк: Folder, Package, Engine, Tree hash (обрезанный `sha256-...` до 12 симв.),
   Project file, Lock file, MCP, Spec changes.
3. Панель «Index and checks» — 6 строк: Index status (тон по статусу), Generation, Indexed (относительное
   время), Pending files, Problems (успех/предупреждение/ошибка по числу error/warning/info), Quarantined
   files.
4. Блок «Workflows» — список карточек флоу (id, `{input}→{output}`, root_path, теги: число узлов, статус
   компиляции, опционально число проблем) или `Empty`, если флоу нет.

## 3. Канвас — `/flows/$flowId/canvas`

Route `routes/flows/$flowId/canvas.tsx:20-32`, поиск-параметр `node`. `CanvasScreen`
(`features/flow/canvas-screen.tsx:9-37`) = `GraphCanvas` + `NodeInspector`.

**Граф** (`features/flow/canvas/graph-canvas.tsx`, обёртка над `@xyflow/react`): узлы **не
перетаскиваются и не соединяются вручную** (`nodesDraggable=false`, `nodesConnectable=false`) — только
клик для выбора. Два вида карточек узлов: `StepNode` (обычный узел: цветная полоса по виду узла, тег вида,
имя, точка-индикатор проблемы, подзаголовок «agent · inference» или имя функции, счётчики входов/выходов)
и `ContainerNode` (группа для loop/switch/parallel — тег вида, имя, число элементов). Рёбра: обычная
сплошная стрелка (зависимость) и пунктирная U-образная (обратное ребро цикла, только для `loop`).
Раскладка — собственный слоистый DAG-алгоритм (`features/flow/layout.ts`), не сторонняя библиотека.
Легенда (свёрнутый popover) и zoom-контрол — плавающие панели.

**Инспектор узла** — правая выезжающая панель (не модальная, канвас остаётся кликабельным), 520px.
Вкладки: definition / input / prompt / output / config(или «agent», если есть `agent_spec`) / problems
— «prompt» только если у узла есть промт, «problems» только если есть проблемы. Переключатель
formatted/raw переключает КАЖДУЮ секцию между читаемым видом и сырым JSON. Вкладка prompt показывает
формат (template/function), id инференса, уровень, список слотов, варианты промта и сам текст промта в
прокручиваемом блоке — промты реально видны в Studio.

## 4. Список узлов — `/flows/$flowId/nodes`

Отдельный, архитектурно независимый экран (не переиспользует код инспектора канваса). Route
`routes/flows/$flowId/nodes.tsx:27-38`. Плоский список с отступами по родителю (не граф) слева (276px) +
табы справа: definition / prompt / schemas / problems (другой набор вкладок, чем у канваса — нет
input/output/config, есть отдельная «schemas»). Полезно, когда нужно быстро проглядеть все узлы списком,
а не по графу.

## 5. Отладчик прогона — `/flows/$flowId/runs`

Route `routes/flows/$flowId/runs.tsx:67-95` — самый важный экран волны, прямая доставка «30-секундного»
обещания.

**Верх экрана**: выбор прогона (поиск по ref/статусу/датасету), две кнопки — «Start a run» (ведёт на
датасеты) и «Enter input manually» (открывает форму на этой же странице). `RunHeader` — статус, режим,
время старта, хэш спеки, ссылка «forked from» если прогон — форк, предупреждение «definition changed».
`RunMetrics` — 4 карточки: Cost, Duration, Tokens, Nodes (готово/всего + число упавших). `WaitsPanel` —
ожидающие human-узлы (кто назначен, дедлайн). `RunError` — код, сообщение, узел, подсказка.

**Таймлайн стадий** (`features/trace/`): по одной карточке на каждый узел верхнего уровня в порядке
флоу, плюс серые «not started» для ещё не выполненных. Каждая карточка узла — заголовок (id + тег вида:
LLM/CALL/PARALLEL/MAP/LOOP/SWITCH), статус, итоги (цена/время/число вызовов), матрица вызовов, лесенка
неудачных попыток, для loop — сводка выхода («вышел по причине X, оставлена итерация N»). Вложенные
parallel/map/loop/switch/call открываются рекурсивно как вложенные матрицы — это и есть механизм
«найти конкретное исполнение узла по адресу (ветка/итерация/элемент)» из `/concepts/engineering-loop/`.

**Матрица вызова** — до 7 строк на колонку (=одно исполнение): call, agent, model, input, prompt,
output, post-check. Клик по любой ячейке открывает боковую панель `CallSheet` на нужной вкладке.

**CallSheet** — боковая панель, вкладки model/input/prompt/output/checks. Вкладка prompt показывает
реально отправленный промт как нумерованную ленту сообщений + свёрнутый оригинальный шаблон с диска.
Вкладка checks — карточки прошёл/не прошёл + для human-узлов свойства ожидания и полученный ответ.

**Ручной запуск** (`StartRun`): выбор диапазона узлов (drag start→end) с живой проверкой доступности,
форма ввода, построенная из JSON Schema (только реально читаемые диапазоном поля), поля контекста прогона
(date/time_zone/locale/tenant_id), при старте с середины — JSON для выходов более ранних узлов (с кнопкой
«взять из прогона #N»), и финальный обзор. Отправка всегда идёт в режиме `"live"` (нет отдельного
dry-run режима на этом экране).

## 6. Human-review — `/flows/$flowId/review`

Route `routes/flows/$flowId/review.tsx`. Левая колонка — очередь приостановленных прогонов (сортировка
по дедлайну), карточка = дедлайн-точка, id прогона, адрес исполнения, вид ожидания + исполнитель.

**Кнопок Approve/Reject НЕТ.** Форма ответа полностью управляется JSON Schema самого узла: boolean →
переключатель Да/Нет, enum → сегментированный выбор, string → текст, число → number-поле, всё остальное
или отсутствие схемы → сырое JSON-поле. Одна кнопка «Submit and resume» отправляет `POST
/api/runs/{run_id}/resume`. «Approve» vs «reject» — это просто то значение, которое человек выставил в
этой обобщённой форме (чаще всего boolean/enum поле, определённое схемой конкретного узла).

## 7. Датасеты — `/flows/$flowId/datasets`

Список кейсов — постраничная таблица (25/страница) с динамическими колонками из полей кейса, поиск,
выбор кейсов (в том числе «выбрать все подходящие» по запросу на сервере). Два способа СОЗДАТЬ новый
датасет — ИИ-генерация (запрос чат-агенту написать `datasets/<name>.yaml`) или импорт CSV с
предпросмотром/проверкой перед сохранением. **Редактирования существующего сохранённого кейса на месте
нет** — только создание нового датасета/повторный импорт. Запуск: один кейс («Start») или батч по
выбранным кейсам («Run selected (N)») — батч отслеживается отдельной панелью с прогрессом, статусом,
ценой и таблицей результатов по кейсам (с ссылкой на соответствующий прогон).

## 8. Эвалы — `/flows/$flowId/evals`

**Экран полностью read-only.** Кнопки «запустить» нет нигде — ни в UI, ни в вызываемом API-клиенте
Studio (`api.evals` не содержит метода, вызывающего `POST /api/eval-runs`, хотя сам эндпоинт существует
на сервере). Пустое состояние прямо говорит: «The CLI command `aqven eval --eval {evalId}` produces
one.» Запуск эвала — задача терминала; Studio только показывает то, что движок уже записал.

Вердикт гейта — это **обычный цветной текст**, не значок: строка `PASS`/`WARN`/`BLOCK`/
`GATE_UNAVAILABLE` дословно, покрашенная зелёным/жёлтым/красным/нейтральным — и как общее решение, и
построчно в таблице по каждому скореру (колонка verdict). Два разных «нет гейта» состояния показаны
отдельным текстом: «нет базовой линии вообще» и «база есть, но движок не вернул отчёт по гейту».

## 9. Чат — глобальная панель

Панель `ChatPanel` смонтирована в `features/shell/shell.tsx` рядом с канвасом (352px, фиксированная
боковая колонка), не в корне приложения. Бэкенды — ровно два, `"claude"|"codex"` (подтверждено серверной
OpenAPI-схемой), Studio запускает локальный Claude Code/Codex пользователя, никогда не читает и не
хранит учётные данные сама.

Меню настроек чата (модель/уровень усилия/режим одобрения) — один Popover+Command. Режимы одобрения:
`default`/`accept_edits`/`plan`/`trust`. **Подтверждённое поведение (не по ADR-0041, который устарел
относительно кода)**: если тред уже открыт, смена модели/усилия/режима через это меню сразу применяется
к открытому треду (`PATCH /api/chat/sessions/{id}`), а не только к следующему новому — подтверждено
тестами `chat-settings.test.tsx` и коммитами «the chat menu configures the open thread» /
«the composer names what the open thread runs, not the pending pick».

Агент в чате реально может: выполнять команды оболочки (показ с кодом выхода), редактировать файлы
(показ диффа), вызывать инструменты, включая инструменты внешних MCP-серверов (показ `{сервер} ·
{инструмент}` + аргументы + результат). Любой вызов инструмента может нести гейт одобрения — рендерится
как полоса Allow/Deny. Пользователь может прервать выполняющийся ход. Кнопки «Add context» и «ещё
действия» у сообщения — на момент прохода нерабочие заглушки (`noop`), перепроверить перед публикацией.

## 10. Настройки — `/settings`

Почти полностью read-only статус-экран, 5 разделов: Project, Chat agent, Model keys, MCP connections,
Updates. Единственный интерактивный элемент на всём экране — переключатель бэкенда чата claude/codex.
Ключи провайдеров и секреты показаны замаскированными, без формы редактирования (хотя сервер имеет
эндпоинты записи/удаления — просто не подключены ни к одному элементу интерфейса). MCP-раздел — адрес
сервера + команда подключения для копирования. Updates — команды обновления для копирования.
