# Статистика гейтов выпуска (A vs B на одном датасете)

Статус: ГОТОВО (разделы 1-6). Дата: 2026-09-11.
Проверено first-hand: npm view + установка в probe-fe + рантайм-вызовы + MC-симуляция мощности.

## 1. Парные сравнения A vs B (процедура)

### 1.1. Единица спаривания и что с чем сравниваем

Спека §12: «Эксперименты: версия спеки x датасет x скореры -> дельты по узлам с доверительными
интервалами». Ключевое: **датасет один и тот же**, значит наблюдения спарены по `case_id`.
Непарные тесты (Mann-Whitney/`wilcoxonRankSum`, two-sample t) здесь **запрещены**: они выбрасывают
корреляцию между A и B на одном и том же элементе и раздувают дисперсию в 2-5 раз на реальных
eval-данных. Это главная причина, по которой «на глаз видно улучшение, а тест не значим».

Структура данных эксперимента (наша таблица node-level метрик):

```ts
type Observation = {
  case_id: string;        // элемент датасета — ЕДИНИЦА СПАРИВАНИЯ
  node_id: string;        // узел IR
  version: 'A' | 'B';
  run_idx: number;        // повтор (seed), см. §4
  scorer_id: string;
  value: number;          // 0/1 | ordinal 1..5 | continuous
  kind: 'binary' | 'ordinal' | 'continuous';
};
```

Перед любым тестом — **свёртка повторов**: `s_V(node, case) = mean_r value` (для binary — доля
успехов по R прогонам, это делает метрику непрерывной на [0,1] и повышает мощность). Затем
`d_i = s_B(i) - s_A(i)`.

**Инвариант гейта:** множества `case_id` у A и B идентичны. Любой пропуск (падение прогона,
таймаут) — либо чинится, либо элемент выбрасывается ИЗ ОБЕИХ версий, и это логируется как
`dropped_cases`. Тихая непарность — это класс ошибки, который ломает всю статистику молча.

### 1.2. Три семейства метрик -> три процедуры

| Метрика узла | Тип | Основной тест | Оценка эффекта |
|---|---|---|---|
| схема валидна, инвариант держится, вердикт судьи pass/fail | binary | **McNemar (exact)** | разница долей `(c-b)/n` + парный бутстрап CI |
| рубрика судьи 1..5, similarity 0..1, ранг | ordinal | **Wilcoxon signed-rank** | парный бутстрап CI на медиану разницы + win-rate |
| стоимость, токены, латентность, mean-по-R accuracy | continuous | **парный бутстрап CI на среднюю разницу** (+ парный t как проверка согласованности) | mean diff + CI, Cohen's d_z |

### 1.3. Парный бутстрап доверительного интервала (наш основной инструмент)

Ресемплим **элементы датасета**, а не отдельные оценки. Пара `(s_A(i), s_B(i))` переносится
целиком — это и сохраняет спаривание.

```
PAIRED_BOOTSTRAP_CI(pairs[(a_i, b_i)] i=1..n, stat, B=10000, alpha=0.05, seed):
  rng  = seededRng(seed)                 # ОБЯЗАТЕЛЬНО seed -> гейт воспроизводим
  θ̂    = stat(pairs)                     # напр. mean(b_i - a_i)
  θ*   = []
  repeat B times:
      idx = n draws with replacement from 1..n   using rng
      θ*.push( stat(pairs[idx]) )
  # percentile-интервал:
  return [ quantile(θ*, alpha/2), quantile(θ*, 1 - alpha/2) ]
```

- `B`: **10000** для гейта (решение о выпуске), 2000 — минимум для интерактивного превью в Studio.
  Ниже 2000 хвостовые квантили шумят настолько, что граница CI гуляет на уровне самого эффекта.
- **Percentile** достаточно для `mean diff` на симметричных данных. Для ограниченных/скошенных
  метрик (accuracy у потолка 0.95+, стоимость с тяжёлым хвостом) percentile смещён — берём **BCa**
  (bias-corrected and accelerated): поправка `z0` из доли реплик ниже `θ̂`, ускорение `a` из
  jackknife по элементам. Разница на n=100 и accuracy 0.9 реально достигает 1-2 pp на границе CI.
- Стратификация: если датасет размечен на срезы (`slice_id` — язык, длина входа, класс кейса),
  ресемплим **внутри страт**, чтобы состав срезов не плавал между репликами. Иначе дисперсия
  включает шум состава датасета, которого в реальности нет.
- **Кластеры**: если из одного исходного документа нарезано несколько `case_id`, единица ресемплинга
  — кластер (документ), а не кейс. Иначе CI занижен и гейт пропускает шум.

### 1.4. McNemar для бинарных исходов

Таблица сопряжённости по парам (n = число кейсов):

```
                     B: fail   B: pass
        A: fail         d         c      <- c = A провалил, B прошёл  (в пользу B)
        A: pass         b         a      <- b = A прошёл, B провалил  (в пользу A)
```

Информативны **только дискордантные пары** `b` и `c`. `a` и `d` (обе версии согласны) в тест не входят —
отсюда следствие: **размер датасета сам по себе ничего не гарантирует**, гарантирует `b + c`.
Датасет на 500 кейсов, где версии расходятся на 6 элементах, даёт мощность как n=6.

```
MCNEMAR(b, c, alpha=0.05):
  n_disc = b + c
  if n_disc == 0: return { p: 1.0, note: 'no discordant pairs' }
  if n_disc < 25:
      p = 2 * min( P(X <= min(b,c)), 0.5 )   # exact binomial, X ~ Binom(n_disc, 0.5)
  else:
      chi2 = (|b - c| - 1)^2 / n_disc        # с поправкой Йейтса
      p    = 1 - Chi2CDF(chi2, df=1)
  effect = (c - b) / n                        # разница долей успеха B - A
```

- **Exact-вариант обязателен при малом `n_disc`** — chi2-аппроксимация при `b+c < 25` даёт
  анти-консервативный p и пропускает шум в выпуск. У нас `n_disc` мал почти всегда.
- Проверено в рантайме: exact-часть = `@stdlib/stats-binomial-test(min(b,c), b+c, { p: 0.5 })`,
  возвращает `{ pValue, ci, method: 'Exact binomial test' }`.
- CI на разницу долей — не из McNemar (он даёт только p), а **парным бутстрапом** по п.1.3 со
  `stat = mean(b_i) - mean(a_i)`. Так p и CI считаются на одних и тех же данных и не противоречат
  друг другу.
- Mid-p вариант (`p_mid = p_exact - P(X = min(b,c))`) — компромисс мощности; допускаем как
  `gate.mcnemar_variant = 'mid-p'`, но **по умолчанию exact** (консервативно = не выпускаем лишнего).

### 1.5. Wilcoxon signed-rank для порядковых оценок

Проверено в рантайме, `@stdlib/stats-wilcoxon`:

```ts
import wilcoxon from '@stdlib/stats-wilcoxon';
const out = wilcoxon(scoresA, scoresB);          // ПАРНЫЙ вариант, x и y выровнены по case_id
// -> { method: 'Paired Wilcoxon signed rank test', pValue, statistic, rejected, alpha,
//      nullValue, alternative, print() }
// опции: { alpha, alternative: 'two-sided'|'less'|'greater',
//          zeroMethod: 'pratt'|'wilcox'|'zsplit', correction: true, exact: false, mu: 0 }
```

Подводные камни, критичные именно для рубрик судьи 1..5:

- **Нули (ничьи).** Дефолт `zeroMethod: 'wilcox'` **выбрасывает** пары с нулевой разницей и уменьшает
  n. На рубриках судьи ничьих бывает 50-70% -> эффективный n падает вдвое-втрое незаметно. Ставим
  `zeroMethod: 'pratt'` (нули ранжируются, но не дают знака — консервативнее и честнее по n) и
  **обязательно логируем `n_ties`** в отчёт эксперимента.
- **Связки рангов.** Шкала 1..5 даёт массу одинаковых |d| -> нормальная аппроксимация со связками
  смещена. `exact: true` форсирует точное распределение (пакет сам переключается на аппроксимацию
  при n > 50). При n <= 50 ставим `exact: true`.
- **Допущение симметрии.** Wilcoxon signed-rank проверяет не «медиана разницы = 0», а симметрию
  распределения разниц вокруг 0. На усечённых шкалах (потолок 5) симметрии нет. Поэтому Wilcoxon у
  нас — **сопутствующий p-value**, а решающая величина — бутстрап-CI и **win-rate** (§4.2).
- Не путать: `simple-statistics.wilcoxonRankSum(x, y)` — это Mann-Whitney для **независимых**
  выборок, для нашей задачи неприменим.

### 1.6. Когда уместен парный t-тест

Уместен, когда одновременно: метрика непрерывная (или mean по R >= 3 повторам), `n >= 30`
эффективных пар, распределение разниц без экстремальных выбросов, и нам нужен **CI в единицах
метрики**. Тогда он мощнее Wilcoxon и даёт готовый интервал.

Проверено в рантайме, `@stdlib/stats-ttest`:

```ts
import ttest from '@stdlib/stats-ttest';
const t = ttest(scoresA, scoresB);   // -> method: 'Paired t-test'
// { pValue, statistic, ci: [lo, hi], alpha, rejected, nullValue, alternative, print() }
```

**ГОТЧА (проверено):** `ttest(x, y)` даёт CI для `mean(x) - mean(y)`, т.е. для **A - B**.
Для «прироста B над A» либо зови `ttest(diffs)` где `diffs[i] = b_i - a_i` (даёт тот же p и
зеркальный CI), либо инвертируй знак. Нашу обёртку пишем так, чтобы наружу торчал только
`delta = B - A`, и покрываем это тестом.

Неуместен: сырые 0/1 (там McNemar), стоимость/латентность с тяжёлым хвостом (там бутстрап или
лог-трансформация), n < 20 без проверки хвостов. При расхождении парного t и бутстрапа более чем
на 30% по ширине CI — доверяем бутстрапу и помечаем метрику `distribution_warning`.

### 1.7. Уровень воркфлоу (итог)

End-to-end метрика — ровно та же процедура на тех же `case_id`. **Нельзя** получать итог
усреднением p-значений или «голосованием» узлов: итоговая метрика — самостоятельное наблюдение и
входит в семью тестов как отдельная строка (§2).

### 1.8. Два разных вопроса: улучшение и отсутствие регрессии

Спека §12 требует и «нет регрессии на детерминированных скорерах», и «прирост по LLM-метрикам
значим». Это **разные статистические задачи**, и путать их нельзя:

- **Superiority** (изменённый узел, целевая метрика): H0: delta <= 0. Гейт: нижняя граница
  одностороннего 95% CI > 0.
- **Non-inferiority** (все остальные узлы и метрики): H0: delta <= -margin. Гейт: нижняя граница
  95% CI > `-margin`, где `margin` — заранее объявленный допуск деградации (по умолчанию 0.02
  абсолютных для долей). «p > 0.05, значит регрессии нет» — **логическая ошибка**: отсутствие
  доказательства вреда не есть доказательство отсутствия вреда, и на n=30 так проезжает любая
  регрессия. Проверяем именно границу CI.


## 2. Множественные сравнения по узлам

### 2.1. Сначала объявляем семью (family) — до прогона

15+ узлов x 3-5 скореров = 45-75 тестов. При alpha=0.05 и 60 тестах **ожидаемо 3 ложных
«значимых» результата даже когда B идентична A**. Без поправки гейт превращается в генератор
красивых отчётов.

Семья фиксируется в записи эксперимента ДО прогона (иначе это p-hacking):

```ts
type TestFamily = {
  primary:   TestSpec[];   // 1-3 теста: целевая метрика изменённого узла + end-to-end итог
  secondary: TestSpec[];   // остальные узлы/скореры — «где ещё что-то поменялось»
  safety:    TestSpec[];   // non-inferiority по детерминированным скорерам и стоимости
};
```

### 2.2. Разные семьи — разные поправки

| Семья | Что контролируем | Метод | Уровень |
|---|---|---|---|
| `primary` (m = 1..3) | FWER, ошибка I рода дорогая (выпускаем плохое) | **Holm-Bonferroni** | alpha = 0.05 |
| `secondary` (m = 40..70) | FDR, ошибка I рода дешёвая (лишний кандидат в ревью) | **Benjamini-Hochberg** | q = 0.10 |
| `safety` (non-inferiority) | **мощность обнаружения вреда** | **без поправки**, каждый узел отдельно | alpha = 0.05 |

**Почему Holm, а не голый Bonferroni:** Holm контролирует тот же FWER, но равномерно мощнее —
при одинаковой гарантии отвергает не меньше гипотез. Голый Bonferroni не имеет преимуществ, кроме
простоты объяснения. Берём Holm всегда, где нужен FWER.

**Почему BH для secondary:** цена ложного открытия здесь — человек посмотрит на узел и увидит, что
эффекта нет. Это дёшево. Цена пропуска — мы не заметим, что правка узла 3 сломала узел 11. BH при
q=0.10 говорит: «из того, что я назвал улучшенным, в среднем 10% — случайность». Это правильный
язык для отчёта в Studio.

**Почему safety БЕЗ поправки — и это не ошибка:** поправка на множественность снижает число
отвержений. В superiority это защита. В non-inferiority отвержение H0 означает «вреда нет», то есть
поправка делает **выпуск легче**, а обнаружение регрессии — труднее. Двигаться надо в
консервативную сторону: каждый safety-тест держим на нетронутом alpha=0.05, а решение принимаем
по границе CI, а не по p. Это надо явно написать в доке, иначе ревьюер «исправит» на BH и снимет
защиту.

### 2.3. Зависимость тестов

Тесты по узлам сильно положительно коррелированы (одни и те же кейсы, один и тот же датасет,
ошибка сквозная по графу). BH доказан при независимости и при **PRDS** (positive regression
dependency) — положительная корреляция сюда попадает, BH валиден. Benjamini-Yekutieli (BH с
делителем `sum(1/i)`, ~4.5x при m=60) нужен только при произвольной зависимости — для нас это
избыточный консерватизм, **по умолчанию не включаем**, оставляем флагом
`gate.fdr_method: 'BH' | 'BY'` для параноидальных проектов.

### 2.4. Алгоритмы (пишем сами, ~20 строк)

```
BH(pvalues p[1..m], q):
  order = argsort(p) ascending
  k_max = 0
  for k in 1..m:
      if p[order[k]] <= (k / m) * q: k_max = k
  rejected = { order[1..k_max] }
  # adjusted q-values (монотонизированные, для показа в UI):
  for k in m..1 descending:
      qadj[order[k]] = min( qadj_prev, p[order[k]] * m / k )   # qadj_prev = +inf на старте
      qadj_prev = qadj[order[k]]
  return { rejected, qadj }

HOLM(pvalues p[1..m], alpha):
  order = argsort(p) ascending
  for k in 1..m:
      if p[order[k]] > alpha / (m - k + 1): break   # остановка: всё дальше не отвергается
      reject order[k]
  padj[order[k]] = cummax( p[order[k]] * (m - k + 1) )  # монотонизация слева направо
```

**Ключевая деталь BH, которую часто ломают:** ищется **наибольшее** k с `p_(k) <= k/m*q`, и
отвергаются ВСЕ гипотезы с 1 по k, включая те, чей собственный p порог не прошёл. Наивная реализация
«отвергай каждую, чья p <= k/m*q» неверна.

### 2.5. Как отчитываться (обязательный минимум в отчёте эксперимента)

Для каждой строки: `node_id`, `scorer_id`, `n_pairs`, `n_discordant` (binary) / `n_ties` (ordinal),
`delta` (в единицах метрики), `CI95 [lo, hi]`, `p_raw`, `p_adj`/`q_adj`, `method`, `family`,
`decision: pass | warn | block`. Плюс шапка: `m` (размер каждой семьи), `B` (реплик бутстрапа),
`seed`, `R` (повторов на кейс), `dropped_cases`, `dataset_version`, `judge_calibration_id`.

Без явного `m` и состава семьи отчёт не воспроизводим и не проверяем.


## 3. Минимальные размеры датасета: MDE и power

Все таблицы ниже **посчитаны Monte-Carlo симуляцией** (4000 итераций на клетку, seeded xorshift),

### 3.1. Бинарные метрики (McNemar). Критерий: двусторонний alpha=0.05 + требование направления

Мощность как функция n (число кейсов), `pd` = доля дискордантных пар (насколько часто A и B вообще
расходятся), `delta` = истинный прирост доли успеха в процентных пунктах.

**pd = 0.10 (версии расходятся на 10% кейсов — типично для точечной правки промта):**

| +3pp | 0.00 | 0.02 | 0.09 | 0.21 | 0.31 | 0.52 | **0.83** |
| +5pp | 0.01 | 0.06 | 0.25 | 0.55 | 0.74 | **0.94** | 1.00 |
| +8pp | 0.03 | 0.20 | 0.67 | **0.97** | 1.00 | 1.00 | 1.00 |
| +10pp | 0.07 | 0.38 | **0.94** | 1.00 | 1.00 | 1.00 | 1.00 |

| +2pp | 0.01 | 0.02 | 0.04 | 0.07 | 0.09 | 0.15 | 0.27 |
| +3pp | 0.02 | 0.03 | 0.07 | 0.12 | 0.17 | 0.28 | 0.55 |
| +5pp | 0.03 | 0.07 | 0.14 | 0.29 | 0.45 | 0.68 | **0.94** |

| +10pp | 0.09 | 0.23 | 0.54 | **0.87** | 0.97 | 1.00 | 1.00 |
| +15pp | 0.26 | 0.58 | **0.93** | 1.00 | 1.00 | 1.00 | 1.00 |

**pd = 0.30 (смена модели/семейства — расхождения повсюду):**

| delta | n=30 | 50 | 100 | 200 | 300 | 500 | 1000 |
|---|---|---|---|---|---|---|---|
| +3pp | 0.02 | 0.03 | 0.05 | 0.09 | 0.13 | 0.20 | 0.39 |
| +5pp | 0.03 | 0.06 | 0.10 | 0.21 | 0.31 | 0.51 | **0.81** |
| +8pp | 0.06 | 0.12 | 0.25 | 0.50 | 0.69 | **0.90** | 1.00 |
| +10pp | 0.09 | 0.18 | 0.38 | 0.70 | **0.87** | 0.98 | 1.00 |

**Что из этого читается (главные выводы для продукта):**

1. **n = 30-50 не годится ни для чего.** Мощность 0.01-0.20 на реалистичных эффектах. «Датасет из
   30 кейсов» ловит только катастрофы (+20pp и выше). Это нужно сказать пользователю в Studio
   прямым текстом, а не прятать в мелком шрифте.
2. **Больше расхождений (pd выше) — НУЖЕН БОЛЬШИЙ n при том же delta.** Контринтуитивно, но верно:
   при pd=0.10 и +5pp нужно ~500, при pd=0.30 и +5pp нужно ~1000. Причина: тот же нетто-прирост,
   размазанный по большему числу дискордантных пар, — это более шумный процесс. Поэтому «переписали
   промт целиком» доказать труднее, чем «поправили одну формулировку».
3. **Практический минимум для гейта: n >= 200 при целевом эффекте +8pp и выше; n >= 500 при
   целевом +5pp.** Меньше +3pp на бинарной метрике на разумных n не доказывается — такие правки
   надо либо копить в пачку, либо переводить метрику в непрерывную (см. 3.3).

### 3.2. Через число дискордантных пар (планирование без знания pd)

Закрытая формула, `psi = c / (b + c)` — доля дискордантов в пользу B. Для power 0.80, двусторонний
alpha=0.05: `n_disc = (1.96 + 0.8416)^2 * 4*psi*(1-psi) / (2*psi - 1)^2`.

| psi (доля дискордантов в пользу B) | нужно дискордантных пар |
|---|---|
| 0.60 (слабое, 3:2) | 189 |
| 0.65 | 80 |
| 0.70 (2.3:1) | 42 |
| 0.75 (3:1) | 24 |
| 0.80 (4:1) | 14 |
| 0.90 (9:1) | 5 |

Это самый полезный операционный критерий: `n_disc = b + c` видно **сразу после прогона**. Studio
показывает «дискордантных пар: 11 из нужных ~42» — и человек понимает, что датасет надо растить, не
дожидаясь p-value. Переход к n: `n = n_disc / pd`.

### 3.3. Непрерывные / усреднённые метрики (парный бутстрап и парный t)

Эффект в единицах `dz = mean(d) / sd(d)` (Cohen's d_z, парный). Мощность, односторонний alpha=0.05:

| dz | n=30 | 50 | 100 | 200 | 300 | 500 | 1000 |
|---|---|---|---|---|---|---|---|
| 0.10 | 0.13 | 0.16 | 0.25 | 0.40 | 0.53 | 0.72 | **0.93** |
| 0.15 | 0.20 | 0.26 | 0.43 | 0.68 | **0.82** | 0.95 | 1.00 |
| 0.20 | 0.28 | 0.39 | 0.63 | **0.87** | 0.96 | 1.00 | 1.00 |
| 0.30 | 0.48 | 0.67 | **0.90** | 0.99 | 1.00 | 1.00 | 1.00 |
| 0.50 | **0.85** | 0.96 | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 |
| 0.80 | 0.99 | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 |

n для power 0.80, двусторонний alpha=0.05: `n = (1.96 + 0.8416)^2 / dz^2 = 7.85 / dz^2`

| dz | 0.10 | 0.15 | 0.20 | 0.30 | 0.50 | 0.80 |
|---|---|---|---|---|---|---|
| n | 785 | 349 | 197 | 88 | 32 | 13 |

**Как перевести в «свою» метрику.** `dz` считается по разницам, а не по сырым оценкам, поэтому
`sd(d)` малo, когда версии похожи. Для рубрики судьи 1..5 с типичным `sd(d) ~ 0.6` прирост
`+0.15 балла` даёт `dz = 0.25` -> нужно ~125 кейсов. Тот же прирост при нестабильном судье
(`sd(d) ~ 1.2`) даёт `dz = 0.125` -> нужно ~500. **Вот почему усреднение по R прогонам (§4.3) —
не роскошь, а способ сократить датасет в разы:** оно режет `sd(d)`, а не двигает эффект.

### 3.4. Практический дефолт платформы

```ts
const MIN_DATASET_SIZE = {
  smoke:  30,    // только для «не сломалось совсем», гейтить НЕЛЬЗЯ
  gate:   200,   // минимум для блокирующего гейта, MDE ~ +8pp binary / dz 0.20
  strict: 500,   // для смены модели/провайдера и изменений в критичных узлах
} as const;
```

Спека §12 требует «у каждого изменённого узла есть датасет не меньше минимального размера» —
вот это число. **Дополнительно** гейт требует `n_disc >= 25` для бинарных метрик, иначе решение
не принимается вообще (статус `insufficient_power`, а не `pass`).


## 4. Размер эффекта, практическая значимость и отделение шума LLM

### 4.1. Какие размеры эффекта отчитываем

| Величина | Формула | Когда |
|---|---|---|
| **delta в единицах метрики** | `mean(s_B) - mean(s_A)` | ВСЕГДА, это главная цифра в UI |
| **Cohen's d_z (парный)** | `mean(d) / sd(d)` | для планирования n; в UI не показывать как «важность» |
| **Cohen's d_av** | `mean(d) / sd_pooled(s_A, s_B)` | для сравнения эффектов между разными узлами |
| **win-rate (доля улучшенных)** | `#{i: s_B(i) > s_A(i)} / #{i: s_B(i) != s_A(i)}` | самая понятная человеку цифра |
| **NNT-аналог** | `1 / delta` | «сколько кейсов надо прогнать, чтобы получить один дополнительно успешный» |

**Осторожно с d_z.** Он растёт при росте корреляции A и B, поэтому «d_z = 0.8» на парных
LLM-данных не значит «большой эффект» в смысле Коэна — шкалы Коэна (0.2/0.5/0.8) откалиброваны на
независимых выборках. Использовать d_z только как вход в расчёт мощности, а для «важно ли это»
брать `d_av` и сырую delta. Иначе гейт будет выпускать косметические правки с красивым d_z.

**win-rate** считаем с исключением ничьих и отчитываем ничьи отдельно: `wins / losses / ties`.
CI — Clopper-Pearson на `wins` из `wins + losses` (это в точности та же статистика, что exact
McNemar, только выраженная как эффект). Формулировка для человека: «B лучше A на 34 кейсах, хуже на
11, одинаково на 155».

### 4.2. Порог практической значимости (MPE)

Объявляется **в спеке узла, до эксперимента**:

```ts
type NodeGatePolicy = {
  node_id: string;
  primary_metric: string;
  mpe: number;                 // minimum practical effect, в единицах метрики
  ni_margin: number;           // допуск non-inferiority (регрессия), по умолчанию 0.02
  min_dataset: 200 | 500;
  mode: 'normal' | 'strict';
};
```

Дефолты: `mpe = 0.02` (2 pp) для долей, `mpe = 0.10` балла для рубрики 1..5, `mpe = -0.05`
(т.е. -5%) для стоимости, `ni_margin = 0.02`.

Два режима решения — и разницу надо понимать:

- **normal:** `CI95_lo > 0` (статистически значим) **И** `delta_hat >= mpe` (практически значим).
  Так гейт не пускает «значимые» +0.3pp, которые ничего не меняют.
- **strict:** `CI95_lo > mpe` — доказываем, что эффект **не меньше** порога. Честнее, но требует
  примерно вчетверо большего датасета. Включаем для смены модели/провайдера и для узлов с
  `criticality: high`.

По умолчанию `normal`. Явно задокументировать, что `normal` не доказывает `delta >= mpe`, а только
`delta > 0` при точечной оценке выше порога.

### 4.3. Отделение эффекта от шума LLM — самое важное в разделе

LLM не детерминированы даже при `temperature = 0` (батчинг, роутинг MoE, апдейты на стороне
провайдера). Значит наблюдаемое `d_i` содержит и эффект правки, и run-to-run шум.

**Модель дисперсии.** Оценка кейса — среднее по R прогонам:
`Var(s_V(i)) = sigma^2_item + sigma^2_run / R`.
Повторы бьют **только** `sigma^2_run`. Если основной шум межкейсовый (`sigma^2_item`), растить R
бесполезно — надо растить n. Поэтому платформа должна оценивать обе компоненты и **советовать
конкретное действие**: «добавь кейсов» либо «добавь повторов».

Оценка из данных (одна и та же версия, R >= 2):
```
sigma2_run  = mean_i [ var_r( value(i, r) ) ]                    # внутрикейсовая
sigma2_item = var_i [ mean_r value(i, r) ] - sigma2_run / R      # межкейсовая, может выйти <0 -> 0
ICC         = sigma2_item / (sigma2_item + sigma2_run)           # надёжность метрики
```
`ICC < 0.5` -> метрика шумнее, чем сигнал: сначала стабилизируй скорер/судью, потом гейти.

**Рекомендуемые R:**

| Тип узла / скорера | R |
|---|---|
| детерминированный скорер (схема, инвариант) над стохастическим выходом | 3 |
| LLM-судья, рубрика | 3-5 |
| judge_panel (K судей) | 1 прогон x K судей уже даёт усреднение, R = 2 |
| temperature = 0, extractor со строгой схемой | 2 (для контроля, не для точности) |

Все R прогонов **должны идти с разными явными seed**, и seed'ы у A и B **одинаковые** — это ещё
один слой спаривания, он дополнительно режет дисперсию.

### 4.4. A/A-прогон — обязательная калибровка нуля

**Самая сильная практическая защита, которую надо встроить в платформу.** До сравнения A vs B
прогоняем **A vs A'**: та же самая версия спеки, другой набор seed'ов, тот же датасет, те же
скореры, тот же пайплайн гейта.

Истинный эффект там ровно 0. Значит:

- Если A/A даёт хоть одно отвержение в `primary` — **пайплайн сломан или метрика нестабильна**.
  Гейт по B не запускается вообще.
- Доля отвержений в `secondary` на A/A должна быть ~q (0.10 при BH q=0.10). Заметно больше —
  зависимость сильнее, чем предполагали, либо ошибка в спаривании (перепутанные `case_id`).
- Ширина CI на A/A — это **эмпирический пол шума**. Любой эффект B уже CI на A/A неотличим от шума,
  как бы ни выглядел p-value. Этот номер («noise floor») показываем в Studio рядом с delta.

```
NOISE_FLOOR(dataset, spec_A, R, seeds1, seeds2):
  run1 = execute(spec_A, dataset, seeds1)
  run2 = execute(spec_A, dataset, seeds2)
  for each (node, scorer):
      ci = PAIRED_BOOTSTRAP_CI(pairs(run1, run2), mean_diff, B=10000, seed=fixed)
      noise_floor[node][scorer] = (ci.hi - ci.lo) / 2
  assert no rejection in primary family   # иначе GATE_UNAVAILABLE
```

A/A-прогон стоит денег (ещё один полный прогон датасета), поэтому кешируем его по ключу
`(spec_version_A, dataset_version, scorers_version, R)` — он валиден, пока ничего из этого не
менялось, и переиспользуется для всех кандидатов B против той же базы.

### 4.5. Дрейф провайдера

Метрики A, посчитанные месяц назад, **нельзя** сравнивать с B, посчитанной сегодня: модель у
провайдера могла измениться. Правило: **A и B прогоняются в одном окне**, и `provider_snapshot`
(модель, версия, дата) пишется в запись эксперимента. Иначе «прирост» — это дрейф провайдера.
Это прямое следствие §8 п.52/53 спеки (закреплённые версии, смена через eval-гейт).

### 5.4. Нужен ли Python-сайдкар со scipy — честный ответ

**Для гейта в том виде, как он описан в §6 — НЕТ.** Всё закрывается тремя пакетами stdlib плюс
~150 строками своего кода (McNemar, bootstrap percentile+BCa, BH, Holm, power). Это ровно то, что
спека называет «ядро доверия строим сами»: код маленький, детерминированный, целиком
юнит-тестируемый.

**Стратегия проверки без рантайм-Python:** генерируем golden-фикстуры **один раз** оффлайн
(`scipy.stats.wilcoxon`, `statsmodels.stats.contingency_tables.mcnemar`,
`statsmodels.stats.multitest.multipletests`, `scipy.stats.bootstrap`), коммитим JSON в репозиторий
и гоняем наши TS-реализации против них в vitest с допуском 1e-9. Python остаётся **инструментом
разработки**, а не зависимостью рантайма. Это снимает весь операционный риск.

**Где Python действительно понадобится** (и это не v1):

1. **Смешанные модели (mixed effects)** — когда судей несколько и надо развести случайные эффекты
   кейса, судьи и прогона: `statsmodels.MixedLM` / `lme4`. В TS эквивалента нет.
2. **Кластерно-робастные / GEE** оценки при сильно вложенных датасетах.
3. **Байесовские иерархические модели** (PyMC) — если захотим отчитываться в терминах
   «вероятность того, что B лучше A, = 0.93» вместо p-value. Для продукта это язык понятнее, но
   это отдельная фаза.

**Как изолировать, если дойдём:** stateless HTTP-сайдкар (FastAPI + uvicorn), собственный
контейнер с пиннутыми `scipy`/`statsmodels`, **вызывается только воркером evals**, никогда не в
пути запроса, вход/выход — JSON-схемы, валидируемые zod на нашей стороне; при недоступности
сайдкара гейт отдаёт `GATE_UNAVAILABLE`, а не «pass». Ни одного состояния, ни одной БД. Прямой
запрет: не тащить Python в монорепу Node как `child_process` — это ломает деплой и наблюдаемость.

### 5.5. Где этот код живёт

Пакет `@app/stats` в монорепе — чистые функции, **ноль зависимостей от VoltAgent, Langfuse и БД**.
Вход — массивы чисел и конфиг, выход — типизированный результат. Так он тестируется в вакууме и
переиспользуется и воркером evals, и MCP-инструментом `experiment.compare`, и Studio (через API,
не в браузере: 10000 реплик бутстрапа на 60 тестах — это серверная работа, не клиентская).


## 6. ИТОГ: спецификация гейта выпуска

### 6.1. Три исхода, а не два

`BLOCK` (не выпускаем) / `WARN` (выпускаем, но с пометкой и требованием аппрува человека) /
`PASS`. Плюс четвёртый, технический: **`GATE_UNAVAILABLE`** — данных не хватает, чтобы принять
решение. Это НЕ `PASS`. Самая частая ошибка проектирования гейтов — трактовать «не смогли
проверить» как «проверка пройдена».

### 6.2. Пороги по умолчанию

```ts
const GATE_DEFAULTS = {
  alpha_primary:    0.05,   // Holm-Bonferroni, FWER
  q_secondary:      0.10,   // Benjamini-Hochberg, FDR
  alpha_safety:     0.05,   // БЕЗ поправки (см. §2.2)
  bootstrap_B:      10_000,
  bootstrap_method: 'BCa' as const,
  min_dataset:      200,
  min_discordant:   25,     // для бинарных метрик
  min_runs_R:       3,      // повторов на кейс
  mpe_proportion:   0.02,   // 2 pp
  mpe_rubric_1_5:   0.10,   // 0.1 балла
  mpe_cost:        -0.05,   // -5%
  ni_margin:        0.02,   // допуск регрессии
  min_icc:          0.50,   // надёжность метрики
  judge_agreement:  0.70,   // Cohen's kappa судьи с разметкой человека (§12, R-J6)
  mode:             'normal' as 'normal' | 'strict',
};
```

### 6.3. Алгоритм

```
GATE(spec_A, spec_B, dataset, scorers, policy) -> Decision

# ---------- ФАЗА 0: предусловия. Любой провал -> GATE_UNAVAILABLE, не BLOCK и не PASS ----------
0.1  changed = diffNodes(spec_A, spec_B)                     # какие узлы реально изменились
0.2  for node in changed:
         if dataset.sizeFor(node) < policy.min_dataset:
             return GATE_UNAVAILABLE('dataset_too_small', node, have, need)
0.3  if dataset.split != 'test' or dataset.wasSeenByOptimizer:
         return GATE_UNAVAILABLE('test_split_contaminated')   # §12: test недоступен оптимизатору
0.4  for judge in scorers.judges:
         if judge.kappa_vs_human < policy.judge_agreement or judge.calibration.stale:
             return GATE_UNAVAILABLE('judge_not_calibrated', judge)
0.5  if provider_snapshot(A) != provider_snapshot(B):
         return GATE_UNAVAILABLE('provider_drift')            # A и B в одном окне, §4.5

# ---------- ФАЗА 1: A/A калибровка нуля ----------
1.1  aa = cached_or_run(NOISE_FLOOR, key=(spec_A, dataset.version, scorers.version, R))
1.2  if aa.rejections_in_primary > 0:
         return GATE_UNAVAILABLE('pipeline_unstable', aa.details)
1.3  if aa.fdr_rejection_rate_secondary > 2 * policy.q_secondary:
         return GATE_UNAVAILABLE('dependence_underestimated')
1.4  noise_floor = aa.noise_floor          # пол шума на узел x скорер

# ---------- ФАЗА 2: прогон и свёртка ----------
2.1  seeds = deriveSeeds(experiment_id, R)                    # ОДИНАКОВЫЕ для A и B
2.2  runsA = execute(spec_A, dataset, seeds); runsB = execute(spec_B, dataset, seeds)
2.3  cases = intersect(runsA.case_ids, runsB.case_ids)
     dropped = symmetricDiff(...)                              # логируем, ЖЁСТКО спариваем
2.4  if |dropped| / |dataset| > 0.05: return GATE_UNAVAILABLE('too_many_dropped')
2.5  for (node, scorer): s_V(i) = mean over R of value(V, node, scorer, i, r)
2.6  icc = estimateICC(node, scorer)                           # §4.3
     if icc < policy.min_icc: mark metric 'unreliable' -> вклад только в WARN, не в BLOCK

# ---------- ФАЗА 3: семьи тестов (объявлены ДО прогона) ----------
3.1  primary   = [ (changed_node, primary_metric) for changed_node ] + [ (workflow, e2e_metric) ]
3.2  secondary = all other (node, scorer) pairs
3.3  safety    = all deterministic scorers on ALL nodes + cost + latency_p95

# ---------- ФАЗА 4: статистика ----------
4.1  for each test t in primary ∪ secondary ∪ safety:
       pairs = [ (s_A(i), s_B(i)) for i in cases ]
       switch t.kind:
         binary:
            b = #{ s_A=1, s_B=0 }; c = #{ s_A=0, s_B=1 }
            if b + c < policy.min_discordant and t in primary:
                 return GATE_UNAVAILABLE('insufficient_discordant', t, b+c, need=25)
            t.p  = MCNEMAR(b, c)                              # exact при b+c<25, иначе chi2+Yates
            t.ci = PAIRED_BOOTSTRAP_CI(pairs, mean_diff, B, 'BCa', seed)
         ordinal:
            t.p  = wilcoxon(a, b, { zeroMethod:'pratt', exact: n<=50 }).pValue
            t.ci = PAIRED_BOOTSTRAP_CI(pairs, median_diff, B, 'BCa', seed)
            t.win_rate = winRateWithClopperPearson(pairs)
         continuous:
            t.ci = PAIRED_BOOTSTRAP_CI(pairs, mean_diff, B, 'BCa', seed)
            t.p  = ttest(a, b).pValue                          # сверка; при расхождении CI >30%
                                                               # -> flag 'distribution_warning'
       t.delta = mean(s_B) - mean(s_A)
       t.dz    = mean(d) / sd(d)

4.2  primary.p_adj   = HOLM(primary.p, alpha=0.05)
4.3  secondary.q_adj = BH(secondary.p, q=0.10)
4.4  safety: БЕЗ поправки, решение по границе CI, не по p

# ---------- ФАЗА 5: решение ----------
5.1  BLOCK if any safety test has  ci_lo < -policy.ni_margin
         # доказанная регрессия или недоказанное отсутствие регрессии на детерминированном скорере
5.2  BLOCK if any safety test on cost/latency has ci_lo < -budget_margin  (бюджет §9 спеки)
5.3  for t in primary:
        improved = (mode=='normal')
                   ? (t.ci_lo > 0 and t.delta >= t.mpe)
                   : (t.ci_lo > t.mpe)
        if not improved: BLOCK('no_significant_improvement', t)
        if t.delta <= noise_floor[t]: BLOCK('within_noise_floor', t)
5.4  WARN if any secondary test rejected with negative delta (побочная деградация непервичной
        метрики) — не блокирует, но требует аппрува человека
5.5  WARN if any metric flagged 'unreliable' (ICC<0.5) or 'distribution_warning'
5.6  WARN if achieved_power(t.delta_hat, n) < 0.80 for any primary test
        # эффект поймали, но датасет был маловат — повезло; пусть человек знает
5.7  else PASS

# ---------- ФАЗА 6: неизменяемая запись ----------
6.1  persist GateReport {
        decision, spec_A_hash, spec_B_hash, dataset_version, scorers_version,
        provider_snapshot, seeds, R, B, bootstrap_method, families {m, tests[]},
        per_test { node, scorer, n, n_disc|n_ties, delta, ci, p_raw, p_adj, method,
                   dz, win_rate, noise_floor, verdict },
        dropped_cases, icc, judge_calibration_ids, gate_config_hash, started_at, finished_at }
6.2  GateReport иммутабелен и адресуется хешем; выпуск ссылается на него.
```

### 6.4. Что блокирует, а что предупреждает — сводка

| Условие | Исход |
|---|---|
| датасет < 200 / дискордантов < 25 / test-сплит загрязнён / судья не откалиброван / дрейф провайдера | `GATE_UNAVAILABLE` |
| A/A даёт отвержение в primary | `GATE_UNAVAILABLE` |
| регрессия на детерминированном скорере: `ci_lo < -ni_margin` | **BLOCK** |
| выход за бюджет стоимости/латентности | **BLOCK** |
| нет значимого прироста на целевой метрике изменённого узла | **BLOCK** |
| прирост меньше пола шума A/A | **BLOCK** |
| побочная деградация вторичной метрики (BH-значимая, delta<0) | WARN + аппрув |
| ICC < 0.5 либо расхождение t-теста и бутстрапа | WARN |
| достигнутая мощность < 0.80 | WARN |
| всё выше пройдено | PASS |

### 6.5. Пять правил, которые нельзя нарушать (иначе гейт — театр)

1. **Семья тестов и пороги объявлены до прогона.** Подбор метрики после того, как увидели цифры, —
   p-hacking; при 60 метриках всегда найдётся «значимая».
2. **`test`-сплит не виден оптимизатору** (GEPA работает на `train`/`dev`). Иначе гейт валидирует
   то, подо что оптимизировали.
3. **Seed зафиксирован и сохранён.** Бутстрап случаен; без seed один и тот же эксперимент даёт
   разные решения на границе, и это невозможно отладить.
4. **«Не смогли проверить» != «проверка пройдена».** `GATE_UNAVAILABLE` никогда не деградирует в
   `PASS` — ни по таймауту, ни при падении сайдкара, ни при пустом датасете.
5. **Non-inferiority проверяется границей CI, а не `p > 0.05`.** Иначе маленький датасет
   автоматически «доказывает» отсутствие регрессии — то есть чем хуже данные, тем легче выпуск.
